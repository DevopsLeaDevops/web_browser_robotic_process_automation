ADR 0018：程式層與執行環境分開打包，伺服器把更新分發給裝置

每個版本多發一個約 2 MB 的更新檔，只含我們自己的程式；交給伺服器一次，伺服器更新自己，Worker 與錄製端從區網取得同一個版本，在不打斷工作的時機套用。執行環境（Python、第三方套件）沒變時不必重新下載完整包。

背景

使用者 2026-10-24 提出：伺服器、錄製端、Worker 每次升級都要重新下載整包，效率不高，希望能熱更新。

v0.5.0 的伺服器分發包 x64 約 103 MB、arm64 約 97 MB；Windows Worker 的建置產物合計約 136 MB；兩個 DMG 各約 84 MB。這些包裡真正每版會變的，是七個工作區套件（含 Portal 頁面、翻譯、資料庫遷移），原始碼壓縮後只有約 0.6 MB（main a8cde7f 實測）；其餘是 Python、第三方套件與 Playwright driver。

第三方套件不常變：0.2.0 → 0.3.0 變 6 項（新增 macOS 用的 PyObjC），0.3.0 → 0.4.0 變 20 項（含 Playwright 1.63 → 1.64，部分只是開發工具），0.4.0 → 0.5.0 是 0 項。

倉庫在 2026-10-22 改成私有，Release 與 App 的「下載新版」只有登入且有權限的 GitHub 帳號下載得到；每台裝置都要有人下載、搬過去、安裝。瀏覽器（解壓後 570～710 MB）只在 Playwright 版本改變時重新下載，已經是增量的，不在本篇處理。

決策

  1. 分層。程式層：七個工作區套件，純 Python，各平台共用同一份。執行環境：Python 3.13、執行時需要的第三方套件、PyInstaller 外殼（桌面 App），各平台一份。瀏覽器照舊。Python 腳本場景的運行環境（PR #82，待確認）若採用，是另一層，有自己的版本，不受本篇影響。
  2. 環境代號。每個平台的執行環境有一個代號：Python 版本、執行時第三方套件的鎖定清單（uv export，不含開發工具）、外殼的版本與收入的模組清單的雜湊。CI 建置完整包時算出並寫進包裡。程式層寫明各平台需要的代號；代號相同才能只換程式層，不同就要完整包。
  3. 更新檔。發布時多產生 RPA-Update-<版本>.zip：程式層的檔案、清單（版本、提交、程式指紋、協定版本、看得懂的 DSL 擴充、各平台的環境代號、每個檔案的 SHA-256 與大小）與清單的 Ed25519 簽章。完整包照舊發布，用於第一次安裝與環境代號改變時。
  4. 伺服器。安裝位置改成 runtimes/<環境代號>/python（多版本共用）＋ releases/<版本>-<提交>/app（程式層），current 的原子切換照舊。bin/rpa update <更新檔>：驗證簽章與雜湊 → 確認有所需的環境代號 → 安裝並用包內 Python 載入伺服器程式 → 切換 current → 請執行中的伺服器重新啟動。伺服器等到沒有進行中的錄製、逐步調試、人工登入、本機執行才結束（--now 不等）；新版本啟動時有新的遷移，先備份 SQLite 再遷移（PostgreSQL 提醒自行備份）。更新檔留在該版本的資料夾（releases/<版本>/update.zip）供裝置下載。伺服器啟動時把執行中遠端任務的租約延長一個週期，重新啟動期間不會被標成「worker 失聯」。
  5. 伺服器自己重新啟動。bin/rpa serve 看顧伺服器程序：伺服器以約定的結束碼結束時，用同樣的參數啟動 current 的新版本；新版本在開始服務之前就結束，切回上一版、還原遷移前的備份再啟動。不依賴 systemd，用 nohup 或 systemd 啟動都一樣（使用者的內網伺服器用 nohup，2026-10-25 說明）。從 clone（.venv-server）執行的伺服器不支援更新檔，因為 git 管理的檔案不能被覆蓋：要先改用分發包一次，命令只把 .venv-server/bin/rpa 換成 ~/rpa-server/bin/rpa，參數與資料目錄照舊。
  6. 裝置的啟動器。PyInstaller 的入口改成一個很小的啟動器，我們的程式不再編進執行檔的封存。啟動器讀資料夾裡 app/active.json 指定的版本，驗證簽章、每個檔案的雜湊與環境代號，通過才放到 sys.path 最前面；否則用 App 內建的程式層（安裝時的版本）並記日誌。子程序（rpa-child）由父程序以環境變數指定同一份程式層。外殼收入完整的標準函式庫（不含 tkinter、test 等），新版程式用到新模組時不會在舊外殼上找不到。
  7. 不改 App 本身。程式層下載到裝置既有的資料夾：Windows %LOCALAPPDATA%\rpa\worker\app\、macOS ~/Library/Application Support/rpa/{worker,recorder}/app/。macOS 的 .app 簽章不被破壞，也不需要「App 管理」權限。
  8. 裝置跟隨伺服器的版本。裝置上線前先呼叫更新端點（Worker API 與 Client API 各一個），回報 App 種類、平台、版本、環境代號。端點的格式固定、不檢查協定版本，之後協定升級時舊 App 也能先更新。伺服器回覆：已是同版本／可以更新（版本、大小、雜湊）／要完整安裝。裝置追的是伺服器現在的版本，不是最新版；伺服器退回時裝置也跟著退回。
  9. 套用的時機。Worker：做完目前的任務、暫停領取，自己重新啟動（數秒）；只在沒有任務時重啟。錄製端：不打斷錄製與調試，視窗提示「重新開啟即可套用」，下次開啟時套用。新的一層在 App 正常結束或執行滿 20 秒時確認；連續兩次啟動都沒確認，第三次啟動就退回上一層（沒有上一層就用內建的程式），下次檢查更新時回報伺服器，同一個版本不再自動安裝；保留最近 3 層。伺服器設定有「自動更新裝置」開關，預設開；裝置頁顯示每台的版本與更新狀態。
  10. 簽章。CI 用 Ed25519 私鑰（GitHub Secrets）簽清單，公鑰隨執行環境發布；伺服器安裝時、裝置下載時、啟動器每次啟動時都驗證。驗證以 RFC 8032 的參考演算法實作（只做驗證），不加依賴。啟動器接受一組公鑰，以便日後換鑰。
  11. 依賴更新的節奏。每週的依賴更新 PR 中，只動到開發工具的照常合併（不改環境代號）；動到執行環境的累積起來，在「環境版本」一起合併，節奏由使用者決定。Playwright 升級會讓每台裝置重新下載瀏覽器，PR 與 Release 說明要標出。

實作

第一、二階段，2026-10-25，PR #83
  • 套件 rpa_update。清單、簽章驗證、環境代號、程式碼層的安裝與選層、桌面 App 的啟動器都在這裡（packages/rpa_update）。只用標準函式庫，跟著執行環境走：改了它就是改了環境代號，要發完整的安裝包。
  • 環境代號的內容。伺服器：Python 版本與執行時第三方套件的鎖定清單。桌面 App：PyInstaller 版本、收入的模組所屬的第三方套件與版本、這些檔案內容的雜湊與模組數量（我們自己的七個套件不算）。runtime.json 另外記下內建的程式版本（版本-提交）與信任的公鑰。
  • 同一個環境，每次建置都是同一個代號（2026-10-26）。0.6.1 的三個桌面 App 和 0.6.0 的環境代號都不同，伺服器的卻相同：外殼把 rpa_update 的 *.dist-info 也算進去了，它帶著這一版的版本號，uv 從原始碼安裝時還留下記錄時間的 uv_cache.json，每次建置都不同。結果裝置一直被要求用完整的安裝包更新，也因此一直顯示「和 Portal 的程式版本不同」。之後工作區套件的 *.dist-info 不算（tools/build_desktop.py 的 shell_files；rpa_update 的內容由原始碼的雜湊代表）。這段沒有放進 rpa_update：改它的任何一個檔案都會改變伺服器的環境代號。修好的那一版桌面 App 要再用完整的安裝包裝一次，之後環境沒變就能用更新檔。
  • 和上一次發布比較。tools/runtime_changes.py 拿這次建置的環境代號和最近一次發布的更新檔比較：PR 上的桌面端建置與伺服器分發包寫成 annotation（不同是警告），發布時再寫進 Release 說明的「從 v上一版 升級」，標出哪些可以只用更新檔、哪些要完整的安裝包。
  • 伺服器。bin/rpa update 更新檔 [--now] 驗證、裝成新的版本資料夾、換 current；伺服器以結束碼 75 結束，bin/rpa serve 用 current 的版本再啟動；剛換上的版本還沒開始服務就結束時，退回上一版並還原遷移前的 SQLite 備份。用完整的分發包安裝的版本資料夾沒有更新檔，拿同一版的更新檔再執行一次 rpa update 就會放進去，裝置才有得更新。
  • 桌面 App 的程式碼層。放在 App 資料夾的 app/<版本-提交>/（manifest.json、manifest.sig、app/），旁邊是 active.json 與 boot.log（只記改用內建的程式、退回、重新啟動再試）。每次啟動都驗證簽章、環境代號與每個檔案；子程序由 RPA_APP_LAYER 指定同一層。重新安裝完整的安裝包後改回內建的程式。外殼收入完整的標準函式庫，只排除用不到的（tkinter、test、ensurepip 等）與依賴系統函式庫的 readline、curses。
  • 裝置的更新檢查。POST /update（Worker API 與 Client API）回報 App 種類、目標、環境代號、目前的版本與上次退回的版本；回覆 current、available（大小、SHA-256）、full、failed、off、unavailable，GET /update/file 下載。裝置在上線時、以及因協定版本不同被拒時檢查；舊的管理 Portal 沒有這個端點時不提示。
  • Worker 的套用。視窗版裝好之後暫停領取，目前的任務結束後以 --background 重新啟動；新的程序帶著舊程序的 pid（RPA_RESTART_AFTER），等它結束、放開單一執行的鎖才選層。使用者按「繼續接任務」就取消；使用者原本就暫停時也不重新啟動；這兩種都改在下次開啟時套用。重新啟動後新的一層還沒確認就失敗時，啟動器再重新啟動一次，沒有人在電腦前也會退回上一層。--no-window 只提示。
  • 錄製端。只提示「關掉再開啟就會套用」，不自己重新啟動。
  • 設定與畫面。「自動更新裝置」存在 settings 表（device_updates），預設開。裝置頁顯示伺服器的更新檔，以及每台最近一次的更新狀態（只記在記憶體，伺服器重新啟動後等裝置再回報）。「要用完整的安裝包」說明是執行環境不同，滑過去看這台與更新檔的環境代號；有更新狀態說明時不再另外提醒「和 Portal 的程式版本不同」（2026-10-26）。
  • 發布。release.yml 用 Secrets 的 RPA_UPDATE_SIGNING_KEY 產生並簽署 RPA-Update-<版本>.zip，並確認每個安裝包信任的公鑰都是 rpa_update/keys.py 的 RELEASE_KEYS；還沒有正式金鑰時發布會失敗。產生金鑰的步驟見CI 與流水線 › 更新檔的簽署金鑰。PR 上的建置用臨時金鑰測試。
  • 頁面的靜態檔帶內容雜湊（2026-10-28）。更新檔換掉程式層之後，網址不變的 /static/replay.js 之類會被瀏覽器沿用舊的快取（之前沒有 Cache-Control，瀏覽器自己猜快取多久）：v0.7.0 驗收時頁面是新版、播放器的程式還是舊的。樣板改用 static_url()，網址加上內容的雜湊（?v=…），帶版本的長期快取，沒帶的每次向伺服器確認（no-cache）。
  • 實測（Linux x86_64 本地建置）。更新檔約 1.9 MB（七個套件編譯成 .pyc）。打包的 Worker 裝上更新檔後載入新的一層、確認、兩次啟動失敗後退回，新的程序會等舊的結束後才啟動（約 0.5 秒內接手）。

後果

  • 環境代號沒變的版本（例如 0.4.0 → 0.5.0），整套系統的升級從「6 個 84～136 MB 的檔案、每台裝置各自下載安裝」變成「1 個約 2 MB 的檔案、交給伺服器一次」。裝置從區網下載，不需要 GitHub 帳號。
  • 伺服器與裝置的程式指紋保持一致，「版本不同」提醒與 M7a「App 太舊」的失敗幾乎不再出現。
  • 伺服器仍要重新啟動（Python 在啟動時載入程式），Portal 會有數秒打不開；遠端 Worker 的回報重試 10 分鐘、領取自動重連（現有行為），加上租約延長，任務不會丟。
  • 現有的 0.5.0 沒有啟動器，要用第一個分層的版本（預定 0.6.0）完整安裝最後一次；配對、設定與資料保留。從 clone 執行的伺服器同時改用分發包。
  • 代價：多一個啟動器與更新流程要維護；桌面 App 因為收入完整的標準函式庫會變大一些；程式從使用者可寫的資料夾載入，安全靠簽章；更新端點的格式要永遠相容；簽章私鑰遺失或外洩時，要發新的完整包換鑰。
  • CI 多一條路徑：把這次建置的完整包當成上一版，裝上換了提交的更新檔再跑自我測試，並確認啟動就失敗的更新會自動退回；伺服器分發包另測升級、退回與拒絕竄改。

沒有選的方案

方案為什麼不選
逐檔比對、只下載改變的檔案PyInstaller 把我們的程式編進執行檔的封存，每版執行檔都變；還是要先把程式層拆出來，拆出來之後逐檔比對沒有多少好處。
安裝檔的二進位差分（bsdiff 之類）壓縮過的安裝檔差分效果差；每一對版本都要一份差分，發布與保存變複雜。
Sparkle、WinSparkle 等整包自動更新解決「自動」但不解決「大」；需要一個對外的下載網址（倉庫是私有的）與簽章憑證。
執行中重新載入模組（importlib.reload）舊的物件與狀態留在記憶體，行為難以預期，出錯難查。
伺服器完全不停機（兩個程序輪流接手）要在前面加反向代理；SQLite 不能讓兩個程序同時寫（ADR 0008）。收益只有數秒。
每台裝置直接向 GitHub 下載倉庫是私有的，要帳號；內網的裝置不一定連得到 GitHub。
不簽章，只靠雜湊與裝置權杖裝置與伺服器之間目前是 HTTP；更新檔換掉的是程式本身而且一直留著，比一次性的場景風險大。
