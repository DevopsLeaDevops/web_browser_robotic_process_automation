ADR 0012：遠端 worker 經由 HTTP 向管理 Portal 領取任務

執行可以交給另一台電腦。遠端 worker 不連資料庫，只透過管理 Portal 另一個埠上的 Worker API（權杖）領取任務、回報進度與結果；本機模式維持不變。

已接受
日期
2026-10-13
影響範圍
rpa-worker、rpa-server、rpa-cli（M9a 起）；部署（M9）
相關
部分取代 ADR 0003（worker 不直接連資料庫）；ADR 0008、ADR 0010；遠端 worker、管理 Portal › 遠端 worker

背景

管理 Portal、資料庫、worker 與檔案原本都在同一台電腦。測試時大多用有頭模式，瀏覽器視窗一開，這台電腦就沒辦法做別的事。使用者另外有一台可以專門執行的電腦，所以把路線圖 M9「分散式 worker」的一小塊提前做（M9a）。

原方案（ADR 0003）是 worker 直接連 PostgreSQL、用 Procrastinate 領取任務。MVP 用 SQLite，只允許單一程序存取（ADR 0008）；而且讓另一台電腦拿到資料庫帳密、開放資料庫的網路，都不是 MVP 該有的負擔。

決策

  • 只有管理 Portal 存取資料庫。遠端 worker 透過 Worker API（/worker-api/v1）上線、長輪詢領取任務、每 5 秒心跳、上傳執行目錄、回報結果。
  • worker 主動連 Portal。只要 worker 機器連得到 Portal 的一個埠；Portal 不需要連 worker。
  • Worker API 在獨立的埠、每個請求要權杖。rpa serve --worker-port 開啟，預設聽所有網路介面；管理頁面與 /api 仍然只在原本的位址（預設 127.0.0.1）。每台 worker 一個權杖，資料庫只存雜湊。
  • 租約，不自動重跑。領取時給 60 秒租約，心跳延長；過期就標為「worker 失聯」並失敗，因為可能已經有副作用。之後 worker 才回報的結果一律拒絕。
  • 本機 worker 照舊。沿用同一個 rpa_worker.Worker，只換任務來源；沒有登記遠端 worker 時一切和以前一樣。執行多一個「執行位置」：本機、遠端、任一。
  • 結果的規則不變。遠端 runner 算的雜湊照樣經過發布門檻比對；產物上傳到 Portal 的執行目錄，報告和本機執行看起來一樣。

後果

好處

  • worker 機器不需要資料庫帳密，也不用開資料庫的網路；之後換 PostgreSQL、加更多 worker 一樣適用。
  • 有頭模式的視窗出現在 worker 機器，自己的電腦不再被占住。
  • 本機與遠端共用 runner、執行目錄與發布門檻，沒有第二套執行邏輯。

代價

  • Secrets 與角色的登入狀態要送到 worker（只在記憶體與執行期間的暫存檔）；用 HTTP 時在區網上是明文，只適合信任的網路，之後可以改 HTTPS。
  • 多一個開放給區網的埠；作業系統的防火牆要允許。
  • worker 失聯時那次執行直接失敗，要人確認後重新執行。
  • 試驗場序列整個固定在第一個節點的 worker，那台離線時後面的節點會等著。

沒有選的方案

方案為什麼不選
worker 直接連 PostgreSQL（Procrastinate，ADR 0003）MVP 用 SQLite；worker 機器要拿到資料庫帳密並開放資料庫網路。
Portal 推送任務給 workerPortal 要連得到每一台 worker，網路設定反過來比較麻煩；只有 worker 連不到 Portal 時才考慮。
Redis 等訊息佇列多一個要部署、要維護的服務；目前的量用 HTTP 長輪詢就夠。
整個管理 Portal 開放給區網管理頁面沒有登入（M8 才有），區網上的人都能操作。
遠端桌面看執行畫面只解決「看得到」，不解決「本機被占住」；每次都要手動連線。
