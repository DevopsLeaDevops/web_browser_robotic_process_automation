ADR 0011：管理介面以 FastAPI + Jinja 伺服器端渲染

MVP 的管理 Portal 由 FastAPI 提供 API 與頁面，頁面用 Jinja 樣板加設計系統的 CSS 與少量 JavaScript。取代 ADR 0004 的 React。

已接受
日期
2026-10-10
影響範圍
rpa-server（M3 起）、管理介面的所有頁面、CI
相關
取代 ADR 0004；ADR 0002、ADR 0006、ADR 0010

背景

ADR 0004 選擇 React，主要理由是視覺化的步驟編輯器需要拖拽與複雜互動。MVP 原型的頁面則是卡片、表單、篩選、草稿編輯與序列編排，全部用設計系統 v1.0 的 portal.css、shell.js 與一支 JavaScript 完成，沒有用框架。

原型的交付任務書建議 Flask + Jinja。後端已經以 Pydantic 定義 DSL（ADR 0002），API 也要回傳同一套模型。

決策

  • FastAPI 提供 API 與頁面。REST API 直接使用 rpa-core 的 Pydantic 模型並產生 OpenAPI；頁面由同一個服務以 Jinja2 樣板渲染。
  • 前端只用設計系統與少量 JavaScript。沿用 portal.css、shell.js 與設計變數；互動以小型、不需建置的 JavaScript 模組完成，不引入框架與 Node.js 建置流程。
  • 長任務不阻塞請求。執行交給背景 worker；頁面以輪詢或伺服器推送事件讀取進度。
  • 多語言。Jinja 樣板的文字放在訊息目錄，與命令列共用同一套機制（ADR 0007）。
  • 保留調整空間。若之後的步驟編輯器確實需要框架，只在那一頁引入，並另寫 ADR。

後果

好處

  • 整個工程只有 Python，不必維護 TypeScript 與前端建置。
  • 頁面與原型一致：同一套 CSS、同樣的版面與元件。
  • API 與頁面共用模型與校驗，錯誤訊息一致。

代價

  • 複雜的拖拽編輯要自己寫 JavaScript；超過一定規模就要重新評估。
  • 伺服器端渲染的頁面要另外確保鍵盤操作與窄螢幕版面。

沒有選的方案

方案為什麼不選
Flask + Jinja（原型任務書）同樣簡單，但請求校驗與 API 文件要另外接；FastAPI 直接使用 Pydantic 模型並產生 OpenAPI。
FastAPI + React（ADR 0004）互動最強，但 MVP 的頁面用不到，卻要多維護一套 TypeScript 與建置流程。
NiceGUI、Streamlit純 Python，但無法沿用設計系統的版面與元件。
