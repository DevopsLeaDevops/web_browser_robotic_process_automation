ADR 0014：錄製端與 Worker 以桌面 App 分發，殼內沿用現有網頁

伺服器與資料庫部署在一台電腦，錄製者與執行機各自安裝一個桌面 App 就能用。App 是 pywebview 殼＋伺服器現有的 Jinja 頁面；錄製、逐步調試、人工登入的瀏覽器改開在操作的那台電腦。

已接受
日期
2026-10-15（提議）；2026-10-16（接受）
影響範圍
新套件 rpa-desktop；rpa-runner（子程序命令）、rpa-server（裝置、邀請、對外埠、互動子程序）、rpa-worker（版本資訊）；CI 與發布（M10 起）
相關
延伸 ADR 0012（對外埠與權杖）；ADR 0011（只用 Python、伺服器渲染頁面）；ADR 0010；桌面端分發。編號 0013 保留未用。

背景

伺服器與資料庫之後會部署在固定的電腦（先在使用者自己的電腦調試，再搬到正式環境）。錄製者與執行機目前都要裝 uv、git、Python 並跑安裝腳本，版本也要手動對齊；使用者希望像 Claude Desktop 一樣，拿到一個安裝檔就能用。

更根本的限制是：錄製、逐步調試、人工登入的瀏覽器都開在執行 Portal 的那台電腦（M4 的設計，ADR 0012 也維持）。伺服器搬走以後，錄製者在自己的電腦上什麼都開不了。管理頁面又沒有登入（M8 才有），不能整個開放給區網。

Claude Desktop 是 Electron 應用：殼裡帶一個 Chromium，主要介面是網頁。我們的介面本來就是伺服器渲染的網頁，殼只需要一個能載入網址的視窗。

決策

  • 兩個 App，同一份程式碼。「RPA 錄製端」與「RPA Worker」都在 apps/desktop（套件 rpa-desktop），各自一份建置設定。MVP 交付錄製端 macOS（Apple 晶片）與 Worker Windows（x64）；其他組合保留方案。
  • 殼用 pywebview。macOS 用系統的 WKWebView、Windows 用 WebView2，不另帶瀏覽器。錄製端的視窗載入伺服器現有的 Portal 頁面，模板不分兩套；App 自己的少數頁面（配對、下載瀏覽器、狀態）也用設計系統的 HTML。
  • 邀請配對。Portal 的「裝置」頁產生一次性邀請（24 小時內有效、只能用一次、限定是哪個 App）；App 用邀請換到裝置權杖，存在系統鑰匙圈或 Windows 認證管理員。
  • 對外埠多兩種用途。rpa serve --worker-port 的埠除了 Worker API，也提供 Client API（配對、互動子程序）與 Portal 頁面；Portal 頁面只接受錄製端的裝置權杖，沒有就拒絕。127.0.0.1:8080 的本機用法不變。
  • 互動子程序在操作的那台執行。伺服器多一層子程序主機：請求從錄製端進來時，錄製、逐步調試、人工登入的子程序交給那台錄製端執行，輸出與檔案傳回；從本機瀏覽器進來時照舊在伺服器執行。轉換、遮罩、版本與發布門檻仍在伺服器。
  • 子程序命令集中。所有 sys.executable -m … 改由 rpa_runner.commands 產生；打包後改走 App 自己的入口。
  • 瀏覽器第一次啟動時下載。用 App 內附的 Playwright driver 下載，版本必定相符；可以設定內部鏡像。
  • MVP 不簽章。macOS 只有 ad-hoc 簽章、Windows 沒有程式碼簽章；文件說明第一次開啟要怎麼允許。之後有帳號再加簽章與公證。

後果

好處

  • 錄製者與執行機不需要 uv、git、Python；貼上邀請、下載瀏覽器就能用。
  • 錄製的瀏覽器開在錄製者自己的電腦，伺服器可以放在任何地方（包括沒有螢幕的正式環境）。
  • 介面只有一套：Portal 頁面的修改，錄製端立即看到；工程仍然只有 Python。
  • Worker 沿用 M9a 的 Worker API 與 runner，沒有第二套執行邏輯。
  • 沒配對的電腦打開對外埠看不到管理頁面，是 M8 之前最小的存取控制。

代價

  • 多一個 CI 建置流程（macOS、Windows），每次發布要附兩個安裝檔；App 與伺服器版本要對齊。
  • 沒有簽章時，第一次開啟要手動允許（macOS「隱私權與安全性」、Windows SmartScreen）。
  • 錄製、調試要經過網路傳輸輸出與截圖；裝置權杖、Secrets 與登入狀態在 HTTP 下是明文，只適合信任的區網（同 ADR 0012）。
  • 打包後的 Python 腳本場景只能 import 標準函式庫與 App 內附的套件。
  • 系統 WebView 依賴作業系統版本：Windows 要有 WebView2（Windows 11 內建），macOS 依系統的 Safari 核心。

沒有選的方案

方案為什麼不選
Electron 殼＋Python 子程序（Claude Desktop 的做法）生態完整（自動更新、簽章工具），但要多一套 Node／TypeScript 工具鏈與第二個 Chromium；殼只負責開視窗，換成本小，之後需要時可以替換。
Tauri 殼安裝檔最小，但要 Rust 工具鏈；理由同上。
不做殼，用系統瀏覽器開 Portal，背景跑一個程式看起來不像一個 App；權杖要放進瀏覽器 Cookie，換瀏覽器就失效。
一個 App，邀請決定角色建置只有一份，但使用者選了兩個 App：名稱與安裝對象清楚，Worker 機器上不會出現錄製功能。
安裝檔內含瀏覽器離線可用，但安裝檔多 150 MB 以上，macOS 之後公證也較麻煩；保留為離線方案。
整個 Portal 開放給區網沒有登入（M8），區網上的人都能操作（ADR 0012 已排除）。
遠端畫面串流（錄製時看伺服器那台的瀏覽器）操作延遲高、要另做串流元件，伺服器還是要有圖形介面。
PyInstaller 單檔（onefile）每次啟動都要解壓上百 MB，也較容易被防毒誤判；改用資料夾（onedir）加安裝檔。
