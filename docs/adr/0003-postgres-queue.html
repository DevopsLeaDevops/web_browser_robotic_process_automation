ADR 0003：以 PostgreSQL 作為任務佇列

執行任務與排程直接存放在 PostgreSQL，不另外引入 Redis。

已接受
ADR 0008 補充：本決策適用於使用 PostgreSQL 的正式環境。開發與原型使用 SQLite 時，佇列與排程改在 API 程序內執行，只有單一 worker。
日期
2026-10-09
影響範圍
rpa-server、rpa-worker、部署（M7、M9）
相關
系統架構、ADR 0008

背景

多用戶共用需要多個 worker 併發執行、定時排程、失敗重試。平台本來就需要 PostgreSQL 存放場景與執行紀錄。

RPA 的瓶頸在瀏覽器本身：一次執行通常是數秒到數分鐘，任務量是每分鐘數十到數百筆，而不是每秒數千筆。

決策

  • 使用 Procrastinate：以 PostgreSQL 為後端、原生 asyncio 的任務佇列，支援定時任務。
  • 建立執行紀錄與入列任務放在同一個資料庫交易裡，不會出現有紀錄沒任務的情況。
  • worker 透過一層薄介面呼叫佇列，必要時可替換實作。

後果

好處

  • 部署少一個元件，備份與監控只需顧好 PostgreSQL。
  • 任務與執行紀錄的一致性由交易保證。
  • 與 Playwright async 執行模型相容。

代價

  • 吞吐量上限低於專用訊息佇列；以本工程的規模足夠。
  • 依賴單一函式庫，因此保留替換介面。

沒有選的方案

方案為什麼不選
Celery + Redis成熟但多一個元件，asyncio 支援較弱。
arq（Redis）asyncio 原生，但同樣需要 Redis。
自行實作 SKIP LOCKED 佇列可行，但重試、排程、監控都要自己寫。
