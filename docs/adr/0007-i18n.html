ADR 0007：產品與文檔支援英文、繁體中文、簡體中文

從 M0 開始建立多語言機制，不必等功能寫多了再回頭找出所有寫死的文字。

提議中
日期
2026-10-10
影響範圍
所有套件中使用者看得到的文字、rpa 命令、M8 Web UI、docs/
相關
開發規範、文檔與 ADR、ADR 0005

背景

平台的使用者與文檔讀者包括使用英文、繁體中文、簡體中文的同事。

如果先把繁中寫死，之後要從命令列、校驗訊息、執行報告與介面裡逐一找出文字改寫，成本會隨程式碼一起成長。M0 只有少量文字，是導入成本最低的時候。

決策

  • 三種語言。繁體中文 zh-Hant（預設）、簡體中文 zh-Hans、英文 en。網址、檔名與參數都用這組代碼。
  • 預設固定繁中，不跟隨作業系統或瀏覽器語言，由使用者手動切換：命令列用 --lang 或環境變數 RPA_LANG，Web UI 記在使用者設定，文檔站在頁首切換。
  • 產品文字放在訊息目錄。每個套件的 locales/<語言>.json，程式碼以訊息鍵取用（rpa_core.i18n.Catalog），不寫死使用者看得到的文字。click 內建的「用法」「選項」與錯誤訊息也一併翻譯。
  • 簡中自動產生。繁中與英文由人維護；簡中用 OpenCC 的 tw2sp（繁轉簡並換成大陸用語）產生後提交，不道地的詞在 tools/zh-Hans-overrides.json 修正。OpenCC 鎖定版本。
  • 文檔三個目錄。繁中在 docs/（網址不變），英文在 docs/en/，簡中在 docs/zh-Hans/；目錄結構與錨點相同。
  • 用檢查保持同步。測試確保三種語言的訊息鍵與佔位符一致、簡中是最新產生的、英文頁對照的是目前的繁中版本。

翻譯範圍

內容處理方式
命令列輸出、錯誤與校驗訊息、執行報告三種語言，放在訊息目錄
Web UI 與 API 錯誤訊息（M7、M8）三種語言；前端沿用同一套代碼與預設語言
工程文檔 docs/三種語言，各一個目錄
使用者撰寫的內容：場景名稱、步驟說明、定位器裡的頁面文字不翻譯，原樣保存與顯示
DSL 的欄位與動作名稱、程式碼識別字維持英文，不翻譯
程式碼註解與文件字串、README、一鍵安裝腳本的輸出維持繁中

後果

好處

  • 新功能從第一行開始就有三種語言，不必事後補。
  • 人工只維護兩種語言，簡中的用詞也一致。
  • 漏翻或翻譯過期會讓 CI 失敗，不會悄悄變成語言混雜的畫面。

代價

  • 修改使用者看得到的文字或文檔時，要同時改英文，PR 會變大。
  • 預設固定繁中，英文使用者每次要加 --lang en，或設定 RPA_LANG。
  • 自動轉換的簡中偶爾有不道地的詞，要靠對照表修正。
  • 介面設計系統 v1.0 以繁中設計；英文通常較長，M6 的頁面原型要檢查英文版面。

沒有選的方案

方案為什麼不選
gettext 與 Babel（.po 檔）業界常用，但以英文原文當鍵、需要編譯步驟；本工程以繁中為主要語言，Web UI 也要讀同一份翻譯，JSON 更直接。
三種語言都人工維護簡中用詞最精準，但每次改文字要寫三份，最容易不同步。
跟隨系統或瀏覽器語言同一個命令在不同電腦上會輸出不同語言，文檔範例與問題回報不易對照；改為固定繁中、手動切換。
文檔在瀏覽器裡即時轉換簡中不用產生檔案，但要附上數 MB 的詞庫，連結檢查與離線閱讀也較複雜。
