ADR 0019：以一次組合運行看報告與錄影，錄影在播放器裡接起來

一次組合運行有一份匯總報告與一個合併回看。合併回看不產生新的影片檔：播放器把各節點的錄影依序放在同一條時間軸上，節點之間沒有畫面的時間換成短短的卡片。組合裡的節點錄影整組保留。

相關

背景

一次組合運行（workflow_runs 一筆）的每個節點都是一次獨立的運行，各有報告、截圖與錄影。原本的組合運行頁只列出節點與連結：要知道停在哪一步、為什麼、前面傳了什麼值，要逐一打開節點的報告；要看錄影，也要一段一段打開。使用者 2026-10-27 要求以「一次組合運行」的視角看報告與錄像。

節點依 DAG 的拓撲順序一個一個執行，整次固定在同一台 Worker，所以各節點的錄影在時間上是一條線、不會重疊。每段錄影只涵蓋那個節點的自動化階段：排隊、開瀏覽器、登入檢查、斷言與出參都沒有畫面。

Linux 伺服器沒有瀏覽器，也沒有 ffmpeg（ADR 0016）；伺服器加影音套件會改變執行環境，就不能只發更新檔（ADR 0018）。各節點的畫面大小可能不同（頁面大小、Firefox 的差異）。

決策

  • 匯總報告。組合運行頁改成一份報告：結論（全部通過，或停在哪個節點的哪一步，附定位器、錯誤、沒通過的斷言與截圖，以及沒有執行的節點）、數字、依結果上色的 DAG 與時間軸、每個節點的入參（值與來源）與出參（值與流向）、步驟、斷言。資料在看的時候從資料庫與各節點的 result.json 組出來，不另存檔。可以下載成單一 HTML（只嵌入沒通過的節點的截圖，D4）；API 與 Agent API 給同一份 JSON。
  • 錄影在播放器裡接起來（D1）。不產生新的影片檔：每個有錄影的節點是一段，它的片段與步驟移到這一段的開始；分頁代號加上節點（n2/page-1）。播放器沿用 ADR 0016 的多片段時鐘：載入片段時暫停時鐘，片段之間依實際時間前進。下載是各節點原始錄影的 zip，附說明順序的 playlist.json。
  • 空檔換成卡片（D2）。兩段錄影之間是 2 秒的轉場卡：上一個節點的出參與傳給誰、下一個節點的入參與來源、實際隔了多久。沒有錄影的節點（已刪除、需要登入、沒有開始、沒有進到自動化）是 3 秒的說明卡。從停下的節點繼續時，沿用的節點只放一張卡片並連到原本那次的回看（D3）；最後沒有執行或還沒結束的節點合成一張卡片。
  • 步驟重新編號。整次運行一個編號，另外記下節點與節點裡的編號（n2·3）；步驟代號加上節點（n2:search），?step= 指到某個節點的某一步，?node= 從某個節點開始。
  • 錄影整組保留（D6）。組合運行裡的節點，保留天數看整次組合運行的結果與結束時間（還在執行就不刪）；釘選一個節點就是釘選整次；超過總量時整次一起刪。單獨的運行規則不變。

後果

  • 不用打開節點也知道失敗在哪裡、為什麼；一個播放器看完整次運行，點右側任一節點的任一步就跳到那個畫面。
  • 只改伺服器：不加第三方套件、沒有資料庫遷移、不改 Worker 與錄製端，可以只發更新檔。
  • 沒有一支真正合併的影片：要拿到 Portal 以外看，下載的是各節點的影片與順序說明。
  • 卡片取代了實際的空檔，影片的時間軸不是實際經過的時間；實際時間在報告的時間軸與轉場卡上。
  • 沒通過的組合運行，前面通過的節點錄影多留到 30 天，磁碟用量比各自計算多一些；總量上限照舊。
  • 節點畫面大小不同時，播放器以第一段的比例顯示，其他段等比例縮放置中。
  • 將來支援平行節點時，時間軸要改成多軌；資料保留了各段的實際時間，可以在這上面擴充。

沒有選的方案

方案為什麼不選
伺服器把各段接成一支 .webm伺服器沒有 ffmpeg；畫面大小不同要重新編碼；加影音套件就不能只發更新檔；多存一份影片。
Worker 在最後一個節點後接影片Worker 不知道整次運行何時結束；重跑、沿用、取消都要處理；一樣要重新編碼。
保留實際的空檔排隊、開瀏覽器、斷言常常比操作本身還長，影片裡會有大段空白。
直接把各段接上、不放卡片看不出節點之間傳了什麼值，也看不出換了節點。
匯總報告在運行結束時存成檔案要決定用誰的語言、資料改了（例如錄影被刪）要重產；目前在看的時候產生就夠，歸檔（M11 D4）時再存。
