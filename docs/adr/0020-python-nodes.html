ADR 0020：Python 腳本場景演進成 Python 節點，和瀏覽器場景串在組合場景裡

不另開新的場景種類：現有的 script: 加上 runtime，就跑在平台建置的 RPA Python 運行環境、不開瀏覽器；沒寫 runtime 的照舊執行。組合場景的節點可以是瀏覽器場景，也可以是 Python 節點，資料以 array／object 出入參傳遞，檔案經由同一台 Worker 上的共用工作資料夾傳遞。

背景

瀏覽器場景做不到的事很多：讀寫 Excel、合併檔案、整理資料、呼叫 API、建模型。M1.1 起有「Python 腳本場景」（script: { automation, assertion }），但打包後的 App 用自己內附的 Python 執行它，只有標準函式庫與 App 帶的套件，派工也一律當成要開瀏覽器。

10-24 的第二版設計打算封存它、另開一種 python: 場景。10-29 查證後發現：腳本場景的契約本來就不依賴瀏覽器（Runner 交 input.json、收 facts.json 與候選出參）；組合場景的節點只記「場景＋固定版本＋入參綁定」，不分種類；同一次組合運行本來就固定在同一台 Worker。缺的是套件、派工、結構化入參與檔案的傳遞。

決策

  • 一種節點、兩種模式。script.runtime 沒寫是相容模式，和以前完全相同（雜湊不變、可以自己開瀏覽器）；寫了 "1" 是運行環境模式：用 RPA Python 運行環境 1，不能寫 browser、login，斷言可以是 assertion.py 或 DSL 的 verify（用 verify 時出參寫 from），可以有 file 入參。兩種模式都可以寫 files（腳本會用到的其他文字檔，納入雜湊）與 platforms。
  • RPA Python 運行環境。平台建置、測試的一套 Python 3.13 加固定的套件，CI 為每個平台建好，附在 Worker App 與 Linux 分發包；第一次用到時解壓到快取資料夾、自我檢查後沿用。執行時以 -E -s 隔開電腦上的 Python 與 PYTHON* 環境變數。模型套件不放進基本版，之後另做選用層（D4）。
  • 派工。運行環境模式的任務只交給回報了這個主版本、平台在 platforms 裡的裝置，不看瀏覽器與視窗；沒有時執行頁說明在等什麼。舊版 App 由 M7a 的 features（pythonNodes、jsonInputs）擋下。
  • 組合場景裡的資料與檔案。入參多 array、object，上游的同型別出參可以直接接；同一次組合運行在那台 Worker 上有一個共用工作資料夾，也是 Python 節點的工作目錄，組合運行結束就刪，只有宣告的產出檔案上傳（D3）。
  • rpa_script。運行環境模式由 rpa_script 的啟動器執行腳本：照契約自己讀寫檔案的腳本不用改；用 @automation 的腳本有步驟、事實、產出檔案與資料預覽，寫成和 DSL 相同格式的 steps.json。rpa_script 不裝在運行環境裡，由 Runner 把自己的那份（只用標準函式庫）加在 import 路徑最後：它屬於程式碼層，跟著更新檔更新，不會和運行環境的版本錯開（2026-10-29 實作時確定）。
  • 執行的 runtime 階段。入參之後、自動化之前準備運行環境，不算進總期限；result.json 多一個 python（模式、版本、平台、沿用或新解壓）。

後果

  • 瀏覽器場景與 Python 節點在同一個組合場景、同一套入參出參、同一個發布門檻；不需要學另一種模型。
  • 既有的腳本場景不用遷移；ADR 0009「腳本場景不寫 verify」只對相容模式成立。ADR 0014「打包後的腳本只能用 App 內附的套件」也只對相容模式成立。
  • Worker App 與 Linux 分發包多帶一個運行環境（壓縮後約 60～75 MB），第一次用到時多幾秒解壓。
  • 沒有下載瀏覽器、沒有螢幕的電腦也能當 Python 節點的 Worker。
  • Python 節點不是沙箱：等於在 Worker 上以那位使用者的身分執行任意程式，只給信任的人編輯，審核時特別標示。
  • 共用工作資料夾裡的中間檔案不會留下；要看的檔案寫到產出檔案。遠端 Worker 錯過了結束通知時，一天後在上線時清掉。
  • 檔案在節點之間傳遞（2026-10-29 實作時確定）：DSL 多了 download 步驟與 type: file 出參，檔案值多一種 {"workspace": 相對路徑}（不用 path，免得和「那台電腦上的路徑」混淆）；Python 節點寫在 outputs/ 的檔案是產出檔案，跟著執行目錄上傳、運行詳情可以下載，另外複製一份到共用工作資料夾的 .outputs/<執行編號>/ 給下游。執行目錄的檔名可以是中文，打包上傳時跳過伺服器會拒絕的檔名。
  • 報告與回看：Python 節點不錄影；用 run.step() 的腳本有步驟時間軸，單一運行的回看是章節軸，組合運行的合併回看裡是一段一步一格的時間軸（依實際耗時佔 1.5～6 秒），和瀏覽器節點的錄影接在一起播（2026-10-30）。主控台以位元組位置逐步對應：rpa_script 記下每一步開始、結束時 automation.log 寫到哪裡，不在 print() 的每一行加上時間與步驟；腳本的輸出照原樣保留，腳本開的子程序寫的也對得上（取代設計第 6.2 節原本的寫法）。
  • 之後（P3）：模型套件的選用層、腳本工作台、組合場景的扇出（foreach）、Python 節點使用登入角色（待決定）。

沒有選的方案

方案為什麼不選
封存 script:、另開 python:（第二版）多一套模型、派工與報告，舊場景要遷移；使用者 10-29 選擇統一。
運行環境模式也能開瀏覽器使用者選擇不能：網頁操作留在 DSL；運行環境的 Playwright 版本要和 Worker 下載的瀏覽器綁在一起，容易出錯。
用電腦上的 Python、conda 或場景自己鎖定套件每台結果不同、Worker 要連得到套件來源；正是要避免的版本與倚賴問題。
檔案經由伺服器在節點之間傳遞同一次組合運行已經在同一台 Worker，走本機路徑最快；只有宣告的產出檔案上傳。
組合場景裡直接寫一段轉換程式的節點少了版本、發布門檻與獨立斷言；Python 節點已經涵蓋。
