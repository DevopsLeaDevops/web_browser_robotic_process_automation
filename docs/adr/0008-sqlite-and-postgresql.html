ADR 0008：資料庫同時支援 SQLite 與 PostgreSQL

開發與原型用 SQLite，不必安裝資料庫；正式環境用 PostgreSQL。同一套程式碼與遷移在兩種資料庫上都要能跑。

已接受
路線圖 v2（ADR 0010）之後：SQLite 從 M3 的管理 Portal 開始使用，PostgreSQL 與多個 worker 在 M8、M9。下文提到的 M7 對應新的 M3 與 M8。
日期
2026-10-10
影響範圍
rpa-server、rpa-worker、資料庫遷移、CI、部署（M7 起）
相關
ADR 0003、技術選型、系統架構

背景

M7 之前場景以 YAML 檔放在倉庫，不需要資料庫。M7 開始的管理後端要存放使用者、專案、場景版本與執行紀錄。

開發與設計階段要快速走通原型，不希望每位開發者都先安裝、設定 PostgreSQL。正式環境則是多用戶共用，需要併發寫入、多個 worker 與正式的備份。

決策

  • 兩種資料庫，用途分開。開發、測試與原型用 SQLite（Python 內建，不用另外安裝）；正式環境一律用 PostgreSQL。
  • 一個設定切換。連線字串放在環境變數 RPA_DATABASE_URL；沒有設定時使用本機的 SQLite 檔。
  • 只寫兩邊都支援的程式碼。模型與查詢只用 SQLAlchemy 2.0 的通用型別與寫法，不直接使用 PostgreSQL 專屬功能。
  • 同一套遷移。Alembic 遷移兩種資料庫共用，啟用 batch 模式讓 SQLite 也能修改資料表結構。
  • 佇列依資料庫切換實作。PostgreSQL 用 Procrastinate，可以有多個 worker（ADR 0003）；SQLite 只允許單一程序，佇列與排程在 API 程序內執行。
  • CI 兩種都測。M7 起資料庫相關的測試在 SQLite 與 PostgreSQL 上各跑一次，兩邊都通過才能合併。

寫程式時的規則

兩種資料庫行為不同的地方
項目做法
JSON 欄位用 SQLAlchemy 的 JSON，在 PostgreSQL 上以 with_variant 存成 JSONB；查詢不用 JSONB 專屬運算子。
時間一律以 UTC 存放，用共用的欄位型別轉換；SQLite 不會保存時區。
外鍵SQLite 預設不檢查外鍵，每個連線都要開啟 foreign_keys，並使用 WAL 模式。
不分大小寫搜尋不用 ILIKE；兩邊都轉成小寫再比較。
PostgreSQL 專屬功能陣列、LISTEN/NOTIFY、SKIP LOCKED、advisory lock 等，只能出現在可替換的實作裡（例如佇列），不能出現在模型與一般查詢。
併發SQLite 同一時間只能有一個寫入者。需要驗證多個 worker、併發寫入的測試只在 PostgreSQL 上跑。

後果

好處

  • 開發者不用安裝資料庫，uv sync 之後就能跑起後端；測試也更快。
  • 正式環境仍有 PostgreSQL 的併發、多 worker 與備份能力。
  • 不綁定資料庫專屬功能，之後要換資料庫也比較容易。

代價

  • 不能直接使用 PostgreSQL 的進階功能；需要時要另外包成可替換的實作。
  • 佇列要維護兩份實作；SQLite 模式驗證不到多 worker 的行為，只能靠 PostgreSQL 的測試。
  • 兩種資料庫在型別、鎖與交易隔離上的差異，可能讓問題只在其中一邊出現，所以 CI 要兩邊都測。
  • 原型階段的資料不搬到正式環境；場景本身是 YAML，需要時用匯出、匯入（rpa push）帶過去。

沒有選的方案

方案為什麼不選
只支援 PostgreSQL，開發用 Docker 起一個開發與正式環境最一致，但每個人都要先裝 Docker 或 PostgreSQL，拖慢原型。
正式環境也用 SQLite只能單機、單一寫入者，無法支援多個 worker 與多用戶併發。
測試時臨時啟動 PostgreSQL（例如 testcontainers）測試貼近正式環境，但本機要有 Docker；改在 CI 用 PostgreSQL 補上。
安全措施：正式部署的設定範例（M9）一律使用 PostgreSQL；伺服器啟動時在日誌標明使用的資料庫，使用 SQLite 時提醒「僅供開發與原型」；設定多個 worker 卻連到 SQLite 時拒絕啟動。
