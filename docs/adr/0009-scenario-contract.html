ADR 0009：場景契約與獨立斷言

每個場景都有入參、出參與獨立斷言；「腳本沒有拋錯」不算成功，出參只在獨立斷言通過後發布。DSL 為主，Python 腳本是受控的逃生門。

已接受
日期
2026-10-10
影響範圍
rpa-core（DSL）、rpa-runner（M2）、管理 Portal、錄製與 AI 生成、編排
相關
ADR 0001、ADR 0010、場景 DSL、MVP 原型

背景

MVP 原型以真實的 Python / Playwright 範例驗證了一套執行契約：入參在啟動瀏覽器前以 JSON Schema 校驗；自動化只負責操作頁面並留下「頁面事實」；另一個獨立的斷言比對事實與入參；全部通過後，出參才發布，並可以交給下一個場景。

M1 的 DSL 只有 params 與步驟內的 expect：成功等於「步驟都沒失敗」，沒有出參，也無法串接場景。原型的流程與錄製、AI 生成、編排都依賴這份契約。

決策

  • 場景契約。每個場景可以宣告 inputs（入參）與 outputs（出參），型別與限制取 JSON Schema 2020-12 的常用子集，可以匯出成 JSON Schema。params 改名為 inputs。
  • 頁面事實。extract 的結果放在 facts；事實只描述頁面上看到了什麼，不代表成功。
  • 獨立斷言。verify 在自動化結束後比對 facts 與 inputs。有出參的場景一定要有 verify。
  • 出參最後才發布。入參校驗 → 自動化 → 獨立斷言 → 出參校驗，全部通過才產生 output.json；任何一步失敗都沒有成功出參。
  • 總期限。deadline 限制整次執行；每一步只能用剩下的時間。
  • DSL 為主，Python 腳本為逃生門。DSL 表達不了的場景可用 script 指定 automation.py 與 assertion.py，沿用原型的命令列契約；審核時特別標示，錄製與 AI 不產生這種場景。

一次執行的順序

M2 實作
階段輸入產出失敗時
入參校驗入參、inputs 宣告input.json不啟動瀏覽器
自動化steps 或 automation.pyfacts.json、截圖、日誌保留階段、錯誤與能取得的截圖
獨立斷言verify 或 assertion.py、facts、入參候選出參沒有成功出參
出參校驗與發布候選出參、outputs 宣告output.json沒有成功出參
每一階段都受總期限限制；有副作用的動作（例如送出表單）不會因為逾時自動重試。

後果

好處

  • 成功有證據：報告可以指出是哪一條斷言、哪一個事實不符。
  • 場景可以串接：下游的入參綁定上游的出參，型別在執行前就能檢查。
  • API、管理介面與 AI 用同一份入參、出參 Schema。
  • DSL 仍是預設，錄製與 AI 的輸出可以先校驗；少數複雜場景有退路。

代價

  • 寫場景時要多寫 verify 與 outputs；只截圖或查看的簡單場景可以省略。
  • Python 腳本場景能做任何事，安全邊界要靠審核、權限與執行隔離。
  • 執行引擎要支援兩種場景，報告格式要一致。

沒有選的方案

方案為什麼不選
以 Python 腳本為主（照原型）最有彈性，但錄製與 AI 的輸出無法在執行前校驗，網頁上難以編輯，安全邊界不清楚（ADR 0001 的理由仍然成立）。
只用 DSL最單純，但 DSL 擴充前遇到複雜頁面就沒有退路。
只用步驟內的 expect 判定成功斷言與操作混在一起，無法保證「發布的出參」真的被檢查過，也不能獨立重跑斷言。
