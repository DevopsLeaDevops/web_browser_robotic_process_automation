桌面端分發

M10：伺服器與資料庫部署在一台電腦，錄製者與執行機各裝一個桌面 App，貼上邀請就能用。App 的視窗沿用伺服器現有的頁面；錄製、逐步調試、人工登入的瀏覽器開在操作的那台電腦。決策見 ADR 0014。

錄製端：使用者的流程

macOS
  1. 從 Portal 的「下載桌面端」取得 DMG，把「RPA 錄製端」（RPA Recorder.app）拖進「應用程式」。
  2. 第一次開啟：沒有簽章，macOS 會擋下；到「系統設定 › 隱私權與安全性」允許打開（步驟見簽章與第一次開啟）。
  3. 貼上 Portal「裝置」頁產生的錄製端邀請，配對完成。
  4. 下載瀏覽器（只有第一次，顯示進度）。
  5. 視窗裡就是 Portal。按「開始錄製」「調試」「登入」時，瀏覽器開在這台 Mac。

Worker：使用者的流程

Windows
  1. 取得 RPA-Worker-Setup.exe，安裝到使用者目錄；不需要管理員、uv、git、Python。
  2. SmartScreen 出現時按「其他資訊 › 仍要執行」。
  3. 貼上 Worker 邀請，配對完成。
  4. 下載瀏覽器，狀態變成「線上」。
  5. 關掉視窗是縮到通知區；可勾選「登入 Windows 時自動啟動」。

裝置與邀請

M10.1
  • 「遠端 Worker」頁改成「裝置」頁。列出 Worker 與錄製端兩種裝置；新增時選種類與名稱，產生邀請，取代現在「複製權杖＋啟動命令」。
  • 邀請。一行文字：rpa://pair?server=http://192.168.1.10:8081&app=worker&code=…。代碼一次性、24 小時內有效、限定 App 種類；資料庫只存雜湊。App 也接受分開填寫的伺服器網址與代碼。
  • 配對。App 用邀請呼叫 POST /client-api/v1/pair 換到裝置權杖，存進 macOS 鑰匙圈或 Windows 認證管理員。Worker 邀請貼到錄製端（或反過來）會被拒絕並說明。
  • Worker 裝置就是現有的 worker 紀錄：拿到的權杖直接用在 Worker API。命令列也能用邀請配對：uv run rpa worker --invite …，權杖存在工作資料夾，之後直接 uv run rpa worker；用環境變數或 --token-file 給權杖的方式照舊可用。
  • 管理。停用、重新邀請（舊權杖立刻失效）、刪除；頁面顯示線上狀態、App 版本、作業系統、瀏覽器。

對外埠與存取控制

M10.1、M10.2
  • 沿用 --worker-port。不加新的命令列參數；文件改稱「對外埠」。
  • 依路徑分流（擴充 PortGateMiddleware）：/worker-api/ 要 worker 權杖；/client-api/v1/pair 只接受邀請代碼；其他 /client-api/ 要裝置權杖；其他所有路徑（Portal 頁面、/api、靜態檔）要錄製端的裝置權杖，沒有就回 401。
  • 結果。沒配對的電腦打開 8081 看不到管理頁面；worker 權杖也打不開管理頁面。這是 M8 之前最小的存取控制，M8 再把裝置對應到使用者。
  • 本機 8080 不變。伺服器那台的瀏覽器照舊直接用。
  • 傳輸。維持 HTTP＋權杖（信任的區網，2026-10-13 的決定）；HTTPS 列在保留方案。

互動子程序：瀏覽器開在操作的那台

M10.2；錄製、逐步調試、人工登入

「這台電腦」改成指「你正在操作的那台」。請求從錄製端進來，子程序就交給那台錄製端；從伺服器本機的瀏覽器（8080）進來，照舊在伺服器執行。頁面不多一個選項。

  • 子程序主機（ProcessHost）。錄製、調試、人工登入三個服務現在已經用可注入的 launcher 啟動子程序，只用到一小部分 Popen 的功能：寫一行到標準輸入、逐行讀標準輸出、結束。LocalHost 是現在的行為；DeviceHost 介面相同，但經由 Client API 交給錄製端。伺服器端讀 Lines、解析事件的程式不變。
  • 啟動。伺服器送出「啟動」指令：模組名稱（例如 rpa_runner.debug、playwright codegen）、參數（工作目錄用代號，不帶伺服器的路徑）、需要的檔案（場景、入參、登入狀態）、環境變數（語言、用到的 Secrets）。錄製端在自己的暫存資料夾寫出檔案並啟動。
  • 輸出與檔案。錄製端把每一行標準輸出傳回；在傳一行之前先上傳這段期間新增或改變的檔案（截圖、錄製稿、登入狀態），所以伺服器處理那一行時檔案一定已經到了。結束時再同步一次並回報結束碼。
  • 輸入與結束。伺服器要送一行命令（例如調試的「執行第 3 步」）或結束時，放進錄製端的指令佇列；錄製端以長輪詢取得。
  • 失聯。錄製端每次長輪詢就是心跳；超過 30 秒沒有回來，伺服器把它的子程序視為結束（調試標為中斷、錄製標為失敗），錄製端重新連上時結束殘留的瀏覽器。
  • 不變的。錄製稿轉成 DSL、遮罩密碼、建立草稿版本、調試步驟的副作用確認、登入狀態保存，全部仍在伺服器。Secrets 與登入狀態在錄製端只放記憶體與暫存檔，用完刪除（同 M9a 的 worker）。
  • 瀏覽器檢查。錄製端上線時回報已下載的瀏覽器；選了這台沒有的瀏覽器時，頁面直接說明，不啟動子程序。
  • 紀錄。錄製與調試工作階段記下是哪台裝置；頁首顯示目前透過哪台錄製端操作。

RPA 錄製端

M10.2，macOS
  • 本機閘道。App 在 127.0.0.1 的隨機埠開一個小閘道，視窗只載入閘道的網址；閘道加上裝置權杖後轉給伺服器的對外埠。權杖不進網頁、也不靠伺服器的 Cookie；以後改 HTTPS 時在閘道釘選憑證即可，WebView 不必處理自簽憑證。
  • 只給這個 App 用。閘道每次啟動產生一個密語，視窗第一次載入時設成 Cookie；沒有這個 Cookie 的請求一律拒絕，同一台電腦上的其他程式與瀏覽器用不了。
  • App 自己的頁面（配對、下載瀏覽器、離線提示、設定）放在閘道的 /__desktop/ 下，用設計系統的 CSS。
  • 新視窗與下載。target="_blank" 的連結（報告、截圖）在 App 內開新視窗；匯出檔案存到「下載項目」。
  • 伺服器在同一台時（MVP 的情況）：一樣配對 http://127.0.0.1:8081，走同一條路。
  • 執行位置的用詞。透過錄製端看頁面時，「本機」顯示為「伺服器」，避免誤會成錄製端這台。
  • 本地網路權限。macOS 15 起連區網要使用者允許；Info.plist 寫用途說明（NSLocalNetworkUsageDescription）。

RPA Worker

M10.1，Windows
  • 內部就是現有的 RemoteWorker。權杖改從配對取得；領取、心跳、上傳、測試網站的行為都和 rpa worker 一樣（執行迴圈在 rpa_worker.service，兩邊共用）。
  • 分兩步交付（2026-10-16 決定）。第一步是主控台版：雙擊 rpa-worker.exe 貼上邀請、下載瀏覽器、接任務，配對結果暫存在資料夾裡只有本人能讀寫的 pairing.json；CI 用打包版實際配對並執行 BA-001 → BA-002。第二步加上下面的狀態視窗、通知區、自動啟動、只執行一份與認證管理員，之後是安裝檔。
  • 狀態視窗。伺服器、線上狀態、目前執行、最近的執行、App 版本；版本與伺服器不同時提醒並連到下載頁。
  • 通知區圖示。關掉視窗是縮到通知區；選單有「開啟視窗」「暫停接任務」「結束」。
  • 自動啟動。勾選後寫入目前使用者的「登入時執行」；有頭模式需要使用者登入桌面，所以不做成系統服務。
  • 只執行一份。重複開啟時叫出已經在跑的那份。
  • 資料位置。工作資料與日誌在 %LOCALAPPDATA%\rpa\worker，Firefox 預熱範本照舊在 %LOCALAPPDATA%\rpa\cache，瀏覽器在 Playwright 預設的 %LOCALAPPDATA%\ms-playwright。
  • M9a 剩下的三項併入 M10.1：執行報告的「執行位置」篩選、場景網址是本機位址時的提醒、等待 worker 的提示。

打包與建置

M10.0
  • 子程序命令集中。目前 10 處用 sys.executable -m … 啟動子程序（runner、登入檢查、錄製、調試、codegen）。改由 rpa_runner.commands 產生：開發環境是 python -m 模組，打包後是 App --rpa-module 模組；Python 腳本場景是 App --rpa-script 檔案；codegen 直接呼叫 Playwright 內附的 driver。
  • PyInstaller，資料夾模式（onedir）。macOS 做成 RPA Recorder.app（顯示名稱「RPA 錄製端」）再包成 DMG；Windows 用 Inno Setup 做成安裝到使用者目錄的 RPA-Worker-Setup.exe。不用單檔模式（每次啟動解壓上百 MB，也較容易被防毒誤判）。
  • 建置資訊。版本、程式指紋、協定版本在建置時寫進 App（打包後沒有原始碼檔案可以算指紋）。版本規則沿用 M9a：協定不同才拒絕，程式指紋不同只提醒。
  • 瀏覽器。第一次啟動用 App 內附的 Playwright driver 下載，版本必定相符；放在 Playwright 預設的使用者快取。可以在設定填內部鏡像（PLAYWRIGHT_DOWNLOAD_HOST）。錄製端必要 Chromium、選用 Firefox；Worker 同。
  • Python 腳本場景。打包後用 App 內的 Python 執行，只能 import 標準函式庫與 App 內附的套件（Playwright、Pydantic 等）。
  • CI。新增桌面端建置流程：macOS（Apple 晶片）建錄製端、Windows 建 Worker；建好後跑自我測試：用打包後的 App 下載 Chromium、啟動測試網站，以無頭模式跑 BA-001，確認打包後的子程序路徑真的能用。產物（DMG、安裝檔）掛在該次建置上。
  • 大小（M10.0 在 CI 實測）。錄製端的 DMG 68 MB（App 解壓後 166 MB）；Worker 的 zip 58 MB（解壓後 139 MB）。第一次下載的 Chromium（含無頭版）解壓後約 570 MB（macOS）～710 MB（Windows）；Firefox 另計。

簽章與第一次開啟

MVP 不簽章
  • macOS。只有 ad-hoc 簽章（Apple 晶片必需，PyInstaller 自動處理），沒有公證。從瀏覽器下載後第一次打開會被擋下：到「系統設定 › 隱私權與安全性」，在下方找到這個 App，選擇允許打開並輸入密碼。macOS 15 起，按住 Control 點「打開」已經不能略過這一步。熟悉終端機的人也可以執行 xattr -dr com.apple.quarantine "/Applications/RPA Recorder.app"。
  • Windows。沒有程式碼簽章：SmartScreen 顯示「Windows 已保護您的電腦」時按「其他資訊 › 仍要執行」；瀏覽器下載時也可能要確認保留檔案。
  • 之後。有 Apple Developer 帳號後加上 Developer ID 簽章與公證；Windows 加程式碼簽章憑證。只改 CI 的建置步驟。

要實測的風險

  • WebView2。Windows 11 內建，Windows 10 大多已隨 Edge 更新裝好；安裝檔偵測不到時先安裝。
  • macOS 本地網路權限。確認 Playwright 開的 Chromium 連內網網站時，權限算在 App 身上。
  • 防毒誤判。PyInstaller 的啟動器偶爾被誤判；資料夾模式較少，必要時回報給防毒廠商。
  • Playwright 私有命令。「接著錄製」用 codegen 內部的 enableRecorder；打包後要用同一個 driver，升級 Playwright 時由自我測試發現。
  • pywebview 的新視窗與下載。WKWebView 與 WebView2 的行為不同，兩邊都要手動確認。
