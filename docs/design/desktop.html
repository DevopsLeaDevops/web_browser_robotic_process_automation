桌面端分發

M10：伺服器與資料庫部署在一台電腦（可以是沒有螢幕的 Linux），錄製者與執行機各裝一個桌面 App，貼上邀請就能用。App 的視窗沿用伺服器現有的頁面；錄製、逐步調試、人工登入的瀏覽器開在操作的那台電腦。決策見 ADR 0014。

架構

伺服器只多了對外埠上的兩種用途

藍框是 M10 新增或改動最多的部分。只有伺服器存取資料庫（ADR 0008、ADR 0012 不變）；兩個 App 都主動連伺服器，伺服器不需要連到它們。閘道不轉送 /client-api/ 與 /worker-api/，網頁拿不到權杖。伺服器沒有瀏覽器時，「檢查」登入狀態交給錄製端，人工登入也在開視窗的那台確認（#50）。整體部署見系統架構。

配對與上線

兩個 App 相同；邀請貼錯 App 會被拒絕
第 3 步換到權杖之後，App 每次啟動直接用保存的權杖上線（第 5 步的 hello）。重新邀請、停用或刪除裝置，舊權杖立刻失效。

裝置與邀請

M10.1
  • 「遠端 Worker」頁改成「裝置」頁。列出 Worker 與錄製端兩種裝置；新增時選種類與名稱，產生邀請，取代現在「複製權杖＋啟動命令」。
  • 邀請。一行文字：rpa://pair?server=http://192.168.1.10:8081&app=worker&code=…。代碼一次性、24 小時內有效、限定 App 種類；資料庫只存雜湊。App 也接受分開填寫的伺服器網址與代碼。
  • 配對。App 用邀請呼叫 POST /client-api/v1/pair 換到裝置權杖，存進 macOS 鑰匙圈或 Windows 認證管理員。Worker 邀請貼到錄製端（或反過來）會被拒絕並說明。
  • Worker 裝置就是現有的 worker 紀錄：拿到的權杖直接用在 Worker API。命令列也能用邀請配對：uv run rpa worker --invite …，權杖存在工作資料夾，之後直接 uv run rpa worker；用環境變數或 --token-file 給權杖的方式照舊可用。
  • 管理。停用、重新邀請（舊權杖立刻失效）、刪除；頁面顯示線上狀態、App 版本、作業系統、瀏覽器。

對外埠與存取控制

M10.1、M10.2
  • 沿用 --worker-port。不加新的命令列參數；文件改稱「對外埠」。
  • 依路徑分流（擴充 PortGateMiddleware）：/worker-api/ 要 worker 權杖；/client-api/v1/pair 只接受邀請代碼；其他 /client-api/ 要裝置權杖；其他所有路徑（Portal 頁面、/api、靜態檔）要錄製端的裝置權杖，沒有就回 401。
  • 結果。沒配對的電腦打開 8081 看不到管理頁面；worker 權杖也打不開管理頁面。這是 M8 之前最小的存取控制，M8 再把裝置對應到使用者。
  • 本機 8080 不變。伺服器那台的瀏覽器照舊直接用。
  • 傳輸。維持 HTTP＋權杖（信任的區網，2026-10-13 的決定）；HTTPS 列在保留方案。

互動子程序：瀏覽器開在操作的那台

M10.2；錄製、逐步調試、人工登入、登入檢查
以錄製為例；逐步調試（送一行「執行第 3 步」）、人工登入、登入檢查走同一條路。實線是請求，虛線是回應或經由閘道。

「這台電腦」改成指「你正在操作的那台」。請求從錄製端進來，子程序就交給那台錄製端；從伺服器本機的瀏覽器（8080）進來，照舊在伺服器執行。頁面不多一個選項。

  • 子程序主機。錄製、調試、人工登入三個服務用可注入的 launcher 啟動子程序，只用到一小部分 Popen 的功能：寫一行到標準輸入、逐行讀標準輸出、結束。從伺服器本機來的請求照舊是 subprocess.Popen；從錄製端來的請求改用 RecorderHub.launcher(裝置)（rpa_server.devices），傳回介面相同的 RemoteProcess，經由 Client API 交給那台。哪一台由請求決定：對外埠的存取控制認出錄製端的權杖後，把裝置放進這個請求的 context（rpa_server.context）。伺服器端讀 Lines、解析事件的程式不變。
  • 啟動。伺服器送出「啟動」指令：模組名稱（rpa_runner.record、rpa_runner.debug、rpa_runner.login）、參數（工作目錄用代號 {work}，不帶伺服器的路徑；工作目錄外的輸入檔，例如角色的登入狀態，放進 .inputs/）、需要的檔案（場景、入參、登入狀態）、環境變數（只送服務明確指定的：語言、用到的 Secrets）。錄製端在自己的暫存資料夾寫出檔案並啟動，結束後刪掉整個資料夾（下次啟動時也清掉上次沒刪的）。連線是區網裡的 HTTP，所以錄製端只執行這三個模組與 playwright codegen，也不接受會改變直譯器或載入程式庫的環境變數（PYTHON*、NODE_*、DYLD_*、PATH 等）。
  • 輸出與檔案。錄製端把每一行標準輸出傳回；在傳一行之前先上傳這段期間新增或改變的檔案（截圖、錄製稿、登入狀態），所以伺服器處理那一行時檔案一定已經到了。結束時再同步一次並回報結束碼。
  • 輸入與結束。伺服器要送一行命令（例如調試的「執行第 3 步」）或結束時，放進錄製端的指令佇列；錄製端以長輪詢取得。
  • 失聯。錄製端每次長輪詢就是心跳；超過 30 秒沒有回來，伺服器把它的子程序視為結束（結束碼 -1001，原因寫進那段工作的日誌，頁面照一般的失敗顯示），錄製端重新連上時結束殘留的瀏覽器。錄製端重新啟動（上線時的開機代號不同）、在裝置頁被停用、刪除或重新邀請，以及伺服器停止時也一樣。
  • 不變的。錄製稿轉成 DSL、遮罩密碼、建立草稿版本、調試步驟的副作用確認、登入狀態保存，全部仍在伺服器。Secrets 與登入狀態在錄製端只放記憶體與暫存檔，用完刪除（同 M9a 的 worker）。
  • 瀏覽器檢查。錄製端上線時回報已下載的瀏覽器；選了這台沒有的瀏覽器時，頁面直接說明，不啟動子程序。
  • 紀錄。錄製（recordings.device_id）、調試與人工登入的工作階段記下是哪台裝置；頁首顯示目前透過哪台錄製端操作。每台裝置同一時間各一段錄製；同一個場景的調試只有一個，在另一台開始時關掉原本的。

RPA 錄製端

M10.2，macOS
  • 本機閘道。App 在 127.0.0.1 的隨機埠開一個小閘道，視窗只載入閘道的網址；閘道加上裝置權杖後轉給伺服器的對外埠。權杖不進網頁、也不靠伺服器的 Cookie；以後改 HTTPS 時在閘道釘選憑證即可，WebView 不必處理自簽憑證。
  • 只給這個 App 用。閘道每次啟動產生一個密語，視窗第一次載入時設成 Cookie；沒有這個 Cookie 的請求一律拒絕，同一台電腦上的其他程式與瀏覽器用不了。閘道不轉送 /client-api/ 與 /worker-api/：網頁不能拿權杖去確認或偽造錄製端的指令與輸出。
  • App 自己的頁面（配對、下載瀏覽器、離線提示、設定）放在閘道的 /__desktop/ 下，用設計系統的 CSS。
  • 新視窗與下載。target="_blank" 的連結（報告、截圖）在 App 內開新視窗；匯出檔案存到「下載項目」。
  • 伺服器在同一台時（MVP 的情況）：一樣配對 http://127.0.0.1:8081，走同一條路。
  • App（M10.2 PR 2）。pywebview（WKWebView）的視窗只載入閘道的網址；狀態、配對、下載瀏覽器、設定是閘道另一個埠的 /__desktop/ 頁面（rpa_desktop.recorder_pages，用 fetch 呼叫，不用 pywebview 的 js_api）：和 Portal 不同來源、各有自己的密語與 Cookie，寫入的請求一定要帶這個埠的 Origin，所以 Portal 的頁面（或塞進去的腳本）讀不到 App 的狀態，也叫不動配對、重新配對、鏡像這些動作（2026-10-18 審閱後改的）。還沒配對、或 Portal 回 401 時，Portal 那個埠只回說明頁（不放 App 頁面帶著密語的網址），主視窗在配對失效時自己回到 App 的頁面。選單「RPA 錄製端」：狀態與設定、管理 Portal、重新整理。target="_blank" 經由自訂的 webbrowser 處理器：閘道的網址在另一個執行緒開 App 的新視窗（pywebview 在主執行緒呼叫，那裡建不出視窗；新視窗共用 Cookie），其他網站只接受 http(s)、用預設瀏覽器；下載不能顯示的檔案時 pywebview 改用 NSURLSession，所以閘道的 Cookie 也放進 App 的 NSHTTPCookieStorage。關掉主視窗或 ⌘Q 都先攔下、確認後由 App 自己關（⌘Q 直接放行時 AppKit 會立刻結束程序、來不及收拾），結束時不等長輪詢、直接結束子程序與刪暫存；只執行一份；權杖在鑰匙圈的「RPA Recorder」；資料在 ~/Library/Application Support/rpa/recorder。CI：macOS 跑錄製端 App、閘道與錄製端程式的單元測試，--smoke-test 打開真的 WKWebView 視窗確認頁面經由閘道載入。
  • 不開 App 視窗（M10.2 PR 3）。rpa-recorder --no-window：同一個 controller 與閘道，只是沒有 WKWebView 視窗——管理 Portal 用預設瀏覽器打開（--open），或把經由閘道打開的網址寫到 --url-file（只有本人能讀，結束時刪除）。有頭模式照樣可以用：錄製、有頭模式的逐步調試、人工登入的瀏覽器視窗照樣開在這台，少的只是 App 的視窗；所以要在登入中的桌面（例如「終端機」）啟動，不要從 SSH 或背景服務。已經在執行時再雙擊 App，這一份改用預設瀏覽器打開管理 Portal。結束用資料夾的 stop.request 或 SIGINT、SIGTERM、SIGHUP（關掉終端機）：訊號只設旗標，主執行緒先結束子程序、回報、刪暫存（同視窗版）；結束碼和 Worker 的 --no-window 相同（4：同一個資料夾已經有一份在執行）。--open 用一般的瀏覽器時，閘道的 Cookie 綁在 127.0.0.1（Cookie 不分埠），同一個瀏覽器打開的其他本機服務也收得到；在意時改用 --url-file 搭配獨立的瀏覽器設定檔（rpa recorder 也一樣）。CI 的端到端（tools/recorder_e2e.py）：從原始碼啟動管理 Portal，打包版以 --no-window 用邀請配對（權杖要存進鑰匙圈），經由閘道在錄製端逐步調試 BA-001，無頭與有頭各一次，截圖經由閘道傳回；最後用 stop.request 結束（結束碼 0）。
  • 開發環境的 rpa recorder。同一套閘道（rpa_worker.gateway）與子程序主機（rpa_worker.recorder），改在預設瀏覽器打開；給有開發環境的人與端到端測試用（用法）。
  • 執行位置的用詞。透過錄製端看頁面時，「本機」顯示為「伺服器」，避免誤會成錄製端這台。
  • 本地網路權限。macOS 15 起連區網要使用者允許；Info.plist 寫用途說明（NSLocalNetworkUsageDescription）。

RPA Worker

M10.1，Windows；macOS 2026-10-22
  • 內部就是現有的 RemoteWorker。權杖改從配對取得；領取、心跳、上傳、測試網站的行為都和 rpa worker 一樣（執行迴圈在 rpa_worker.service，兩邊共用）。
  • 分兩步交付（2026-10-16 決定）。第一步是主控台版：雙擊 rpa-worker.exe 貼上邀請、下載瀏覽器、接任務；CI 用打包版實際配對並執行 BA-001 → BA-002。第二步（2026-10-17 核准）加上下面的狀態視窗、通知區、自動啟動、只執行一份與認證管理員；主控台版保留為同資料夾的 rpa-child.exe --worker，排查問題用。之後是安裝檔（2026-10-18 核准）。
  • 狀態視窗。pywebview（WebView2）載入 App 內的頁面（設計系統的 CSS 內嵌，原檔不改）：配對（貼邀請，只貼代碼時另外填伺服器）、下載瀏覽器的進度、伺服器、線上狀態、目前執行、最近 10 筆、App 版本、權杖存放；版本與伺服器不同時提醒，附「下載新版」打開最新的 GitHub Release。「設定」：自動啟動、Firefox、內部鏡像、語言（依 ADR 0007 預設繁中、不跟作業系統，選擇記在資料夾的 settings.json）、開啟日誌資料夾、重新配對。視窗不連到 Portal 的頁面：管理頁只在伺服器那台的 127.0.0.1，對外埠要到 M10.2 才開放給錄製端。
  • 通知區圖示。關掉視窗是縮到通知區（第一次提示）；選單有「開啟視窗」「暫停接任務」「結束」，圖示的圓點表示狀態。有任務在執行時結束要先確認，取消後回報。「暫停接任務」是做完目前的任務後不再領取：伺服器不改，Portal 約一分鐘後顯示離線（2026-10-17 決定）。
  • 自動啟動。寫入目前使用者的「登入時執行」（HKCU\…\Run，加上 --background 只出現在通知區；還沒配對時仍打開視窗）。第一次配對成功後預設開啟，之後照使用者在設定裡的選擇；每次啟動時把路徑更新成目前的位置（免安裝的資料夾可能被搬走）。有頭模式需要使用者登入桌面，所以不做成系統服務。
  • 只執行一份。資料夾裡 instance.lock 的獨占鎖，視窗版、--no-window 與主控台版互斥；重複開啟時叫出已經在跑的那份。拿到鎖的那份另外建立具名 mutex RPAWorker.App，讓安裝檔知道 App 正在執行；資料夾的 stop.request 請它取消任務、回報後結束。
  • 認證管理員。權杖經由 keyring 存在 Windows 認證管理員；不能用時退回 pairing.json（只有本人能讀寫）並記在日誌。第一步存在檔案裡的權杖自動搬過去。
  • 不跳主控台視窗。視窗程式啟動的主控台子程序（rpa-child、taskkill）加上 CREATE_NO_WINDOW；下載瀏覽器直接啟動 Playwright 的 driver，不經過 rpa-child。
  • 沒有 WebView2、登出與關機。沒有 WebView2 Runtime 時說明怎麼安裝，在那之前只用通知區接任務。Windows 登出或關機時立刻取消執行中的任務並回報（最多等 3 秒，不擋住關機）；來不及時由租約判定失聯（ADR 0012）。
  • 資料位置。工作資料、設定與日誌在 %LOCALAPPDATA%\rpa\worker（日誌會輪替，不記權杖與邀請代碼），Firefox 預熱範本照舊在 %LOCALAPPDATA%\rpa\cache，瀏覽器在 Playwright 預設的 %LOCALAPPDATA%\ms-playwright。
  • CI。Windows 的建置工作先跑桌面端的單元測試（登錄檔、單一執行、認證管理員用真的）；--smoke-test 打開真的 WebView2 視窗與通知區圖示；端到端先靜默安裝，用裝好的 App 以 --no-window 配對並執行 BA-001 → BA-002，再在 App 執行中升級、解除安裝（安裝檔）。視窗程式沒有標準輸出，--version、--self-test 改用 rpa-child。
  • M9a 剩下的三項併入 M10.1：執行報告的「執行位置」篩選、場景網址是本機位址時的提醒、等待 worker 的提示。
  • macOS 版（2026-10-22，ADR 0014 的保留方案）。同一份程式（rpa_desktop.gui），Apple 晶片，DMG 拖進「應用程式」，沒有安裝檔；功能和上面相同，差別在系統的部分（rpa_desktop.macos）：
    • 通知區換成選單列圖示（NSStatusItem，選單與圓點相同）。不用 pystray：它和 pywebview 都要在主執行緒跑 NSApplication 的迴圈；改用 PyObjC 掛在 pywebview 的迴圈裡，AppKit 的呼叫一律排到主執行緒，選單動作在另一個執行緒執行。
    • 關掉視窗是縮到選單列，同時拿掉 Dock 圖示（Accessory），叫出視窗時恢復；⌘Q 當成「結束」（有任務先確認）：pywebview 把 ⌘Q 和關閉鈕都變成同一個 closing 事件，看主執行緒是不是在 applicationShouldTerminate_ 裡來區分，先取消 AppKit 的結束（它會立刻結束程序，來不及回報），確認後由 App 自己關。
    • 在 Finder 再打開或點 Dock 圖示時（rapp），叫出視窗：LaunchServices 不會啟動第二份，所以在 pywebview 的 App 委派補上 applicationShouldHandleReopen:hasVisibleWindows:。直接執行第二份（例如 open -n）照舊走 show.request。
    • 自動啟動是目前使用者的 LaunchAgent（~/Library/LaunchAgents/io.github.devopsleadevops.rpa.worker.plist，--background，只在登入的桌面工作階段）；macOS 13 起列在「登入項目」。
    • 權杖在鑰匙圈（RPA Worker，和錄製端的 RPA Recorder 分開）；資料在 ~/Library/Application Support/rpa/worker。登出、關機前（NSWorkspaceWillPowerOffNotification）取消任務並回報，最多等幾秒。視窗關掉、收拾完後直接結束程序（同錄製端，pywebview 留下的執行緒不是 daemon）。
    • 畫面上的「通知區、認證管理員、登入 Windows」在 macOS 上換成「選單列、鑰匙圈、登入 macOS」：訊息目錄的 window.darwin.*。
    • CI：macOS 的 Worker 建置先跑桌面端的單元測試（鑰匙圈用真的）；open RPA Worker.app --args --smoke-test 打開 WKWebView 視窗與選單列圖示；端到端和 Windows 相同（不含安裝檔），權杖要存進鑰匙圈。

打包與建置

M10.0
  • 子程序命令集中。目前 10 處用 sys.executable -m … 啟動子程序（runner、登入檢查、錄製、調試、codegen）。改由 rpa_runner.commands 產生：開發環境是 python -m 模組，打包後是 App --rpa-module 模組；Python 腳本場景是 App --rpa-script 檔案；codegen 直接呼叫 Playwright 內附的 driver。
  • PyInstaller，資料夾模式（onedir）。macOS 做成 RPA Recorder.app（顯示名稱「RPA 錄製端」）再包成 DMG；Windows 用 Inno Setup 做成安裝到使用者目錄的 RPA-Worker-Setup-版本-windows-x64.exe（安裝檔），另外照樣產生免安裝的 zip。不用單檔模式（每次啟動解壓上百 MB，也較容易被防毒誤判）。
  • 建置資訊。版本、程式指紋、協定版本在建置時寫進 App（打包後沒有原始碼檔案可以算指紋）。版本規則沿用 M9a：協定不同才拒絕，程式指紋不同只提醒。M7a 起 App 另外回報看得懂的 DSL 擴充（features，例如 iframe 的 frame、anyFrame，M7b 新分頁的 page、popup）：要交給它的場景或登入設定用到它不懂的寫法時，伺服器不交給它，直接說明要更新哪個 App（舊 App 自己只會回「場景校驗失敗」）；Worker 的執行位置是「任一」而伺服器自己也執行時，留給伺服器。
  • 瀏覽器。第一次啟動用 App 內附的 Playwright driver 下載，版本必定相符；放在 Playwright 預設的使用者快取。可以在設定填內部鏡像（PLAYWRIGHT_DOWNLOAD_HOST）。錄製端必要 Chromium、選用 Firefox；Worker 同。
  • Python 腳本場景。打包後用 App 內的 Python 執行，只能 import 標準函式庫與 App 內附的套件（Playwright、Pydantic 等）。
  • CI。新增桌面端建置流程：macOS（Apple 晶片）建錄製端、Windows 建 Worker；建好後跑自我測試：用打包後的 App 下載 Chromium、啟動測試網站，以無頭模式跑 BA-001，確認打包後的子程序路徑真的能用。產物（DMG、安裝檔）掛在該次建置上。
  • 大小（M10.0 在 CI 實測）。錄製端的 DMG 68 MB（App 解壓後 166 MB）；Worker 的 zip 58 MB（解壓後 139 MB）。第一次下載的 Chromium（含無頭版）解壓後約 570 MB（macOS）～710 MB（Windows）；Firefox 另計。

Worker 的安裝檔

M10.1，Inno Setup 6.7
  • 只裝給目前的使用者。不需要管理員，裝到 %LOCALAPPDATA%\Programs\RPA Worker；開始功能表捷徑，桌面捷徑選用；裝完開啟。資料夾 %LOCALAPPDATA%\rpa\worker 和免安裝版相同。
  • 語言。繁中、簡中、英文，預設繁中、安裝時可以選（ADR 0007）。Inno Setup 的介面用它原始碼 is-6_7_1 的翻譯檔（建置時下載並核對 SHA-256，倉庫不放）；安裝檔自己的訊息從 App 的訊息目錄（installer.*）產生，所以一樣是繁中、英文人工維護，簡中由工具產生。
  • App 正在執行時。用 App 的具名 mutex 判斷，在資料夾寫 stop.request 請它取消執行中的任務、回報後結束（最多等 150 秒），再換檔案（只有通知區、沒有 WebView2 時也一樣；主控台版在配對、下載瀏覽器那一步做完後結束）；不用 Windows 的 Restart Manager 強制關閉。升級時配對、設定與自動啟動都保留，舊版的程式庫先刪掉。
  • WebView2。沒有 Runtime 時執行建置時附上的 Microsoft Evergreen 引導程式（建置時核對 Microsoft 的數位簽章）；失敗時說明，App 仍可只用通知區接任務。
  • 解除安裝。使用者確認要解除安裝後（Inno Setup 的 usAppMutexCheck，取消時 App 不受影響）才詢問是否也刪除配對、設定與日誌（含認證管理員裡的權杖）：預設保留；靜默解除安裝不問、保留，命令列 /REMOVEDATA=yes 才刪除。接著停止 App，刪除程式、捷徑與「登入時執行」的項目。只刪 App 自己的檔案：資料夾可能是 RPA_WORKER_HOME 指定的任何地方，瀏覽器與 Firefox 範本的快取別的程式也在用。
  • 建置與 CI。tools/build_desktop.py worker 在 Windows 上建好 App 與 zip 後呼叫 ISCC（GitHub 的 Windows 執行環境已裝 Inno Setup）。端到端：靜默安裝 → 檢查檔案、捷徑、解除安裝項目的版本 → 用裝好的 App 配對並執行 BA-001 → BA-002 → App 執行中再安裝一次（App 要以結束碼 0 結束）→ 解除安裝，確認程式、捷徑、解除安裝項目與自動啟動已刪、配對保留 → 再安裝一次並以 /REMOVEDATA=yes 解除安裝，確認資料夾與認證管理員裡的權杖已刪。失敗時附上 Inno Setup 的日誌。
  • 不包含。程式碼簽章、自動更新、內含 Chromium 的離線安裝檔。

版本與發布

GitHub Releases，草稿由維護者發布
  • 同一個版本。伺服器、Worker、錄製端與所有套件用同一個版本（主.次.修，數字），標籤是 v0.2.0 這種格式（2026-10-18 決定）。python3 tools/release_version.py bump 0.2.0 一次改全部套件與 uv.lock。
  • 流程。在功能分支 bump 版本 → PR 合併 → 在 main 上打標籤並推送 → 「發布」流程（.github/workflows/release.yml）確認標籤和套件版本一致、標籤在 main 上，呼叫桌面端建置（含安裝、升級、解除安裝的端到端），建立草稿 Release：Worker 的安裝檔與免安裝 zip、錄製端的 DMG（M10.2 起）、SHA256SUMS.txt。
  • 草稿。倉庫是公開的，發布後任何人都下載得到（沒有邀請連不上 Portal）；所以由維護者確認草稿的內容後才按「發布」。重新執行時換掉同一個草稿的檔案；已經發布的版本不換，改用新的版本。
  • 下載新版。App 的版本和伺服器不同時，視窗的「下載新版」打開最新的 Release（…/releases/latest，只算已發布的）。

簽章與第一次開啟

MVP 不簽章

要實測的風險

  • WebView2。Windows 11 內建，Windows 10 大多已隨 Edge 更新裝好；安裝檔偵測不到時先安裝。
  • macOS 本地網路權限。確認 Playwright 開的 Chromium 連內網網站時，權限算在 App 身上。
  • 防毒誤判。PyInstaller 的啟動器偶爾被誤判；資料夾模式較少，必要時回報給防毒廠商。
  • Playwright 私有命令。「接著錄製」用 codegen 內部的 enableRecorder；打包後要用同一個 driver，升級 Playwright 時由自我測試發現。
  • pywebview 的新視窗與下載。WKWebView 與 WebView2 的行為不同，兩邊都要手動確認。
