MVP 階段的樣貌

M2～M6：單機、單使用者、序列執行
管理 Portal

瀏覽器開啟；頁面由 API 服務以 Jinja 渲染，沿用 MVP 原型的版面（M3 起）。

API 服務

FastAPI：場景、版本與發布門檻、入參出參、執行、報告、調試工作階段（ADR 0011）。

背景 worker

同一台電腦；每次執行以子程序跑 Runner，套用總期限與取消，失敗或逾時就終止整個程序群組。

資料與產物

SQLite 存元資料（ADR 0008）；檔案目錄存場景版本快照與每次執行的目錄。

請求方向：Portal → API → worker。worker 寫入執行狀態與產物，Portal 以輪詢或伺服器推送事件讀取進度；長任務不阻塞網頁請求。M2 之前只有 CLI 與 Runner，直接在本機執行。

runs/<執行編號>/
  input.json          # 校驗後的本次入參
  facts.json          # 自動化抽取的頁面事實
  output.json         # 只有獨立斷言與出參校驗都通過才產生
  screenshot.png、trace.zip
  automation.log、assertion.log
  scenario/           # 本次使用的場景版本快照（含 Python 腳本）
  result.json、report.html

套件職責

uv workspace，每個套件可單獨測試
套件職責依賴起始
rpa-coreDSL 模型、YAML 載入與校驗、表達式引擎、JSON Schema 導出、多語言訊息目錄。不碰瀏覽器、不碰資料庫。Pydantic、PyYAML、Jinja2M0
rpa-runner執行引擎：入參校驗、步驟處理器註冊表、瀏覽器與上下文管理、獨立斷言、出參發布、執行目錄與報告；也執行 Python 腳本場景。無狀態。rpa-core、PlaywrightM2
rpa-recorder錄製：在隔離的瀏覽器中記錄使用者操作，保存原始錄製稿並轉成 DSL 草稿。rpa-core、PlaywrightM4
rpa-generatorAI 助手：對話調試、自然語言 → DSL、校驗失敗回饋修正、選擇器自癒；只能修改草稿。rpa-core、LLM SDKM5
rpa-clirpa 命令：validate、run、record、generate、push。上述套件、clickM0
rpa-serverAPI 與管理頁面、資料庫模型、版本與發布門檻、調試工作階段；權限（M8）、排程（M9）。rpa-core、FastAPI、Jinja2、SQLAlchemyM3
rpa-worker取出待執行的任務，以子程序呼叫 rpa-runner，套用總期限與取消，回寫結果與產物。M3 在同一台電腦，M9 改為分散式。rpa-runner；Procrastinate（M9）M3

一次執行的資料流

  1. 使用者在管理 Portal 或 CLI 觸發執行（M9 起也可以由排程器建立）。
  2. API 檢查已發布的版本，在啟動瀏覽器前校驗入參，寫入一筆執行紀錄與一個任務。
  3. worker 領取任務，以子程序啟動 Runner，傳入場景版本快照、入參與 Secrets（只在記憶體中），並設定總期限。
  4. Runner 開啟獨立的瀏覽器上下文逐步執行，記下頁面事實；每一步回報狀態。
  5. 獨立斷言比對頁面事實與入參；通過後出參校驗，才寫出 output.json。
  6. 截圖、Trace、日誌與報告存入執行目錄（M9 改為物件儲存）；失敗時標出出錯的階段、步驟與截圖。
