为什么是这个顺序

  • 先打通一条真实链路。M2 用 CLI 跑通 BA-001 → BA-002，管理界面只是在上面加一层。
  • MVP 先行。单机、单用户、串行运行；SQLite 与文件目录就够用（ADR 0008）。多用户、分布式等 MVP 验证后再做。
  • 成功要有证据。从 M2 起，出参只在独立断言通过后发布；界面上的模拟结果不能当成发布依据。
  • 先串接、再生成（M6 先于 M5）。试验场只用已发布的场景，不需要新的外部服务，可以马上开工；M5 要先决定 AI 模型（内部页面能否送到外部 API）。先有试验场，M5 生成的场景也能直接放进组合场景验证。
  • 先把运行搬离自己的电脑（M9a 插在 M5 前）。测试大多用有头模式，浏览器窗口会占住运行 Portal 的电脑；有一台专门运行的电脑，就先把 M9 的远程 worker 做出来。只动运行的位置，不改场景、契约与发布门槛。
  • 先让别人装得起来（M10 插在 M5 前）。服务器之后要放到正式环境；录制者与运行机要能不装开发工具就用，录制的浏览器也要开在录制者自己的电脑。只动安装与「子进程在哪台运行」，不改场景、契约与发布门槛。
  • 先解掉挡住录制的 iframe（M7a 插在 M5 前）。真实系统的表单常在 iframe 里，录制稿转不了就无法验证。只多一个定位器字段，不改场景契约与发布门槛；M7 的其他流程能力仍照原顺序。
  • 生成只产生草稿。录制与 AI 的输出都要经过真实验证与人工发布，验证的版本必须就是发布的版本。
  • Runner 从一开始就无状态。只吃场景、入参与 Secrets，输出结果与产物；M3 的背景 worker 与 M9a 的远程 worker 直接沿用。

尚待决定

AI 模型
M5 前决定。需先确认内部系统的页面内容能否送到外部 API；不行就接自建模型。
登录方式
M4 先以人工登录为主（任何登录流程都能处理），单纯帐密的系统可以加自动登录；测试网站用「一般用户」「主管」两个角色。还要确认目标系统的实际登录流程与需要的角色。
SSO 类型
M8 前确认公司使用 OIDC 还是 LDAP / AD。
部署环境
M9 前确认是单机 Docker Compose 还是 Kubernetes。
签章
M10 先不签章（第一次打开要手动允许）；有 Apple Developer 账号与 Windows 代码签章凭证后再加上，只改 CI。
对象存储
M9 前选定 S3 兼容的产品，例如 SeaweedFS、Garage 或公司现有的保存；原定的 MinIO 社区版已停止维护。
