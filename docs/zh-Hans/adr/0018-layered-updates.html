ADR 0018：程序层与运行环境分开打包，服务器把更新分发给设备

每个版本多发一个约 1 MB 的更新档，只含我们自己的程序；交给服务器一次，服务器更新自己，Worker 与录制端从区网取得同一个版本，在不打断工作的时机应用。运行环境（Python、第三方包）没变时不必重新下载完整包。

背景

用户 2026-10-24 提出：服务器、录制端、Worker 每次升级都要重新下载整包，效率不高，希望能热更新。

v0.5.0 的服务器分发包 x64 约 103 MB、arm64 约 97 MB；Windows Worker 的建置产物合计约 136 MB；两个 DMG 各约 84 MB。这些包里真正每版会变的，是七个工作区包（含 Portal 页面、翻译、数据库迁移），源代码压缩后只有约 0.6 MB（main a8cde7f 实测）；其余是 Python、第三方包与 Playwright driver。

第三方包不常变：0.2.0 → 0.3.0 变 6 项（添加 macOS 用的 PyObjC），0.3.0 → 0.4.0 变 20 项（含 Playwright 1.63 → 1.64，部分只是开发工具），0.4.0 → 0.5.0 是 0 项。

仓库在 2026-10-22 改成私有，Release 与 App 的「下载新版」只有登录且有权限的 GitHub 账号下载得到；每台设备都要有人下载、搬过去、安装。浏览器（解压后 570～710 MB）只在 Playwright 版本改变时重新下载，已经是增量的，不在本篇处理。

决策

  1. 分层。程序层：七个工作区包，纯 Python，各平台共用同一份。运行环境：Python 3.13、运行时需要的第三方包、PyInstaller 外壳（桌面 App），各平台一份。浏览器照旧。Python 脚本场景的运行环境（PR #82，待确认）若采用，是另一层，有自己的版本，不受本篇影响。
  2. 环境代号。每个平台的运行环境有一个代号：Python 版本、运行时第三方包的锁定清单（uv export，不含开发工具）、外壳的版本与收入的模块清单的哈希。CI 建置完整包时算出并写进包里。程序层写明各平台需要的代号；代号相同才能只换程序层，不同就要完整包。
  3. 更新档。发布时多产生 RPA-Update-<版本>.zip：程序层的文件、清单（版本、提交、程序指纹、协定版本、看得懂的 DSL 扩充、各平台的环境代号、每个文件的 SHA-256 与大小）与清单的 Ed25519 签章。完整包照旧发布，用于第一次安装与环境代号改变时。
  4. 服务器。安装位置改成 runtimes/<环境代号>/python（多版本共用）＋ releases/<版本>-<提交>/app（程序层），current 的原子切换照旧。bin/rpa update <更新档>：验证签章与哈希 → 确认有所需的环境代号 → 安装并用包内 Python 加载服务器程序 → 切换 current → 请运行中的服务器重新启动。服务器等到没有进行中的录制、逐步调试、人工登录才结束（--now 不等）；新版本启动时有新的迁移，先备份 SQLite 再迁移（PostgreSQL 提醒自行备份）。更新档保存在数据目录的 updates/ 供设备下载。服务器启动时把运行中远程任务的租约延长一个周期，重新启动期间不会被标成「worker 失联」。
  5. 服务器自己重新启动。bin/rpa serve 看顾服务器进程：服务器以约定的结束码结束时，用同样的参数启动 current 的新版本；新版本在开始服务之前就结束，切回上一版、还原迁移前的备份再启动。不依赖 systemd，用 nohup 或 systemd 启动都一样（用户的内网服务器用 nohup，2026-10-25 说明）。从 clone（.venv-server）运行的服务器不支持更新档，因为 git 管理的文件不能被覆盖：要先改用分发包一次，命令只把 .venv-server/bin/rpa 换成 ~/rpa-server/bin/rpa，参数与数据目录照旧。
  6. 设备的启动器。PyInstaller 的入口改成一个很小的启动器，我们的程序不再编进可执行文件的封存。启动器读文件夹里 app/active.json 指定的版本，验证签章、每个文件的哈希与环境代号，通过才放到 sys.path 最前面；否则用 App 内置的程序层（安装时的版本）并记日志。子进程（rpa-child）由父进程以环境变量指定同一份程序层。外壳收入完整的标准函数库（不含 tkinter、test 等），新版程序用到新模块时不会在旧外壳上找不到。
  7. 不改 App 本身。程序层下载到设备既有的文件夹：Windows %LOCALAPPDATA%\rpa\worker\app\、macOS ~/Library/Application Support/rpa/{worker,recorder}/app/。macOS 的 .app 签章不被破坏，也不需要「App 管理」权限。
  8. 设备跟随服务器的版本。设备上线前先调用更新端点（Worker API 与 Client API 各一个），回报 App 种类、平台、版本、环境代号。端点的格式固定、不检查协定版本，之后协定升级时旧 App 也能先更新。服务器回复：已是同版本／可以更新（版本、大小、哈希）／要完整安装。设备追的是服务器现在的版本，不是最新版；服务器退回时设备也跟着退回。
  9. 应用的时机。Worker：做完目前的任务、暂停领取，自己重新启动（数秒）；只在没有任务时重启。录制端：不打断录制与调试，窗口提示「重新打开即可应用」，下次打开时应用。新版本启动后 2 分钟内没能上线、或连续当掉两次，就退回上一版并回报服务器；保留最近 3 个版本。服务器设置有「自动更新设备」开关，默认开；设备页显示每台的版本与更新状态。
  10. 签章。CI 用 Ed25519 私钥（GitHub Secrets）签清单，公钥随运行环境发布；服务器安装时、设备下载时、启动器每次启动时都验证。验证以 RFC 8032 的参考算法实现（只做验证），不加依赖。启动器接受一组公钥，以便日后换钥。
  11. 依赖更新的节奏。每周的依赖更新 PR 中，只动到开发工具的照常合并（不改环境代号）；动到运行环境的累积起来，在「环境版本」一起合并，节奏由用户决定。Playwright 升级会让每台设备重新下载浏览器，PR 与 Release 说明要标出。

后果

  • 环境代号没变的版本（例如 0.4.0 → 0.5.0），整套系统的升级从「6 个 84～136 MB 的文件、每台设备各自下载安装」变成「1 个约 1 MB 的文件、交给服务器一次」。设备从区网下载，不需要 GitHub 账号。
  • 服务器与设备的程序指纹保持一致，「版本不同」提醒与 M7a「App 太旧」的失败几乎不再出现。
  • 服务器仍要重新启动（Python 在启动时引导程序），Portal 会有数秒打不开；远程 Worker 的回报重试 10 分钟、领取自动重连（现有行为），加上租约延长，任务不会丢。
  • 现有的 0.5.0 没有启动器，要用第一个分层的版本（预定 0.6.0）完整安装最后一次；配对、设置与数据保留。从 clone 运行的服务器同时改用分发包。
  • 代价：多一个启动器与更新流程要维护；桌面 App 因为收入完整的标准函数库会变大一些（实现时实测）；程序从用户可写的文件夹加载，安全靠签章；更新端点的格式要永远兼容；签章私钥遗失或外泄时，要发新的完整包换钥。
  • CI 要多一条路径：用上一版的完整包安装，应用这一版的更新档，再跑端到端。

没有选的方案

方案为什么不选
逐档比较、只下载改变的文件PyInstaller 把我们的程序编进可执行文件的封存，每版可执行文件都变；还是要先把程序层拆出来，拆出来之后逐档比较没有多少好处。
安装档的二进位差分（bsdiff 之类）压缩过的安装档差分效果差；每一对版本都要一份差分，发布与保存变复杂。
Sparkle、WinSparkle 等整包自动更新解决「自动」但不解决「大」；需要一个对外的下载网址（仓库是私有的）与签章凭证。
运行中重新加载模块（importlib.reload）旧的对象与状态留在内存，行为难以预期，出错难查。
服务器完全不停机（两个进程轮流接手）要在前面加反向代理；SQLite 不能让两个进程同时写（ADR 0008）。收益只有数秒。
每台设备直接向 GitHub 下载仓库是私有的，要账号；内网的设备不一定连得到 GitHub。
不签章，只靠哈希与设备权杖设备与服务器之间目前是 HTTP；更新档换掉的是程序本身而且一直留着，比一次性的场景风险大。
