ADR 0012：远程 worker 经由 HTTP 向管理 Portal 领取任务

运行可以交给另一台电脑。远程 worker 不连数据库，只通过管理 Portal 另一个端口上的 Worker API（权杖）领取任务、回报进度与结果；本机模式维持不变。

已接受
日期
2026-10-13
影响范围
rpa-worker、rpa-server、rpa-cli（M9a 起）；部署（M9）
相关

背景

管理 Portal、数据库、worker 与文件原本都在同一台电脑。测试时大多用有头模式，浏览器窗口一开，这台电脑就没办法做别的事。用户另外有一台可以专门运行的电脑，所以把路线图 M9「分布式 worker」的一小块提前做（M9a）。

原方案（ADR 0003）是 worker 直接连 PostgreSQL、用 Procrastinate 领取任务。MVP 用 SQLite，只允许单一进程访问（ADR 0008）；而且让另一台电脑拿到数据库帐密、开放数据库的网络，都不是 MVP 该有的负担。

决策

  • 只有管理 Portal 访问数据库。远程 worker 通过 Worker API（/worker-api/v1）上线、长轮询领取任务、每 5 秒心跳、上传运行目录、回报结果。
  • worker 主动连 Portal。只要 worker 机器连得到 Portal 的一个端口；Portal 不需要连 worker。
  • Worker API 在独立的端口、每个请求要权杖。rpa serve --worker-port 打开，默认听所有网络界面；管理页面与 /api 仍然只在原本的地址（默认 127.0.0.1）。每台 worker 一个权杖，数据库只存哈希。
  • 租约，不自动重跑。领取时给 60 秒租约，心跳延长；过期就标为「worker 失联」并失败，因为可能已经有副作用。之后 worker 才回报的结果一律拒绝。
  • 本机 worker 照旧。沿用同一个 rpa_worker.Worker，只换任务来源；没有登记远程 worker 时一切和以前一样。运行多一个「运行位置」：本机、远程、任一。
  • 结果的规则不变。远程 runner 算的哈希照样经过发布门槛比较；产物上传到 Portal 的运行目录，报告和本机运行看起来一样。

后果

好处

  • worker 机器不需要数据库帐密，也不用开数据库的网络；之后换 PostgreSQL、加更多 worker 一样适用。
  • 有头模式的窗口出现在 worker 机器，自己的电脑不再被占住。
  • 本机与远程共用 runner、运行目录与发布门槛，没有第二套运行逻辑。

代价

  • Secrets 与角色的登录状态要送到 worker（只在内存与运行期间的暂保存）；用 HTTP 时在区网上是明文，只适合信任的网络，之后可以改 HTTPS。
  • 多一个开放给区网的端口；操作系统的防火墙要允许。
  • worker 失联时那次运行直接失败，要人确认后重新运行。
  • 试验场串行整个固定在第一个节点的 worker，那台脱机时后面的节点会等着。

没有选的方案

方案为什么不选
worker 直接连 PostgreSQL（Procrastinate，ADR 0003）MVP 用 SQLite；worker 机器要拿到数据库帐密并开放数据库网络。
Portal 推送任务给 workerPortal 要连得到每一台 worker，网络设置反过来比较麻烦；只有 worker 连不到 Portal 时才考虑。
Redis 等消息队列多一个要部署、要维护的服务；目前的量用 HTTP 长轮询就够。
整个管理 Portal 开放给区网管理页面没有登录（M8 才有），区网上的人都能操作。
远程桌面看运行画面只解决「看得到」，不解决「本机被占住」；每次都要手动连接。
