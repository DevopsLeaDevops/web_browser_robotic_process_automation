ADR 0010：MVP 先行与路线图 v2

以 MVP 原型为准，先交付单机、单用户、串行运行的 MVP（M2～M6），多用户与分布式移到 MVP 之后。

已接受
日期
2026-10-10
影响范围
路线图、系统架构、多用户设计、M2 之后的所有里程碑
相关
路线图、ADR 0008、ADR 0009、ADR 0011、MVP 原型

背景

原路线图依「CLI → 流程能力 → 录制 → AI → 页面原型 → 管理后端 → Web UI → 营运」排序，管理界面要到 M8 才出现，多用户在 M7 就要完成。

MVP 原型描述了第一版要交付的产品：场景管理、录制与调试、报告、自由试验场，并且明确把任意 DAG、分布式集群、多租户权限与跨环境调度排除在 MVP 之外。原型也附了一条已用真实浏览器跑通的 Python 链路。

决策

  • MVP 范围。单机、单用户、串行运行；SQLite 存元数据，文件目录存脚本快照与运行产物。
  • 新的里程碑顺序。M1.1 场景契约 → M2 Runner → M3 管理 Portal → M4 场景生产与登录 → M5 AI 助手 → M6 自由试验场（MVP 完成）→ M7 流程能力 → M8 多用户与治理 → M9 营运。
  • 原型就是页面原型。原 M6 的页面原型由 MVP 原型交付；原 Web UI 拆进 M3～M6，每个阶段交付自己的页面，沿用原型的顶部一级、左侧二级版面。
  • 原型收进仓库。放在 docs/prototypes/mvp/，比照设计系统以 MANIFEST.json 校验，不改写、不翻译；原型的模拟结果不能当成真实验证。
  • 版本与发布门槛。场景版本不可变：草稿 → 验证中 → 通过或失败 → 已发布；改过脚本、Schema 或默认值就要重新验证，发布的版本必须就是验证通过的版本。
  • 浏览器。Chromium 与 Firefox 都支持，CI 都测；场景以 browser.engine 指定。

后果

好处

  • 用户在 M3 就能在浏览器里操作，比原计划早五个里程碑。
  • 每个阶段都以原型的情境验收，需求有共同的参照。
  • 多用户、分布式等成本高的能力，等 MVP 验证方向后再做。

代价

  • M3～M6 的页面在多用户（M8）时要补上权限与项目范围；数据模型从一开始就预留 owner 与 project 字段以降低成本。
  • 条件、循环、上传下载等流程能力延到 M7，MVP 期间较复杂的场景要用 Python 脚本逃生门。
  • 每一页都直接连到后端，原型与实现的差异要在各阶段的 PR 中说明。

没有选的方案

方案为什么不选
维持原路线图管理界面太晚出现，与原型描述的 MVP 不一致。
一开始就做多用户与 PostgreSQL原型明确排除多租户；先做会拖慢 MVP，而 ADR 0008 已保留之后切换的路。
直接把原型的 localStorage 前端接上后端原型是展示用的单一 JavaScript 档；正式页面改由服务器端渲染（ADR 0011），只沿用版面与流程。
