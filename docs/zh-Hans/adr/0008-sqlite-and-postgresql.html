ADR 0008：数据库同时支持 SQLite 与 PostgreSQL

开发与原型用 SQLite，不必安装数据库；正式环境用 PostgreSQL。同一套代码与迁移在两种数据库上都要能跑。

已接受
路线图 v2（ADR 0010）之后：SQLite 从 M3 的管理 Portal 开始使用，PostgreSQL 与多个 worker 在 M8、M9。下文提到的 M7 对应新的 M3 与 M8。
日期
2026-10-10
影响范围
rpa-server、rpa-worker、数据库迁移、CI、部署（M7 起）
相关
ADR 0003、技术选型、系统架构

背景

M7 之前场景以 YAML 文件放在仓库，不需要数据库。M7 开始的管理后端要存放用户、项目、场景版本与运行记录。

开发与设计阶段要快速走通原型，不希望每位开发者都先安装、设置 PostgreSQL。正式环境则是多用户共用，需要并发写入、多个 worker 与正式的备份。

决策

  • 两种数据库，用途分开。开发、测试与原型用 SQLite（Python 内置，不用另外安装）；正式环境一律用 PostgreSQL。
  • 一个设置切换。连接字符串放在环境变量 RPA_DATABASE_URL；没有设置时使用本机的 SQLite 文件。
  • 只写两边都支持的代码。模型与查询只用 SQLAlchemy 2.0 的通用类型与写法，不直接使用 PostgreSQL 专属功能。
  • 同一套迁移。Alembic 迁移两种数据库共用，启用 batch 模式让 SQLite 也能修改数据表结构。
  • 队列依数据库切换实现。PostgreSQL 用 Procrastinate，可以有多个 worker（ADR 0003）；SQLite 只允许单一进程，队列与调度在 API 进程内运行。
  • CI 两种都测。M7 起数据库相关的测试在 SQLite 与 PostgreSQL 上各跑一次，两边都通过才能合并。

写程序时的规则

两种数据库行为不同的地方
项目做法
JSON 字段用 SQLAlchemy 的 JSON，在 PostgreSQL 上以 with_variant 存成 JSONB；查询不用 JSONB 专属操作符。
时间一律以 UTC 存放，用共用的字段类型转换；SQLite 不会保存时区。
外键SQLite 默认不检查外键，每个连接都要开启 foreign_keys，并使用 WAL 模式。
不分大小写搜索不用 ILIKE；两边都转成小写再比较。
PostgreSQL 专属功能数组、LISTEN/NOTIFY、SKIP LOCKED、advisory lock 等，只能出现在可替换的实现里（例如队列），不能出现在模型与一般查询。
并发SQLite 同一时间只能有一个写入者。需要验证多个 worker、并发写入的测试只在 PostgreSQL 上跑。

后果

好处

  • 开发者不用安装数据库，uv sync 之后就能跑起后端；测试也更快。
  • 正式环境仍有 PostgreSQL 的并发、多 worker 与备份能力。
  • 不绑定数据库专属功能，之后要换数据库也比较容易。

代价

  • 不能直接使用 PostgreSQL 的高级功能；需要时要另外包成可替换的实现。
  • 队列要维护两份实现；SQLite 模式验证不到多 worker 的行为，只能靠 PostgreSQL 的测试。
  • 两种数据库在类型、锁与事务隔离上的差异，可能让问题只在其中一边出现，所以 CI 要两边都测。
  • 原型阶段的数据不搬到正式环境；场景本身是 YAML，需要时用导出、导入（rpa push）带过去。

没有选的方案

方案为什么不选
只支持 PostgreSQL，开发用 Docker 起一个开发与正式环境最一致，但每个人都要先装 Docker 或 PostgreSQL，拖慢原型。
正式环境也用 SQLite只能单机、单一写入者，无法支持多个 worker 与多用户并发。
测试时临时启动 PostgreSQL（例如 testcontainers）测试贴近正式环境，但本机要有 Docker；改在 CI 用 PostgreSQL 补上。
安全措施：正式部署的配置示例（M9）一律使用 PostgreSQL；服务器启动时在日志标明使用的数据库，使用 SQLite 时提醒「仅供开发与原型」；设置多个 worker 却连到 SQLite 时拒绝启动。
