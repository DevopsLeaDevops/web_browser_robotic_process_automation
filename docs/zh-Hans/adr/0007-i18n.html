ADR 0007：产品与文档支持英文、繁体中文、简体中文

从 M0 开始创建多语言机制，不必等功能写多了再回头找出所有写死的文字。

提议中
日期
2026-10-10
影响范围
所有套件中用户看得到的文字、rpa 命令、M8 Web UI、docs/
相关
开发规范、文档与 ADR、ADR 0005

背景

平台的用户与文档读者包括使用英文、繁体中文、简体中文的同事。

如果先把繁中写死，之后要从命令行、校验消息、运行报告与界面里逐一找出文字改写，成本会随代码一起成长。M0 只有少量文字，是导入成本最低的时候。

决策

  • 三种语言。繁体中文 zh-Hant（预设）、简体中文 zh-Hans、英文 en。网址、文件名与参数都用这组代码。
  • 预设固定繁中，不跟随操作系统或浏览器语言，由用户手动切换：命令行用 --lang 或环境变量 RPA_LANG，Web UI 记在用户设置，文档站在页眉切换。
  • 产品文字放在消息目录。每个套件的 locales/<语言>.json，代码以消息键取用（rpa_core.i18n.Catalog），不写死用户看得到的文字。click 内置的「用法」「选项」与错误消息也一并翻译。
  • 简中自动产生。繁中与英文由人维护；简中用 OpenCC 的 tw2sp（繁转简并换成大陆用语）产生后提交，不道地的词在 tools/zh-Hans-overrides.json 修正。OpenCC 锁定版本。
  • 文档三个目录。繁中在 docs/（网址不变），英文在 docs/en/，简中在 docs/zh-Hans/；目录结构与锚点相同。
  • 用检查保持同步。测试确保三种语言的消息键与占位符一致、简中是最新产生的、英文页对照的是目前的繁中版本。

翻译范围

内容处理方式
命令行输出、错误与校验消息、运行报告三种语言，放在消息目录
Web UI 与 API 错误消息（M7、M8）三种语言；前端沿用同一套代码与预设语言
工程文档 docs/三种语言，各一个目录
用户撰写的内容：场景名称、步骤说明、定位器里的页面文字不翻译，原样保存与显示
DSL 的字段与动作名称、代码识别字维持英文，不翻译
代码注解与文档字符串、README、一键安装脚本的输出维持繁中

后果

好处

  • 新功能从第一行开始就有三种语言，不必事后补。
  • 人工只维护两种语言，简中的用词也一致。
  • 漏翻或翻译过期会让 CI 失败，不会悄悄变成语言混杂的画面。

代价

  • 修改用户看得到的文字或文档时，要同时改英文，PR 会变大。
  • 预设固定繁中，英文用户每次要加 --lang en，或设置 RPA_LANG。
  • 自动转换的简中偶尔有不道地的词，要靠对照表修正。
  • 界面设计系统 v1.0 以繁中设计；英文通常较长，M6 的页面原型要检查英文版面。

没有选的方案

方案为什么不选
gettext 与 Babel（.po 档）业界常用，但以英文原文当键、需要编译步骤；本工程以繁中为主要语言，Web UI 也要读同一份翻译，JSON 更直接。
三种语言都人工维护简中用词最精准，但每次改文字要写三份，最容易不同步。
跟随系统或浏览器语言同一个命令在不同电脑上会输出不同语言，文档范例与问题回报不易对照；改为固定繁中、手动切换。
文档在浏览器里实时转换简中不用产生文件，但要附上数 MB 的词库，链接检查与脱机阅读也较复杂。
