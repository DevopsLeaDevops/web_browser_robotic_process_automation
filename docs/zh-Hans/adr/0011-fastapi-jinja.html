ADR 0011：管理界面以 FastAPI + Jinja 服务器端渲染

MVP 的管理 Portal 由 FastAPI 提供 API 与页面，页面用 Jinja 样板加设计系统的 CSS 与少量 JavaScript。取代 ADR 0004 的 React。

已接受
日期
2026-10-10
影响范围
rpa-server（M3 起）、管理界面的所有页面、CI
相关
取代 ADR 0004；ADR 0002、ADR 0006、ADR 0010

背景

ADR 0004 选择 React，主要理由是可视化的步骤编辑器需要拖拽与复杂交互。MVP 原型的页面则是卡片、表单、筛选、草稿编辑与序列编排，全部用设计系统 v1.0 的 portal.css、shell.js 与一支 JavaScript 完成，没有用框架。

原型的交付任务书建议 Flask + Jinja。后端已经以 Pydantic 定义 DSL（ADR 0002），API 也要回传同一套模型。

决策

  • FastAPI 提供 API 与页面。REST API 直接使用 rpa-core 的 Pydantic 模型并产生 OpenAPI；页面由同一个服务以 Jinja2 样板渲染。
  • 前端只用设计系统与少量 JavaScript。沿用 portal.css、shell.js 与设计变量；交互以小型、不需建置的 JavaScript 模块完成，不引入框架与 Node.js 构建流程。
  • 长任务不阻塞请求。运行交给背景 worker；页面以轮询或服务器推送事件读取进度。
  • 多语言。Jinja 样板的文字放在消息目录，与命令行共用同一套机制（ADR 0007）。
  • 保留调整空间。若之后的步骤编辑器确实需要框架，只在那一页引入，并另写 ADR。

后果

好处

  • 整个工程只有 Python，不必维护 TypeScript 与前端建置。
  • 页面与原型一致：同一套 CSS、同样的版面与组件。
  • API 与页面共用模型与校验，错误消息一致。

代价

  • 复杂的拖拽编辑要自己写 JavaScript；超过一定规模就要重新评估。
  • 服务器端渲染的页面要另外确保键盘操作与窄屏幕版面。

没有选的方案

方案为什么不选
Flask + Jinja（原型任务书）同样简单，但请求校验与 API 文档要另外置；FastAPI 直接使用 Pydantic 模型并产生 OpenAPI。
FastAPI + React（ADR 0004）交互最强，但 MVP 的页面用不到，却要多维护一套 TypeScript 与构建流程。
NiceGUI、Streamlit纯 Python，但无法沿用设计系统的版面与组件。
