ADR 0009：场景契约与独立断言

每个场景都有入参、出参与独立断言；「脚本没有抛错」不算成功，出参只在独立断言通过后发布。DSL 为主，Python 脚本是受控的逃生门。

已接受
日期
2026-10-10
影响范围
rpa-core（DSL）、rpa-runner（M2）、管理 Portal、录制与 AI 生成、编排
相关
ADR 0001、ADR 0010、场景 DSL、MVP 原型

背景

MVP 原型以真实的 Python / Playwright 示例验证了一套运行契约：入参在启动浏览器前以 JSON Schema 校验；自动化只负责操作页面并留下「页面事实」；另一个独立的断言比对事实与入参；全部通过后，出参才发布，并可以交给下一个场景。

M1 的 DSL 只有 params 与步骤内的 expect：成功等于「步骤都没失败」，没有出参，也无法串接场景。原型的流程与录制、AI 生成、编排都依赖这份契约。

决策

  • 场景契约。每个场景可以声明 inputs（入参）与 outputs（出参），类型与限制取 JSON Schema 2020-12 的常用子集，可以导出成 JSON Schema。params 改名为 inputs。
  • 页面事实。extract 的结果放在 facts；事实只描述页面上看到了什么，不代表成功。
  • 独立断言。verify 在自动化结束后比对 facts 与 inputs。有出参的场景一定要有 verify。
  • 出参最后才发布。入参校验 → 自动化 → 独立断言 → 出参校验，全部通过才产生 output.json；任何一步失败都没有成功出参。
  • 总期限。deadline 限制整次运行；每一步只能用剩下的时间。
  • DSL 为主，Python 脚本为逃生门。DSL 表达不了的场景可用 script 指定 automation.py 与 assertion.py，沿用原型的命令行契约；审核时特别标示，录制与 AI 不产生这种场景。

一次运行的顺序

M2 实现
阶段输入产出失败时
入参校验入参、inputs 声明input.json不启动浏览器
自动化steps 或 automation.pyfacts.json、截图、日志保留阶段、错误与能取得的截图
独立断言verify 或 assertion.py、facts、入参候选出参没有成功出参
出参校验与发布候选出参、outputs 声明output.json没有成功出参
每一阶段都受总期限限制；有副作用的动作（例如送出表单）不会因为超时自动重试。

后果

好处

  • 成功有证据：报告可以指出是哪一条断言、哪一个事实不符。
  • 场景可以串接：下游的入参绑定上游的出参，类型在运行前就能检查。
  • API、管理界面与 AI 用同一份入参、出参 Schema。
  • DSL 仍是默认，录制与 AI 的输出可以先校验；少数复杂场景有退路。

代价

  • 写场景时要多写 verify 与 outputs；只截图或查看的简单场景可以省略。
  • Python 脚本场景能做任何事，安全边界要靠审核、权限与运行隔离。
  • 运行引擎要支持两种场景，报告格式要一致。

没有选的方案

方案为什么不选
以 Python 脚本为主（照原型）最有弹性，但录制与 AI 的输出无法在运行前校验，网页上难以编辑，安全边界不清楚（ADR 0001 的理由仍然成立）。
只用 DSL最单纯，但 DSL 扩充前遇到复杂页面就没有退路。
只用步骤内的 expect 判定成功断言与操作混在一起，无法保证「发布的出参」真的被检查过，也不能独立重跑断言。
