测试报告指南

写给接入平台的第三方 Agent：依签核的测试方案运行项目里的组合场景、跟踪进度、处理失败与重跑，最后写出交给人验收的测试报告（单一 HTML 档，另附给 Agent 自己用的 JSON），并能从报告回溯到每一步的细节。

第一期已发布（v0.6.0）
测试报告是 Agent 的交付物，给人验收；平台不读取、不上传、不保存它。平台保存的是每次运行的记录（状态、步骤、断言、截图），报告用运行代号与 Portal 路径指向它们。测试方案与 TestCase 的写法见测试方案指南，API 的基本约定见 Agent 使用指南。本指南 2026-10-24 依用户的要求撰写，随 v0.6.0 发布。

运行前检查

  • 方案已签核：测试方案的状态是「已签核」；还没签核时先问人，不要直接正式运行。
  • 权限：GET /meta 的 scopes 有 projects:read、runs:read，以及要用的 runs:validate 或 runs:execute（自己发布组合场景要 projects:publish）；记下 limits.queuedRuns。
  • 组合场景与方案一致：GET /projects/{id} 列出的每个 TestCase 的组合场景 problems 是 0；要验证的版本是方案写的版本，正式运行时 publishedRevision 是方案写的版本。不一致时停下，请人决定要不要更新方案。
  • 角色已登录：GET /roles 里方案用到的角色是 logged_in；needs_login 或 none 时请人在录制端登录。
  • Worker 在线：GET /workers 至少一台在线；方案指定了 Worker 时是那一台。
  • 记下环境：开始时间、服务器代号与版本（/meta），写进报告。

运行

验证、发布、正式运行
目的调用跑哪个版本权限
验证（新写或刚改的 TestCase）POST /composites/{code}/revisions/{n}/validate；整批用 POST /projects/{id}/runs，"purpose": "validation"指定的版本；整批时是每个组合场景的最新版本runs:validate
发布POST /composites/{code}/revisions/{n}/publish验证通过、依赖完整的版本projects:publish；没有时请人在 Portal 发布
正式运行（回归）POST /composites/{code}/runs；整批用 POST /projects/{id}/runs，"purpose": "execution"发布的版本runs:execute

一份报告对应一轮运行。一轮用一个编号当幂等键，例如 TR-ORDER-2026-10-R1：

  • 只跑方案里的 TestCase：用 composites 列出代号；不给时是项目里全部没有封存的组合场景。
  • 没排进去的在 skipped：依 error.code 处理：workflow_unpublished 先验证、发布；limit_reached 等前面的结束；composite_scenes_forbidden、target_forbidden 请人调整权限。
  • 重送同一个请求：超时、断线或处理完 skipped 之后，用同一个幂等键再送一次：已经开始的回传原本那次运行，没排进去的这次才排入，不会重复运行。

  • 记下每个运行代号：它是报告回溯的起点。

GET /agent-api/v1/composite-runs?project=order-regression&mine=true&status=running
  • 频率：运行中的每 3～5 秒查一次；同时有好几个时用列表一次查，不要每个都高频查。长时间没有变化时逐步拉长到 30 秒。
  • 结束：finished 是 true 才算结束；status 是 passed、failed、timed_out、cancelled 或 needs_login。failedNode 是停下的节点；resumable 表示可以从那里继续。
  • 节点的状态：pending（还没轮到）、queued、running、passed、reused（接着运行时沿用上一次通过的结果）、failed、timed_out、cancelled、needs_login、skipped（前面停下而略过）。节点的 error 是没有开始的原因，例如绑定的值不符合入参规则。
  • 向人回报进度：每完成一个 TestCase 或每 5 分钟一次，例如「12 个 TestCase：完成 5（通过 4、失败 1），运行中 1，排队 6」。
  • 卡住：节点一直是 queued 时看 GET /workers：Worker 不在线或忙碌时告诉人，不要自己取消。要取消用 POST /composite-runs/{id}/cancel，只能取消自己触发的；目前的节点停止，后面的不运行。

失败、阻塞与重跑

状态意思Agent 该做什么
needs_login某个节点的登录角色要重新登录告诉人角色名称，请人在录制端登录；完成后 POST /composite-runs/{id}/rerun {"resume": true}，前面通过的节点沿用
failed节点的步骤或断言没有通过先取证（下一节）、判断原因，不要为了通过而直接重跑
timed_out节点超时取证；原因是环境慢时可以重跑一次并记录
cancelled被取消记录谁取消、为什么
  • 原因是环境（Worker 脱机、网络、目标系统暂时错误）：可以重跑一次；两次的结果与原因都写进报告。
  • 原因是产品缺陷：不要重跑到通过为止；记为失败并写缺陷。
  • 原因是场景或组合场景写错（定位器、断言、数据）：修正后存新版本、重新验证；报告记为「测试脚本问题」，TestCase 的结果以修正后的运行为准，并在「偏离方案」说明版本改了。
  • 从头或接着："resume": true 只在前面节点的结果仍然有效时用（例如人工登录之后）；修正的节点在停下的节点之前时，用 "resume": false 从头再跑。
  • 重跑带新的幂等键，例如 TR-ORDER-2026-10-R1/tc-order-003/2。还在运行时回 409 workflow_run_active；没有可以接着的节点时回 409 workflow_not_resumable，改用从头运行。

  • 失败与阻塞的 TestCase：整条链都存成证据档，放在 evidence/<TestCase 编号>/<运行代号>/：组合场景运行、每个节点的运行、步骤、result.json，有权限时加截图。
  • 通过的 TestCase：记运行代号、耗时、关键的出参即可；人要看细节时用 Portal 路径。
  • Portal 路径：portalPath 只是路径。人在服务器本机的 Portal（http://127.0.0.1:8080）或录制端 App 里打开；不要猜服务器的网址。
  • 敏感数据：Secret 的值平台一律显示为 ***，不要设法还原。截图与出参可能含业务数据，只放在交给人的报告文件夹，不另外转传。
  • 时间：API 的时间是 UTC；报告用 UTC，知道验收者的时区时另外标当地时间。服务器可能依保留设置清理旧的运行产物，结束后尽快下载证据。

TestCase 的结果

结果什么时候JSONXMind 标记
通过组合场景的运行是 passed（接着运行时含沿用的节点）passedsymbol-right
失败failed 或 timed_out，原因是产品或测试脚本failedsymbol-wrong
阻塞needs_login 没等到登录；原因是环境或平台、重跑后仍然不行；被取消blockedsymbol-pause
跳过人决定这一轮不跑skippedsymbol-minus
未运行没能开始：skipped 清单里的错误、权限不足、没有发布的版本not_run不加

一个 TestCase 在一轮里可能跑了好几次：结果以最后一次有效的运行为准，每一次都列在报告里。没跑的不能算通过。

测试报告的格式

一轮一个文件夹，名称用报告编号，例如 TR-ORDER-2026-10-R1/：

TR-ORDER-2026-10-R1/
  test-report.html      测试报告本身，给人用浏览器打开、验收
  test-report.json      同样内容的结构化数据，给 Agent 用
  test-report.xmind     （可选）测试方案的 XMind 加上结果标记
  evidence/             失败与阻塞的 TestCase 的完整证据，HTML 用相对路径连过来
    TC-ORDER-004/tc-order-004-20261024-081530-1a2b3c/
      composite-run.json
      reject/run.json  reject/steps.json  reject/result.json  reject/screenshot.png
test-report.html 的章节内容
文档信息报告编号、对应的方案编号与版本、轮次、状态（草稿、待验收、已验收）、产生的 Agent 与时间、服务器代号与版本、运行期间
1. 结论摘要建议（通过、有条件通过、不通过），逐条对照方案的退出准则；通过率；重大缺陷与阻塞；一段话写给验收者
2. 运行范围方案有几个 TestCase、运行了几个、没运行的与原因
3. 结果统计依结果、优先级、模块；总耗时
4. TestCase 明细编号、标题、优先级、结果、组合场景与版本、运行代号、运行次数、耗时、Portal 路径
5. 缺陷与问题编号、严重程度（严重、一般、轻微）、类别（产品缺陷、测试脚本问题、环境问题、测试数据问题、平台问题）、TestCase、节点与步骤、预期与实际、证据档、建议
6. 运行时间线开始、重跑、请人登录、取消、修正版本等事件，含时间与谁做的
7. 详细回溯每个失败与阻塞的 TestCase：组合场景运行 → 节点 → 运行 → 阶段 → 步骤 → 断言 → 证据档
8. 偏离方案改了哪些场景或组合场景的版本、增减了哪些 TestCase、为什么
9. 风险与遗留没测到的、只在特定环境验证过的、建议下一轮补的
10. 人工验收建议抽查的运行（全部失败与阻塞的、每个 P1、其他的抽一部分）及 Portal 路径；签核栏（验收者、日期、结论、意见）留空给人填

HTML 的写法

  • 单一文件、可以脱机打开：样式写在 <style> 里，不加载外部的字体、脚本或 CDN（验收的电脑可能在内网）；不需要 JavaScript 也能完整阅读，长的回溯用 <details> 折叠。
  • 整个文件夹一起交：截图与证据用相对路径连到 evidence/，例如 <img src="../../develop/evidence/…/screenshot.png">；人解压后直接打开 test-report.html。
  • 互相链接：每个 TestCase 一个锚点（id="TC-ORDER-004"），结论、明细、缺陷与回溯之间用 # 链接。
  • 跳脱：从 API 拿到的文字（错误消息、实际值、页面上的字）一律做 HTML 跳脱再放进页面；不要把运行的 report.html 或页面源代码整段嵌进来，要看时连到证据档。
  • 结果要有文字：通过、失败、阻塞要写出来，不能只靠颜色；打印时也看得清楚。
  • Portal：portalPath 写成文字；人给过 Portal 的网址时再做成链接。

结果的 XMind

拷贝测试方案的 XMind（写法见测试方案指南），在每个 TestCase 主题上：

  • 加上结果标记：symbol-right、symbol-wrong、symbol-pause、symbol-minus（见上方的表），未运行的不加。
  • 加一个标签「结果：通过」之类的文字：标记只是方便看，不认得标记的工具以标签为准。
  • 备注后面加上运行代号、Portal 路径；失败的加缺陷编号。
