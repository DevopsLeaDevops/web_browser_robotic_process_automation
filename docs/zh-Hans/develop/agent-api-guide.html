Agent 使用指南

写给接入平台的 Agent 系统（以及替它写集成的人）：怎么用 /agent-api/v1 从空白创建场景、在录制端调试、交给 Worker 验证、发布并正式运行，在项目里把场景组成组合场景并运行，遇到错误时怎么处理。

第一期实现中
本指南依 2026-10-23 确认的设计与第一期的实现撰写（2026-10-23，审阅中）；项目与组合场景 2026-10-24 加入。用 API 做测试时，测试方案与测试报告的写法见测试方案指南与测试报告指南。字段以服务器的 GET /agent-api/v1/openapi.json 为准；/agent-api/v1/docs 是可以直接试的交互式文档，两者都不需要密钥。

基本约定

地址
http://<服务器>:8081/agent-api/v1；服务器前有 HTTPS 反向代理时用代理的地址。
认证
每个请求带 Authorization: Bearer <API 密钥>。密钥由管理员在管理后台的「API 用户端」创建，只显示一次；不要写进日志或场景。
格式
JSON，字段 camelCase；时间是 ISO 8601（UTC）。
错误
{"error": {"code": "…", "message": "…", …}}。程序依 code 判断，message 给人看；有些错误另带细节，例如 issues、problems、latest。
语言
?lang=zh-Hant、zh-Hans 或 en 决定 message 的语言；没给时用服务器默认。
幂等
会创建东西的请求（创建场景、项目与组合场景，存版本，验证、运行、重跑）接受 idempotencyKey。超时或断线后用同一个值重送，回传的是上次的结果，不会重复创建或重复运行。验证、运行、重跑的幂等键记在运行记录里；创建与存版本的幂等键记在服务器的内存 24 小时，服务器重新启动后就忘了，这时重送会收到 scene_exists、project_exists、workflow_code_exists、stale_base 或 stale_workflow，读最新状态即可。不同用户端用同一个值互不影响。
轮询
查运行状态每 2～5 秒一次即可；第二期改用事件长轮询。

开始之前

先调用 GET /meta，确认这把密钥能做什么，缺的请管理员补，不要用试错的方式找出权限。

GET /agent-api/v1/meta

{
  "apiVersion": "1",
  "serverVersion": "0.6.0",
  "server": {"id": "srv-linux-01", "name": "Linux 服务器"},
  "client": {"id": "agent-erp", "name": "ERP 助理"},
  "scopes": ["scenes:read", "scenes:write", "debug", "runs:validate", "runs:read",
             "projects:read", "projects:write"],
  "pageContent": true,
  "limits": {"debugSessions": 2, "queuedRuns": 20},
  "domains": ["sales"],
  "projects": ["order-regression"],
  "recorders": ["agent-mac"],
  "target": null,
  "workers": null,
  "expiresAt": null,
  "dslFeatures": ["anyFrame", "dynamicValues", "frame", "page", "popup"]
}
  • scopes 没有 scenes:publish：做到验证通过为止，再请人在 Portal 发布。
  • pageContent 是 false：截图、页面结构、录像都拿不到，只能靠定位器测试与步骤结果写场景。
  • domains 是可以读写的领域、projects 是可以用的项目（null 不限）；recorders 是可以开调试的录制端；target、workers 是固定的运行位置与可以指定的 Worker（null 不限）。
  • 接着读 GET /dsl/schema（场景 YAML 的 JSON Schema）、GET /recorders（可用的录制端：是否在线、allowAgent、headlessOnly、capabilities 有没有 debugSnapshot）、GET /roles（登录角色与状态）、GET /secrets（只有名称）、GET /workers（可以指定的 Worker）。

场景长什么样

一个场景是一份 YAML（scenario.yaml）。步骤只负责操作页面、抽取「页面事实」；成功与否由 verify 独立判断，全部通过才发布出参。完整规格见场景 DSL。

schemaVersion: 1
id: order-create
name: 创建订单
category: 订单
inputs:
  customer: { type: string, minLength: 1 }
  quantity: { type: integer, minimum: 1, maximum: 99, default: 1 }
outputs:
  orderId: { type: string, pattern: '^SO-\d+$', from: '{{ facts.order.orderId }}' }
login: { role: sales }
browser:
  engine: chromium
  baseUrl: https://erp.example.internal
defaults:
  timeout: 10000
steps:
  - id: open
    action: goto
    url: /orders/new
  - id: fill-customer
    action: fill
    target: { label: 客户, exact: true }
    value: '{{ inputs.customer }}'
  - id: fill-quantity
    action: fill
    target: { label: 数量, exact: true }
    value: '{{ inputs.quantity }}'
  - id: submit
    action: click
    target: { role: button, name: 创建, exact: true }
  - id: read-order
    action: extract
    target: { css: '#order-summary' }
    as: order
    fields:
      orderId: { target: { testId: order-id } }
      customer: { target: { testId: order-customer } }
verify:
  - name: 取得订单编号
    value: '{{ facts.order.orderId }}'
    matches: '^SO-\d+$'
  - name: 客户与入参相同
    value: '{{ facts.order.customer }}'
    equals: '{{ inputs.customer }}'
  • 步骤 id 要稳定：调试换版本时，已运行的步骤靠 id 对应；改内容不要改 id。
  • 定位器的优先级：role＋name、label、text、testId，最后才是 css／xpath；容易变的加 fallback。元素在 iframe 里用 frame，点击开出新分页用 popup 与 page。
  • 会变的值写成入参：不要把客户、日期、数量写死在步骤里。
  • 密码不写进场景：用 secrets 声明名称、{{ secrets.名称 }} 引用；需要登录的系统用 login: { role }，登录状态由平台管理。
  • verify 要比较页面事实与入参：「步骤没有出错」不等于成功。

从空白到正式运行

1. 创建场景并存第一版

POST /agent-api/v1/scenes
{"id": "order-create", "name": "创建订单", "category": "订单", "domainId": "sales",
 "idempotencyKey": "order-create"}
→ 201 {"id": "order-create", "latestRevision": 1, …}

POST /agent-api/v1/scenes/order-create/revisions
{"baseRevision": 1, "files": {"scenario.yaml": "schemaVersion: 1\nid: order-create\n…"},
 "note": "只开页面", "idempotencyKey": "order-create-r2"}
→ 201 {"sceneId": "order-create", "number": 2, "status": "draft",
       "note": "Agent〈ERP 助理〉：只开页面", …}

创建场景时服务器会先存第 1 版（只有名称的模板），所以第一次保存的 baseRevision 是 1。没给 domainId 时场景放进「未分类」，密钥限定了领域时就要给。保存前可以先 POST /dsl/check {"yaml": "…", "sceneId": "order-create"}，回应的 ok 与 issues（行号、步骤、字段）和保存时的检查相同。这一版只放 goto（和需要的 login）就好，后面的步骤看了页面再写。

2. 在录制端开调试工作阶段

POST /agent-api/v1/scenes/order-create/debug
{"recorderId": "agent-mac", "revision": 2,
 "inputs": {"customer": "测试客户", "quantity": 2}}
→ 202 {"id": "a1b2c3d4e5f6", "status": "starting", "deviceId": "agent-mac",
       "headless": true, "clientId": "agent-erp", …}

GET /agent-api/v1/debug/a1b2c3d4e5f6
→ {"status": "ready", "nextIndex": 0, "steps": [{"index": 0, "id": "open", "status": "pending", …}], …}

等 status 变成 ready（第一次用 Firefox 可能要一两分钟）。默认无头；这把密钥只允许一台录制端时可以不给 recorderId。一个场景同时只有一个工作阶段：自己已经开了就回传原本那个（要换版本或入参重开时带 "restart": true），别人（人或其他 Agent）正在调试时回 409 debug_in_use。你只看得到、只能操作自己开的工作阶段（GET /debug 列出），闲置 15 分钟自动关闭。

3. 看页面，再写下一段步骤

POST /agent-api/v1/debug/a1b2c3d4e5f6/run-to/0
POST /agent-api/v1/debug/a1b2c3d4e5f6/snapshot
→ {"url": "https://erp.example.internal/orders/new", "title": "添加订单",
   "tabs": [{"page": null, "url": "…", "title": "添加订单", "active": true}],
   "frames": [],
   "fields": [{"tag": "input", "type": "text", "role": "textbox", "label": "客户",
               "name": "customer", "required": true, "disabled": false, "visible": true, "value": ""},
              {"tag": "input", "type": "number", "role": "spinbutton", "label": "数量", …}],
   "aria": "- heading \"添加订单\" [level=1]\n- textbox \"客户\"\n- spinbutton \"数量\"\n- button \"创建\"",
   "truncated": false}

POST /agent-api/v1/debug/a1b2c3d4e5f6/locate
{"locator": {"role": "button", "name": "创建", "exact": true}}
→ {"located": {"locator": "…", "ok": true, "count": 1,
               "matches": [{"tag": "button", "text": "创建"}], "error": null}, …}

locate 找到刚好 1 个才用它；0 个或好几个就换定位器。tabs 的 page 是步骤用 popup 开出、取了名字的分页（一开始的分页是 null）；frames 是 iframe，parent 指向上一层在清单里的位置。fields 列出目前页面的表单字段，密码字段与填了 Secret 的值一律是 ***。页面很大时 aria 会截断并标 truncated，用 {"within": {"css": "#main"}} 只看一部分（within 是定位器，iframe 里的用 frame）。需要看画面时用 screenshot，回应里的 screenshotUrl 可以下载图片。读页面结构与截图都要「回传页面内容」，录制端也要是新版 App。

4. 存新版本、换过去、接着跑

POST /agent-api/v1/scenes/order-create/revisions
{"baseRevision": 2, "files": {"scenario.yaml": "…加上 fill-customer、fill-quantity、submit…"}}
→ 201 {"number": 3, …}

POST /agent-api/v1/debug/a1b2c3d4e5f6/reload   {"revision": 3}
POST /agent-api/v1/debug/a1b2c3d4e5f6/run-to/3
→ {"steps": [… {"index": 3, "id": "submit", "status": "failed", "error": "…"}], …}

浏览器与已运行的步骤会保留，run-to 只运行还没运行过的步骤，失败就停。改好再存一版、reload、run-to，直到每一步都是 passed。想从头重跑用 reset。

录制端在另一台电脑时，reload 要服务器与录制端都是 0.6.3 以上：0.6.2 以前在录制端换版本一定回 422 revision_invalid「场景校验失败」（服务器把自己的文件路径交给录制端，录制端读不到）。服务器已更新、录制端还没更新时回 422 recorder_outdated；这时请人更新录制端，或改用 POST /scenes/{id}/debug 带新的 revision 与 "restart": true 重新开始（从第 1 步重跑，有副作用的步骤会再做一次）。

点击、填写、选择、勾选、按键是有副作用的步骤，会在目标系统上真的发生。运行过一次的有副作用步骤用 POST /debug/{sid}/steps/{index} 再运行时回 409 confirm_required，必须带 {"force": true}；只在确定重做不会造成重复数据时才这样做。run-to 的目标在下一个还没运行的步骤之前时回 409 already_executed。

5. 补齐入参、出参与独立断言

用 GET／PUT /scenes/{id}/sections/steps、verify、inputs、outputs 只读写一段（{"baseRevision": n, "text": "verify:\n - …"}），或 PUT /scenes/{id}/contract 以表格形式改入参与出参；每次都会存成新版本。已经有 Playwright（Python）脚本时，可以用 POST /scenes/{id}/import {"source": "…", "mode": "replace"} 转成 DSL，转不了的写在 warnings。完成后 DELETE /debug/{sid} 结束工作阶段，释放录制端。

6. 交给 Worker 验证

POST /agent-api/v1/scenes/order-create/revisions/6/validate
{"inputs": {"customer": "测试客户", "quantity": 2}, "idempotencyKey": "order-create-v6-1"}
→ 202 {"id": "order-create-20261023-…", "purpose": "validation", "status": "queued", …}

GET /agent-api/v1/runs/order-create-20261023-…
→ {"status": "running", "stage": "automation", …}
→ {"status": "failed", "error": "…", "finished": true, …}
GET /agent-api/v1/runs/order-create-20261023-…/steps

失败时看 error、result（结束后的完整结果：阶段、步骤、断言）、/steps 中第一个失败的步骤，以及（有「回传页面内容」时）files 列出的截图与 reportUrl；回到调试修正。验证可以用任何版本，正式运行只用已发布版本。可以带 workerId 指定 Worker（local 是服务器本机）或 target；密钥固定了运行位置时不能指定别的。第一期的 /steps 在运行结束后才完整，运行中请看 status 与 stage。

7. 发布与正式运行

POST /agent-api/v1/scenes/order-create/revisions/6/publish      （需要 scenes:publish）

POST /agent-api/v1/scenes/order-create/runs
{"inputs": {"customer": "王小明", "quantity": 3}, "idempotencyKey": "job-8812"}
→ 202 {"id": "…", "purpose": "execution", "status": "queued", …}
GET /agent-api/v1/runs/…
→ {"status": "passed", "output": {"orderId": "SO-10231"}, …}

只有 status 是 passed 时才有 output。没有发布权限时，告诉用户哪个场景的哪个版本已验证通过，请人在 Portal 发布。GET /runs?scene=…&status=…&purpose=…&mine=true 列出看得到的运行（可用领域里的场景，mine 只列自己触发的）；POST /runs/{id}/cancel 只能取消自己触发的。

项目与组合场景

项目空间里的项目收纳组合场景；组合场景把发布过的场景版本接成一个流程（DAG），前面节点的出参可以绑到后面节点的入参。用 API 做测试时，一个组合场景就是一个 TestCase，见测试方案指南。

端点用途权限范围
GET /projects、GET /projects/{id}可用的项目；项目与它的组合场景摘要projects:read
POST /projects、PATCH /projects/{id}添加项目（限定了可用项目的密钥不能添加）；改名称与说明projects:write
GET /composites/library可以放进组合场景的场景版本，与入参、出参、登录角色projects:read
POST /composites/check不保存检查定义，回传 problems（节点、入参）projects:read
GET /composites?project=、GET /composites/{code}组合场景摘要；完整的定义、问题、版本、验证记录、依赖、最近的运行projects:read
POST /projects/{id}/composites在项目里创建组合场景（带定义时就是第 1 版）projects:write
PUT /composites/{code}、PATCH /composites/{code}存新版本（带 baseRevision）；移到另一个项目projects:write
POST /composites/{code}/revisions/{n}/validate交给 Worker 验证这个版本runs:validate
POST /composites/{code}/revisions/{n}/publish发布验证通过、依赖完整的版本projects:publish（默认不给）
POST /composites/{code}/runs正式运行发布的版本runs:execute
POST /projects/{id}/runs把项目里的组合场景（或 composites 列出的）逐一排入；排不进去的在 skipped依 purpose：runs:validate 或 runs:execute
GET /composite-runs、GET /composite-runs/{id}组合场景的运行：状态、进度（progress）、每个节点的状态与那次运行runs:read
GET /composite-runs/{id}/report汇总报告：结论（failure：停在哪个节点、哪一步、错误、没通过的断言）、counts、timeline、每个节点的入参出参、步骤与断言；写测试报告时用它，附上 portalPath 让人在 Portal 看同一份runs:read
POST /composite-runs/{id}/cancel、/rerun取消自己触发的；从头或从停下的节点（"resume": true）再运行依运行的目的
  • 看得到哪些：组合场景要在可用的项目里，放的领域也要可用；不属于任何项目的组合场景不给 Agent。看不到的一律回 404。节点用到的场景要在可用的领域，否则 403 composite_scenes_forbidden。
  • 没有运行时的入参：入参在定义里绑定（固定值、动态值、上游的出参）；同一个流程换一组数据就是另一个组合场景。
  • 节点的细节：每个节点的 run 是一次普通的运行，步骤、断言与产物用 /runs/{id}、/runs/{id}/steps 读；节点不能单独重跑（409 rerun_workflow），要重跑组合场景的运行。
  • Portal 路径：回应带 portalPath（例如 /playground/runs/…），人在 Portal 看同一笔数据用；写测试报告时附上。
  • 限额：组合场景的节点也算进「排队中与运行中」的限额。

错误怎么处理

状态码code意思Agent 该做什么
401unauthorized密钥缺少、错误、禁用、到期，或不能从这个地址使用停止，请管理员处理；不要重试
403scope_missing这把密钥没有需要的权限范围（scopes 列出缺哪个）请人授权或改由人完成这一步
403content_disabled「回传页面内容」没开改用 locate 与步骤结果；或请管理员打开
403domain_forbidden、recorder_forbidden不能用这个领域或录制端换一个允许的，或请管理员加上
403recorder_agent_off录制端没有打开「允许 Agent 调试」或已禁用请人在设备页打开，或换一台
403recorder_headless_only这台录制端只允许无头不要带 "headless": false
403target_forbidden、worker_forbidden这把密钥固定了运行位置，或不能指定这台 Worker不要指定，或换允许的
403run_forbidden想取消别人触发的运行请人处理
403project_forbidden、project_create_forbidden不能用这个项目；限定了可用项目的密钥不能添加项目用允许的项目，或请管理员处理
403composite_scenes_forbidden组合场景的节点用到不可用领域的场景（scenes 列出哪些）换场景，或请管理员加上领域
404debug_not_found、run_not_found、project_not_found、workflow_not_found、workflow_run_not_found 等找不到，或不是你看得到的确认代号
409stale_basebaseRevision 不是最新版，有人改过读 latest 那一版，把修改套上去再存
409scene_exists场景代号已经有了换代号，或读现有的场景
409debug_in_use这个场景有别人正在调试稍后再试，不要抢
409debug_busy、debug_starting上一个命令还在跑，或浏览器还在启动等它完成再送下一个命令
409debug_closed工作阶段已经结束（闲置、出错或被关掉）重新开始调试
409confirm_required有副作用的步骤已运行过确定可以重做才带 force；否则 reset
409already_executedrun-to 的目标已经运行过用单步运行或 reset
409recorder_offline录制端不在线换一台，或请人打开录制端 App
409not_validated、content_changed这个版本没有验证通过的记录，或内容和验证时不同先验证
409not_published场景没有已发布版本，不能正式运行发布，或请人发布
409rerun_workflow组合场景的节点不能单独重跑重跑组合场景的运行：POST /composite-runs/{id}/rerun
409stale_workflow组合场景的 baseRevision 不是最新版读 latest 那一版，把修改套上去再存
409project_exists、workflow_code_exists项目或组合场景的代号已经有了换代号，或读现有的
409workflow_unpublished组合场景没有发布的版本，不能正式运行先验证、发布，或请人发布
409workflow_invalid、workflow_not_validated、workflow_dependencies定义有问题不能运行；这个版本没有验证通过的记录；依赖不完整（problems）不能发布依 problems 修正、先验证
409workflow_run_active、workflow_not_resumable组合场景的运行还没结束；没有可以接着的节点等它结束；改用从头运行
422request_invalid请求的格式不对，problems 列出字段依 problems 修正
422recorder_required这把密钥允许好几台录制端，没给 recorderId带上 recorderId
422recorder_outdated录制端 App 太旧（例如不支持读页面结构、调试时换版本，或看不懂场景用到的写法）请人更新 RPA 录制端
422display_unavailable那台没有画面，不能有头改用 "headless": true
422revision_invalidYAML 校验失败，issues 列出位置（存版本时，或 reload 时录制端校验不过）依 issues 修正后再存
422inputs_invalid入参不符合类型或限制，problems 列出哪一个修正入参
422worker_target_mismatch指定的 Worker 和运行位置不一致只给其中一个
429limit_reached超过同时调试或排队、运行中的限额（limit）等现有的完成，或结束不用的工作阶段

运行本身的结果不是 HTTP 错误：failed、timed_out、cancelled、needs_login 都在 GET /runs/{id} 的 status。

需要人的时候

  • 需要登录：运行停在 needs_login，或 GET /roles 显示角色要重新登录。请用户在录制端做人工登录，完成后调用 POST /runs/{id}/rerun。
  • 没有发布权限：告诉用户场景或组合场景的代号与验证通过的版本号，请人在 Portal 发布。
  • 缺 Secret：GET /scenes/{id} 的 needs 列出还没设置的 Secrets；值由人在 Portal 填，Agent 不能写入也读不到。
  • 录制端不在线或太旧：请人打开或更新 RPA 录制端 App。

守则

  • 每次存版本（场景与组合场景）都带上次读到的 baseRevision，不要覆盖人的修改。
  • 用完调试工作阶段就 DELETE，不要占住录制端。
  • 不要在正式数据上反复运行有副作用的步骤；能用测试账号的角色就用。
  • 截图、页面结构与出参可能含业务数据，只用在当前的任务，不要另外保存或转传。
  • 所有写入都会记在审核记录，版本说明会标出你的用户端名称；在 note 写清楚这一版改了什么。
