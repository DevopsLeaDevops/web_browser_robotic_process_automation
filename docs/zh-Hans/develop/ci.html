CI 与流水线

GitHub Actions 什么时候跑、跑哪些测试、大约多久；怎么手动触发，以及到哪里看历次的运行耗时。平常的 PR 只在每个系统上测它在生产环境的角色，其他组合交给每天凌晨的完整测试；同一组输入只验证一次，外壳没变的桌面 App 不重新打包。

依层建置：同一组输入只验证一次

2026-10-27 起

ADR 0018 把安装包拆成外壳（Python、第三方包、PyInstaller 收进去的一切、rpa_update）与代码层（七个工作区包）。CI 照同一条线拆：

  • 同一组输入已经通过就不重跑。每个重的工作（三个桌面 App、服务器分发包、一键安装脚本、CI 的 Windows Worker 测试）有自己的输入清单；这些文件的内容算成输入指纹，同一个指纹已经在这个仓库通过，就略过、沿用那次的结果。只改服务器的 PR 不碰 macOS；合并到 main 时内容和 PR 测过的相同，也不再跑一次。
  • 版本号不算改动。pyproject.toml 的 version 与 uv.lock 里工作区包的版本不算进指纹：发布 PR 只改版本号，不必重建三个 App、四个安装脚本与 Windows 测试。
  • 外壳没变就不重新打包。桌面 App 要跑时，先看外壳键：外壳和缓存里的相同，就从缓存取出上次建好的 DMG／zip，用这次的程序建更新档、装上去再测（代码层路径）。这正是设备在现场升级的方式：旧外壳加新程序。外壳变了才完整建置。
  • macOS 只在需要时排队。录制端（macOS）只在录制、逐步调试、本机闸道、macOS 专属的程序或外壳改了时跑；Worker（macOS）只在外壳或它的 macOS 部分改了时跑。一般的程序改动由每晚的 macOS 代码层检查补上，最晚隔天看得到；发布一律完整建置。
推送／PR → 运行范围（Linux，几秒；tools/ci_changes.py）：每个重的工作算输入指纹
  ├─ 这个指纹已经有通过记录 → 略过，注记沿用哪一次（macOS 不必排队）
  └─ 要跑 → 桌面 App 再看外壳键在不在缓存里
        ├─ 在 → 代码层路径：取出缓存的 DMG／zip → 用这次的程序建更新档、装上
        │        → 自我测试、窗口自我测试、端到端（不跑 PyInstaller、不下载浏览器）
        └─ 不在 → 完整建置（PyInstaller、DMG、安装档、升级与退回）→ 成功后存进缓存
发布（v* 标签）、每周六的完整建置：一律完整建置，不沿用
输入指纹
一个工作的输入文件（路径与内容）加上工作名称的 SHA-256 前 16 个字符。清单在 tools/ci_changes.py 的 GROUPS，每个工作都包含依赖（版本号不算）、自己的 workflow 档与 tools/ci_changes.py 本身。
通过记录
工作成功时上传的小产物 pass-<工作>-<指纹>，保留 30 天。只认这个仓库自己的运行，fork 的 PR 不能替别人声明通过。
外壳键
外壳的输入（依赖、.python-version、packages/rpa_update/src、apps/desktop/packaging、tools/build_desktop.py；RPA Worker 另加它附带的 RPA Python 运行环境：runtimes/python/、tools/build_python_runtime.py）加上目标的哈希。缓存键是 desktop-shell-v1-<目标>-<外壳键>-<CI 密钥代号>，内容是 DMG 或 zip、runtime.json 与下载好的浏览器。
代码层路径
从缓存取出 App（tools/desktop_shell.py restore），用这次的程序建更新档（tools/build_update.py，CI 密钥签章），装进 App 的文件夹；自我测试、窗口自我测试、端到端都用这一层，跑完确认这一层已经确认、没有被退回。不建安装档，也不上传试用包。
完整建置路径
原本的全部步骤，外加「下一个提交」的更新与自动退回。成功时把 DMG 或 zip 存进缓存（推版本标签时不存）。
工作改了这些才跑（另加依赖、workflow 与 ci_changes.py）说明
RPA 录制端（macOS）外壳；录制端的程序（recorder_*、本机闸道、交互子进程、配对、debug.py、record.py、commands.py）；两个 App 共用、有系统分支的程序（入口、自我测试、更新、下载浏览器、钥匙串）；macos.py；Client API 与设备更新端点；测试网站与示例；端到端窄的范围（2026-10-27 决定）：其他代码的改动交给 Linux 的 role_recorder 测试、Windows 的代码层测试与每晚的 macOS 检查
RPA Worker（Windows）外壳；它会运行的全部代码（rpa_core、rpa_runner、rpa_worker、rpa_desktop 的源代码、测试网站）；Worker API、Client API、设备管理与更新端点；示例；建置前的单元测试生产角色：代码一改就跑（大多走代码层路径）
RPA Worker（macOS）外壳；菜单栏、LaunchAgent、钥匙串、窗口（macos.py、autostart.py、credentials.py、gui.py）；建置前的单元测试不是生产角色；每晚的 macOS 检查也跑它
服务器分发包（x64、arm64）原本的路径：服务器、命令行、Worker、测试网站与包的源代码、示例、建置工具；RPA Python 运行环境（分发包附带一份）Linux，约 2 分；在 Rocky 8 另外运行示例 Python 节点
RPA Python 运行环境（Linux x64、arm64、Windows、macOS）runtimes/python/、tools/build_python_runtime.py、rpa_script、rpa_runner、rpa_core 的源代码与 Python 节点的测试（2026-10-29 起，ADR 0020）每个平台建一份、跑自我测试、解压到缓存，再用它跑 Python 节点的测试；Linux 另在 Rocky 8 容器解压、自我测试
一键安装脚本（Rocky 8 两种、三个系统的项目内运行）原本的路径：脚本、依赖、Python 版本、相关工具与测试调度时照常跑完整范围
CI 的 Worker 测试（Windows）原本的 Worker 路径（packages/、apps/worker、apps/cli、apps/testsite、apps/desktop、scenarios/ 等）CI 的 Linux 测试每次照跑

一律运行、不沿用的时候

调度（每晚完整测试、一键安装脚本、每周六的桌面完整建置）、手动触发、推版本标签。这些照样留下通过记录（完整范围涵盖一般范围）。通过记录过期（30 天）或被「清理产物」删掉时，同一组输入再验证一次。

怎么用

  • 看这次跑了什么：每个流程的「运行范围」工作在运行摘要写一张表：每个工作的指纹、外壳键、运行还是沿用哪一次（连到那次运行）；同样的内容也写成注记。桌面端建置每个 App 的摘要第一行写「代码层路径」或「完整建置」，以及外壳来自哪一版。
  • 要试用包（DMG、安装档）：代码层路径不产生新的安装包。手动触发桌面端建置，默认就是完整建置：gh workflow run desktop.yml --ref 分支 -f build=full，只要其中一个 App 时加 -f targets=recorder-macos-arm64。
  • 不想沿用、重新验证一次：手动触发那个流程（手动触发一律运行）。
  • 改了 desktop.yml 的建置步骤：把 tools/ci_changes.py 的 SHELL_EPOCH 加 1，缓存的外壳全部重建一次。改了指纹的算法或输入的写法时，把 EPOCH 加 1，所有通过记录失效。
  • 添加文件：放在已登记的文件夹下就自动算进去。新的 macOS 专属模块要加到 RECORDER 或 WORKER_MACOS；tests/ci/test_ci_changes.py 会检查每个模式都还对得到文件（改名不会悄悄失效），以及桌面 App 的源代码都在 Windows Worker 的输入里。
  • 本机看指纹：python3 tools/ci_changes.py --workflow desktop.yml --show（另有 server-package.yml、setup-scripts.yml、ci.yml、python-runtime.yml）。

代码层路径失败时

  • 「装不上更新档」：签章或环境代号不符。看「测试更新档用的密钥」步骤用的是不是 RPA_UPDATE_CI_KEY，以及 runtime.json 的目标。
  • 「提交不是…」或「active.json 用的是内置的程序」：启动器没有用这一层，看 App 文件夹的 app/boot.log。
  • 新程序导入不到某个第三方模块：这正是设备升级后会遇到的问题，外壳没有收进那个模块。把它加进 apps/desktop/packaging/rpa_desktop.spec 的 FULL_PACKAGES 之类的清单：外壳键改变，这次完整建置，发布时这一版要用完整的安装包。

依角色分配测试

短期的主要运行路径（2026-10-19 确认，见部署与操作）：Linux 只跑网站，macOS 只跑录制端，Windows 只跑 Worker。三条路径都用 Python 3.13；一键安装脚本装的是开发环境，不在主要路径上。

系统生产角色PR 与合并到 main 时跑什么只在完整测试跑
Linux网站（管理 Portal）静态检查；全部不需浏览器的测试；网站、录制端协定的浏览器测试与冒烟测试，只用 Chromium（CI，4 个进程平行）Firefox 的组合；Worker 的浏览器测试
WindowsWorkerWorker 的浏览器测试（运行、登录、Firefox 模板、领取任务）与冒烟测试，两种浏览器；Worker App 的端到端（外壳没变时只换代码层，见依层建置）网站、录制端的浏览器测试
macOS录制端录制端 App 的端到端（配对、本机闸道、逐步调试）：只在录制、调试、闸道、macOS 专属的程序或外壳改了时全部 pytest；每晚的 macOS 代码层检查

测试依文件路径自动加上 role_server、role_worker、role_recorder，用 Firefox 的参数组合加上 firefox（tools/ci_roles.py、根目录的 conftest.py）。添加浏览器测试的文件时，在 tools/ci_roles.py 的 ROLES 登记它属于哪个角色；没有角色的浏览器测试会让 tests/ci/test_ci_roles.py 失败。Python 3.12 维持原状：PR 上只跑不需浏览器的测试，合并到 main 时跑全部；跑全部时和每晚完整测试一样在 xvfb-run 底下，有头模式的录像测试才有屏幕（2026-10-28）。

触发节点与时间

节点跑哪些流程大约多久
往 PR 推送、合并到 mainCI（Linux）每次都跑；其他重的工作只在它的输入指纹还没通过时跑（依层建置）：Windows 的 Worker 测试、三个桌面 App（外壳没变时只换代码层）、服务器分发包（建置 x64、arm64，在 Rocky 8 容器里安装、启动、升级）、一键安装脚本（只验证脚本与冒烟测试）约 2.5～3 分（CI 是下限）；要建桌面 App 时约 4 分
只改 handoff/、docs/ 的推送见下一节约 1 分
推版本标签 v*发布：确认版本、建桌面 App 与服务器分发包、产生并签署更新档（密钥）、草稿 Release约 4 分
每天 20:17 UTC每晚完整测试：三个系统、两种浏览器、Python 3.12 与 3.13 的全部测试，浏览器测试连跑三遍约 30 分
每天 20:17 UTC（同上）macOS 代码层检查：每晚完整测试调用桌面端建置，两个 macOS App 走代码层路径（外壳不在缓存里时完整建置）约 3 分
每天 20:47 UTC一键安装脚本的完整范围：项目内运行跑全部测试，加上从零开始约 15 分
每周六 22:47 UTC桌面 App 每周完整建置：三个 App 完整建置（不用缓存、不沿用），抓 GitHub 映像的变化；由每晚完整测试的流程运行，失败时开在同一个 issue约 5 分
每周日 22:17 UTCPython 依赖更新：有更新时开 PR 并触发 CI不到 1 分；CI 另计

调度放在仓库最空闲的时段：20:17 UTC 是 America/Los_Angeles 13:17 PDT（UTC−07:00）／12:17 PST（UTC−08:00），新加坡 04:17。调度失败时自动开（或更新）一个 ci-schedule 标签的 issue；一直排不到机器而被取消的工作（注记写「The job was not acquired by Runner」，macOS 较常见）也算，留言会注明那个系统这次没有测、不是测试失败，可以在运行页按「Re-run failed jobs」补跑（2026-10-29 起；之前这种情况不开 issue，整个运行是红的却没有通知）。PR 上比的是合并后的内容（GitHub 测的是 PR 合并进 main 的结果）；同一个分支推了新版本，旧的运行会被取消。依赖更新的 PR 由 GitHub Actions 开，只自动触发 CI，其他流程要等有人往那个分支推送。CI 的 Linux 测试与 Windows 的 Worker 测试各最多跑 30 分钟，卡住时直接失败（2026-10-21 起；之前没有上限，Windows 上卡住的运行会一直跑到 GitHub 的 6 小时上限）。

Windows 的每晚完整测试开跑前，把动态连接端口从默认的 49152～65535（16384 个）放大到 10000～65535：连接关闭后还要等 TIME_WAIT 才放回去，连跑三遍时本机网站、管理 Portal 与浏览器之间的短连接可能把它用完，Chromium 回报 net::ERR_NO_BUFFER_SPACE（2026-10-27 第 3 遍，issue #99）。测试与产品的固定连接端口（8080 起的管理 Portal、测试网站）都在 10000 以下，不受影响。每一遍结束时另外注记 TCP 连接依状态的数量与还在跑的 Chromium、Firefox、Node 进程，再遇到时分得出是连接端口用完还是进程没有结束（2026-10-29 起）。

只改文档的推送

CI 的 Linux 测试：每个流程的第一个工作「运行范围」（tools/ci_changes.py）比较这次推送和上一次推送，只改了 handoff/、docs/ 或 *.md，而且上一次推送在同一个流程的运行已经通过时，只跑静态检查与不需浏览器的测试（含文档与翻译的检查），浏览器测试沿用那次的结果，注记里写明是哪一次。上一次的运行失败、取消或还没跑完时照常运行。

其他重的工作不必另外判断：文档不在任何一个的输入里，指纹和上一次相同，自然沿用（依层建置）。协作规则见共用协作流程的第 5 节。

手动触发

在 GitHub 的 Actions 页面选流程，按「Run workflow」，选分支与选项。也可以用 gh：

# 大全量：三个系统的全部测试，浏览器测试再跑两遍（约 30 分）
gh workflow run nightly.yml --ref 分支名称
# 只跑 Windows，不重跑
gh workflow run nightly.yml --ref 分支名称 -f systems=windows -f extra=0
# CI：role＝同 PR；full＝Linux 跑全部测试
gh workflow run ci.yml --ref 分支名称 -f scope=full
# 一键安装脚本：full（默认）＝全部测试加从零开始；role＝同 PR
gh workflow run setup-scripts.yml --ref 分支名称
# 桌面端建置：手动触发一律运行；默认完整建置（产生试用包）
gh workflow run desktop.yml --ref 分支名称
# 只建录制端，外壳在缓存里就只换代码层（不产生试用包）
gh workflow run desktop.yml --ref 分支名称 -f targets=recorder-macos-arm64 -f build=auto
# 服务器分发包（Linux x64、arm64）
gh workflow run server-package.yml --ref 分支名称
# RPA Python 运行环境（四个平台建置、自我测试、Python 节点的测试）
gh workflow run python-runtime.yml --ref 分支名称

本机照角色跑：uv run pytest -m "browser and (role_worker or smoke)"（Worker）、uv run pytest -m "not browser or ((smoke or role_server or role_recorder) and not firefox)"（同 CI 的 Linux）。

产物与保存额度

仓库自 2026-10-22 起是私有的，Actions 的产物计入账号方案的保存额度；额度用完时上传产物会失败，发布也建不出草稿 Release（v0.5.0 就是这样）。所以桌面端建置与服务器分发包的产物在 PR 与 main 上留 3 天、发布时留 1 天，发布流程建好草稿后删掉那次运行的产物；测试报告与 Portal 轨迹只是诊断用，上传失败不让工作失败。

依层建置另外留下两种东西：通过记录（产物 pass-*，每个不到 1 KB，留 30 天）与外壳缓存（Actions 的缓存，不计入产物额度；每个仓库上限 10 GB，7 天没用到就被清掉，清掉之后下一次完整建置再存）。

要一次释放额度时，手动运行「清理产物」（cleanup-artifacts.yml）：默认只列出，摘要里依名称统计个数与大小；确认后取消勾选「只列出、不删」再运行一次。删除不能复原；正式版的文件在 Releases 上，不受影响；删掉 pass-* 只会让那些输入再验证一次。删完要等 GitHub 重新计算用量，额度才会降下来。

# 只列出全部产物
gh workflow run cleanup-artifacts.yml
# 删掉 3 天以前创建的产物
gh workflow run cleanup-artifacts.yml -f older-than-days=3 -f dry-run=false

更新档的签署密钥

ADR 0018

发布时产生的 RPA-Update-<版本>.zip 用 Ed25519 私钥签章；服务器、设备与桌面 App 的启动器用安装包里的公钥验证，验证不过就不用。私钥只放在 GitHub Secrets 的 RPA_UPDATE_SIGNING_KEY，不进仓库、不贴到对话或 issue；公钥写在 packages/rpa_update/src/rpa_update/keys.py 的 RELEASE_KEYS，随完整的安装包发布。RELEASE_KEYS 是空的、Secret 没设、或两者对不上时，发布流程会失败，不会发出设备验证不了的版本。PR 与 main 上的建置用 CI 的测试密钥（下面），不碰正式密钥。

第一次产生

  1. 在一台有 OpenSSL 1.1.1 以上的电脑产生私钥，并印出公钥（一行 base64）。用 openssl version 查看版本：CentOS 7 的 1.0.2 与 macOS 内置的 LibreSSL 没有 Ed25519，会显示 Algorithm ed25519 not found，请换一台电脑或改用下面项目的工具。
openssl genpkey -algorithm ed25519 -out rpa-update-signing.pem
openssl pkey -in rpa-update-signing.pem -pubout -outform DER | tail -c 32 | base64
  1. 到仓库的 Settings › Secrets and variables › Actions › New repository secret，名称填 RPA_UPDATE_SIGNING_KEY，值粘贴 rpa-update-signing.pem 的全部内容（含 -----BEGIN PRIVATE KEY----- 与 -----END PRIVATE KEY----- 两行）。
  2. 把公钥加进 RELEASE_KEYS，用 PR 合并。公钥可以公开。
  3. 私钥档另外备份到只有自己拿得到的地方（例如密码管理器），再从那台电脑删掉。遗失私钥之后的版本签不了，设备要重新安装带新公钥的完整安装包；外泄时也一样要换。

也可以用项目的工具产生：uv run python -m rpa_update.build keygen --private rpa-update-signing.pem，印出的就是公钥；格式和 OpenSSL 相同。

换密钥

先把新的公钥加进 RELEASE_KEYS（旧的留着），发一版完整的安装包；等服务器与设备都换上这一版，再把 Secret 换成新的私钥，最后拿掉旧的公钥。RELEASE_KEYS 改变会改变环境代号，所以这两版都要用完整的安装包安装。

CI 的测试密钥（RPA_UPDATE_CI_KEY）

另一把 Ed25519 私钥，只给 CI 测试用。PR、main 与调度建的桌面 App（试用包）信任它；发布的安装包不信任（发布流程的 --release 会核对）。代码层路径要用它：缓存里的外壳是之前建的，它信任的密钥在之后的运行也要拿得到，才签得出它认得的更新档。没有这个 Secret 时，桌面端建置照旧每次产生临时密钥、一律完整建置，「测试更新档用的密钥」步骤会留下警告。fork 与 Dependabot 的 PR 拿不到 Secrets，也是这样。

查有没有设置：仓库的 Settings › Secrets and variables › Actions，Repository secrets 列表里有没有 RPA_UPDATE_CI_KEY（只看得到名称与更新时间，值看不到）；或在有权限的电脑运行 gh secret list。设置之后跑一次桌面端建置，「测试更新档用的密钥」步骤的注记写「测试更新档的密钥 <代号>（RPA_UPDATE_CI_KEY）」就是读到了。

产生并设置（和发布密钥不同，不要共用；公钥不必写进仓库）：

uv run python -m rpa_update.build keygen --private rpa-update-ci.pem
gh secret set RPA_UPDATE_CI_KEY < rpa-update-ci.pem   # 或贴到网页上的 New repository secret
rm rpa-update-ci.pem

换这把密钥不必通知任何人：换掉 Secret 之后，缓存键里的密钥代号不同，第一次建置会完整建置并存一份新的缓存。外泄时影响的只有 CI 的试用包（拿到私钥的人签得出试用包接受的更新档），正式安装包不受影响；重新产生、换掉 Secret 即可。

运行耗时记录

每次 CI、桌面端建置、服务器分发包、一键安装脚本、每晚完整测试、发布结束后，「运行耗时记录」流程（tools/ci_metrics.py）把结果追加到仓库的 ci-metrics 分支，不碰 main，也不触发其他流程。在 GitHub 切到 ci-metrics 分支就看得到总览 README.md：各流程近 7 天与前 7 天的比较、每天各系统的机器时间、最慢的测试文件、最近的运行。

data/runs.jsonl
每次运行（重跑各一行）：触发方式、分支、结果、耗时（含排队）、最长排队、各系统的机器时间
data/jobs.jsonl
每个工作的排队与运行时间
data/test-files.jsonl
CI 与每晚完整测试的 JUnit 报告里，每个测试文件的时间

补记历史：手动触发「运行耗时记录」，since 填 UTC 日期，例如 2026-10-09；已经记过的不会重复。每次测试的 annotations 也有一则「pytest 耗时」，列出最慢的文件与测试。
