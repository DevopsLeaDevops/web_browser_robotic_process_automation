产品定位

要解决什么问题，以及整个平台围绕的核心概念。

要解决的问题

  • 重复的人工操作。每天在内部系统登录、填表、查询、导出报表，耗人力又容易出错。
  • 脚本只有开发者能写。自动化脚本散落在个人电脑，难以共用，也没人知道哪个版本是对的。
  • 页面一改就坏。选择器失效后很难看出坏在哪一步、为什么坏。
  • 团队共用缺少治理。没有权限、审核与凭证管理，账号密码常常直接写在脚本里。

不在范围内

  • 桌面应用程序自动化：只处理浏览器内的操作。
  • 破解验证码或绕过目标系统的安全机制。
  • 大规模网页爬取。
  • 取代测试框架：可以做检查，但定位是业务流程自动化。

生成 → 管理 → 运行 → 反馈

平台的主循环

1　生成

  • 录制用户操作
  • 用自然语言让 AI 产生
  • 由模板或子场景组合

2　管理

  • 版本与发布门槛
  • 入参、出参与分类
  • 权限与审核

3　运行

  • 手动、调度或 API 触发
  • 交给远程 Worker，多台同时运行
  • 重试与超时控制

4　反馈

  • 每一步的截图与日志
  • 运行录像回看，视频和步骤对上（M12）
  • 失败定位与选择器自愈

内核概念

场景 Scenario
一段可重复运行的浏览器操作流程，以声明式 DSL 描述（少数情况用 Python 脚本，见 ADR 0009）。平台的核心资产，有稳定的 id 与分类。
版本 Revision
场景的一个不可变版本：草稿 → 验证中 → 通过或失败 → 已发布。修改后要重新验证，发布的版本必须就是验证通过的版本。
步骤 Step
场景中的一个动作，例如打开网址、点击、填写、抽取数据。每个步骤有稳定的 id。
定位器 Target
描述「要操作页面上的哪个元素」，可以有多个候选，依优先级尝试。
入参 Input
运行时才给定的值，例如查询月份；有类型、限制与默认值，启动浏览器前校验。
页面事实 Fact
运行中从页面抽取的值，只描述看到了什么，不代表成功。
独立断言 Verify
自动化结束后，比较页面事实与入参的规则。「脚本没有出错」不等于成功。
出参 Output
独立断言通过后才发布的结果，可以串到下一个场景的入参。
Secret
账号密码等机密，场景只引用名称，明文不会出现在场景、日志或截图说明中。
运行 Run
某个版本的一次运行，记录触发者、入参、每一步的结果与耗时；状态为排队、运行中、通过、失败、超时、已取消或需要登录。
产物 Artifact
运行产生的截图、录像、报告、日志、下载文件与抽取的数据，存在服务器的运行目录。
组合场景 Composite
把已发布场景的固定版本排成 DAG（可分叉、可汇合），上游的出参绑到下游的入参，依序运行、失败就停止（M6，原称编排）；本身也有版本、验证与发布，可以依赖其他领域的场景（M11）。
领域 Domain
场景、角色与组合场景的归属与存放单位：一个领域一个文件夹，保存不可变版本与验证、发布记录，可以和 git 仓库的一个目录同步（M11）。
角色 Role
目标系统的一个登录身分；每个角色一份登录状态，场景以 login: { role } 声明要用哪个角色，失效时运行停在「需要登录」（M4）。
设备 Device
用邀请配对的录制端或 Worker：录制端让浏览器开在录制者的电脑，Worker 运行场景（M10）。
调试工作阶段 Debug session
录制稿或草稿在隔离的浏览器中逐步调试，浏览器开在操作的那台录制端（M4、M10.2）；AI 助手只能修改草稿，发布要用户确认（M5）。
项目 Project
权限隔离的单位。场景、Secrets、运行记录都属于某个项目（M8；MVP 是单用户）。
