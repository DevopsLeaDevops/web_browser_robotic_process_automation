多用户与内部系统

团队共用与内部系统这两个前提，对设计提出的具体要求。

多用户

主要在 M7 实现
认证
先做本地账号；预留 OIDC 与 LDAP 接口，方便接公司的 AD 或 SSO。
权限
以「项目」为单位隔离场景、Secrets 与运行记录。
Secrets
加密存放。用户可以在场景中引用，但无法读出明文。
审核
谁在什么时间修改、运行了哪个场景，全部留记录，不可删改。
版本
场景每次保存产生不可变的新版本；运行记录指向确切版本。
数据库
正式环境用 PostgreSQL，支持多个 worker 与并发写入；SQLite 只用于开发与原型（单机、单一进程），见 ADR 0008。
Runner 无状态
从 M2 起只接收场景、参数与 Secrets，输出结果与产物；放进 worker 时不用改。

内部系统带来的要求

情况对策落在
目标系统只能从内网访问平台与 worker 都部署在内网；worker 必须能直连目标系统M9
每次运行都要登录保存并重用登录状态（Playwright storage state），减少登录次数，也降低触发账号锁定的风险M3
老系统缺少语意化标签定位器更依赖 css、xpath 与文字；录制器避开自动生成的 id，产出稳定的选择器M1、M4
iframe、弹出窗口、多标签页DSL 提供切换 frame 与标签页的步骤，定位器可指定所在 frameM3
文件上传与下载upload、download 动作；下载文件作为产物保存M3
表格数据抽取extract 支持表格转成结构化数据M1
自签凭证场景层级可设置忽略 HTTPS 错误，默认关闭并在审核时标示M2
页面内容可能敏感AI 生成可切换到自建模型；截图与 Trace 依项目权限访问M5、M7
录制在用户自己的电脑上进行：CLI 开一个有画面的浏览器，录好后上传到服务器。之后可考虑改成浏览器扩充功能。测试网站（M2）会模拟一个典型内部系统：登录、菜单、iframe、表格与文件下载。
