系统架构

组件、数据流与目录结构。平台全部部署在内网，worker 直接连到目标系统。

组件总览

M9 完成后的样貌
蓝框为内核组件；灰底为平台外部的系统。这是 M9 完成后的样貌；MVP 阶段的样貌见下一节。

MVP 阶段的样貌

M2～M6：单机、单用户、串行运行
管理 Portal

浏览器打开；页面由 API 服务以 Jinja 渲染，沿用 MVP 原型的版面（M3 起）。

API 服务

FastAPI：场景、版本与发布门槛、入参出参、运行、报告、调试工作阶段（ADR 0011）。

背景 worker

同一台电脑；每次运行以子进程跑 Runner，应用总期限与取消，失败或超时就终止整个进程群组。

数据与产物

SQLite 存元数据（ADR 0008）；文件目录存场景版本快照与每次运行的目录。

请求方向：Portal → API → worker。worker 写入运行状态与产物，Portal 以轮询或服务器推送事件读取进度；长任务不阻塞网页请求。M2 之前只有 CLI 与 Runner，直接在本机运行。

runs/<运行编号>/
  input.json          # 校验后的本次入参
  facts.json          # 自动化抽取的页面事实
  output.json         # 只有独立断言与出参校验都通过才产生
  screenshot.png、trace.zip
  automation.log、assertion.log
  scenario/           # 本次使用的场景版本快照（含 Python 脚本）
  result.json、report.html

包职责

uv workspace，每个包可单独测试
包职责依赖起始
rpa-coreDSL 模型、YAML 加载与校验、表达式引擎、JSON Schema 导出、多语言消息目录。不碰浏览器、不碰数据库。Pydantic、PyYAML、Jinja2M0
rpa-runner运行引擎：入参校验、步骤处理器注册表、浏览器与上下文管理、独立断言、出参发布、运行目录与报告；也运行 Python 脚本场景。无状态。rpa-core、PlaywrightM2
rpa-recorder录制：在隔离的浏览器中记录用户操作，保存原始录制稿并转成 DSL 草稿。rpa-core、PlaywrightM4
rpa-generatorAI 助手：对话调试、自然语言 → DSL、校验失败反馈修正、选择器自愈；只能修改草稿。rpa-core、LLM SDKM5
rpa-clirpa 命令：validate、run、record、generate、push。上述包、clickM0
rpa-serverAPI 与管理页面、数据库模型、版本与发布门槛、调试工作阶段；权限（M8）、调度（M9）。rpa-core、FastAPI、Jinja2、SQLAlchemyM3
rpa-worker取出待运行的任务，以子进程调用 rpa-runner，应用总期限与取消，回写结果与产物。M3 在同一台电脑，M9 改为分布式。rpa-runner；Procrastinate（M9）M3

一次运行的数据流

  1. 用户在管理 Portal 或 CLI 触发运行（M9 起也可以由调度器创建）。
  2. API 检查已发布的版本，在启动浏览器前校验入参，写入一笔运行记录与一个任务。
  3. worker 领取任务，以子进程启动 Runner，传入场景版本快照、入参与 Secrets（只在内存中），并设置总期限。
  4. Runner 打开独立的浏览器上下文逐步运行，记下页面事实；每一步回报状态。
  5. 独立断言比对页面事实与入参；通过后出参校验，才写出 output.json。
  6. 截图、Trace、日志与报告存入运行目录（M9 改为对象存储）；失败时标出出错的阶段、步骤与截图。
