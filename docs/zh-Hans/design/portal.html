管理 Portal

在浏览器里创建场景、验证、发布、运行并查看报告（M3）；录制、逐步调试、登录角色与入参出参的表单（M4）；自由试验场的 DAG 组合场景（M6）。单机、单用户（ADR 0010），FastAPI + Jinja（ADR 0011），SQLite（ADR 0008）；版面沿用 MVP 原型与设计系统 v1.1。

M6
启动：uv run rpa serve，再打开 http://127.0.0.1:8080。会一起在 127.0.0.1:8765 启动本机测试网站，「测试网站自动化」的案例直接就能运行。数据放在 data/（或 --data 指定的文件夹，见文件夹）。没有登录保护，默认只开放本机连接。

文件夹

管理 Portal 的所有数据都在一个文件夹里
  • 是什么。领域、场景与每个版本的文件、运行记录与报告、登录角色的登录状态、Secrets、录制稿，全部存在同一个文件夹（里面有什么见下方数据）。换一个文件夹，就是一份全新、互不相干的管理 Portal。
  • 默认与指定。默认是运行命令时所在文件夹里的 data（在项目文件夹运行就是项目里的 data）。用 uv run rpa serve --data 文件夹 或环境变量 RPA_DATA_DIR 换成别的，例如 --data data-m4；相对路径以运行命令时所在的文件夹为准，文件夹不存在时自动创建。
  • 每次用同一个。要看到同一份内容，每次启动都要指定同一个文件夹；不加 --data 就回到 data。
  • 全新的文件夹。第一次启动（还没有任何领域）时，自动创建「测试网站自动化」，放进 scenarios/demo 的示例与登录角色。适合验收新版本，又不动到平常用的数据。
  • 旧的文件夹。新版本第一次打开时自动升级数据库，原有的场景与记录都保留；新版本添加的示例要到「测试网站自动化」按「导入示例」。
  • 领域文件夹（M11）。场景、版本、角色与验证、发布记录放在 domains/<领域>/，一个领域一个文件夹，可以单独校验（rpa pack check）。M11 之前的文件夹第一次打开时自动把旧的 scenes/ 搬进去，搬之前先把数据库与 scenes/ 备份到 backups/<时间>-before-domains/；没有领域的场景与没有场景用到的角色放进「未分类」。数据库里的组合场景（M11 PR 2）搬进「组合场景」领域，代号是 wf-<原编号>、现在的定义成为第 1 版；搬之前先把数据库备份到 backups/<时间>-before-composites/。
  • git 同步（M11 PR 3）。领域可以和 git 仓库里的一个目录同步：「领域管理 › 同步」设置仓库网址、分支、目录与认证方式（公开仓库免认证只能拉取；HTTPS 用用户名＋访问权杖；SSH 用 Portal 产生的部署密钥），也可以「从 git 添加」领域。只有服务器做拉取与推送，录制端与 worker 照旧由服务器送来需要的文件。本机变更＝文件夹和上次同步的提交的差异，保存不必每次提交；拉取与推送都以文件为单位合并，同一个文件两边改成不同内容就停下来三选一（版本说明档的内容哈希相同时视为同一个版本、用远程的那份，所以各自自动导入示例的两台第一次拉取不会冲突）（取消、推送到新分支 rpa/<领域>-<时间>、以远程为准并先备份到 backups/），永远不强推。推送前挡下登录状态、Secrets、私钥之类的文件名、非定义档、超过 1 MB 的文件，以及内容含有已保存的 Secret 值的文件；组合场景依赖的其他领域的版本还没推送时提醒。服务器启动时在背景拉取设置了「自动拉取」的领域，连不上时用本机上一次的数据。
  • 从头开始与备份。先停止管理 Portal（终端按 Ctrl+C）：删掉文件夹就是从头开始，拷贝整个文件夹就是备份。
  • 不要提交或分享。里面有登录状态与 Secrets 的值（只有本人能读写）。Git 已经忽略项目里的 data/ 与 data-*/；用其他名称或放在别处时请自己留意。

领域

场景管理的二级菜单
  • 依目标系统或业务划分场景。例如「测试网站自动化」「谷歌自动化」「微软自动化」。每个领域是「场景管理」左侧的一个菜单，最后一项是「领域管理」。
  • 领域页是场景卡片。1440 宽一列 4 张（每张至少 272px）。每张卡片有名称与分类（没有分类时显示 DSL 场景或 Python 脚本）、最近一次运行的截图、说明，「自动化脚本、断言脚本、运行报告、入参设置、出参设置」五个链接，以及场景编号、最近一次结果、「调试」（DSL 场景打开逐步调试，在那里可以接着验证；Python 脚本场景直接验证最新版本）与「运行」（运行已发布版本；还没发布时显示「待发布」）。
  • 领域管理。添加领域（代号用在网址，创建后不能改）、改名称与说明、删除没有场景的领域。场景页的「运行设置」可以把场景移到其他领域。
  • 测试网站自动化。第一次启动时自动创建，放进对测试网站运行的真实案例：创建记录（BA-001）、查询记录（BA-002，入参是 BA-001 的出参）、查询不存在的记录（BA-003）、Python 脚本版的创建记录，以及两个登录示例（BA-004 一般用户、BA-005 主管）。它的名称与说明跟着界面语言显示，改过之后就照改的内容；场景的名称与说明是场景文件的内容，不会翻译。

流程

验收：在浏览器内走完一次
1 创建或导入2 编辑3 验证4 发布5 运行6 看报告
  1. 创建或导入。添加场景会产生第 1 版草稿（只开一个网页）；也可以一键导入 scenarios/demo 的示例。场景编号就是 DSL 的 id，创建后不能改、也不会重复使用。
  2. 编辑。直接编辑 YAML（脚本场景另有两支脚本）。保存前先用 rpa validate 同一套规则校验，有问题时列出行号、步骤与字段，不会创建新版本。
  3. 验证。用真实浏览器运行指定版本，入参、浏览器、浏览器窗口、网址都可以在表单调整。
  4. 发布。只有通过验证的版本可以发布，而且要用户在对话框确认。
  5. 运行。一律使用已发布的版本；新的草稿不影响正式运行。
  6. 看报告。依分类、场景、结果与目的筛选：每个条件是一个按钮，显示目前的选择，点开勾选一项或多项，按「应用」或关闭菜单就更新；没勾选代表全部。每次运行都有 M2 的 report.html、截图与完整的运行目录。

版本与发布门槛

  • 版本不可变。每次保存都是新版本（v1、v2…），内容写进数据目录后设成唯读。保存要带「从哪一版开始改」，不是最新版就回 409，避免覆盖别人的修改。
  • 状态。草稿 → 验证中 → 验证通过／验证失败；状态是最近一次验证记录的结果。发布后场景指向该版本，旧的发布版本留在历史中。
  • 验证的就是发布的。版本记录内容哈希，算法与 rpa-runner 写在 result.json 的 scenarioHash 相同。发布时要同时符合：磁盘上的内容重新计算后是同一个哈希、版本说明档记的也是它，而且领域文件夹里有一份哈希相符的通过验证记录。
  • 记录跟着领域文件夹（M11）。每次验证写一份验证记录（通过、失败都写：谁、哪台服务器、哪台 worker、结果、哈希），发布写进 scene.yaml。记录跟着领域文件夹同步，任何一台服务器的通过记录都能当发布的依据；场景页列出全部验证记录。
  • 改内容就重新验证。新版本一律从草稿开始，旧版本的验证结果不能拿来发布新内容。

运行

  • 先校验、再排队。请求运行时先检查入参，不合规则直接回 422，不会排进队列；通过后回 202 与运行编号。
  • 背景 worker。rpa-worker 在服务器进程内的背景线程，依创建时间一次运行一个（SQLite 只允许单一进程）。它调用 M2 的 rpa_runner.run.execute，总期限、子进程与进程组的终止都沿用 M2。
  • 有头模式与无头模式。运行表单的「浏览器窗口」：显示（有头模式，headed）会在运行 Portal 的这台电脑上打开浏览器窗口，看得到每个步骤；不显示（无头模式，headless）在背景运行。默认有头模式；这台电脑没有图形界面（Windows、macOS 以外，又没有 DISPLAY 或 WAYLAND_DISPLAY）时只能无头，API 要求有头会回 422。运行页会记下用的是哪一种。rpa run 命令行维持无头，加 --headed 才显示。
  • 进度。运行页每秒查询一次状态，阶段或状态改变时刷新。
  • 取消。排队中的直接取消；运行中的立即终止子进程与浏览器，状态为「已取消」。已经在目标网站完成的动作不会复原。
  • 不重复送出。表单每次加载产生一个 idempotencyKey，重复送出只会得到同一个运行。
  • 重新运行。结束的运行都可以用同样的入参与选项再运行一次（验证用同一个版本，正式运行用目前发布的版本）。
  • 服务器重启。启动时把上次运行到一半的任务标为失败；排队中的会继续运行。
  • 录像（M12）。DSL 场景的自动化阶段录像，有头、无头都录，存成运行目录的 video.webm 与 video.json；steps.json 记下每一步的开始、结束时间与步骤后的网址，回看时和视频对上。画面跟页面一样大，宽度最多 1280。取消、超时、失败的运行也有完整的视频（Windows 上取消时先只结束浏览器，让 Playwright 把视频写完；写坏的视频用 Playwright 自带的 ffmpeg 重新封装）。登录检查、逐步调试、录制与 Python 脚本场景不录。默认全部录；通过的运行保留 7 天，失败、超时、取消、需要登录的保留 30 天，全部最多 20 GB（超过时从最旧的删起），钉选的不删。清理只删视频，运行记录、报告、截图都留着。见 ADR 0016。

登录与角色

M4：每个角色一份登录状态，运行前先检查
  • 场景只写角色。需要登录的场景写 login: { role: 角色代号 }（DSL）。怎么登录、怎么判断已登录，在「场景管理 › 登录与凭证」登记：登录网址、确认网址、已登录时看得到的元素（DSL 定位器），以及选用的自动登录步骤。
  • 人工登录为主。按「登录」会在操作的那台电脑开浏览器窗口到登录网址（直接打开管理 Portal 时是运行 Portal 的这台，通过录制端时是录制端那台），由用户自己登录，所以 SSO、验证码、手机或 App 二次验证都能处理。完成后按「完成登录」或直接关掉窗口；开窗口的那台先用刚取得的登录状态开一个无头浏览器打开确认网址，看得到已登录时的元素，才把登录状态传回服务器、取代原本的，所以服务器不需要浏览器。还没登录就按「完成登录」时，页面说明确认网址停在哪里，窗口不关，登录后再按一次；关掉窗口时还没登录就结束，原本的登录状态不变。操作的那台没有图形界面时不能人工登录。旧版的录制端不会自己确认，改由服务器确认（服务器没有浏览器时会说明要更新录制端）。
  • 自动登录（选用）。只适合单纯账号密码的系统：角色附一段 DSL 步骤，密码用 {{ secrets.名称 }}。运行前发现没登录时先自动登录一次。
  • 检查。角色的「检查」用无头浏览器确认登录状态是否仍然有效（有自动登录步骤时，没登录就自动登录）。服务器有下载角色用的浏览器时在服务器检查；没有时（例如 Linux 安装脚本装的服务器），通过录制端打开管理 Portal 就在录制端检查，直接打开时按钮是灰的。检查用登录状态的复本，通过后才取代原本的；检查期间人工登录或运行更新了登录状态时，保留较新的那份。不先检查也可以：每次运行都会先在运行的那台检查。
  • 需要登录（needs_login）。每次运行先在「登录检查」阶段打开确认网址：看得到元素就继续；没有（例如被转到登录页）而且不能自动登录时，停在「需要登录」，不运行任何步骤，并留下登录检查的截图。运行页有「登录角色」与「重新运行」：登录后用同样的入参再跑一次。
  • 角色互不干扰。登录状态（Playwright storageState）每个角色一份，存在数据目录的 roles/<角色>/state.json，只有本人能读写；每次运行开新的浏览器 context，只加载场景指定的那个角色。登录状态不会拷贝进运行目录，也不经由网页或 API 提供。运行的结果也会更新角色的状态（已登录、需要登录）。
  • Secrets。同一页可以设置 Secrets 的值：存在数据目录的 secrets.json（只有本人能读写，M8 改为加密），页面与 API 只显示名称与更新时间，永远不回传值。运行时把场景与角色用到的值交给运行引擎；没有设置的再从同名的环境变量找。页面也列出场景用到、但还没设置的 Secrets。
  • 测试网站的两个角色。导入示例时，BA-004（一般用户）与 BA-005（主管）用到的角色依 scenarios/demo/roles.json 一起创建；示范账号写在测试网站的登录页。两个账号看到的待办不同，用来确认角色之间没有混用。

录制

M4：原始录制稿 → DSL 草稿
1 录制草稿2 调试与修改3 验证4 确认发布
  • 在这台电脑录制。「场景生产 › 自主脚本录制」按「开始录制」，运行 Portal 的电脑会打开 Playwright codegen 的浏览器与 Inspector；照平常的方式操作，完成后关掉浏览器窗口。选了登录角色时先加载它的登录状态。也可以在命令行用 rpa record 网址 --out 录制稿.py --scenario 草稿.yaml。
  • 三种目标。新场景（存成 v1）；既有场景「接着现有步骤录制」：先在录制的浏览器里用入参默认值运行最新版本的步骤，停在最后一步的页面，再开始录制，录到的步骤、出参与断言接在原有内容后面（原有的内容与注释不变；既有步骤运行失败时录制停止，不会保存）；既有场景「整份换成录制的内容」：从起始网址重新录，存成新版本。选既有场景时，起始网址、浏览器、登录角色自动带入它的设置。
  • Inspector 的代码不能直接改。Inspector 右侧的代码是 Playwright 依操作实时产生的，只能看、拷贝（Playwright 本身的设计，不是本工程限制）；Locator 分页可以输入并测试定位器。要修改请在转换后到场景的「自动化脚本」「断言脚本」编辑。
  • 粘贴录制稿。在别台电脑录好的 codegen 原始稿（同步、异步或 pytest 写法）可以粘贴直接转换，例如 Portal 跑在没有图形界面的电脑时。
  • 断言变成出参。Inspector 的「Assert text」「Assert value」（expect(…).to_contain_text、to_have_value、to_have_text）不当成步骤里的检查，而是：自动化脚本多一个 extract 读取那个元素（先等它出现），出参多一项取自这个页面事实，断言脚本（verify:）多一条检查——录到的值等于某个输入的值时检查「等于该入参」，否则检查「有取得内容」。出参名称取自元素的英数名称，之后可以改。
  • 转换规则。goto、click、fill、press、select_option、check 与其他常见的 expect，以及 get_by_role、label、placeholder、text、test_id、CSS、XPath、first、nth、filter(has_text) 等定位器；iframe 里的元素（frame_locator(…)、locator(…).content_frame，可嵌套）转成定位器的 frame，开头不带参数的 frame_locator() 转成 anyFrame；点击 iframe 元素本身的那一步保留，但列为提醒（M7a）。第一个网址的来源成为 browser.baseUrl。转不了的行（hover、上传、新分页…）以注释留在草稿里并列在录制详情。
  • 自动参数化。每个输入的值变成一个入参，默认值是录到的值；名称取自字段的英数名称（没有时叫 field、field_2…），字段标签写在说明，之后在场景页的表单改名。
  • 密码不落地。密码字段（标签、提示文字或选择器含有 password、密码等字）改成 Secret 引用，原始录制稿也遮罩成 *** 才保存；录制中的暂存原始稿转换后就删除。
  • 只产生草稿。转换结果存成新场景的 v1，或既有场景的新版本；录制稿只当来源，一样要调试、验证通过才能发布。录制详情列出步骤、入参、出参、断言与转不了的行的数量。

逐步调试

M4：一个浏览器、一次一步
  • 开始。场景页的「逐步调试」或卡片的「调试」选版本、入参、浏览器与窗口模式。有图形界面时浏览器窗口开在这台电脑上；两种模式都在页面上显示每一步之后的截图、网址与页面事实。只支持 DSL 场景。
  • 运行。每一步可以「运行这一步」，或「运行到这里」（只运行还没运行过的步骤，遇到失败就停）。有副作用的步骤（点击、填写、选择、勾选、按键）运行过一次后，再运行要先确认；不会自动重复任何步骤。「从头开始」开新的页面并重新加载登录状态。
  • 定位器测试。输入 DSL 定位器（例如 { role: button, name: 登录 }），回报找到几个元素与前几个的文字，截图时以红框标出。
  • 修改。页面下方直接编辑 YAML，存成新版本后换到新版本继续；浏览器与页面事实保留，运行过的步骤依 id 保留状态。
  • 限制。每个场景同一时间一个工作阶段；闲置 15 分钟自动结束，服务器关闭时全部结束。调试会真的操作目标网站，请用测试环境。

分段编辑：自动化脚本、断言脚本、入参、出参

M4
  • 自动化脚本与断言脚本分开。DSL 场景的卡片与场景页有「自动化脚本」（steps:）与「断言脚本」（verify:）两个入口，各自只显示、只改写场景文件的那一段；运行时先跑自动化步骤，再用断言脚本检查取得的页面事实，全部通过才发布出参。断言脚本右侧可以一键插入 notEmpty、equals、contains、matches 的检查，点一下页面事实或入参的名称就插入到光标位置。保存前校验，问题标出段落里的行号。
  • 入参与出参左右编辑。场景页优先呈现契约工作台，默认左右两栏 YAML 原文；表格仍可添加、排序、改名与设置限制。切换查看保留两栏草稿，统一「保存入参与出参」会一起校验并创建一个版本，任一栏有错不会部分保存。错误标示字段及段落行号；版本冲突回 409，保留草稿。
  • 三个唯读预览。在左右编辑器下方依序平铺「默认入参」「出参样例」「出参提取映射」，桌面三栏同时可见，窄屏纵向排列，无需切换页签。默认入参与提取映射随草稿自动刷新；草稿无效时清除旧预览并提示不可用。默认入参由目前草稿产生，没有默认值的必填项另列，不伪造值。出参样例只取该已保存版本最近一次成功运行的真实出参，标明版本与运行编号；没有结果时明确显示空状态，草稿已修改时提示尚未验证。提取映射来自草稿的 outputs.from；Python 场景明示由 assertion.py 产生。三个预览不接受编辑保存。
  • 修改与验证动线。契约、完整文件与脚本分段保存后留在原页，更新版本并显示「验证这个版本」。发布后留在报告，显示已发布版本与运行入口。离开有修改的编辑器会提示。契约保存只替换 inputs／outputs，其他段落与注释保留；表格改名同步更新 DSL 引用，YAML 改名需自行调整引用。新版本仍需重新验证、发布；不修改 Python 脚本。

自由试验场与组合场景

DAG：可分叉、可汇合，成功出参传给下游，失败即停
  • 管理与生产。「场景管理 › 组合场景自动化」沿用测试网站自动化的卡片风格，以真实节点座标和依赖产生 DAG 缩略图，管理名称、节点、问题与最近运行；卡片的「运行组合场景」可直接选引擎、运行位置与窗口模式；「场景生产 › 自由试验场」创建、打开与编辑画布。场景生产菜单依序为自主脚本录制、自由试验场、运行报告、设备（M10.1 前叫「远程 Worker」）。
  • 依赖画布。场景库可点击加入或拖入画布。拖动节点或用方向键微调位置；点上游右侧圆点，再点下游左侧圆点创建连接。点连接设置下游入参，也可以从右侧加入上游。缩放与适应只改视角，不改座标。节点座标随组合场景保存；画布位置和节点数组顺序不代表运行顺序。顶部名称与操作合并成一列，说明收在「说明」，运行历史默认折叠。画布下方的全宽参数区独立卷动，并列上游出参、下游入参、匹配方式、取值／来源；点击 DAG 连接会切到该组上游与下游。多上游可切换来源节点。
  • 四种入参来源。同名匹配仅搜索直接连接的上游，唯一同名且类型兼容时取其出参，没有命中则用场景默认，多个命中必须指定来源；场景默认强制忽略上游同名值；人工指定只覆盖此节点；指定上游出参可以跨字段绑定。选择出参会创建依赖；一个出参可供多个下游，一个入参只有一个来源。整数可以传给数字，其他类型必须相同。
  • 参数连接。拖动出参圆点到入参，或依次用鼠标／键盘选取两端，创建显式绑定；类型不符不修改原值。四种模式以按钮同列呈现，仍可用出参选单精确选择。唯一同名匹配与显式来源画出对应连接；歧义、默认值及人工值不画假连接。契约按钮原地显示该固定版本的唯读原文；编辑场景明示另开分页，并提示验证、发布后回画布选新版本。
  • 运行与返回。从画布启动后原地显示快照版本、进度与各节点状态，点节点可看本次入参、成功出参或错误；可原地取消。完整报告与节点报告由用户主动打开，回画布恢复选取节点、上游与缩放／卷动位置。卡片快捷运行仍直接进入报告。编辑画布不改变已开始运行的快照。
  • 直接依赖与清理。显式连接及出参引用都形成依赖。移除连接清理对应的出参引用并重新检查来源；移除节点同时清理它的连接与下游引用。重设入参会恢复同名匹配。循环、自我依赖、重复边或不存在的端点不可运行。
  • 代号、领域与版本（M11 PR 2）。组合场景有英数代号（没填就是 wf-<数字>，所有领域不能重复），放在某个领域文件夹的 composites/<代号>/，没选领域就放「组合场景」领域。改定义的每次保存都是新版本（revisions/<版本>/workflow.json，唯读），版本说明档钉住每个节点用到的场景版本（领域、场景、版本、哈希）；改名称与说明只改 composite.yaml，不分版本。用到其他领域时写进 pack.yaml 的 requires。
  • 验证、发布与运行（M11 PR 2）。运行时选目的：「验证」跑某个版本（默认最新），结束时写验证记录（每个节点的场景、版本、哈希、状态与运行编号）；「运行」只跑发布的版本，不写验证记录。发布要有哈希相符的通过验证记录，而且每个节点跑的都是钉住的场景版本、那些场景版本现在还在且哈希相同；发布写进 composite.yaml。每次运行在 workflow-runs/<运行编号>/run.json 记下定义快照、版本、目的与每个节点的状态。
  • 依赖检查（M11 PR 2）。组合场景页列出最新版本与发布版本的依赖问题并给补全方式：没有那个领域（添加领域）、场景或版本不在、版本不能运行（重新加载领域）、哈希不符或没钉住（重新保存）是错误，不能运行与发布；角色没登录、缺少 Secrets 是提醒。卡片显示「依赖不完整」或「依赖有提醒」。有组合场景的领域不能删除。rpa pack check 一次给多个文件夹时也检查它们之间的依赖。
  • 补全依赖与管理（M11 收尾）。领域接上 git 后，依赖它的领域的 pack.yaml 在 requires 记下 source（仓库、目录、分支，不含帐密）；别人缺这个领域时，依赖提示的「从 git 添加」带着它预填；领域有数据源但缺场景或版本时提示「拉取」。领域管理页列出每个领域被哪些组合场景依赖。组合场景页可以改代号、搬到其他领域（文件夹连同版本与验证记录改名或搬走）、封存（不能运行），也可以验证指定的旧版本。
  • 保存与预检。草稿可带待修正的问题保存；保存携带 baseVersion，版本冲突回 409，页面保留草稿供导出。运行前检查全图、已发布固定版本、字段、类型、必填值及固定值规则；有问题时第一个节点也不排入队列。问题清单与运行阻挡对话框显示节点、场景、入参及具体原因，点击可定位到画布节点或入参字段；字段同步标红。「运行前检查」可手动检查，卡片运行也重新取得最新问题。添加场景时不自动创建与前一节点的连接。
  • 分叉与汇合。拓扑排序保证所有上游都通过才运行下游；就绪节点以定义中的顺序稳定选取，逐个排入既有队列。每个节点有自己的真实运行、入参、成功出参与报告。下游运行前再检查实际值，不符合规则就停止，不回退到默认值。
  • 快照与恢复。开始时固定编排、场景版本及同名匹配的具体来源，后续编辑不影响已开始的运行。失败、超时、取消、需要登录或 worker 失联皆停止全图；续跑沿用拓扑顺序中已通过的结果，不重复已成功的外部操作。所有节点沿用同一台 worker；取消不回滚外部动作。
  • 格式与兼容。新定义使用 version: 2、mode: "dag"、onFailure: "stop"、nodes 及 edges: [{"source":"n1","target":"n2"}]。节点可带 position: {"x":40,"y":60}；inputs 的值可为 {"auto":true}、{"value":7} 或 {"node":"n1","output":"quantity"}，省略代表场景默认。旧版 serial 定义与历史快照继续可用；旧串行打开画布后，下次保存转成相同顺序的依赖边，不更动已有历史运行。JSON 导出、导入保留座标与绑定。
  • 本次范围。最多 50 节点，支持一般分叉与汇合，不做条件路由或同时运行。沿用现有 DSL 的字符串、整数、数字、布尔入参；原型里的重复次数、日期／随机占位符与复合类型入参未纳入本次五项需求。原型 JSON 是参考契约，不直接当成 Portal 的导入格式。

远程 worker

M9a：运行交给另一台电脑，这台电脑不再被浏览器窗口占住（ADR 0012）
  • 两个端口。rpa serve --worker-port 8081 另外开一个对外端口（M10 起的称呼），只有 Worker API（/worker-api/v1）与桌面 App 的 Client API（/client-api/v1，M10.1 只有配对），默认听所有网络界面；管理页面与 /api 仍然只在 --host（默认 127.0.0.1）。两边的路径互相挡掉：从对外端口看不到管理页面，从管理页面的端口也调用不到 Worker API 与 Client API。
  • 设备与邀请（M10.1）。「场景生产 › 设备」（原「远程 Worker」页，旧网址 /workers 转到 /devices）添加设备（代号、名称；目前种类只有 Worker），产生一份邀请：一行 rpa://pair?server=…&app=worker&code=…，代码一次性、24 小时内有效、限定 App 种类，数据库只存哈希；也分开显示服务器与代码。在那台电脑的 RPA Worker（或 rpa worker --invite）粘贴，经由 Client API 的 /pair 换到权杖。「重新邀请」让旧权杖与之前的邀请立刻失效。邀请要先开对外端口；没开时「添加设备」不能按。可以禁用、删除（运行中不能删；指定给它而还在排队的运行标为失败）。页面列出每台的状态（在线、运行中、脱机、禁用）、最后回报、操作系统、浏览器、能不能有头模式、App 版本，以及程序版本是否和 Portal 相同。
  • 领取。worker 运行 rpa worker --server …，上线时回报协定版本（不同就拒绝）、程序指纹（不同只提醒）、浏览器与能不能显示窗口；之后长轮询（最多 25 秒）领取任务。只给它能跑的：运行位置是远程或任一、浏览器有下载、有头模式要能显示窗口、指定给它的。依创建顺序先进先出。
  • 任务的内容。场景版本的文件（照字节发送，哈希和 Portal 一致）、入参、浏览器、网址、窗口模式、语言；场景有登录角色时加上登录设置与目前的登录状态，以及用到的 Secrets 的值。worker 只放在内存与运行期间的暂保存，运行完删除。
  • 心跳、取消、失联。运行中每 5 秒心跳，同时回报阶段；在 Portal 取消时，下一次心跳就终止浏览器。领取时给 60 秒租约、心跳延长；过期就把运行标为失败「worker 失联」，不自动重跑（可能已经有副作用），之后 worker 才回报的结果一律拒绝。Portal 重新启动时，远程运行中的任务给一次租约的时间重新报到；本机的照旧标为中断。
  • 结果。worker 把整个运行目录打包上传（只接受安全的相对路径，有文件数与大小上限），再回报 result.json 的内容；写回的规则和本机相同，包括验证时的哈希比较。自动登录后的新登录状态传回角色。
  • 运行位置。登记了远程 worker 之后，验证、运行与「运行串行」的表单多一个「运行位置」：本机、远程 worker、任一；默认在设备页设置（没设置是本机）。有头模式能不能选，跟着所选的位置。场景的网址指向本机（127.0.0.1、localhost、::1，测试网站的 8765 除外）而位置不是本机时，表单提醒那指的是 worker 自己。运行报告与运行页显示由哪台运行；运行报告可以依「运行位置」筛选（本机与各台 worker）。排队中而没有在线的远程 worker 可以接时（包括串行固定的那台脱机），运行页与串行运行页说明正在等待并连到设备页。
  • 试验场串行。整个串行用同一个运行位置，而且第一个节点由哪台 worker 领取，后面的节点都固定给它（测试网站的数据、登录状态一致）；那台脱机时后面的节点等着，可以取消。「从停下的节点继续」也固定给原本那台。
  • 只让 worker 运行。--no-local-worker：这台电脑不运行，运行位置不能选本机，默认改成任一。
  • 仍在这台电脑的。录制、逐步调试、人工登录要有人操作，还是在运行 Portal 的电脑。

手动验收

M4、M6、M9a：录制、人工登录、试验场与远程 worker 要有人操作；自动测试用预先录好的录制稿

在有图形界面的电脑（macOS、Windows，或有桌面的 Linux）上，用一个全新的文件夹走一次，大约二十分钟：

  1. 启动。uv run rpa serve --data data-check，打开 http://127.0.0.1:8080；「测试网站自动化」已经有 BA-001～BA-005。
  2. 录制新场景。「场景生产 › 自主脚本录制」选「新场景」，起始网址 http://127.0.0.1:8765/，按「开始录制」。在测试页填标题与数量、按「创建记录」，在 Inspector 用「Assert text」点一下记录编号，关掉浏览器。录制详情应该有 goto、两个 fill、click、一个 extract，入参 2 个、出参 1 个、断言 1 条。
  3. 调试、验证、发布、运行。在新场景按「调试」，逐步运行到最后一步并看截图；回到场景页验证 v1，通过后发布，再从卡片按「运行」，报告是「通过」，出参有记录编号。
  4. 接着现有步骤录制。选「既有场景的新版本」与刚才的场景，再选「接着现有步骤录制」：浏览器先自动跑完原有步骤，停在创建结果的页面，再录一个动作；新版本的步骤接在原有内容后面，原本的注释不变。
  5. 两个角色。「场景管理 › 登录与凭证」对 testsite-user 按「登录」，在跳出的窗口用 user / user-pass 登录后按「完成登录」；testsite-manager 用 manager / manager-pass。再分别运行 BA-004、BA-005：两份报告看到的待办不同。
  6. 需要登录与重新运行。对 testsite-user 按「注销」，再运行 BA-004：停在「需要登录」，没有运行任何步骤；点运行页的登录角色回到「登录与凭证」再登录一次，回到运行页按「重新运行」，结果是「通过」。
  7. 自由试验场。先验证并发布 BA-001、BA-002。创建组合场景，加入一个 BA-001、两个 BA-002 及另一个 BA-001 作为汇合节点；连接「创建 → 两次查询 → 汇合」，让两个查询的 recordId 同名匹配上游，汇合的 title 与 quantity 分别取自两个查询。拖动节点、保存并重载，确认位置保留。运行后四个节点都通过且实际入参相符；反向连接应被拒绝。从场景管理的组合场景卡片打开最近运行，确认报告可追溯。
  8. 远程 worker（两台电脑，M9a）。Portal 改用 uv run rpa serve --data data-check --worker-port 8081 启动；「场景生产 › 设备」添加 win-01，在另一台电脑用对话框里的邀请启动 rpa worker --invite …（M10.1 的 RPA Worker App 交付后改在 App 粘贴；步骤见远程 worker），设备页变成「在线」。用「远程 worker」、有头模式运行 BA-001：浏览器窗口出现在 worker 机器，这台电脑没有跳出窗口；报告是「通过」，运行页显示「运行的电脑：win-01」，截图看得到。再用「远程 worker」运行第 7 步的组合场景，四个节点都在 win-01。运行中在 worker 机器按 Ctrl+C：Portal 上那次运行变成「已取消」。
  9. 运行回看（M12）。运行报告的「回看」栏有 ▶ 与视频长度；打开第 3 步的验证：视频可以播放、暂停、拖曳，滑过时间轴有预览，步骤列表跟着视频走，点一步跳到那一步。运行 BA-002 查询不存在的编号（失败）：打开回看就停在失败步骤之前，结束时有「回到失败的步骤」。在 win-01 用有头、无头各运行一次，运行中取消一次：三段视频都能播放与拖曳。在 Mac 录制端 App 里打开同一页也能播放。

结束后停止管理 Portal，删掉 data-check 文件夹即可；worker 机器上的 worker-data 文件夹也可以删掉。

/scenes/{id}/edit编辑 YAML 与脚本，存成新版本；校验问题列在页面上
/scenes/{id}/edit?part=steps、?part=verifyDSL 场景的自动化脚本、断言脚本：只编辑那一段，右侧可插入页面事实、入参与检查
/scenes/{id}/run验证或运行的表单：入参（JSON，已带入默认值）、浏览器、网址
/runs运行报告：分类、场景、结果、目的的筛选菜单，每一项都可以复选
/runs/{运行编号}状态、阶段、独立断言、入参与出参、截图、运行目录的文件；取消、发布；有录像时「回看」
/replay运行回看（M12）：还有录像的运行（筛选同运行报告）、录像设置与目前用量
/runs/{运行编号}/replay回看一次运行：视频（网址列、目前步骤的标签）、控制列（播放、上一步／下一步、逐格、¼×～2×、全屏幕、快捷键）、缩略图时间轴（滑过预览、拖曳、步骤轨）、步骤列表跟着视频走（点一步跳到那一步；详细有错误、定位器、填入的值、抽到的事实、场景文件原文与行号、「在场景中打开」）、断言、运行信息与钉选；失败的运行打开就停在失败步骤之前 1 秒；同一个场景的上一次、下一次、上一次没通过；组合场景的节点之间切换。?t=秒&step=步骤 打开时跳到那一刻
/roles登录与凭证：登录角色（登录、检查、注销）、Secrets
/recording、/recordings/{录制编号}自主脚本录制：在这台电脑录制或粘贴录制稿；最近的录制；录制详情（转不了的行、转换结果、遮罩过的原始录制稿）
/composites组合场景卡片管理、DAG 缩略图、快捷运行、最近报告、打开画布、删除
/playground自由试验场：创建、导入组合场景与继续编辑画布
/playground/{串行}编辑组合场景：场景库、DAG 画布、入参与节点设置（固定版本、入参的来源）；保存、运行、导出
/playground/runs/{串行运行}串行的运行：每个节点的状态、入参的值与来源、出参、报告；取消、从头再运行、从停下的节点继续
/devices设备（M10.1；/workers 转到这里）：添加并产生邀请、状态、禁用、重新邀请、删除；默认运行位置

GET /api/scenes/{id}/revisions/{n}版本与文件内容

GET /api/scenes/{id}/contract-workspace?revision={n}取得指定版本（默认最新）的契约 YAML 与该版本最近成功出参样例，不会取其他版本或失败结果
PUT /api/scenes/{id}/contract-yaml；POST …/preview左右契约一起保存或唯读校验：baseRevision、inputs／outputs 原文、可选的表格 renames 与 note。保存是单一新版本，校验回传解析后契约、不写入；错误包含 section、sectionLine
POST /api/contract/render表格的内容（key、items）转成和保存一样的 YAML 写法，切到原文查看时用
GET、PUT /api/scenes/{id}/sections/{段}；POST …/preview场景文件的一段（steps、verify、inputs、outputs）：读取、只换掉这一段存成新版本（baseRevision、text、note）、换掉后校验但不保存（入参、出参回传表格用的数据）；问题带段落里的行号 sectionLine

POST /api/roles/{角色}/check、DELETE /api/roles/{角色}/state在背景检查是否已登录（必要时自动登录），在服务器或发出请求的录制端检查；两边都没有角色用的浏览器时回 422 role_check_unavailable。注销

GET /api/recordings/{录制编号}、…/cancel录制状态、转不了的行与文件；取消录制
POST /api/scenes/{id}/debug开始逐步调试（revision、inputs、engine、headless、baseUrl）；已经有工作阶段时回传它
GET、DELETE /api/debug/{工作阶段}；POST …/steps/{n}、…/run-to/{n}、…/locate、…/screenshot、…/reset、…/reload调试状态与结束；运行一步（有副作用而且运行过时 409 confirm_required，带 force 再送）、运行到第 n 步、测试定位器、截图、从头开始、换到新版本
GET、POST /api/workflows串行清单（含问题、依赖状态与最近一次运行）；添加串行（name、description、选用的 definition，带了就是导入；选用的 code 与 domainId）
GET /api/workflows/library场景库：发布过的场景版本，以及它们的入参、出参与登录角色
POST /api/workflows/check检查一份定义（不保存），回传 problems
GET、PUT、DELETE /api/workflows/{串行}串行与最近的运行、版本、验证记录、依赖问题；保存（baseVersion 是最新的版本号码、name、description、definition；不是最新版本就 409，定义改了才是新版本）；删除（运行中不能删，连同文件夹）
POST /api/workflows/{串行}/revisions/{n}/publish发布组合场景的版本（M11 PR 2）；没有哈希相符的通过验证记录 409 workflow_not_validated，依赖不完整 409 workflow_dependencies
PATCH /api/workflows/{串行}改代号（code）、搬到其他领域（domainId）、封存（archived）；运行中不能改代号或搬，代号重复 409
POST /api/workflows/{串行}/runs运行串行（engine、headless、target、idempotencyKey；purpose 是 validation 或 execution，验证时可带 revision；还没发布就运行 409 workflow_unpublished）；有问题（含依赖错误）时 422 并列出 problems；202 回串行的运行

POST /api/workflow-runs/{串行运行}/cancel、…/rerun取消；再运行一次（resume: true 从停下的节点继续，否则从头）
GET、POST /api/workers远程 worker 清单（含默认运行位置、本机执不运行、Portal 的程序指纹）；登记（id、name），回应的 token 只有这一次拿得到
GET、PATCH、DELETE /api/workers/{代号}；POST …/token状态（含 App 版本）；改名称、禁用（disabled）；删除（运行中 409）；重新产生权杖（命令行与脚本用）
POST /api/workers/{代号}/invite产生邀请（M10.1）：旧权杖与之前的邀请立刻失效；回应的 invite（line、server、code、app、expiresAt）只有这一次拿得到；没开对外端口时 409 invite_needs_port，禁用中 409 worker_disabled
PUT /api/settings/default-target默认运行位置（target：local、remote、any）
GET、PUT /api/settings/server这台服务器的代号与名称（name）；写进版本、验证、发布的记录
GET、PUT /api/settings/video录像设置（M12）：enabled、keepPassedDays、keepOtherDays（0～3650）、maxTotalGb；回应另有 usage（几段、多大、钉选几段）。改了之后新的任务照新设置，保留规则立刻应用
POST /client-api/v1/pair只在对外端口、不需要权杖（M10.1）：code、app 换权杖，回应设备代号、名称、token 与服务器的协定、指纹、版本；代码不对或已用过 401 invite_invalid、过期 401 invite_expired、App 种类不对 409 invite_wrong_app（代码保留）、设备禁用 409；格式在 rpa_worker.pairing
/worker-api/v1/…只在对外端口、要权杖：hello、claim、runs/{运行编号}/heartbeat、…/artifacts（zip）、…/role-state、…/finish、…/fail；格式在 rpa_worker.protocol
错误一律是 {"error": {"code", "message", …}}：404 找不到、409 状态冲突、422 内容有问题。

数据

默认是项目里的 data/；用 --data 指定时是那个文件夹（见文件夹）。里面有：

rpa.db
SQLite 数据库（各表见下方）
domains/<领域>/
领域文件夹（M11）：pack.yaml；scenes/<场景>/ 里的 scene.yaml、revisions/<版本>/（scenario.yaml，脚本场景另有两支脚本）与版本说明档 revisions/<版本>.yaml、验证记录 verifications/<版本>/；角色定义 roles/<角色>.yaml；组合场景 composites/<代号>/（composite.yaml、revisions/<版本>/workflow.json 与版本说明档、验证记录）。格式见 rpa_core.pack
runs/<运行编号>/
M2 的运行目录（input.json、report.html…）；run.json 记下服务器、领域、场景、版本、哈希、时间与每个文件的 sha256；录像 video.webm 与 video.json（M12；依保留规则删除视频时，run.json 的 removed 记下删除的时间与原因）
workflow-runs/<运行编号>/
组合场景的运行（M11 PR 2）：run.json 记下定义快照、版本、目的、每个节点的状态与运行编号
work/<运行编号>/
本机运行中的版本文件快照（M11 收尾）：开始时从领域文件夹拷贝，运行中拉取或重新加载不影响；结束就删，服务器启动时清空
roles/<角色>/state.json
角色的登录状态（只有本人能读写）
recordings/<录制编号>/
遮罩过的原始录制稿与转换结果
debug/<工作阶段>/
调试的截图（工作阶段结束就删除）
secrets.json
Secrets 的值（只有本人能读写）
backups/
升级到领域文件夹之前的数据库与 scenes/；组合场景搬进文件夹之前的数据库；冲突时「以远程为准」之前的领域文件夹
git/
git 同步（M11 PR 3，只有本人能读写）：repos/<领域>.git 裸仓库（只用来取得与创建提交）、credentials.json（HTTPS 权杖）、keys/<领域>（SSH 部署密钥）、known_hosts。git 子进程不读系统与用户的设置、不用凭证缓存，权杖只经由 GIT_ASKPASS 交给那一次子进程

数据库的表：

domains
代号、名称、说明、排列顺序；最近一次加载领域文件夹的时间与加载问题；git 数据源（不含权杖）与同步状态（上次同步的提交、上次看到的远程提交、分支、错误、冲突的文件）
scenes
id、名称与分类（取自最新版本）、所属领域、默认网址、最新与已发布的版本号码、封存、来源缺失
revisions
场景、版本号码（唯一）、内容哈希、种类、状态、说明、发布时间；来源缺失、不能运行的问题、有没有哈希相符的通过验证记录
runs
运行编号、场景与版本、当时的名称与分类、目的、状态与阶段、有头或无头模式、入参与出参、错误、哈希、时间；试验场节点的串行运行与节点代号；运行位置、指定的 worker、实际运行的 worker 与租约；录像的长度与大小、钉选、删除的时间与原因（M12）
roles
代号、名称、登录网址、确认网址与判断元素、浏览器、自动登录步骤、最近的状态与检查时间；所在领域、来源缺失
recordings
录制编号、目标场景与版本、方式（新场景、接着现有步骤、整份换掉）与接续的版本、来源（录制或粘贴）、网址、浏览器、角色、状态、转不了的行
workflows
组合场景：代号、所在领域、名称、说明、最新版本的定义（JSON）与版本号码、发布的版本、封存、来源缺失
workflow_revisions
组合场景的版本（文件夹的索引）：版本号码、哈希、状态、有没有哈希相符的通过验证记录、不能运行的问题、说明、发布时间
workflow_runs
串行的运行：串行与当时的名称、代号、版本与目的、定义的快照、状态、停在哪个节点与原因、沿用的节点（从停下的节点继续时）、浏览器与窗口模式、时间；运行位置与固定的 worker
workers
远程 worker：代号、名称、权杖的哈希、禁用、上线时回报的信息（M10.1 加上 App 版本）、目前的运行、最后回报时间
device_invites
设备邀请（M10.1）：代码的哈希、App 种类、设备代号、产生时间、期限、使用时间
settings
设置（默认运行位置、服务器代号与名称、文件夹的格式、录像）

模型用 SQLAlchemy 2，结构变更走 Alembic 迁移（服务器启动时自动升级）；测试会比较迁移与模型是否一致。

设置

--host、--port
默认 127.0.0.1:8080；没有指定端口号而 8080 被其他程序占用时，自动改用下一个空的端口号（到 8089）。占用的如果就是管理 Portal，只显示它的网址，不再开第二个
RPA_DATA_DIR
文件夹，默认 data；也可以用 --data（见文件夹）
RPA_DATABASE_URL
默认 SQLite；PostgreSQL 在 M8
RPA_LANG
默认语言，也是运行报告的语言；页面右上角可以切换
--no-testsite
不要一起启动测试网站（默认会在 127.0.0.1:8765 启动；已经在运行就沿用）
RPA_EXAMPLES_DIR
「测试网站自动化」的示例文件夹，默认 scenarios/demo
Secrets
在「登录与凭证」设置；没有设置的，从服务器进程的同名环境变量读取（远程 worker 运行时，从 worker 进程的环境变量读取）
--worker-port、--worker-host
开放对外端口给设备（M9a；M10 起称「对外端口」）：另一个端口，默认听 0.0.0.0；只有 /worker-api（要权杖）与 /client-api（配对用邀请代码）。邀请里的服务器网址：听所有界面时猜这台的区网地址，听特定地址时就用那个地址
--no-local-worker
这台电脑不运行，全部交给远程 worker

安全与限制

  • 没有登录。默认只听 127.0.0.1；改成其他地址时 rpa serve 会提醒。认证与权限在 M8。
  • 挡掉跨站请求。写入请求带了 Origin 标头时必须同源，避免其他网站在背景调用本机的 API。
  • 运行目录的文件。只提供运行目录内的文件；只有 report.html 当成网页显示，并加上只允许内嵌样式与截图的内容安全政策。
  • 脚本场景等同运行任意程序。与 M2 相同，Python 脚本场景只给信任的人编辑。
  • 登录状态与 Secrets 存在这台电脑。两者都在数据目录、只有本人能读写，不经由网页或 /api 提供，也不写进运行目录、报告与日志；录制稿里的密码遮罩后才保存。M8 加密存放。
  • 远程 worker 拿得到运行要用的 Secrets 与登录状态。只在领取任务的回应里，worker 放在内存与运行期间只有本人能读写的暂保存，运行完删除。Worker API 用 HTTP 时在区网上是明文：只在信任的网络使用；权杖只存哈希，可以随时禁用或重新产生。
