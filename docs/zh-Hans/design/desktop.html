桌面端分发

M10：服务器与数据库部署在一台电脑，录制者与运行机各装一个桌面 App，粘贴邀请就能用。App 的窗口沿用服务器现有的页面；录制、逐步调试、人工登录的浏览器开在操作的那台电脑。决策见 ADR 0014。

录制端：用户的流程

macOS
  1. 从 Portal 的「下载桌面端」取得 DMG，把「RPA 录制端」（RPA Recorder.app）拖进「应用程序」。
  2. 第一次打开：没有签章，macOS 会挡下；到「系统设置 › 隐私权与安全性」允许打开（步骤见签章与第一次打开）。
  3. 粘贴 Portal「设备」页产生的录制端邀请，配对完成。
  4. 下载浏览器（只有第一次，显示进度）。
  5. 窗口里就是 Portal。按「开始录制」「调试」「登录」时，浏览器开在这台 Mac。

Worker：用户的流程

Windows
  1. 取得 RPA-Worker-Setup.exe，安装到用户目录；不需要管理员、uv、git、Python。
  2. SmartScreen 出现时按「其他信息 › 仍要运行」。
  3. 粘贴 Worker 邀请，配对完成。
  4. 下载浏览器，状态变成「在线」。
  5. 关掉窗口是缩到通知区；可勾选「登录 Windows 时自动启动」。

只有服务器访问数据库（ADR 0008、ADR 0012 不变）。两个 App 都主动连服务器；服务器不需要连到它们。

设备与邀请

M10.1
  • 「远程 Worker」页改成「设备」页。列出 Worker 与录制端两种设备；添加时选种类与名称，产生邀请，取代现在「拷贝权杖＋启动命令」。
  • 邀请。一行文字：rpa://pair?server=http://192.168.1.10:8081&app=worker&code=…。代码一次性、24 小时内有效、限定 App 种类；数据库只存哈希。App 也接受分开填写的服务器网址与代码。
  • 配对。App 用邀请调用 POST /client-api/v1/pair 换到设备权杖，存进 macOS 钥匙圈或 Windows 认证管理员。Worker 邀请贴到录制端（或反过来）会被拒绝并说明。
  • Worker 设备就是现有的 worker 记录：拿到的权杖直接用在 Worker API。命令行也能用邀请配对：uv run rpa worker --invite …，权杖存在工作文件夹，之后直接 uv run rpa worker；用环境变量或 --token-file 给权杖的方式照旧可用。
  • 管理。禁用、重新邀请（旧权杖立刻失效）、删除；页面显示在线状态、App 版本、操作系统、浏览器。

对外端口与访问控制

M10.1、M10.2
  • 沿用 --worker-port。不加新的命令行参数；文档改称「对外端口」。
  • 依路径分流（扩充 PortGateMiddleware）：/worker-api/ 要 worker 权杖；/client-api/v1/pair 只接受邀请代码；其他 /client-api/ 要设备权杖；其他所有路径（Portal 页面、/api、静态档）要录制端的设备权杖，没有就回 401。
  • 结果。没配对的电脑打开 8081 看不到管理页面；worker 权杖也打不开管理页面。这是 M8 之前最小的访问控制，M8 再把设备对应到用户。
  • 本机 8080 不变。服务器那台的浏览器照旧直接用。
  • 传输。维持 HTTP＋权杖（信任的区网，2026-10-13 的决定）；HTTPS 列在保留方案。

交互子进程：浏览器开在操作的那台

M10.2；录制、逐步调试、人工登录

「这台电脑」改成指「你正在操作的那台」。请求从录制端进来，子进程就交给那台录制端；从服务器本机的浏览器（8080）进来，照旧在服务器运行。页面不多一个选项。

  • 子进程主机。录制、调试、人工登录三个服务用可注入的 launcher 启动子进程，只用到一小部分 Popen 的功能：写一行到标准输入、逐行读标准输出、结束。从服务器本机来的请求照旧是 subprocess.Popen；从录制端来的请求改用 RecorderHub.launcher(设备)（rpa_server.devices），传回界面相同的 RemoteProcess，经由 Client API 交给那台。哪一台由请求决定：对外端口的访问控制认出录制端的权杖后，把设备放进这个请求的 context（rpa_server.context）。服务器端读 Lines、解析事件的程序不变。
  • 启动。服务器送出「启动」指令：模块名称（rpa_runner.record、rpa_runner.debug、rpa_runner.login）、参数（工作目录用代号 {work}，不带服务器的路径；工作目录外的输入档，例如角色的登录状态，放进 .inputs/）、需要的文件（场景、入参、登录状态）、环境变量（只送服务明确指定的：语言、用到的 Secrets）。录制端在自己的暂存文件夹写出文件并启动，结束后删掉整个文件夹（下次启动时也清掉上次没删的）。连接是区网里的 HTTP，所以录制端只运行这三个模块与 playwright codegen，也不接受会改变解释器或引导程序库的环境变量（PYTHON*、NODE_*、DYLD_*、PATH 等）。
  • 输出与文件。录制端把每一行标准输出传回；在传一行之前先上传这段期间添加或改变的文件（截图、录制稿、登录状态），所以服务器处理那一行时文件一定已经到了。结束时再同步一次并回报结束码。
  • 输入与结束。服务器要送一行命令（例如调试的「运行第 3 步」）或结束时，放进录制端的指令队列；录制端以长轮询取得。
  • 失联。录制端每次长轮询就是心跳；超过 30 秒没有回来，服务器把它的子进程视为结束（结束码 -1001，原因写进那段工作的日志，页面照一般的失败显示），录制端重新连上时结束残留的浏览器。录制端重新启动（上线时的开机代号不同）、在设备页被禁用、删除或重新邀请，以及服务器停止时也一样。
  • 不变的。录制稿转成 DSL、遮罩密码、创建草稿版本、调试步骤的副作用确认、登录状态保存，全部仍在服务器。Secrets 与登录状态在录制端只放内存与暂保存，用完删除（同 M9a 的 worker）。
  • 浏览器检查。录制端上线时回报已下载的浏览器；选了这台没有的浏览器时，页面直接说明，不启动子进程。
  • 记录。录制（recordings.device_id）、调试与人工登录的工作阶段记下是哪台设备；页眉显示目前通过哪台录制端操作。每台设备同一时间各一段录制；同一个场景的调试只有一个，在另一台开始时关掉原本的。

RPA 录制端

M10.2，macOS
  • 本机闸道。App 在 127.0.0.1 的随机端口开一个小闸道，窗口只加载闸道的网址；闸道加上设备权杖后转给服务器的对外端口。权杖不进网页、也不靠服务器的 Cookie；以后改 HTTPS 时在闸道钉选凭证即可，WebView 不必处理自签凭证。
  • 只给这个 App 用。闸道每次启动产生一个密语，窗口第一次加载时设成 Cookie；没有这个 Cookie 的请求一律拒绝，同一台电脑上的其他程序与浏览器用不了。闸道不转送 /client-api/ 与 /worker-api/：网页不能拿权杖去确认或伪造录制端的指令与输出。
  • App 自己的页面（配对、下载浏览器、脱机提示、设置）放在闸道的 /__desktop/ 下，用设计系统的 CSS。
  • 新窗口与下载。target="_blank" 的链接（报告、截图）在 App 内开新窗口；导出文件存到「下载项目」。
  • 服务器在同一台时（MVP 的情况）：一样配对 http://127.0.0.1:8081，走同一条路。
  • App（M10.2 PR 2）。pywebview（WKWebView）的窗口只加载闸道的网址；状态、配对、下载浏览器、设置是闸道另一个端口的 /__desktop/ 页面（rpa_desktop.recorder_pages，用 fetch 调用，不用 pywebview 的 js_api）：和 Portal 不同来源、各有自己的密语与 Cookie，写入的请求一定要带这个端口的 Origin，所以 Portal 的页面（或塞进去的脚本）读不到 App 的状态，也叫不动配对、重新配对、镜像这些动作（2026-10-18 审阅后改的）。还没配对、或 Portal 回 401 时，Portal 那个端口只回说明页（不放 App 页面带着密语的网址），主窗口在配对失效时自己回到 App 的页面。菜单「RPA 录制端」：状态与设置、管理 Portal、刷新。target="_blank" 经由自订的 webbrowser 处理器：闸道的网址在另一个线程开 App 的新窗口（pywebview 在主线程调用，那里建不出窗口；新窗口共用 Cookie），其他网站只接受 http(s)、用默认浏览器；下载不能显示的文件时 pywebview 改用 NSURLSession，所以闸道的 Cookie 也放进 App 的 NSHTTPCookieStorage。关掉主窗口或 ⌘Q 都先拦下、确认后由 App 自己关（⌘Q 直接放行时 AppKit 会立刻结束进程、来不及收拾），结束时不等长轮询、直接结束子进程与删暂存；只运行一份；权杖在钥匙圈的「RPA Recorder」；数据在 ~/Library/Application Support/rpa/recorder。CI：macOS 跑录制端 App、闸道与录制端程序的单元测试，--smoke-test 打开真的 WKWebView 窗口确认页面经由闸道加载。
  • 开发环境的 rpa recorder。同一套闸道（rpa_worker.gateway）与子进程主机（rpa_worker.recorder），改在默认浏览器打开；给有开发环境的人与端到端测试用（用法）。
  • 运行位置的用词。通过录制端看页面时，「本机」显示为「服务器」，避免误会成录制端这台。
  • 本地网络权限。macOS 15 起连区网要用户允许；Info.plist 写用途说明（NSLocalNetworkUsageDescription）。

RPA Worker

M10.1，Windows
  • 内部就是现有的 RemoteWorker。权杖改从配对取得；领取、心跳、上传、测试网站的行为都和 rpa worker 一样（运行循环在 rpa_worker.service，两边共用）。
  • 分两步交付（2026-10-16 决定）。第一步是主控台版：双击 rpa-worker.exe 粘贴邀请、下载浏览器、接任务；CI 用打包版实际配对并运行 BA-001 → BA-002。第二步（2026-10-17 核准）加上下面的状态窗口、通知区、自动启动、只运行一份与认证管理员；主控台版保留为同文件夹的 rpa-child.exe --worker，排查问题用。之后是安装档（2026-10-18 核准）。
  • 状态窗口。pywebview（WebView2）加载 App 内的页面（设计系统的 CSS 内嵌，原档不改）：配对（贴邀请，只贴代码时另外填服务器）、下载浏览器的进度、服务器、在线状态、目前运行、最近 10 笔、App 版本、权杖存放；版本与服务器不同时提醒，附「下载新版」打开最新的 GitHub Release。「设置」：自动启动、Firefox、内部镜像、语言（依 ADR 0007 默认繁中、不跟操作系统，选择记在文件夹的 settings.json）、打开日志文件夹、重新配对。窗口不连到 Portal 的页面：管理页只在服务器那台的 127.0.0.1，对外端口要到 M10.2 才开放给录制端。
  • 通知区图标。关掉窗口是缩到通知区（第一次提示）；菜单有「打开窗口」「暂停接任务」「结束」，图标的圆点表示状态。有任务在运行时结束要先确认，取消后回报。「暂停接任务」是做完目前的任务后不再领取：服务器不改，Portal 约一分钟后显示脱机（2026-10-17 决定）。
  • 自动启动。写入目前用户的「登录时运行」（HKCU\…\Run，加上 --background 只出现在通知区；还没配对时仍打开窗口）。第一次配对成功后默认打开，之后照用户在设置里的选择；每次启动时把路径更新成目前的位置（免安装的文件夹可能被搬走）。有头模式需要用户登录桌面，所以不做成系统服务。
  • 只运行一份。文件夹里 instance.lock 的独占锁，窗口版、--no-window 与主控台版互斥；重复打开时叫出已经在跑的那份。拿到锁的那份另外创建具名 mutex RPAWorker.App，让安装档知道 App 正在运行；文件夹的 stop.request 请它取消任务、回报后结束。
  • 认证管理员。权杖经由 keyring 存在 Windows 认证管理员；不能用时退回 pairing.json（只有本人能读写）并记在日志。第一步存在文件里的权杖自动搬过去。
  • 不跳主控台窗口。窗口程序启动的主控台子进程（rpa-child、taskkill）加上 CREATE_NO_WINDOW；下载浏览器直接启动 Playwright 的 driver，不经过 rpa-child。
  • 没有 WebView2、注销与关机。没有 WebView2 Runtime 时说明怎么安装，在那之前只用通知区接任务。Windows 注销或关机时立刻取消运行中的任务并回报（最多等 3 秒，不挡住关机）；来不及时由租约判定失联（ADR 0012）。
  • 数据位置。工作数据、设置与日志在 %LOCALAPPDATA%\rpa\worker（日志会轮替，不记权杖与邀请代码），Firefox 预热模板照旧在 %LOCALAPPDATA%\rpa\cache，浏览器在 Playwright 默认的 %LOCALAPPDATA%\ms-playwright。
  • CI。Windows 的建置工作先跑桌面端的单元测试（注册表、单一运行、认证管理员用真的）；--smoke-test 打开真的 WebView2 窗口与通知区图标；端到端先静默安装，用装好的 App 以 --no-window 配对并运行 BA-001 → BA-002，再在 App 运行中升级、卸载（安装档）。窗口程序没有标准输出，--version、--self-test 改用 rpa-child。
  • M9a 剩下的三项并入 M10.1：运行报告的「运行位置」筛选、场景网址是本机地址时的提醒、等待 worker 的提示。

打包与建置

M10.0
  • 子进程命令集中。目前 10 处用 sys.executable -m … 启动子进程（runner、登录检查、录制、调试、codegen）。改由 rpa_runner.commands 产生：开发环境是 python -m 模块，打包后是 App --rpa-module 模块；Python 脚本场景是 App --rpa-script 文件；codegen 直接调用 Playwright 内附的 driver。
  • PyInstaller，文件夹模式（onedir）。macOS 做成 RPA Recorder.app（显示名称「RPA 录制端」）再包成 DMG；Windows 用 Inno Setup 做成安装到用户目录的 RPA-Worker-Setup-版本-windows-x64.exe（安装档），另外照样产生免安装的 zip。不用单档模式（每次启动解压上百 MB，也较容易被杀毒误判）。
  • 建置信息。版本、程序指纹、协定版本在建置时写进 App（打包后没有源代码文件可以算指纹）。版本规则沿用 M9a：协定不同才拒绝，程序指纹不同只提醒。
  • 浏览器。第一次启动用 App 内附的 Playwright driver 下载，版本必定相符；放在 Playwright 默认的用户缓存。可以在设置填内部镜像（PLAYWRIGHT_DOWNLOAD_HOST）。录制端必要 Chromium、选用 Firefox；Worker 同。
  • Python 脚本场景。打包后用 App 内的 Python 运行，只能 import 标准函数库与 App 内附的包（Playwright、Pydantic 等）。
  • CI。添加桌面端构建流程：macOS（Apple 芯片）建录制端、Windows 建 Worker；建好后跑自我测试：用打包后的 App 下载 Chromium、启动测试网站，以无头模式跑 BA-001，确认打包后的子进程路径真的能用。产物（DMG、安装档）挂在该次建置上。
  • 大小（M10.0 在 CI 实测）。录制端的 DMG 68 MB（App 解压后 166 MB）；Worker 的 zip 58 MB（解压后 139 MB）。第一次下载的 Chromium（含无头版）解压后约 570 MB（macOS）～710 MB（Windows）；Firefox 另计。

Worker 的安装档

M10.1，Inno Setup 6.7
  • 只装给目前的用户。不需要管理员，装到 %LOCALAPPDATA%\Programs\RPA Worker；开始功能表捷径，桌面捷径选用；装完打开。文件夹 %LOCALAPPDATA%\rpa\worker 和免安装版相同。
  • 语言。繁中、简中、英文，默认繁中、安装时可以选（ADR 0007）。Inno Setup 的界面用它源代码 is-6_7_1 的翻译档（建置时下载并核对 SHA-256，仓库不放）；安装档自己的消息从 App 的消息目录（installer.*）产生，所以一样是繁中、英文人工维护，简中由工具产生。
  • App 正在运行时。用 App 的具名 mutex 判断，在文件夹写 stop.request 请它取消运行中的任务、回报后结束（最多等 150 秒），再换文件（只有通知区、没有 WebView2 时也一样；主控台版在配对、下载浏览器那一步做完后结束）；不用 Windows 的 Restart Manager 强制关闭。升级时配对、设置与自动启动都保留，旧版的程序库先删掉。
  • WebView2。没有 Runtime 时运行建置时附上的 Microsoft Evergreen 引导程序（建置时核对 Microsoft 的数字签章）；失败时说明，App 仍可只用通知区接任务。
  • 卸载。用户确认要卸载后（Inno Setup 的 usAppMutexCheck，取消时 App 不受影响）才询问是否也删除配对、设置与日志（含认证管理员里的权杖）：默认保留；静默卸载不问、保留，命令行 /REMOVEDATA=yes 才删除。接着停止 App，删除程序、捷径与「登录时运行」的项目。只删 App 自己的文件：文件夹可能是 RPA_WORKER_HOME 指定的任何地方，浏览器与 Firefox 模板的缓存别的程序也在用。
  • 建置与 CI。tools/build_desktop.py worker 在 Windows 上建好 App 与 zip 后调用 ISCC（GitHub 的 Windows 运行环境已装 Inno Setup）。端到端：静默安装 → 检查文件、捷径、卸载项目的版本 → 用装好的 App 配对并运行 BA-001 → BA-002 → App 运行中再安装一次（App 要以结束码 0 结束）→ 卸载，确认程序、捷径、卸载项目与自动启动已删、配对保留 → 再安装一次并以 /REMOVEDATA=yes 卸载，确认文件夹与认证管理员里的权杖已删。失败时附上 Inno Setup 的日志。
  • 不包含。代码签章、自动更新、内含 Chromium 的脱机安装档。

版本与发布

GitHub Releases，草稿由维护者发布
  • 同一个版本。服务器、Worker、录制端与所有包用同一个版本（主.次.修，数字），标签是 v0.2.0 这种格式（2026-10-18 决定）。python3 tools/release_version.py bump 0.2.0 一次改全部包与 uv.lock。
  • 流程。在功能分支 bump 版本 → PR 合并 → 在 main 上打标签并推送 → 「发布」流程（.github/workflows/release.yml）确认标签和包版本一致、标签在 main 上，调用桌面端建置（含安装、升级、卸载的端到端），创建草稿 Release：安装档、免安装 zip、SHA256SUMS.txt。
  • 草稿。仓库是公开的，发布后任何人都下载得到（没有邀请连不上 Portal）；所以由维护者确认草稿的内容后才按「发布」。重新运行时换掉同一个草稿的文件；已经发布的版本不换，改用新的版本。
  • 下载新版。App 的版本和服务器不同时，窗口的「下载新版」打开最新的 Release（…/releases/latest，只算已发布的）。

签章与第一次打开

MVP 不签章
  • macOS。只有 ad-hoc 签章（Apple 芯片必需，PyInstaller 自动处理），没有公证。从浏览器下载后第一次打开会被挡下：到「系统设置 › 隐私权与安全性」，在下方找到这个 App，选择允许打开并输入密码。macOS 15 起，按住 Control 点「打开」已经不能略过这一步。熟悉终端的人也可以运行 xattr -dr com.apple.quarantine "/Applications/RPA Recorder.app"。
  • Windows。没有代码签章：SmartScreen 显示「Windows 已保护您的电脑」时按「其他信息 › 仍要运行」；浏览器下载时也可能要确认保留文件。
  • 之后。有 Apple Developer 账号后加上 Developer ID 签章与公证；Windows 加代码签章凭证。只改 CI 的建置步骤。

要实测的风险

  • WebView2。Windows 11 内置，Windows 10 大多已随 Edge 更新装好；安装档侦测不到时先安装。
  • macOS 本地网络权限。确认 Playwright 开的 Chromium 连内网网站时，权限算在 App 身上。
  • 杀毒误判。PyInstaller 的启动器偶尔被误判；文件夹模式较少，必要时回报给杀毒厂商。
  • Playwright 私有命令。「接著录制」用 codegen 内部的 enableRecorder；打包后要用同一个 driver，升级 Playwright 时由自我测试发现。
  • pywebview 的新窗口与下载。WKWebView 与 WebView2 的行为不同，两边都要手动确认。
