ADR 0003: PostgreSQL as the task queue

Run tasks and schedules are stored directly in PostgreSQL, without adding Redis.

Accepted
Date
2026-10-09
Affects
rpa-server, rpa-worker, deployment (M7, M9)
Related
Architecture

Context

Shared multi-user use needs many workers running in parallel, scheduled runs and retries on failure. The platform needs PostgreSQL anyway to store scenarios and runs.

In RPA the bottleneck is the browser itself: a run usually takes seconds to minutes, and the load is tens to hundreds of tasks per minute, not thousands per second.

Decision

  • Use Procrastinate: a task queue backed by PostgreSQL, native asyncio, with support for periodic tasks.
  • Creating the run record and enqueuing the task happen in the same database transaction, so there is never a record without a task.
  • Workers call the queue through a thin interface so the implementation can be replaced if needed.

Consequences

Benefits

  • One component fewer to deploy; backups and monitoring only need to cover PostgreSQL.
  • Transactions guarantee consistency between tasks and run records.
  • Compatible with Playwright's async execution model.

Costs

  • Lower maximum throughput than a dedicated message queue; enough for this project's scale.
  • Depends on a single library, which is why the replaceable interface is kept.

Options not chosen

OptionWhy not
Celery + RedisMature, but one more component and weaker asyncio support.
arq (Redis)Native asyncio, but still needs Redis.
A custom SKIP LOCKED queueWorkable, but retries, scheduling and monitoring would all be ours to write.
