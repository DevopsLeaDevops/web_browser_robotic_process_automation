ADR 0014: The recorder and the worker ship as desktop apps that reuse the existing web pages

The server and database are deployed on one computer; recorders and execution machines each install a desktop app and are ready to go. Each app is a pywebview shell around the server's existing Jinja pages. The browser for recording, step-by-step debugging and manual login opens on the computer the person is using.

Accepted
Date
2026-10-15 (proposed); 2026-10-16 (accepted)
Scope
New package rpa-desktop; rpa-runner (child-process commands), rpa-server (devices, invitations, the external port, interactive child processes), rpa-worker (version info); CI and releases (from M10)
Related
Extends ADR 0012 (external port and tokens); ADR 0011 (Python only, server-rendered pages); ADR 0010; Desktop distribution. Number 0013 is reserved and unused.

Context

The server and database will live on a fixed computer (first on the user's own machine while things are tuned, then in production). Today both recorders and execution machines need uv, git and Python plus the setup script, and versions have to be aligned by hand. The user wants something like Claude Desktop: one installer and it works.

The deeper limitation: recording, step-by-step debugging and manual login all open their browser on the computer running the portal (the M4 design, kept by ADR 0012). Once the server moves elsewhere, a recorder can open none of them on their own computer. The management pages also have no sign-in (that comes in M8), so they cannot simply be opened to the LAN.

Claude Desktop is an Electron app: the shell carries its own Chromium and the main interface is a web page. Our interface is already server-rendered web pages, so the shell only needs a window that can load a URL.

Decision

  • Two apps, one codebase."RPA Recorder" and "RPA Worker" both live in apps/desktop (package rpa-desktop), each with its own build configuration. M10 delivers the recorder for macOS (Apple silicon) and the worker for Windows (x64); the other combinations are kept as a planned option.
  • pywebview as the shell.The system WKWebView on macOS and WebView2 on Windows; no extra browser bundled. The recorder window loads the server's existing portal pages, so there is one set of templates. The app's own few pages (pairing, browser download, status) are also HTML using the design system.
  • Pairing by invitation.The portal's "Devices" page creates a one-time invitation (valid for 24 hours, single use, tied to one kind of app). The app exchanges it for a device token, stored in the macOS keychain or the Windows Credential Manager.
  • The external port gains two uses.Besides the Worker API, the rpa serve --worker-port port also serves the Client API (pairing, interactive child processes) and the portal pages; the portal pages accept only a recorder's device token and refuse everything else. Local use of 127.0.0.1:8080 is unchanged.
  • Interactive child processes run where the person is.The server gains a process-host layer: when a request comes from a recorder, the recording, debugging and manual-login child processes run on that recorder, and their output and files come back; requests from a local browser still run on the server. Conversion, masking, revisions and the publish gate stay on the server.
  • Child-process commands in one place.Every sys.executable -m … is produced by rpa_runner.commands instead; a packaged app goes through its own entry point.
  • Browsers download on first launch.The Playwright driver shipped inside the app downloads them, so the versions always match; an internal mirror can be configured.
  • No code signing for the MVP.macOS gets only an ad-hoc signature and Windows has no code-signing certificate; the docs explain how to allow the first launch. Signing and notarization come once accounts exist.

Consequences

Benefits

  • Recorders and execution machines need no uv, git or Python: paste the invitation, download the browsers, done.
  • The recording browser opens on the recorder's own computer, so the server can live anywhere (including a production machine without a screen).
  • One interface: a change to the portal pages shows up in the recorder immediately, and the project is still Python only.
  • The worker reuses the M9a Worker API and runner; there is no second execution path.
  • An unpaired computer opening the external port sees no management pages: the minimum access control before M8.

Costs

  • An extra CI build (macOS, Windows); each release ships two installers, and app and server versions must match.
  • Without signing, the first launch has to be allowed by hand (macOS Privacy & Security, Windows SmartScreen).
  • Recording and debugging send output and screenshots over the network; with HTTP, device tokens, secrets and sign-in states travel in clear text, so this suits trusted LANs only (as in ADR 0012).
  • In the packaged app, Python script scenarios can import only the standard library and the packages shipped inside the app.
  • The system WebView depends on the OS: Windows needs WebView2 (built into Windows 11); macOS uses the system Safari engine.

Alternatives not chosen

OptionWhy not
Electron shell plus Python child processes (the Claude Desktop approach)A complete ecosystem (auto-update, signing tools), but it adds a Node/TypeScript toolchain and a second Chromium. The shell only opens windows, so it is cheap to replace later if needed.
Tauri shellSmallest installers, but needs a Rust toolchain; same reasoning as above.
No shell: open the portal in the system browser and run a background programIt does not feel like an app; the token would have to live in a browser cookie and is lost when switching browsers.
One app whose role comes from the invitationOnly one build, but the user chose two apps: clear names and audiences, and no recording features on worker machines.
Browsers bundled in the installerWorks offline, but adds 150 MB or more and makes later macOS notarization harder; kept as the offline option.
Open the whole portal to the LANNo sign-in (M8), so anyone on the LAN could operate it (already ruled out in ADR 0012).
Remote screen streaming (watch the server's browser while recording)Laggy, needs its own streaming component, and the server would still need a graphical desktop.
PyInstaller one-file modeUnpacks hundreds of MB on every launch and is more often flagged by antivirus; use a folder (onedir) plus an installer instead.
