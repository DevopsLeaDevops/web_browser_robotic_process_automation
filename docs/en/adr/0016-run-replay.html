ADR 0016: Record runs, and line the video up with the steps by the same clock on replay

The automation stage of validations and executions is recorded with Playwright and kept in the run folder. Steps record the real time they started and ended, and the replay page uses those times to find them in the video. Thumbnails are made in the browser that plays the video.

Accepted
Date
2026-10-20
Scope
rpa-runner, rpa-worker, rpa-server (from M12)
Related
ADR 0009 (run folder), ADR 0012 (remote workers upload the run folder); M11 decision D4 (run records stay out of git); Management portal › Runs › Recording

Context

When a run fails, the report only has the last screenshot, the step results and the logs, so you cannot see what happened on the screen before the failure. Runs usually happen on another worker, and in headless mode nothing is visible at all. The user asked (2026-10-20) for validations and executions to be recorded, headed or headless; for the recording to be replayed from the run record after the run; and for replay to be a separate, frequently used feature that can pause, seek, find the moment by thumbnails and follow the steps, so the run can be reconstructed.

Playwright can record video on its own: the browser hands every frame and the real time it appeared to Playwright, which encodes them into WebM with its own ffmpeg.

Decision

  1. What is recorded. The automation stage of DSL scenarios, using BrowserContext recording, headed or headless; the video is as large as the page, at most 1280 wide (scaled down proportionally). Login checks, step-by-step debugging, recording sessions and Python script scenarios are not recorded. Firefox's warm profile starts with a tab already open, and that tab records frames missing the height of the toolbar (measured on Windows and Linux), so recording uses a newly opened tab instead.
  2. How it lines up with the steps. Playwright encodes every frame at its real time, so second t of the video is the recording start time plus t; the start time is in the WebM header (DateUTC, milliseconds). steps.json records each step's startedAt and endedAt (UTC, milliseconds) and the page URL after it. Both come from the same clock on the same computer, so subtracting gives the step's place in the video. If the header has no start time (older Playwright), the time the page was opened is used.
  3. How it is finished. The subprocess closes the BrowserContext before it exits, which is when Playwright finishes the video; the parent turns it into video.webm and video.json (start time, length, size, whether it was repaired). When the subprocess is terminated (cancelled, or past the overall deadline): on Linux and macOS Playwright runs ffmpeg in its own process group, so it is not terminated along with the rest and finishes the file itself; on Windows the process tree cannot simply be ended: taskkill /T would end ffmpeg too, and keeping only ffmpeg is not enough either, because Node (Playwright's driver) puts the processes it starts in a Job Object that ends them all when Node ends. So while recording, the runner lists the descendants first and ends only the browsers: Playwright finishes each page's video as usual, and the subprocess exits by itself because its page closed (0.1 to 0.3 seconds in CI); only if it has not exited within 15 seconds is the whole process tree ended. How the run was stopped is recorded under stop in video.json. A video that still has no length or index is remuxed with Playwright's own ffmpeg (no re-encoding).
  4. Where it is kept. In the run folder (remote workers still upload the whole folder); the runs table records the length, size, pin, and when and why the video was deleted. Videos do not go into domain folders or git.
  5. How long it is kept. A server setting; by default everything is recorded, passed runs keep the video for 7 days, and failed, timed-out, cancelled and needs-login runs for 30 days; all videos together use at most 20 GB, deleting the oldest first; pinned videos are kept. Clean-up only deletes videos: run records, reports and screenshots stay, and run.json records when and why the video was deleted.
  6. How it is replayed. The replay page plays the video straight from the run folder (with Range support and caching). Thumbnails are made in the browser that plays the video, by seeking a hidden video and drawing it to a canvas; the Linux server has neither a browser nor ffmpeg.

Consequences

  • About 1–3 MB per minute (1280 wide; less when the screen is still). The retention rules and the total limit keep disk use in check.
  • Workers run an extra real-time ffmpeg encoder (VP9; Playwright adjusts threads and bitrate to the frame size).
  • The video keeps everything on the screen, including business data and values typed into ordinary fields. The user agreed to keep them (2026-10-20, D3); until M8, anyone who can open the management portal can see them.
  • Cancelling while recording waits on Windows for the subprocess to exit by itself (usually under a second, at most 15 seconds). Actions still stop at the same moment: the browsers are ended right away.
  • The browser has to play WebM VP9: Chrome, Edge and Firefox do; Safari on macOS and the recorder app (WKWebView) need manual acceptance.
  • A terminated video only covers up to the last change on the screen; the waiting after that has no frames. The replay page attaches steps beyond the end of the video to its last frame.

Alternatives not chosen

Playwright tracesLarge files that need the separate Trace Viewer; the user wants video playback, seeking and thumbnails.
A screenshot per stepAn extra browser round trip changes step timing, and nothing between steps is visible.
Playwright's showActions (marking clicks in the video)Injects annotations into the page and waits 500 ms before every action, which changes the run itself. The replay page shows the steps instead.
