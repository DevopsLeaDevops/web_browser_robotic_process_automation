ADR 0010: MVP first and roadmap v2

Following the MVP prototype, deliver a single-machine, single-user MVP with serial execution first (M2–M6); multiple users and distribution move after the MVP.

Accepted
Date
2026-10-10
Scope
Roadmap, system architecture, multi-user design, every milestone from M2 on
Related
Roadmap, ADR 0008, ADR 0009, ADR 0011, MVP prototype

Context

The original roadmap went "CLI → flow features → recording → AI → page prototypes → management backend → Web UI → operations": the management interface would appear only in M8, and multiple users had to be done by M7.

The MVP prototype describes the first product to deliver: scenario management, recording and debugging, reports, and a playground. It explicitly leaves arbitrary DAGs, distributed clusters, multi-tenant permissions and cross-environment scheduling out of the MVP. It also comes with a Python chain already run in a real browser.

Decision

  • MVP scope. Single machine, single user, serial execution; SQLite for metadata and a file directory for script snapshots and run artifacts.
  • New milestone order. M1.1 scenario contract → M2 runner → M3 management portal → M4 scenario production and login → M5 AI assistant → M6 playground (MVP done) → M7 flow features → M8 multiple users and governance → M9 operations.
  • The prototype is the page prototype. The page prototypes of the old M6 are delivered by the MVP prototype; the old Web UI is split across M3–M6, each delivering its own pages with the prototype's top-level and left-side navigation.
  • The prototype lives in the repository. It is kept in docs/prototypes/mvp/ and checked against MANIFEST.json like the design system, without edits or translation; its simulated results never count as real validation.
  • Revisions and the publishing gate. Scenario revisions are immutable: draft → validating → passed or failed → published. Changing scripts, schemas or defaults requires validating again, and the published revision must be exactly the one that passed.
  • Browsers. Chromium and Firefox are both supported and both tested in CI; a scenario chooses one with browser.engine.

Consequences

Benefits

  • Users work in the browser from M3, five milestones earlier than planned.
  • Every stage is accepted against the prototype's scenarios, giving the requirements a shared reference.
  • Expensive capabilities such as multiple users and distribution wait until the MVP has proven the direction.

Costs

  • The M3–M6 pages need permissions and project scope added for multiple users (M8); the data model reserves owner and project fields from the start to keep that cheap.
  • Conditions, loops, uploads, downloads and other flow features move to M7; during the MVP, complex scenarios use the Python script escape hatch.
  • Every page talks to the backend directly, so differences between the prototype and the implementation are explained in each stage's PR.

Alternatives not chosen

OptionWhy not
Keep the original roadmapThe management interface arrives too late and does not match the MVP the prototype describes.
Build multiple users and PostgreSQL from the startThe prototype explicitly excludes multi-tenancy; doing it first slows the MVP, and ADR 0008 already keeps the way open to switch later.
Connect the prototype's localStorage frontend to a backend directlyThe prototype is a single demo JavaScript file; the real pages are rendered on the server (ADR 0011) and keep only its layout and flows.
