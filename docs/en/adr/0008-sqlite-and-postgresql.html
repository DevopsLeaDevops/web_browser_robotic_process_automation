ADR 0008: The database supports both SQLite and PostgreSQL

SQLite for development and prototypes, with nothing to install; PostgreSQL in production. The same code and migrations must run on both.

Accepted
After roadmap v2 (ADR 0010): SQLite is used from the M3 management portal on; PostgreSQL and multiple workers come in M8 and M9. Mentions of M7 below correspond to the new M3 and M8.
Date
2026-10-10
Affects
rpa-server, rpa-worker, database migrations, CI, deployment (from M7)
Related
ADR 0003, Tech stack, Architecture

Context

Until M7, scenarios live as YAML files in the repository and no database is needed. From M7, the management backend stores users, projects, scenario versions and runs.

During development and design we want to get prototypes working quickly, without every developer installing and configuring PostgreSQL first. Production, on the other hand, is shared by many users and needs concurrent writes, several workers and proper backups.

Decision

  • Two databases with separate purposes. SQLite (built into Python, nothing extra to install) for development, tests and prototypes; always PostgreSQL in production.
  • One setting to switch. The connection string goes in the RPA_DATABASE_URL environment variable; when it is not set, a local SQLite file is used.
  • Only write code both support. Models and queries use only SQLAlchemy 2.0's portable types and constructs, never PostgreSQL-specific features directly.
  • One set of migrations. Alembic migrations are shared by both databases, with batch mode enabled so SQLite can alter table structure too.
  • The queue implementation follows the database. PostgreSQL uses Procrastinate and can have several workers (ADR 0003); SQLite allows a single process only, and the queue and scheduler run inside the API process.
  • CI tests both. From M7, database tests run once on SQLite and once on PostgreSQL, and both must pass before merging.

Rules when writing code

Where the two databases behave differently
ItemApproach
JSON columnsUse SQLAlchemy's JSON, stored as JSONB on PostgreSQL through with_variant; queries do not use JSONB-only operators.
TimeAlways stored in UTC through a shared column type; SQLite does not keep time zones.
Foreign keysSQLite does not check foreign keys by default; turn on foreign_keys for every connection and use WAL mode.
Case-insensitive searchNo ILIKE; lower-case both sides before comparing.
PostgreSQL-only featuresArrays, LISTEN/NOTIFY, SKIP LOCKED, advisory locks and the like may appear only in replaceable implementations (such as the queue), never in models or ordinary queries.
ConcurrencySQLite allows one writer at a time. Tests that verify several workers or concurrent writes run on PostgreSQL only.

Consequences

Benefits

  • Developers install no database: the backend runs right after uv sync, and tests are faster.
  • Production still gets PostgreSQL's concurrency, multiple workers and backups.
  • Not tied to database-specific features, which makes switching databases later easier.

Costs

  • PostgreSQL's advanced features cannot be used directly; when needed they must be wrapped in a replaceable implementation.
  • The queue has two implementations to maintain; SQLite mode cannot verify multi-worker behavior, which relies on the PostgreSQL tests.
  • Differences in types, locking and transaction isolation can make a problem appear on only one side, which is why CI tests both.
  • Data from the prototype stage is not moved to production; scenarios are YAML, so they can be carried over by export and import (rpa push) when needed.

Options not chosen

OptionWhy not
PostgreSQL only, with Docker for developmentDevelopment matches production most closely, but everyone must install Docker or PostgreSQL first, which slows prototyping.
SQLite in production tooSingle machine and a single writer only; cannot support several workers or many concurrent users.
Start PostgreSQL on demand for tests (for example testcontainers)Tests closer to production, but needs Docker locally; PostgreSQL coverage comes from CI instead.
Safeguards: the production deployment examples (M9) always use PostgreSQL; the server logs which database it uses at startup and warns "development and prototypes only" for SQLite; it refuses to start when several workers are configured against SQLite.
