ADR 0019: Read reports and recordings per composite run, and join the recordings in the player

A composite run has one summary report and one combined replay. The combined replay makes no new video file: the player places the nodes' recordings one after another on a single timeline and replaces the time between nodes, when nothing is on screen, with short cards. The recordings of a composite run's nodes are kept as a group.

Context

Every node of a composite run (one row in workflow_runs) is a run of its own, with its own report, screenshot and recording. The composite run page used to list only the nodes and links: to find out which step it stopped at, why, and which values were passed, you had to open each node's report; to watch the recordings, you had to open them one by one. On 2026-10-27 the user asked to read reports and recordings from the point of view of one composite run.

Nodes run one at a time in the DAG's topological order and the whole run stays on one Worker, so the nodes' recordings form a single line in time and never overlap. Each recording covers only that node's automation stage: queueing, browser start-up, the login check, checks and outputs have nothing on screen.

The Linux server has no browser and no ffmpeg (ADR 0016); adding media packages to the server changes the runtime, and then an update file is no longer enough (ADR 0018). Nodes may have different frame sizes (page size, Firefox differences).

Decision

  • Summary report. The composite run page becomes one report: the verdict (all passed, or which node stopped at which step, with the locator, the error, failed checks and the screenshot, plus the nodes that did not run), the numbers, the DAG colored by result and a timeline, and each node's inputs (values and sources), outputs (values and where they go), steps and checks. It is assembled when viewed from the database and each node's result.json and is not stored. It can be downloaded as a single HTML file (with screenshots only for nodes that did not pass, D4); the API and the Agent API return the same JSON.
  • Recordings are joined in the player (D1). No new video file: each node with a recording is one segment, and its clips and steps are moved to the start of that segment; tab ids get the node as a prefix (n2/page-1). The player reuses the multi-clip clock from ADR 0016: the clock pauses while a clip loads and advances in real time between clips. The download is a zip of the nodes' original recordings with a playlist.json describing the order.
  • Gaps become cards (D2). Between two recordings there is a 2-second transition card: the previous node's outputs and where they went, the next node's inputs and their sources, and the real gap. A node without a recording (deleted, login required, never started, never reached automation) is a 3-second explanation card. When a run continues from the stopped node, each reused node is one card linking to the original run's replay (D3); nodes that did not run or have not finished are combined into a final card.
  • Steps are renumbered. One number across the whole run, plus the node and the number within the node (n2·3); step ids get the node as a prefix (n2:search), so ?step= points at a step of a node and ?node= starts at a node.
  • Recordings are kept as a group (D6). For the nodes of a composite run, retention follows the whole composite run's result and end time (nothing is deleted while it is still running); pinning one node pins the whole run; over the total limit, the whole run is deleted together. The rules for single runs do not change.

Consequences

  • You know where and why it failed without opening any node, and one player shows the whole run; clicking any step of any node on the right jumps to that frame.
  • Only the server changes: no new third-party package, no database migration, no Worker or recorder change, so an update file is enough.
  • There is no single merged video: to watch outside the portal, the download holds the nodes' videos and a description of their order.
  • Cards replace the real gaps, so the video timeline is not elapsed time; the elapsed time is on the report's timeline and on the transition cards.
  • For a composite run that did not pass, the recordings of nodes that passed are kept for up to 30 days, using somewhat more disk than counting each node separately; the total limit still applies.
  • When nodes have different frame sizes, the player uses the first segment's aspect ratio and scales the others to fit, centered.
  • If parallel nodes are supported later, the timeline needs several lanes; the data keeps each segment's real time, so it can be extended.

Alternatives not chosen

OptionWhy not
The server joins the segments into one .webmThe server has no ffmpeg; different frame sizes need re-encoding; media packages mean an update file is no longer enough; one more copy of the video is stored.
The Worker joins the videos after the last nodeThe Worker does not know when the whole run ends; reruns, reused nodes and cancellations all need handling; it still needs re-encoding.
Keep the real gapsQueueing, browser start-up and checks often take longer than the actions themselves, leaving long blank stretches in the video.
Join the segments directly, without cardsYou cannot see what values passed between nodes, or that the node changed.
Store the summary report as a file when the run endsIt would need a fixed language and regenerating when data changes (for example, a recording is deleted); generating it when viewed is enough for now, and archiving (M11 D4) can store it later.
