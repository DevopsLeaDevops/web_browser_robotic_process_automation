ADR 0009: Scenario contract and independent assertions

Every scenario has inputs, outputs and independent assertions; "the script did not raise" is not success, and outputs are published only after the independent assertions pass. The DSL comes first; Python scripts are a controlled escape hatch.

Accepted
Date
2026-10-10
Scope
rpa-core (DSL), rpa-runner (M2), the management portal, recording and AI generation, workflows
Related
ADR 0001, ADR 0010, Scenario DSL, MVP prototype

Context

The MVP prototype proved an execution contract with a real Python / Playwright example: inputs are validated against a JSON Schema before the browser starts; the automation only operates the page and records "page facts"; a separate, independent assertion compares the facts with the inputs; only when everything passes are the outputs published and handed to the next scenario.

The M1 DSL had only params and in-step expect: success meant "no step failed", there were no outputs, and scenarios could not be chained. The prototype's flows, recording, AI generation and workflows all depend on this contract.

Decision

  • Scenario contract. Every scenario can declare inputs and outputs. Types and constraints are a common subset of JSON Schema 2020-12 and can be exported as JSON Schema. params is renamed to inputs.
  • Page facts. The results of extract go into facts; facts only describe what the page showed and do not mean success.
  • Independent assertions. verify compares facts with inputs after the automation ends. A scenario with outputs must have verify.
  • Outputs are published last. Input validation → automation → independent assertions → output validation; output.json exists only if all of them pass, and a failure at any stage leaves no successful outputs.
  • Overall deadline. deadline limits the whole run; each step may use only the time that remains.
  • DSL first, Python scripts as an escape hatch. A scenario the DSL cannot express may use script to name automation.py and assertion.py, following the prototype's command-line contract. Such scenarios are flagged in review, and recording and AI never produce them.

Every stage is bound by the overall deadline; actions with side effects (such as submitting a form) are never retried automatically after a timeout.

Consequences

Benefits

  • Success comes with evidence: the report points to the assertion and the fact that did not match.
  • Scenarios can be chained: a downstream input binds to an upstream output, and types are checked before running.
  • The API, the management interface and AI share the same input and output schemas.
  • The DSL stays the default, so recorded and AI output can be validated first; a few complex scenarios still have a way out.

Costs

  • Scenario authors write verify and outputs; simple scenarios that only take screenshots or look at pages can leave them out.
  • Python script scenarios can do anything, so their safety relies on review, permissions and isolated execution.
  • The execution engine supports two kinds of scenarios, and their reports must look the same.
