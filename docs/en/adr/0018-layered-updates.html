ADR 0018: Package our code separately from the runtime, and let the server hand updates to devices

Each release also ships an update file of about 1 MB that holds only our own code. Give it to the server once: the server updates itself, and Workers and recorders fetch the same version over the LAN and apply it when it does not interrupt work. When the runtime (Python, third-party packages) has not changed, nobody downloads a full package again.

Context

On 2026-10-24 the user asked for hot updates: every upgrade of the server, the recorder and the Worker downloads a whole package again, which is slow.

In v0.5.0 the server bundle is about 103 MB (x64) and 97 MB (arm64), the Windows Worker build outputs about 136 MB in total, and each DMG about 84 MB. What actually changes between releases is the seven workspace packages (including the Portal pages, translations and database migrations): their source compresses to about 0.6 MB (measured on main a8cde7f). The rest is Python, third-party packages and the Playwright driver.

Third-party packages rarely change: 6 changed from 0.2.0 to 0.3.0 (PyObjC added for macOS), 20 from 0.3.0 to 0.4.0 (including Playwright 1.63 to 1.64; some are only development tools), and none from 0.4.0 to 0.5.0.

The repository became private on 2026-10-22, so only a signed-in GitHub account with access can download a Release or follow the app's "Download new version" link. Someone has to download, carry and install the package on every device. Browsers (570 to 710 MB unpacked) are downloaded again only when the Playwright version changes, which is already incremental and out of scope here.

Decision

  1. Layers. The code layer is the seven workspace packages: pure Python, one copy shared by all platforms. The runtime is Python 3.13, the third-party packages needed at run time and the PyInstaller shell (desktop apps), one per platform. Browsers stay as they are. If the runtime for Python script scenarios (PR #82, awaiting confirmation) is adopted, it is a separate layer with its own version and is not affected by this record.
  2. Runtime ID. Each platform's runtime has an ID: a hash of the Python version, the locked list of run-time third-party packages (uv export, without development tools), and the shell's version and list of collected modules. CI computes it when it builds the full package and writes it into the package. The code layer states the ID it needs on each platform; only the code layer is replaced when the IDs match, and a full package is needed when they differ.
  3. Update file. Each release also produces RPA-Update-<version>.zip: the code layer's files, a manifest (version, commit, code fingerprint, protocol version, understood DSL features, the runtime ID per platform, and the SHA-256 and size of every file) and an Ed25519 signature of the manifest. Full packages are still published, for first installs and for when the runtime ID changes.
  4. Server. The install folder becomes runtimes/<runtime ID>/python (shared by several versions) plus releases/<version>-<commit>/app (the code layer); the atomic switch of current stays. rpa-server update <update file>: verify the signature and hashes, check that the needed runtime ID is present, install and load the server code with the bundled Python, back up SQLite when there are new migrations (remind the operator to back up PostgreSQL), wait until no recording, step debugging or manual login is in progress (--now skips the wait), switch and restart the service, and switch back to the previous version and restore the backup if the admin port does not answer within 60 seconds. The update file is kept in the data folder's updates/ for devices to download. On startup the server extends the lease of running remote runs by one period, so a restart does not mark them as "worker lost".
  5. Device launcher. The PyInstaller entry point becomes a small launcher, and our code is no longer compiled into the executable's archive. The launcher reads the version named in app/active.json in the data folder and checks the signature, every file's hash and the runtime ID. Only then does it put that version first on sys.path; otherwise it uses the code layer built into the app (the installed version) and logs why. The parent process pins child processes (rpa-child) to the same code layer through an environment variable. The shell collects the whole standard library (without tkinter, test and the like), so new code that uses another module still finds it in an older shell.
  6. The app itself is never modified. The code layer is downloaded into the device's existing data folder: %LOCALAPPDATA%\rpa\worker\app\ on Windows, ~/Library/Application Support/rpa/{worker,recorder}/app/ on macOS. The macOS .app signature stays intact and no "App Management" permission is needed.
  7. Devices follow the server's version. Before going online a device calls the update endpoint (one in the Worker API, one in the Client API) with its app kind, platform, version and runtime ID. The endpoint's format is fixed and does not check the protocol version, so an old app can still update first when the protocol changes later. The server answers: same version, update available (version, size, hash), or full install needed. Devices track the server's current version, not the latest release; when the server goes back, the devices go back too.
  8. When to apply. Worker: finish the current run, stop claiming and restart itself (a few seconds), only when it has no run. Recorder: never interrupt recording or debugging; the window says "reopen to apply", and the update is applied on the next start. If a new version cannot go online within 2 minutes after starting, or crashes twice in a row, the device goes back to the previous version and tells the server; the last 3 versions are kept. A server setting "Update devices automatically" is on by default; the Devices page shows each device's version and update state.
  9. Signing. CI signs the manifest with an Ed25519 private key (GitHub Secrets); the public key ships with the runtime. The server verifies on install, devices on download, and the launcher on every start. Verification follows the RFC 8032 reference algorithm (verify only), with no new dependency. The launcher accepts a set of public keys so the key can be rotated later.
  10. Dependency update rhythm. In the weekly dependency update PRs, changes that touch only development tools are merged as usual (the runtime ID does not change); changes to the runtime are collected and merged together as a "runtime release", at a rhythm the user decides. A Playwright upgrade makes every device download browsers again, so its PR and the Release notes must say so.

Consequences

  • For a release whose runtime ID does not change (for example 0.4.0 to 0.5.0), upgrading the whole system goes from "6 files of 84 to 136 MB, downloaded and installed on every device" to "1 file of about 1 MB, given to the server once". Devices download over the LAN and need no GitHub account.
  • The server and the devices keep the same code fingerprint, so the "different version" warning and the M7a "app too old" failures should become rare.
  • The server still restarts (Python loads code at startup), so the Portal is unavailable for a few seconds. Remote Workers retry reports for 10 minutes and reconnect to claim (existing behaviour); with the lease extension no run is lost.
  • 0.5.0 has no launcher, so the first layered release (planned as 0.6.0) needs one last full install; pairing, settings and data are kept.
  • Costs: a launcher and an update flow to maintain; desktop apps get somewhat larger from the full standard library (to be measured during implementation); code is loaded from a user-writable folder, so safety rests on the signature; the update endpoint's format must stay compatible forever; if the signing key is lost or leaked, a new full package is needed to rotate it.
  • CI gains another path: install the previous release's full package, apply this release's update file, then run the end-to-end tests.

Alternatives not chosen

OptionWhy not
Compare files and download only the changed onesPyInstaller compiles our code into the executable's archive, so the executables change every release. The code layer has to be split out anyway, and once it is, comparing files adds little.
Binary diffs of the installers (bsdiff and the like)Diffs of compressed installers are poor, and every pair of versions needs its own diff, which complicates publishing and storage.
Whole-package auto-updaters such as Sparkle or WinSparkleThey make updates automatic but not smaller, and need a public download URL (the repository is private) and signing certificates.
Reload modules while running (importlib.reload)Old objects and state stay in memory; behaviour is hard to predict and failures are hard to trace.
A server that never stops (two processes taking turns)Needs a reverse proxy in front, and SQLite cannot be written by two processes at once (ADR 0008). It saves only a few seconds.
Every device downloads from GitHub directlyThe repository is private and needs an account; devices on the internal network cannot always reach GitHub.
No signature, only hashes and the device tokenDevices talk to the server over HTTP today; an update replaces the program itself and stays, which is a bigger risk than a one-off scenario.
