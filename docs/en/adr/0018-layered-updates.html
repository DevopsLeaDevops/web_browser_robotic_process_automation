ADR 0018: Package our code separately from the runtime, and let the server hand updates to devices

Each release also ships an update file of about 2 MB that holds only our own code. Give it to the server once: the server updates itself, and Workers and recorders fetch the same version over the LAN and apply it when it does not interrupt work. When the runtime (Python, third-party packages) has not changed, nobody downloads a full package again.

Context

On 2026-10-24 the user asked for hot updates: every upgrade of the server, the recorder and the Worker downloads a whole package again, which is slow.

In v0.5.0 the server bundle is about 103 MB (x64) and 97 MB (arm64), the Windows Worker build outputs about 136 MB in total, and each DMG about 84 MB. What actually changes between releases is the seven workspace packages (including the Portal pages, translations and database migrations): their source compresses to about 0.6 MB (measured on main a8cde7f). The rest is Python, third-party packages and the Playwright driver.

Third-party packages rarely change: 6 changed from 0.2.0 to 0.3.0 (PyObjC added for macOS), 20 from 0.3.0 to 0.4.0 (including Playwright 1.63 to 1.64; some are only development tools), and none from 0.4.0 to 0.5.0.

The repository became private on 2026-10-22, so only a signed-in GitHub account with access can download a Release or follow the app's "Download new version" link. Someone has to download, carry and install the package on every device. Browsers (570 to 710 MB unpacked) are downloaded again only when the Playwright version changes, which is already incremental and out of scope here.

Decision

  1. Layers. The code layer is the seven workspace packages: pure Python, one copy shared by all platforms. The runtime is Python 3.13, the third-party packages needed at run time and the PyInstaller shell (desktop apps), one per platform. Browsers stay as they are. If the runtime for Python script scenarios (PR #82, awaiting confirmation) is adopted, it is a separate layer with its own version and is not affected by this record.
  2. Runtime ID. Each platform's runtime has an ID: a hash of the Python version, the locked list of run-time third-party packages (uv export, without development tools), and the shell's version and list of collected modules. CI computes it when it builds the full package and writes it into the package. The code layer states the ID it needs on each platform; only the code layer is replaced when the IDs match, and a full package is needed when they differ.
  3. Update file. Each release also produces RPA-Update-<version>.zip: the code layer's files, a manifest (version, commit, code fingerprint, protocol version, understood DSL features, the runtime ID per platform, and the SHA-256 and size of every file) and an Ed25519 signature of the manifest. Full packages are still published, for first installs and for when the runtime ID changes.
  4. Server. The install folder becomes runtimes/<runtime ID>/python (shared by several versions) plus releases/<version>-<commit>/app (the code layer); the atomic switch of current stays. bin/rpa update <update file>: verify the signature and hashes, check that the needed runtime ID is present, install and load the server code with the bundled Python, switch current, and ask the running server to restart. The server exits only when no recording, step debugging, manual login or local run is in progress (--now skips the wait); when the new version starts with new migrations, it backs up SQLite before migrating (and reminds the operator to back up PostgreSQL). The update file stays in that version's folder (releases/<version>/update.zip) for devices to download. On startup the server extends the lease of running remote runs by one period, so a restart does not mark them as "worker lost".
  5. The server restarts itself. bin/rpa serve watches the server process: when the server exits with the agreed exit code, it starts the version in current with the same arguments; when the new version exits before it starts serving, it switches back to the previous version, restores the pre-migration backup and starts again. This does not depend on systemd and works the same under nohup or systemd (the user's internal server runs under nohup, stated on 2026-10-25). A server run from a clone (.venv-server) does not take update files, because files managed by git must not be overwritten: switch to the server bundle once; the command only changes .venv-server/bin/rpa to ~/rpa-server/bin/rpa, and the arguments and data folder stay.
  6. Device launcher. The PyInstaller entry point becomes a small launcher, and our code is no longer compiled into the executable's archive. The launcher reads the version named in app/active.json in the data folder and checks the signature, every file's hash and the runtime ID. Only then does it put that version first on sys.path; otherwise it uses the code layer built into the app (the installed version) and logs why. The parent process pins child processes (rpa-child) to the same code layer through an environment variable. The shell collects the whole standard library (without tkinter, test and the like), so new code that uses another module still finds it in an older shell.
  7. The app itself is never modified. The code layer is downloaded into the device's existing data folder: %LOCALAPPDATA%\rpa\worker\app\ on Windows, ~/Library/Application Support/rpa/{worker,recorder}/app/ on macOS. The macOS .app signature stays intact and no "App Management" permission is needed.
  8. Devices follow the server's version. Before going online a device calls the update endpoint (one in the Worker API, one in the Client API) with its app kind, platform, version and runtime ID. The endpoint's format is fixed and does not check the protocol version, so an old app can still update first when the protocol changes later. The server answers: same version, update available (version, size, hash), or full install needed. Devices track the server's current version, not the latest release; when the server goes back, the devices go back too.
  9. When to apply. Worker: finish the current run, stop claiming and restart itself (a few seconds), only when it has no run. Recorder: never interrupt recording or debugging; the window says "reopen to apply", and the update is applied on the next start. A new layer is confirmed when the app exits normally or has run for 20 seconds. If two starts in a row are not confirmed, the third start goes back to the previous layer (or the built-in code when there is none), the device tells the server at its next update check, and the same version is not installed automatically again; the last 3 layers are kept. A server setting "Update devices automatically" is on by default; the Devices page shows each device's version and update state.
  10. Signing. CI signs the manifest with an Ed25519 private key (GitHub Secrets); the public key ships with the runtime. The server verifies on install, devices on download, and the launcher on every start. Verification follows the RFC 8032 reference algorithm (verify only), with no new dependency. The launcher accepts a set of public keys so the key can be rotated later.
  11. Dependency update rhythm. In the weekly dependency update PRs, changes that touch only development tools are merged as usual (the runtime ID does not change); changes to the runtime are collected and merged together as a "runtime release", at a rhythm the user decides. A Playwright upgrade makes every device download browsers again, so its PR and the Release notes must say so.

Implementation

Phases 1 and 2, 2026-10-25, PR #83
  • The rpa_update package. The manifest, signature verification, runtime ID, installing and choosing code layers, and the desktop launcher live here (packages/rpa_update). It uses only the standard library and belongs to the runtime: changing it changes the runtime ID and needs a full package.
  • What the runtime ID covers. Server: the Python version and the locked list of run-time third-party packages. Desktop apps: the PyInstaller version, the third-party distributions (with versions) that own the collected modules, a hash of those files' contents and the number of modules (our seven packages are left out). runtime.json also records the built-in code version (version-commit) and the trusted public keys.
  • The same runtime gets the same ID on every build (2026-10-26). All three desktop apps in 0.6.1 had a different runtime ID from 0.6.0 while the servers kept theirs: the shell also hashed rpa_update's *.dist-info, which carries the release's version, and uv records a timestamp in uv_cache.json when it installs from source, so it differed on every build. Devices were therefore always told to use the full installer, and kept showing "Differs from the portal's code". From then on the *.dist-info folders of workspace packages are left out (shell_files in tools/build_desktop.py; rpa_update's content is covered by its source hash). This is not done in rpa_update: changing any of its files changes the servers' runtime ID. The desktop apps of the release with the fix have to be installed from the full installer once more; after that, releases with an unchanged runtime can use the update file.
  • Comparing with the previous release. tools/runtime_changes.py compares this build's runtime IDs with the latest published update file: desktop and server package builds on pull requests write annotations (a warning when different), and the release adds an "Upgrading from vX" section to the Release notes that names which targets can use the update file and which need the full installer.
  • Server. bin/rpa update FILE [--now] verifies the file, installs it as a new version folder and switches current. The server exits with code 75 and bin/rpa serve starts the version in current; when the new version exits before it starts serving, it goes back to the previous version and restores the pre-migration SQLite backup. A version folder installed from a full server bundle has no update file: run rpa update once with the same version's update file to put it there, so devices have something to update from.
  • Desktop code layers. They live in the app's data folder under app/<version-commit>/ (manifest.json, manifest.sig, app/), next to active.json and boot.log (which only records switching to the built-in code, rolling back and retrying after a restart). Every start verifies the signature, runtime ID and every file; child processes are pinned to the same layer through RPA_APP_LAYER. Reinstalling the full installer switches back to the built-in code. The shell collects the whole standard library except unused parts (tkinter, test, ensurepip and the like) and readline and curses, which depend on system libraries.
  • Device update checks. POST /update (Worker API and Client API) reports the app kind, target, runtime ID, current version and the version last rolled back; the answer is current, available (size, SHA-256), full, failed, off or unavailable, and GET /update/file downloads the file. Devices check when they go online and when they are refused because of a protocol mismatch; an older portal without the endpoint is ignored quietly.
  • Applying on a Worker. Once the update is installed, the window app stops claiming runs and restarts with --background after the current run. The new process carries the old one's pid (RPA_RESTART_AFTER) and waits for it to exit and release the single-instance lock before choosing a layer. Pressing "Resume jobs" cancels the restart, and a Worker the user had already paused is not restarted either; both apply the update on the next start. If the new layer fails before it is confirmed after such a restart, the launcher restarts once more, so the device rolls back even with nobody at the computer. --no-window only reports the update.
  • Recorder. It only says "close and reopen to apply" and never restarts itself.
  • Setting and pages. "Update devices automatically" is stored in the settings table (device_updates) and is on by default. The Devices page shows the server's update file and each device's most recent update state (kept in memory only; after a server restart it waits for devices to report again). "Needs the full installer" explains that the runtime differs, and hovering shows the device's and the update file's runtime IDs; when an update state explains the difference, the separate "Differs from the portal's code" warning is not shown (2026-10-26).
  • Release. release.yml builds and signs RPA-Update-<version>.zip with the RPA_UPDATE_SIGNING_KEY secret and checks that every package trusts exactly the public keys in rpa_update/keys.py (RELEASE_KEYS); without a real key the release fails. How to create the key: CI and pipelines › Update signing key. Builds on pull requests test with a temporary key.
  • Measured (local Linux x86_64 build). The update file is about 1.9 MB (the seven packages compiled to .pyc). The packaged Worker loads a newly installed layer, confirms it, rolls back after two failed starts, and a restarted process waits for the old one to exit (taking over within about 0.5 seconds).

Consequences

  • For a release whose runtime ID does not change (for example 0.4.0 to 0.5.0), upgrading the whole system goes from "6 files of 84 to 136 MB, downloaded and installed on every device" to "1 file of about 2 MB, given to the server once". Devices download over the LAN and need no GitHub account.
  • The server and the devices keep the same code fingerprint, so the "different version" warning and the M7a "app too old" failures should become rare.
  • The server still restarts (Python loads code at startup), so the Portal is unavailable for a few seconds. Remote Workers retry reports for 10 minutes and reconnect to claim (existing behaviour); with the lease extension no run is lost.
  • 0.5.0 has no launcher, so the first layered release (planned as 0.6.0) needs one last full install; pairing, settings and data are kept. A server run from a clone switches to the server bundle at the same time.
  • Costs: a launcher and an update flow to maintain; desktop apps get somewhat larger from the full standard library; code is loaded from a user-writable folder, so safety rests on the signature; the update endpoint's format must stay compatible forever; if the signing key is lost or leaked, a new full package is needed to rotate it.
  • CI gains another path: treat the full package from this build as the previous release, install an update file with a different commit, run the self-test again, and check that an update that fails at startup is rolled back automatically; the server bundle job also tests upgrading, rolling back and refusing tampered files.

Alternatives not chosen

OptionWhy not
Compare files and download only the changed onesPyInstaller compiles our code into the executable's archive, so the executables change every release. The code layer has to be split out anyway, and once it is, comparing files adds little.
Binary diffs of the installers (bsdiff and the like)Diffs of compressed installers are poor, and every pair of versions needs its own diff, which complicates publishing and storage.
Whole-package auto-updaters such as Sparkle or WinSparkleThey make updates automatic but not smaller, and need a public download URL (the repository is private) and signing certificates.
Reload modules while running (importlib.reload)Old objects and state stay in memory; behaviour is hard to predict and failures are hard to trace.
A server that never stops (two processes taking turns)Needs a reverse proxy in front, and SQLite cannot be written by two processes at once (ADR 0008). It saves only a few seconds.
Every device downloads from GitHub directlyThe repository is private and needs an account; devices on the internal network cannot always reach GitHub.
No signature, only hashes and the device tokenDevices talk to the server over HTTP today; an update replaces the program itself and stays, which is a bigger risk than a one-off scenario.
