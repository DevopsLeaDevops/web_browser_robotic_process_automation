ADR 0017: Third-party agents operate the platform through a separate /agent-api/v1 authorized by API keys

Agents connect only to the server. Debugging goes to a chosen recorder, validation and execution go to workers, and business rules and the publish gate reuse the existing services. The new layer only handles authentication, permissions, auditing and the external contract.

Context

User request (2026-10-23): a third-party agent system uses the Linux server's API to operate a recorder, creating, changing and debugging scene scripts and parameters; it then has the server call workers to validate and execute them, and reads how each run progresses.

The existing /api already covers scenes, revisions, debugging, validation and execution, but it has no authentication: it is open only on the server's local port 8080, or from the external port with a recorder's device token. Interactive subprocesses open on "the recorder the request came through"; an agent does not come through a recorder and cannot choose one. Workers report only five stages, with no step-level progress.

Decision

  1. A separate external API. The external port gains /agent-api/v1 with its own OpenAPI. Routes only forward to the service layer and do not copy business rules. /api, the Client API and the Worker API do not change.
  2. API clients. Each agent system is registered in the admin area as one client. Its key is shown once and only its hash is stored. A client sets scopes (scenes:read, scenes:write, debug, runs:validate, scenes:publish, runs:execute, runs:read), allowed domains and recorders, run location and worker, limits, page content, expiry and source IPs.
  3. Agents connect only to the server. A debug request carries recorderId, and the server uses the existing use_recorder to hand the subprocess to that recorder. The recorder must have "Allow agent debugging" turned on in its device page and can be limited to headless. When someone is already debugging the scene the API returns 409 and does not close their session.
  4. Publishing needs per-client authorization. Agents may publish, but only clients with scenes:publish ticked, which is off by default (user decision, 2026-10-23). The publish gate does not change: the published revision must be one that passed validation with a matching hash.
  5. Page content is off by default. Screenshots, page structure and video follow the client's "Return page content" setting, which is off by default. An administrator turns it on after confirming the agent's model may receive internal pages (recommendation the user accepted). Secret values are never returned.
  6. Reading page structure is in phase 1. The debug subprocess gains a snapshot command (accessibility tree, form fields, iframes and tabs) with values masked. Recorders report support when they connect, and older ones get 409 with a prompt to update (the user asked to move it forward, 2026-10-23).
  7. Run progress. Phase 1 provides status, stage, and steps and files after the run. Phase 2 reports step progress from steps.json through heartbeats and adds event long polling and webhooks.
  8. Audit. Every write request records time, client, action, target and result, append-only. Revisions and runs show which client triggered them.
  9. No MCP adapter. Only the HTTP API and the usage guide are provided (user decision, 2026-10-23).

Consequences

  • Most endpoints forward to existing services. Phase 1 work centers on authentication, permissions, auditing, choosing the recorder and reading page structure.
  • There is one more external interface. Keys travel in clear text over HTTP, so put HTTPS in front of the server when the agent is not on a trusted network.
  • Reading page structure needs a new Recorder app release. Older apps can still debug but cannot read page structure.
  • When the agent uses an external model, turning on "Return page content" lets internal pages leave the intranet; administrators decide this per client.
  • When M8 adds users and project permissions, API clients must join the same permission model.
