ADR 0012: Remote workers claim jobs from the management portal over HTTP

Runs can be handed to another computer. A remote worker never connects to the database; it claims jobs, reports progress and results through the Worker API on a separate portal port, using a token. Local mode stays as it is.

Accepted
Date
2026-10-13
Scope
rpa-worker, rpa-server, rpa-cli (from M9a); deployment (M9)
Related

Context

The management portal, database, worker and files all lived on one computer. Tests mostly run headed, and once a browser window opens that computer cannot be used for anything else. The user has another computer that can be dedicated to running, so a small part of “distributed workers” from roadmap M9 is brought forward (M9a).

The original plan (ADR 0003) had workers connect directly to PostgreSQL and claim jobs with Procrastinate. The MVP uses SQLite, which allows a single process only (ADR 0008); and giving another computer database credentials and network access to the database is not a burden the MVP should carry.

Decision

  • Only the management portal touches the database. Remote workers use the Worker API (/worker-api/v1) to come online, long-poll for jobs, send a heartbeat every 5 seconds, upload the run directory and report the result.
  • Workers connect to the portal. The worker computer only needs to reach one portal port; the portal never connects to workers.
  • The Worker API has its own port and every request needs a token. rpa serve --worker-port opens it, listening on all network interfaces by default; the portal pages and /api stay on the original address (127.0.0.1 by default). Each worker has its own token, stored only as a hash.
  • Leases, no automatic retries. Claiming grants a 60-second lease that heartbeats extend; when it expires the run is marked failed as “worker lost”, because it may already have had side effects. Anything the worker reports later is refused.
  • The local worker stays. The same rpa_worker.Worker is used with a different job source; with no remote worker registered nothing changes. Runs gain a “where to run”: this computer, remote, or any.
  • The rules for results do not change. The hash computed by the remote runner still goes through the publishing gate; artifacts are uploaded into the portal's run directory, so reports look the same as local ones.

Consequences

Benefits

  • Worker computers need no database credentials and no network access to the database; this still works after moving to PostgreSQL or adding more workers.
  • Headed browser windows appear on the worker computer, so your own computer is no longer taken over.
  • Local and remote runs share the runner, the run directory and the publishing gate; there is no second execution path.

Costs

  • Secrets and role login states have to reach the worker (only in memory and in temporary files during the run); over HTTP they cross the LAN in plain text, so use it only on a trusted network. HTTPS can come later.
  • One more port is open to the LAN; the operating system's firewall must allow it.
  • When a worker is lost, that run simply fails and a person must check before running it again.
  • A playground sequence is pinned to the worker of its first node; if that worker goes offline, the remaining nodes wait.

Alternatives not chosen

OptionWhy not
Workers connect directly to PostgreSQL (Procrastinate, ADR 0003)The MVP uses SQLite; worker computers would need database credentials and network access to the database.
The portal pushes jobs to workersThe portal would have to reach every worker, which reverses the network setup and is harder; only worth it if workers cannot reach the portal.
A message queue such as RedisOne more service to deploy and maintain; HTTP long polling is enough for the current load.
Open the whole management portal to the LANThe portal has no sign-in (that comes in M8), so anyone on the LAN could use it.
Watch runs over remote desktopOnly solves seeing the run, not freeing your computer; and it means connecting by hand every time.
