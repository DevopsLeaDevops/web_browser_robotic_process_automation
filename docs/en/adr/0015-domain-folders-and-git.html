ADR 0015: Scenarios and composite scenarios live in domain folders, synced between servers through git

Each domain is a self-contained folder (manifests, immutable revisions, validation and publication records); the database is only an index. A domain folder can be synced with a directory in a git repository, so servers that record, validate and use scenarios in different places share the same definitions, while login states, Secrets and run records stay on each server.

Context

Before M11, scenario revisions were stored in scenes/<scenario>/<n>/ in the data folder, while revision states, validation results, publications and composite scenario definitions lived only in SQLite. That is fine for one server, but operations are distributed: people record in different places, several people validate before publishing, and scenarios are used on several servers. Two servers had no way to exchange scenarios or see each other's validation results, and a composite scenario that used another business domain's scenarios had nowhere to state what it depends on.

The user wanted scenarios and composite scenarios to live in a third-party repository like code, with each domain loadable on its own, so that a new server pulls only the domains it needs and can record, debug and run them.

Decision

  • Domain folders. domains/<domain>/ holds pack.yaml (name, description, the domains it depends on and where to get them), scenes/, roles/ and composites/. Scenarios and composite scenarios follow the same rules: a manifest, immutable revision directories, revision files (hashes) and validation records. The format is in rpa_core.pack; rpa pack check checks a folder without the Portal.
  • The database is an index. It is rebuilt from the folder on start, after a pull and on Reload; only per-server settings live only in the database (URL overrides, order, sources, sync state).
  • Validation and publication records go into the folder (D3). Each validation writes a record (who, which server, which worker, result, hash; for composite scenarios also the scenario revision each node ran), and publication is written to scene.yaml/composite.yaml. The publishing gate is “the folder has a passed record with a matching hash”, whichever server validated it.
  • Run records stay out of the folder (D4). Reports and screenshots stay in the server's runs/ and workflow-runs/, with a run.json for later review.
  • Only the server does git (D5, D6). Each domain can have a repository, branch, directory and authentication (public repository, HTTPS token, or an SSH deploy key the Portal generates). Pulls and pushes merge file by file (last sync, local, remote); only a file changed differently on both sides is a conflict, which stops with three choices (cancel, push to a new branch, or use the remote after a backup), and nothing is ever force-pushed. Revisions with the same content hash count as the same revision.
  • IDs stay globally unique (D8). References in the DSL, roles and composite scenarios do not change; cross-domain dependencies are recorded in each composite scenario revision's requires (domain, scenario, revision, hash) and in pack.yaml, and the pages say how to fill a gap (add from git, pull, save again).
  • Secrets stay on the server (D9). Secret values, login states, URL overrides, git tokens and private keys stay in the server's data folder; pushing is blocked by file names that look like secrets and by content containing a Secret value.
  • Automatic migration on upgrade (D7). Back up to backups/ first, then move the old revision directories and the database's validations, publications and composite scenarios into domain folders.

Consequences

Benefits

  • Scenarios, composite scenarios and their validation and publication history can be reviewed and traced in git, in the company's own repository.
  • A passed record from any server can back a publication: “A validates, B publishes” needs no rerun.
  • A new server only sets up the domains it needs; recorders and workers do not change (tasks carry their files).
  • An existing revision changed outside the Portal no longer matches its hash, so it can neither run nor be published.

Costs

  • There are two copies of the state: the folder is the truth and the database is aligned on load; files changed outside the Portal need a Reload (D10, no watching).
  • Creating the same revision number of a scenario, or publishing the same scenario, on two servers at once conflicts and needs a person to decide; edit a scenario on one server at a time.
  • The server needs git 2.25 or later; pushing needs write access to the repository (a token or deploy key).
  • MVP trade-offs: the working copy fetches all objects of the branch rather than only the configured directory (it only matters for very large repositories); while a domain is syncing, a second git operation on it gets “syncing” right away, and saving in the Portal does not queue; instead the folder is checked before applying and the user is asked to retry if it changed.

Options not chosen

OptionWhy not
Syncing databases (export/import or replication)No history, no review, no way to take one domain; SQLite does not suit writes from several servers.
Publication state only on each server (not in git)The original proposal; the user asked for publication state to be recorded, because several people validate before publishing and scenarios are used in several places (D3).
A commit for every saveCommits would be tiny and saving would wait for the network; instead local changes are the difference from the last sync, committed once when pushing.
Merging the contents of the same file automaticallyA wrong merge of revision or publication YAML would break the publishing gate; revision directories are immutable and validation records are one file each, so conflicts are rare and left to a person.
A sparse working copy and rebaseThe original design; replaced by a bare repository and low-level git commands that replace only the configured directory, which needs no working tree, gives the same result as a rebase and never touches other directories.
git on recorders and workers tooCredentials would spread to every computer; tasks already carry their revision files (M9a, M10), so the protocol does not change.
