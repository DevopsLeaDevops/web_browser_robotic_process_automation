ADR 0020: Python script scenarios become Python nodes that run with browser scenarios in composite scenarios

No new kind of scenario: the existing script: gains runtime, which runs it in the platform-built RPA Python runtime without a browser; without runtime it runs as before. A composite scenario's nodes can be browser scenarios or Python nodes; data passes through array and object inputs and outputs, files through a shared workspace on the same Worker.

Context

Much work is out of a browser's reach: reading and writing Excel, merging files, cleaning data, calling APIs, building models. Since M1.1 there have been “Python script scenarios” (script: { automation, assertion }), but a packaged app runs them with its own bundled Python, which has only the standard library and the app's packages, and dispatch always treats them as needing a browser.

The second design of 10-24 would have archived them and added a python: scenario. Checking on 10-29 showed that the script contract never depended on a browser (the Runner hands over input.json and collects facts.json and candidate outputs); composite nodes record only “scenario + pinned version + input bindings”, whatever the kind; and a composite run already stays on one Worker. What was missing were packages, dispatch, structured inputs and a way to pass files.

Decision

  • One node, two modes. Without script.runtime it is compatible mode, exactly as before (same hash, may open its own browser). With "1" it is runtime mode: RPA Python runtime 1, no browser or login, the assertion is either assertion.py or DSL verify (with verify, outputs have a from), and file inputs are allowed. Both modes may list files (other text files the scripts use, included in the hash) and platforms.
  • RPA Python runtime. A platform-built and tested Python 3.13 with fixed packages, built per platform in CI and shipped with the Worker app and the Linux package; extracted to the cache on first use, self-checked and reused. Runs use -E -s to keep the computer's Python and PYTHON* variables out. Model packages stay out of the base runtime and become an optional layer later (D4).
  • Dispatch. Runtime-mode jobs go only to devices that report that major version on a platform listed in platforms; browsers and displays do not matter. Otherwise the run page explains what it waits for. Older apps are held back by the M7a features (pythonNodes, jsonInputs).
  • Data and files in composite scenarios. Inputs gain array and object, so an upstream output of the same type connects directly. Each composite run has a shared workspace on its Worker, which is also the Python nodes' working directory; it is deleted when the composite run ends, and only declared produced files are uploaded (D3).
  • rpa_script. Runtime mode starts scripts with python -m rpa_script: scripts that read and write the contract's files themselves need no change; scripts with @automation get steps, facts, produced files and data previews, written as a steps.json in the DSL format.
  • A runtime stage. After the inputs and before the automation the runtime is prepared, not counted against the deadline; result.json gains python (mode, version, platform, reused or freshly extracted).

Consequences

  • Browser scenarios and Python nodes share one composite scenario, one set of inputs and outputs and one publishing gate; there is no second model to learn.
  • Existing script scenarios need no migration; ADR 0009's “script scenarios have no verify” holds only for compatible mode, as does ADR 0014's “packaged scripts can use only the app's bundled packages”.
  • The Worker app and the Linux package carry a runtime (about 60–75 MB compressed); the first use spends a few seconds extracting it.
  • Computers without browsers or a display can be Workers for Python nodes.
  • A Python node is not a sandbox: it runs arbitrary code on the Worker as that user, so only trusted people edit it and reviews flag it.
  • Intermediate files in the shared workspace are not kept; files people need go to produced files. If a remote Worker missed the end notice, it removes the workspace a day later when it goes online.
  • Later (P3): an optional model package layer, the script workbench, composite fan-out (foreach), and Python nodes using login roles (to be decided).
