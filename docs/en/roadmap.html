Why this order

  • One real chain first. M2 runs BA-001 → BA-002 from the CLI; the management interface is a layer on top.
  • MVP first. Single machine, single user, serial execution; SQLite and a file directory are enough (ADR 0008). Multiple users and distribution come after the MVP is proven.
  • Success needs evidence. From M2 on, outputs are published only after the independent assertions pass; simulated results in the interface never count for publishing.
  • Chain first, then generate (M6 before M5). The playground only uses published scenarios and needs no new external service, so it can start right away; M5 first needs a decision on the AI model (whether internal pages may be sent to an external API). With the playground in place, scenarios generated in M5 can be checked in a sequence straight away.
  • Move runs off your own computer first (M9a before M5). Tests mostly run headed, and the browser windows take over the computer running the portal; with a computer dedicated to running, the remote workers of M9 come first. Only where runs happen changes, not scenarios, contracts or the publishing gate.
  • Make it installable for others first (M10 before M5). The server will move to production; recorders and execution machines must work without development tools, and the recording browser must open on the recorder's own computer. Only installation and where child processes run change, not scenarios, contracts or the publishing gate.
  • Generation only produces drafts. Recorded and AI output must pass a real validation and be published by a person, and the published revision must be the validated one.
  • The runner is stateless from day one. It takes a scenario, inputs and secrets and returns results and artifacts; the M3 background worker and the M9a remote workers reuse it as is.

Still to decide

AI model
Decide before M5. First confirm whether internal system pages may be sent to an external API; if not, use a self-hosted model.
Login method
M4 relies on manual login first (it handles any login flow) and offers automatic login for plain username/password systems; the test site uses two roles, “regular user” and “manager”. How the real target systems log in and which roles they need is still to be confirmed.
SSO type
Before M8, confirm whether the company uses OIDC or LDAP / AD.
Deployment
Before M9, confirm a single Docker Compose host or Kubernetes.
Code signing
M10 ships unsigned (the first launch is allowed by hand); signing is added once there is an Apple Developer account and a Windows code-signing certificate, changing only CI.
Object storage
Before M9, choose an S3-compatible product such as SeaweedFS, Garage or the company's existing storage; the originally planned MinIO community edition is no longer maintained.
