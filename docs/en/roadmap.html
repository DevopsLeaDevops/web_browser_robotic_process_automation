Roadmap

Plan v2: combined with the MVP prototype, deliver a single-machine, single-user MVP first, then add flow features, multiple users and operations. Every step: explain the design → confirm → write code and tests → open a PR → merge after review.

Plan v2
The decisions behind v2 are in ADR 0010; the MVP prototype is the reference for the MVP's pages and flows.
Order change (2026-10-13): after M4, M6 Playground comes before M5 AI assistant, so the MVP is now done with M5; milestone numbers stay the same. The reasons are under “Why this order” below. M9a was then inserted between M6 and M5 to bring the remote workers of M9 forward.
M10 inserted (2026-10-15): M10 desktop distribution comes before M5; the rest of M5, M8 and M9 moves later. The three remaining small M9a items and its two-computer acceptance join M10.1. Design in Desktop distribution and ADR 0014.
M11 added (2026-10-19): M11 data storage upgrade comes after M10.2 (D11): scenarios and composite scenarios move into domain folders, validation and publication records travel with the folders, and servers sync through git; M5 still comes later. The decision is in ADR 0015.
M12 added (2026-10-20): M12 run replay comes after M11: runs are recorded during validation and execution and can be replayed in the Portal afterwards, with the video lined up with the steps, so the scene of a run can be reconstructed; M5 still comes later. The decision is in ADR 0016.
M7a inserted (2026-10-21): the iframe part of M7 moves ahead of M5: during validation, recordings with elements inside iframes could not be converted, and forms in real systems often live in iframes. Locators gain frame (the iframe that holds the element; can be nested); the rest of M7 is unchanged.
M7b inserted (2026-10-21): next, tabs opened by a click (part of M7's multiple tabs) move ahead: during validation, expect_popup and actions on the new tab could not be converted. Steps gain popup (this step opens a new tab) and page (the tab a step runs in); the rest of M7 is unchanged.
M14 added (2026-10-23): the Agent API: a third-party agent system creates and debugs scenarios, has Workers validate and run them, and follows run progress through the server's /agent-api/v1. The design is confirmed and split into three phases; the decision is in ADR 0017.

Why this order

  • One real chain first. M2 runs BA-001 → BA-002 from the CLI; the management interface is a layer on top.
  • MVP first. Single machine, single user, serial execution; SQLite and a file directory are enough (ADR 0008). Multiple users and distribution come after the MVP is proven.
  • Success needs evidence. From M2 on, outputs are published only after the independent assertions pass; simulated results in the interface never count for publishing.
  • Chain first, then generate (M6 before M5). The playground only uses published scenarios and needs no new external service, so it can start right away; M5 first needs a decision on the AI model (whether internal pages may be sent to an external API). With the playground in place, scenarios generated in M5 can be checked in a composite scenario straight away.
  • Move runs off your own computer first (M9a before M5). Tests mostly run headed, and the browser windows take over the computer running the portal; with a computer dedicated to running, the remote workers of M9 come first. Only where runs happen changes, not scenarios, contracts or the publishing gate.
  • Make it installable for others first (M10 before M5). The server will move to production; recorders and execution machines must work without development tools, and the recording browser must open on the recorder's own computer. Only installation and where child processes run change, not scenarios, contracts or the publishing gate.
  • Clear the iframe blocker first (M7a before M5). Forms in real systems often live in iframes, and a recording that cannot be converted cannot be validated. Only one locator field is added; scenario contracts and the publishing gate stay the same, and the other flow features of M7 keep their place.
  • Then clear new tabs (M7b before M5). Real systems often open details in a new tab, and a recording that cannot be converted cannot be validated either. Only two step fields are added; scenario contracts and the publishing gate stay the same.
  • Generation only produces drafts. Recorded and AI output must pass a real validation and be published by a person, and the published revision must be the validated one.
  • The runner is stateless from day one. It takes a scenario, inputs and secrets and returns results and artifacts; the M3 background worker and the M9a remote workers reuse it as is.

Still to decide

AI model
Decide before M5. First confirm whether internal system pages may be sent to an external API; if not, use a self-hosted model.
Login method
M4 relies on manual login first (it handles any login flow) and offers automatic login for plain username/password systems; the test site uses two roles, “regular user” and “manager”. How the real target systems log in and which roles they need is still to be confirmed.
SSO type
Before M8, confirm whether the company uses OIDC or LDAP / AD.
Deployment
Before M9, confirm a single Docker Compose host or Kubernetes.
Code signing
M10 ships unsigned (the first launch is allowed by hand); signing is added once there is an Apple Developer account and a Windows code-signing certificate, changing only CI.
Object storage
Before M9, choose an S3-compatible product such as SeaweedFS, Garage or the company's existing storage; the originally planned MinIO community edition is no longer maintained.
