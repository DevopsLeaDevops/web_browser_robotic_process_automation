Positioning

The problem we solve, and the core concepts the whole platform is built around.

The problem

  • Repetitive manual work. Logging in to internal systems, filling in forms, running queries and exporting reports every day takes time and invites mistakes.
  • Only developers can write scripts. Automation scripts are scattered across personal computers, hard to share, and nobody knows which version is the right one.
  • Pages change and scripts break. When a selector stops working, it is hard to see which step broke and why.
  • No governance for shared use. There are no permissions, auditing or credential management, and passwords often sit right in the scripts.

Out of scope

  • Desktop application automation: only actions inside the browser.
  • Solving CAPTCHAs or bypassing the target system's security measures.
  • Large-scale web crawling.
  • Replacing test frameworks: it can run checks, but its purpose is business process automation.

Generate → Manage → Run → Report

The platform's main loop

1　Generate

  • Record user actions
  • Have AI produce it from natural language
  • Compose from templates or sub-scenarios

2　Manage

  • Revisions and the publishing gate
  • Inputs, outputs and categories
  • Permissions and auditing

3　Run

  • Triggered manually, on a schedule or by API
  • Many workers in parallel
  • Retries and timeouts

4　Report

  • Screenshots and logs for every step
  • Playwright trace replay
  • Failure location and self-healing selectors

Core concepts

Scenario
A repeatable sequence of browser actions described in a declarative DSL (in rare cases a Python script, see ADR 0009). The platform's core asset, with a stable id and a category.
Revision
An immutable version of a scenario: draft → validating → passed or failed → published. Any change requires validating again, and the published revision must be the one that passed.
Step
One action in a scenario, such as opening a URL, clicking, filling in a field or extracting data. Every step has a stable id.
Target
Describes which element on the page to act on. It can have several candidates, tried in order of priority.
Input
A value given only at run time, such as the month to query; it has a type, constraints and a default, and is validated before the browser starts.
Fact
A value extracted from the page during a run. It only describes what was seen and does not mean success.
Verify
Rules that compare facts with inputs after the automation ends. "The script did not fail" is not success.
Output
A result published only after the independent assertions pass; it can feed the next scenario's inputs.
Secret
Credentials and other sensitive values. Scenarios refer to them by name only; the plain value never appears in scenarios, logs or screenshot captions.
Run
One execution of a revision, recording who triggered it, the inputs, and the result and duration of every step; its status is queued, running, passed, failed, timed out, cancelled or needs login.
Artifact
Screenshots, traces, downloaded files and extracted data produced by a run.
Workflow
Published scenarios arranged in sequence; upstream outputs bind to downstream inputs, and it stops on failure (M6).
Debug session
A recording or draft is debugged in an isolated browser; the AI assistant can only edit drafts, and publishing needs the user's confirmation (M4, M5).
Project
The unit of permission isolation. Scenarios, secrets and runs all belong to a project (M8; the MVP has a single user).
