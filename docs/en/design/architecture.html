Architecture

Components, data flow and directory layout. The whole platform is deployed on the intranet: the server keeps scenarios and records, the two desktop apps (Recorder and Worker) connect to the server, and the browsers on their computers drive the target systems directly. This page reflects v0.6.3 (released 2026-10-26) and main after it (M7c file uploads, the composite run summary report and combined replay; not yet released).

Current deployment

v0.6.3: one server + Recorder (macOS) + Worker (Windows, macOS)
Blue borders mark the core components; gray boxes are external systems; dashed lines are optional. Every connection is opened by an app, so the server never needs to reach them, and only the server touches the database and the data directory; the server can be Linux, macOS or Windows and needs no screen; on Linux it can be installed from the self-contained package with its own Python (from v0.5.0), and from v0.6.0 it upgrades with a signed update file of about 2 MB while devices follow the server's version when they come online (ADR 0018). The Recorder uses a device token, the Worker a worker token and third-party agents an API key (Agent API); over HTTP all of them travel in plain text, so use a trusted network only. When the server has no browser (for example a Linux host), login checks run on the Recorder. Installation: Deployment and operations, Desktop distribution.

How the parts work

Single user (login and permissions come in M8); one server, any number of devices
Management portal

Pages rendered by the server with Jinja, following the layout of the MVP prototype (ADR 0011). Open 8080 in a browser on the server, or use the Recorder app window, which goes through the external port (ADR 0014).

API service

FastAPI: scenarios, revisions and the publishing gate, inputs and outputs, runs and cancellation, reports, debugging sessions, composite scenarios and the project workspace, composite run summary reports and combined replay, devices and invitations, device updates, domains and git sync, replay, uploaded files; the external port also serves /agent-api/v1 for third-party agents (ADR 0017). Interactive child processes run on the computer the user is operating: requests from a Recorder are handed to that Recorder.

Execution

The local worker is a thread inside the server; remote ones are the Worker app or rpa worker (ADR 0012). One job per machine at a time; each run starts the runner in a subprocess with an overall deadline and cancellation. The run location can be local, remote or any; a composite scenario stays on one machine.

Data and artifacts

Domain folders hold the immutable revisions of scenarios, roles and composite scenarios together with their validation and publishing records, and are the source of truth; SQLite is the index plus each server's own state (ADR 0015, ADR 0008). Run directories, videos, uploaded files, login states and secrets stay on that server.

Requests flow portal → API → worker. Workers write back run status and artifacts and the portal polls for progress; long tasks never block web requests.

Remote execution (M9a, M10.1): the Worker connects to the Worker API on the external port and long-polls for jobs. A job carries the files of the scenario revision, the inputs, the secrets it uses and the login state. It sends a heartbeat every 5 seconds (learning whether to cancel), and uploads the whole run directory and reports the result when done. A worker silent for 60 seconds is considered lost and its run is marked failed, not retried. Apps report which DSL extensions they understand (for example frame for iframes), and the server does not give them a job that uses anything they do not understand. See Remote workers.

Recorder (M10.2): the app pairs with an invitation and its window loads the portal pages through a local gateway. The server hands the child processes for recording, step debugging, manual login and login checks to this computer through the Client API, and their output and files come back; conversion, password masking, revisions and the publishing gate stay on the server. See Desktop distribution.

Sync (M11): each domain can be tied to one folder in a git repository; pull and push merge file by file (three-way), and stop for a choice on conflicts. A passing record with a matching hash written by any server can back a publication. Files that look like secrets are blocked before a push.

File inputs (M7c): files chosen in the run, validation and debugging forms are first streamed to the server's file area, and the input only holds a file reference (ID, name, size, sha256). A local run gets the file's location directly; a remote Worker downloads the files listed in its job and checks the sha256; a Recorder gets them with the debugging command or downloads them. Scenario attachments are stored with the revision in the domain folder and count toward the scenario hash. A Worker may also read the folders it allows in its settings. See Scenario DSL and Management portal.

Updates (from v0.6.0, ADR 0018): each version also ships a signed (Ed25519) update file of about 2 MB with only our own code. A server package switches to it with bin/rpa update and restarts itself; Workers and Recorders check with the server when they come online, download the same version, verify it and apply it when it will not interrupt work. A full installer is only needed when Python or third-party packages (the runtime) change.

Data flow of a run

  1. A user triggers a run in the management portal, a composite scenario or the CLI (from M9 the scheduler can create runs too).
  2. The API checks the revision: normal runs use published revisions only, and the files in the domain folder must match the hash. It validates the inputs before any browser starts (for file inputs: whether the file still exists, its size and type) and writes a run record (with its location) and a task.
  3. The local worker or a remote Worker claims the task and starts the runner in a subprocess with the revision files, the inputs, the secrets and the login state (in memory and temporary files only, deleted afterwards), under an overall deadline; a remote Worker downloads file inputs separately, checks their sha256 and puts them in a temporary folder.
  4. The runner opens an isolated browser context, executes step by step and records page facts, reporting the status and the start and end time of each step. The automation stage is recorded (M12, ADR 0016); replay lines the video up with the steps because both use the same clock.
  5. The independent assertions compare the facts with the inputs; only after they pass are the outputs validated and output.json written.
  6. Screenshots, recordings, logs and the report go into the run directory, which a remote Worker uploads as a whole (object storage from M9); on failure the failing stage, step and screenshot are highlighted.
  7. A validation run writes a validation record into the domain folder; a passing record with a matching hash is what allows publishing, and git can carry it to other servers.
