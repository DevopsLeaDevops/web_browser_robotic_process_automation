The MVP stage

M2–M6: single machine, single user, serial execution
Management portal

Opened in a browser; the API service renders the pages with Jinja, following the layout of the MVP prototype (from M3).

API service

FastAPI: scenarios, revisions and the publishing gate, inputs and outputs, runs, reports, debugging sessions (ADR 0011).

Background worker

On the same computer; every run starts the runner in a subprocess with an overall deadline and cancellation, and the whole process group is terminated on failure or timeout.

Data and artifacts

SQLite for metadata (ADR 0008); a file directory for scenario revision snapshots and one directory per run.

Requests flow portal → API → worker. The worker writes run status and artifacts, and the portal reads progress by polling or server-sent events; long tasks never block web requests. Before M2 there are only the CLI and the runner, running directly on your machine.

Data flow of a run

  1. A user triggers a run in the management portal or the CLI (from M9 the scheduler can create runs too).
  2. The API checks the published revision, validates the inputs before any browser starts, and writes a run record and a task.
  3. The worker takes the task and starts the runner in a subprocess with the scenario revision snapshot, the inputs and the secrets (kept in memory only), under an overall deadline.
  4. The runner opens an isolated browser context, executes step by step and records page facts, reporting the status of each step.
  5. The independent assertions compare the facts with the inputs; only after they pass are the outputs validated and output.json written.
  6. Screenshots, traces, logs and the report go into the run directory (object storage from M9); on failure the failing stage, step and screenshot are highlighted.
