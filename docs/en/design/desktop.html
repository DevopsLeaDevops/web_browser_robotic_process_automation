Desktop distribution

M10: the server and database are deployed on one computer; recorders and execution machines each install a desktop app and paste an invitation. The app window reuses the server's existing pages; the browser for recording, step-by-step debugging and manual login opens on the computer the person is using. Decision in ADR 0014.

Recorder: what the user does

macOS
  1. Get the DMG from the portal's "Download desktop apps" and drag "RPA Recorder" (RPA Recorder.app) into Applications.
  2. First launch: the app is unsigned, so macOS blocks it; allow it in System Settings › Privacy & Security (steps under Signing and first launch).
  3. Paste the recorder invitation created on the portal's "Devices" page; pairing is done.
  4. Download the browsers (first time only, with progress).
  5. The window shows the portal. "Start recording", "Debug" and "Sign in" open the browser on this Mac.

Worker: what the user does

Windows
  1. Get RPA-Worker-Setup.exe and install it into the user profile; no administrator rights, uv, git or Python needed.
  2. If SmartScreen appears, choose "More info › Run anyway".
  3. Paste the worker invitation; pairing is done.
  4. Download the browsers; the status becomes "Online".
  5. Closing the window minimizes it to the notification area; "Start when I sign in to Windows" can be ticked.

Only the server touches the database (ADR 0008 and ADR 0012 unchanged). Both apps connect to the server; the server never needs to reach them.

Devices and invitations

M10.1
  • The "Remote workers" page becomes "Devices".It lists both workers and recorders. Adding one means choosing the kind and a name and creating an invitation, replacing today's "copy the token and the start command".
  • Invitation.One line of text: rpa://pair?server=http://192.168.1.10:8081&app=worker&code=…. The code is single use, valid for 24 hours and tied to one kind of app; the database stores only a hash. The app also accepts the server address and code entered separately.
  • Pairing.The app calls POST /client-api/v1/pair with the invitation and receives a device token, stored in the macOS keychain or the Windows Credential Manager. A worker invitation pasted into the recorder (or the other way round) is refused with an explanation.
  • A worker device is simply the existing worker record: the token it receives is used directly with the Worker API. The command line can pair with an invitation too: uv run rpa worker --invite … saves the token in the working folder, and after that uv run rpa worker is enough; giving a token through the environment variable or --token-file keeps working.
  • Management.Disable, re-invite (the old token stops working at once), delete; the page shows online status, app version, operating system and browsers.

External port and access control

M10.1, M10.2
  • Keep --worker-port.No new command-line option; the docs call it the "external port".
  • Routing by path (extending PortGateMiddleware): /worker-api/ needs a worker token; /client-api/v1/pair accepts only an invitation code; the rest of /client-api/ needs a device token; every other path (portal pages, /api, static files) needs a recorder device token and otherwise gets 401.
  • Result.An unpaired computer opening 8081 sees no management pages, and a worker token cannot open them either. This is the minimum access control before M8; M8 later maps devices to users.
  • Local 8080 unchanged.A browser on the server machine keeps using it directly.
  • Transport.HTTP plus tokens on a trusted LAN (the 2026-10-13 decision); HTTPS is listed under planned options.

Interactive child processes: the browser opens where the person is

M10.2; recording, step-by-step debugging, manual login

"This computer" now means "the computer you are using". A request from a recorder hands the child process to that recorder; a request from a browser on the server machine (8080) still runs it on the server. The pages get no extra option.

  • Process host.The recording, debugging and manual-login services start child processes through an injectable launcher and use only a small part of Popen: write a line to standard input, read standard output line by line, stop. Requests from the server machine still use subprocess.Popen; requests from a recorder use RecorderHub.launcher(device) (rpa_server.devices) instead, which returns a RemoteProcess with the same interface and goes through the Client API to that computer. The request decides which computer: once the external port's access control recognises a recorder token, it puts the device into the request's context (rpa_server.context). The server code that reads Lines and parses events does not change.
  • Start.The server sends a "start" command: the module (rpa_runner.record, rpa_runner.debug or rpa_runner.login), arguments (the working folder as the placeholder {work}, never a server path; input files outside the working folder, such as a role's sign-in state, go into .inputs/), the files it needs (scenario, inputs, sign-in state) and environment variables (only those the service names explicitly: language and the secrets in use). The recorder writes the files into its own temporary folder, starts the process, and deletes the whole folder when it ends (and on its next start, any folder left behind). Because the connection is plain HTTP on the LAN, the recorder runs only these three modules and playwright codegen, and refuses environment variables that change the interpreter or library loading (PYTHON*, NODE_*, DYLD_*, PATH and the like).
  • Output and files.The recorder sends back every line of standard output; before sending a line it uploads files created or changed since the last line (screenshots, the recording, sign-in state), so the files are always there when the server handles that line. On exit it syncs once more and reports the exit code.
  • Input and stop.When the server needs to send a line (such as "run step 3" while debugging) or stop the process, it queues a command for the recorder, which picks it up by long polling.
  • Lost connection.Each long poll from the recorder is a heartbeat. After 30 seconds without one, the server treats its child processes as ended (exit code -1001, with the reason written to that session's log, and the page shows it like any other failure); when the recorder reconnects it closes any leftover browser. The same happens when the recorder restarts (a different boot ID when it comes online), when it is disabled, deleted or invited again on the Devices page, and when the server stops.
  • Unchanged.Converting the recording to DSL, masking passwords, creating the draft revision, confirming side effects while debugging and saving sign-in states all stay on the server. Secrets and sign-in states live on the recorder only in memory and temporary files and are deleted afterwards (as with M9a workers).
  • Browser check.The recorder reports its downloaded browsers when it connects; picking a browser it lacks gets an explanation on the page instead of a child process.
  • Records.Recording (recordings.device_id), debugging and manual-login sessions remember which device they ran on; the page header shows which recorder is in use. Each device has at most one recording at a time; a scene has a single debugging session, and starting one on another computer closes the first.

RPA Recorder

M10.2, macOS
  • Local gateway.The app runs a small gateway on a random 127.0.0.1 port and the window loads only gateway URLs; the gateway adds the device token and forwards to the server's external port. The token never enters the web page and does not depend on server cookies; when HTTPS arrives, the gateway pins the certificate so the WebView never deals with self-signed certificates.
  • For this app only.The gateway creates a secret on every launch and sets it as a cookie on the window's first load; requests without it are refused, so other programs and browsers on the same computer cannot use it. The gateway does not forward /client-api/ or /worker-api/, so a page cannot use the token to acknowledge or forge the recorder's commands and output.
  • The app's own pages (pairing, browser download, offline notice, settings) live under the gateway's /__desktop/ and use the design-system CSS.
  • New windows and downloads.Links with target="_blank" (reports, screenshots) open in a new app window; exported files go to Downloads.
  • Server on the same computer (the MVP case): pair with http://127.0.0.1:8081 and take the same path.
  • The app (M10.2 PR 2).The pywebview (WKWebView) window loads only gateway URLs; status, pairing, browser download and settings are pages under the gateway's /__desktop/ (rpa_desktop.recorder_pages, called with fetch rather than pywebview's js_api, so portal pages cannot reach the app's actions). Before pairing the gateway serves only these pages; when the portal answers 401, page navigations are sent back here. The “RPA Recorder” menu has Status and settings, Management portal and Reload. target="_blank" goes through a custom webbrowser handler: gateway URLs open a new app window (sharing cookies) and other sites open in the default browser; for files it cannot display pywebview downloads with NSURLSession, so the gateway cookie is also put into the app's NSHTTPCookieStorage. Closing the main window quits (asking first when work is in progress); only one copy runs; the token is in the Keychain item “RPA Recorder”; data lives in ~/Library/Application Support/rpa/recorder. CI on macOS runs the unit tests for the app, the gateway and the recorder host, and --smoke-test opens a real WKWebView window to check that the page loads through the gateway.
  • rpa recorder in the development environment.The same gateway (rpa_worker.gateway) and process host (rpa_worker.recorder), opened in the default browser instead; for people with a development environment and for the end-to-end tests (usage).
  • Run-location wording.Seen through the recorder, "Local" is shown as "Server", so it is not mistaken for the recorder itself.
  • Local network permission.From macOS 15 the user must allow LAN access; Info.plist carries the usage description (NSLocalNetworkUsageDescription).

RPA Worker

M10.1, Windows
  • Inside is the existing RemoteWorker.Only the token now comes from pairing; claiming, heartbeats, uploads and the test site behave exactly like rpa worker (the run loop lives in rpa_worker.service, shared by both).
  • Delivered in two steps (decided 2026-10-16). Step one is a console build: double-click rpa-worker.exe, paste the invitation, download the browser and take jobs; CI pairs the packaged build for real and runs BA-001 → BA-002 with it. Step two (approved 2026-10-17) adds the status window, notification area, auto-start, single instance and Credential Manager described below; the console build stays available as rpa-child.exe --worker in the same folder, for troubleshooting. The installer comes next (approved 2026-10-18).
  • Status window.pywebview (WebView2) loads a page bundled in the app (the design system's CSS inlined, the original unchanged): pairing (paste the invitation; enter the server separately only when pasting just the code), browser download progress, server, online status, current run, the last 10 runs, app version and where the token is stored; a version different from the server's is flagged, with a Download the new version button that opens the latest GitHub release. Settings: auto-start, Firefox, an internal mirror, language (Traditional Chinese by default and not following the OS, per ADR 0007; the choice is kept in settings.json in the data folder), open the log folder, and pair again. The window does not link to portal pages: management pages are only on the server's 127.0.0.1, and the external port opens to recorders only in M10.2.
  • Notification-area icon.Closing the window minimizes it to the notification area (with a hint the first time); the menu has "Open window", "Pause jobs" and "Quit", and a dot on the icon shows the status. Quitting while a job runs asks first, then cancels and reports it. "Pause jobs" means no new jobs after the current one: the server is unchanged, and the portal shows the worker offline after about a minute (decided 2026-10-17).
  • Start at sign-in.Written to the current user's run-at-sign-in list (HKCU\…\Run, with --background so only the tray icon appears; the window still opens if not paired). On after the first successful pairing, then following the user's choice in Settings; on each start the path is updated to the current location (the unzipped folder may be moved). Headed mode needs a signed-in desktop, so it is not a system service.
  • Single instance.An exclusive lock on instance.lock in the data folder keeps the window version, --no-window and the console version from running together; opening it again brings up the running copy. The copy holding the lock also creates the named mutex RPAWorker.App so the installer can tell the app is running; a stop.request file in the data folder asks it to cancel its job, report and quit.
  • Credential Manager.The token is kept in Windows Credential Manager through keyring; if that is unavailable it falls back to pairing.json (readable only by the user) and the log says so. A token saved in the file by step one is moved over automatically.
  • No console windows.Console child processes started by the windowed app (rpa-child, taskkill) get CREATE_NO_WINDOW; browser downloads start Playwright's driver directly instead of going through rpa-child.
  • No WebView2, sign-out and shutdown.Without the WebView2 Runtime it explains how to install it and keeps taking jobs from the notification area in the meantime. When Windows signs out or shuts down, a running job is cancelled and reported right away (waiting at most 3 seconds, without blocking shutdown); if that is too late, the lease marks the worker lost (ADR 0012).
  • Where data lives.Working data, settings and logs in %LOCALAPPDATA%\rpa\worker (logs rotate and never contain the token or invitation code), Firefox warm-up templates still in %LOCALAPPDATA%\rpa\cache, browsers in Playwright's default %LOCALAPPDATA%\ms-playwright.
  • CI.The Windows build job first runs the desktop unit tests (with the real registry, lock and Credential Manager); --smoke-test opens a real WebView2 window and tray icon; the end-to-end test installs silently, pairs the installed app with --no-window and runs BA-001 → BA-002, then upgrades while the app runs and uninstalls (installer). The windowed app has no standard output, so --version and --self-test use rpa-child.
  • The three remaining M9a items join M10.1: a "run location" filter in run reports, a warning when a scenario URL is a local address, and a "waiting for a worker" hint.

Packaging and builds

M10.0
  • Child-process commands in one place.Ten places currently start child processes with sys.executable -m … (runner, sign-in check, recording, debugging, codegen). rpa_runner.commands produces them instead: python -m module in development, App --rpa-module module when packaged; Python script scenarios become App --rpa-script file; codegen calls the driver shipped with Playwright directly.
  • PyInstaller, folder mode (onedir).macOS builds RPA Recorder.app and wraps it in a DMG; Windows uses Inno Setup for RPA-Worker-Setup-VERSION-windows-x64.exe, which installs into the user profile (installer), and still produces the portable zip. No one-file mode (it unpacks hundreds of MB on every launch and is more often flagged by antivirus).
  • Build info.The version, code fingerprint and protocol version are written into the app at build time (a packaged app has no source files to fingerprint). Version rules follow M9a: a different protocol is refused, a different fingerprint is only flagged.
  • Browsers.On first launch the Playwright driver inside the app downloads them, so the versions always match; they go to Playwright's default user cache. An internal mirror can be set in settings (PLAYWRIGHT_DOWNLOAD_HOST). Chromium is required and Firefox optional, for both apps.
  • Python script scenarios.A packaged app runs them with its own Python, which can import only the standard library and the packages shipped inside the app (Playwright, Pydantic and so on).
  • CI.A new desktop build workflow builds the recorder on macOS (Apple silicon) and the worker on Windows, then runs a self-test: the packaged app downloads Chromium, starts the test site and runs BA-001 headless, proving the packaged child-process path really works. The DMG and installer are attached to that build.
  • Sizes (measured in CI for M10.0).The recorder DMG is 68 MB (166 MB unpacked); the worker zip is 58 MB (139 MB unpacked). The first Chromium download (headless shell included) takes about 570 MB (macOS) to 710 MB (Windows) unpacked; Firefox comes on top.

The worker installer

M10.1, Inno Setup 6.7
  • Current user only.No administrator rights; installs into %LOCALAPPDATA%\Programs\RPA Worker with a Start menu shortcut (a desktop shortcut is optional) and opens the app when done. The data folder %LOCALAPPDATA%\rpa\worker is the same as the portable version's.
  • Languages.Traditional Chinese, Simplified Chinese and English, Traditional Chinese by default and selectable during setup (ADR 0007). Inno Setup's own pages use the translation files from its source tag is-6_7_1 (downloaded at build time and checked against SHA-256, not kept in the repository); the installer's own messages are generated from the app's message catalogs (installer.*), so Traditional Chinese and English are written by people and Simplified Chinese is generated, as for the app.
  • When the app is running.Detected through the app's named mutex; the installer writes stop.request in the data folder so the app cancels its running job, reports it and quits (waiting up to 150 seconds), then replaces the files (also in tray-only mode without WebView2; the console version quits once its current pairing or browser-download step finishes). Windows Restart Manager is not used to force it closed. Upgrades keep pairing, settings and auto-start, and remove the old version's libraries first.
  • WebView2.Without the Runtime, setup runs Microsoft's Evergreen bootstrapper shipped with it (its Microsoft signature is checked at build time); if that fails it explains, and the app can still take jobs from the notification area.
  • Uninstalling.Only after the user confirms the uninstall (Inno Setup's usAppMutexCheck; cancelling leaves the app running) does it ask whether to also delete pairing, settings and logs (including the token in Credential Manager): kept by default; a silent uninstall does not ask and keeps them, and /REMOVEDATA=yes on the command line deletes them. It then stops the app and removes the program, shortcuts and the run-at-sign-in entry. Only the app's own files are deleted: the data folder can be anywhere RPA_WORKER_HOME points to, and the browser and Firefox template caches are shared with other programs.
  • Build and CI.tools/build_desktop.py worker builds the app and zip on Windows and then calls ISCC (Inno Setup is installed on GitHub's Windows runners). End to end: silent install → check the files, shortcut and uninstall entry's version → pair the installed app and run BA-001 → BA-002 → install again while the app runs (the app must exit with code 0) → uninstall and confirm the program, shortcut, uninstall entry and auto-start are gone while the pairing stays → install again and uninstall with /REMOVEDATA=yes, confirming the data folder and the token in Credential Manager are gone. Inno Setup's logs are attached on failure.
  • Not included.Code signing, automatic updates, an offline installer with Chromium inside.

Versions and releases

GitHub Releases, drafts published by a maintainer
  • One version.The server, worker, recorder and every package share one version (MAJOR.MINOR.PATCH, numbers only), tagged like v0.2.0 (decided 2026-10-18). python3 tools/release_version.py bump 0.2.0 changes every package and uv.lock at once.
  • Process.Bump the version on a feature branch → merge the PR → tag on main and push the tag → the Release workflow (.github/workflows/release.yml) checks that the tag matches the package versions and is on main, calls the desktop build (including the install, upgrade and uninstall end-to-end test), and creates a draft release with the installer, the portable zip and SHA256SUMS.txt.
  • Drafts.The repository is public, so anyone can download a published release (without an invitation it cannot reach a portal); a maintainer therefore checks the draft before choosing Publish. A rerun replaces the same draft's files; a published version is never replaced, so use a new version instead.
  • Download the new version.When the app's version differs from the server's, the window's Download the new version opens the latest release (…/releases/latest, which counts only published ones).

Signing and first launch

No signing in the MVP
  • macOS.Only an ad-hoc signature (required on Apple silicon; PyInstaller handles it), no notarization. The first launch after downloading in a browser is blocked: in System Settings › Privacy & Security, find the app near the bottom, choose to open it anyway and enter your password. Since macOS 15, Control-clicking "Open" no longer skips this step. Terminal users can instead run xattr -dr com.apple.quarantine "/Applications/RPA Recorder.app".
  • Windows.No code-signing certificate: when SmartScreen shows "Windows protected your PC", choose "More info › Run anyway"; the browser may also ask to keep the download.
  • Later.With an Apple Developer account, add Developer ID signing and notarization; on Windows, add a code-signing certificate. Only the CI build steps change.

Client API v1

/client-api/v1, external port only
EndpointPurpose
POST /pairExchange an invitation code and app kind for a device token; returns device id, name and server version
POST /helloRecorder comes online: protocol, version, fingerprint, OS, downloaded browsers, whether it can show windows, and the boot ID of this launch (a new one means it restarted, so earlier child processes are treated as ended). The reply carries the channel ID and the current sequence number: after a portal restart the ID differs and the recorder starts again from 0
POST /controlLong poll (up to 25 seconds) for commands: start a child process, send a line, close input, stop; it carries the last sequence number received (after), and unacknowledged commands are given again; it also lists the child processes still running, and one whose start was acknowledged but is missing from the list is treated as ended; also serves as the heartbeat
PUT /processes/{id}/filesUpload created or changed files (zip; safe relative paths only, size limits)
POST /processes/{id}/outputLines of standard output; the exit code when the child process ends

Risks to test

  • WebView2.Built into Windows 11 and usually present on Windows 10 through Edge updates; the installer installs it if missing.
  • macOS local network permission.Confirm that the Chromium started by Playwright reaching intranet sites counts against the app's permission.
  • Antivirus false positives.The PyInstaller launcher is occasionally flagged; folder mode is flagged less, and reports go to the vendor if needed.
  • Private Playwright command."Continue recording" uses codegen's internal enableRecorder; the packaged app must use the same driver, and a Playwright upgrade that breaks it is caught by the self-test.
  • New windows and downloads in pywebview.WKWebView and WebView2 behave differently; both need a manual check.
