Desktop distribution

M10: the server and database are deployed on one computer; recorders and execution machines each install a desktop app and paste an invitation. The app window reuses the server's existing pages; the browser for recording, step-by-step debugging and manual login opens on the computer the person is using. Decision in ADR 0014.

Recorder: what the user does

macOS
  1. Get the DMG from the portal's "Download desktop apps" and drag "RPA Recorder" (RPA Recorder.app) into Applications.
  2. First launch: the app is unsigned, so macOS blocks it; allow it in System Settings › Privacy & Security (steps under Signing and first launch).
  3. Paste the recorder invitation created on the portal's "Devices" page; pairing is done.
  4. Download the browsers (first time only, with progress).
  5. The window shows the portal. "Start recording", "Debug" and "Sign in" open the browser on this Mac.

Worker: what the user does

Windows
  1. Get RPA-Worker-Setup.exe and install it into the user profile; no administrator rights, uv, git or Python needed.
  2. If SmartScreen appears, choose "More info › Run anyway".
  3. Paste the worker invitation; pairing is done.
  4. Download the browsers; the status becomes "Online".
  5. Closing the window minimizes it to the notification area; "Start when I sign in to Windows" can be ticked.

Only the server touches the database (ADR 0008 and ADR 0012 unchanged). Both apps connect to the server; the server never needs to reach them.

Devices and invitations

M10.1
  • The "Remote workers" page becomes "Devices".It lists both workers and recorders. Adding one means choosing the kind and a name and creating an invitation, replacing today's "copy the token and the start command".
  • Invitation.One line of text: rpa://pair?server=http://192.168.1.10:8081&app=worker&code=…. The code is single use, valid for 24 hours and tied to one kind of app; the database stores only a hash. The app also accepts the server address and code entered separately.
  • Pairing.The app calls POST /client-api/v1/pair with the invitation and receives a device token, stored in the macOS keychain or the Windows Credential Manager. A worker invitation pasted into the recorder (or the other way round) is refused with an explanation.
  • A worker device is simply the existing worker record: the token it receives is used directly with the Worker API. The command line can pair with an invitation too: uv run rpa worker --invite … saves the token in the working folder, and after that uv run rpa worker is enough; giving a token through the environment variable or --token-file keeps working.
  • Management.Disable, re-invite (the old token stops working at once), delete; the page shows online status, app version, operating system and browsers.

External port and access control

M10.1, M10.2
  • Keep --worker-port.No new command-line option; the docs call it the "external port".
  • Routing by path (extending PortGateMiddleware): /worker-api/ needs a worker token; /client-api/v1/pair accepts only an invitation code; the rest of /client-api/ needs a device token; every other path (portal pages, /api, static files) needs a recorder device token and otherwise gets 401.
  • Result.An unpaired computer opening 8081 sees no management pages, and a worker token cannot open them either. This is the minimum access control before M8; M8 later maps devices to users.
  • Local 8080 unchanged.A browser on the server machine keeps using it directly.
  • Transport.HTTP plus tokens on a trusted LAN (the 2026-10-13 decision); HTTPS is listed under planned options.

Interactive child processes: the browser opens where the person is

M10.2; recording, step-by-step debugging, manual login

"This computer" now means "the computer you are using". A request from a recorder hands the child process to that recorder; a request from a browser on the server machine (8080) still runs it on the server. The pages get no extra option.

  • Process host.The recording, debugging and manual-login services already start child processes through an injectable launcher and use only a small part of Popen: write a line to standard input, read standard output line by line, stop. LocalHost is today's behaviour; DeviceHost has the same interface but goes through the Client API to the recorder. The server code that reads Lines and parses events does not change.
  • Start.The server sends a "start" command: the module (for example rpa_runner.debug or playwright codegen), arguments (the working folder as a placeholder, never a server path), the files it needs (scenario, inputs, sign-in state) and environment variables (language, the secrets in use). The recorder writes the files into its own temporary folder and starts the process.
  • Output and files.The recorder sends back every line of standard output; before sending a line it uploads files created or changed since the last line (screenshots, the recording, sign-in state), so the files are always there when the server handles that line. On exit it syncs once more and reports the exit code.
  • Input and stop.When the server needs to send a line (such as "run step 3" while debugging) or stop the process, it queues a command for the recorder, which picks it up by long polling.
  • Lost connection.Each long poll from the recorder is a heartbeat. After 30 seconds without one, the server treats its child processes as ended (debugging marked interrupted, recording marked failed); when the recorder reconnects it closes any leftover browser.
  • Unchanged.Converting the recording to DSL, masking passwords, creating the draft revision, confirming side effects while debugging and saving sign-in states all stay on the server. Secrets and sign-in states live on the recorder only in memory and temporary files and are deleted afterwards (as with M9a workers).
  • Browser check.The recorder reports its downloaded browsers when it connects; picking a browser it lacks gets an explanation on the page instead of a child process.
  • Records.Recording and debugging sessions remember which device they ran on; the page header shows which recorder is in use.

RPA Recorder

M10.2, macOS
  • Local gateway.The app runs a small gateway on a random 127.0.0.1 port and the window loads only gateway URLs; the gateway adds the device token and forwards to the server's external port. The token never enters the web page and does not depend on server cookies; when HTTPS arrives, the gateway pins the certificate so the WebView never deals with self-signed certificates.
  • For this app only.The gateway creates a secret on every launch and sets it as a cookie on the window's first load; requests without it are refused, so other programs and browsers on the same computer cannot use it.
  • The app's own pages (pairing, browser download, offline notice, settings) live under the gateway's /__desktop/ and use the design-system CSS.
  • New windows and downloads.Links with target="_blank" (reports, screenshots) open in a new app window; exported files go to Downloads.
  • Server on the same computer (the MVP case): pair with http://127.0.0.1:8081 and take the same path.
  • Run-location wording.Seen through the recorder, "Local" is shown as "Server", so it is not mistaken for the recorder itself.
  • Local network permission.From macOS 15 the user must allow LAN access; Info.plist carries the usage description (NSLocalNetworkUsageDescription).

RPA Worker

M10.1, Windows
  • Inside is the existing RemoteWorker.Only the token now comes from pairing; claiming, heartbeats, uploads and the test site behave exactly like rpa worker (the run loop lives in rpa_worker.service, shared by both).
  • Delivered in two steps (decided 2026-10-16). Step one is a console build: double-click rpa-worker.exe, paste the invitation, download the browser and take jobs; the pairing is kept for now in pairing.json, readable only by the user, in its folder. CI pairs the packaged build for real and runs BA-001 → BA-002 with it. Step two adds the status window, notification area, auto-start, single instance and Credential Manager described below, followed by the installer.
  • Status window.Server, online status, current run, recent runs, app version; a version different from the server's is flagged with a link to the download page.
  • Notification-area icon.Closing the window minimizes it to the notification area; the menu has "Open window", "Pause taking jobs" and "Quit".
  • Start at sign-in.When ticked, it is added to the current user's run-at-sign-in list; headed mode needs a signed-in desktop, so it is not a system service.
  • Single instance.Opening it again brings up the running copy.
  • Where data lives.Working data and logs in %LOCALAPPDATA%\rpa\worker, Firefox warm-up templates still in %LOCALAPPDATA%\rpa\cache, browsers in Playwright's default %LOCALAPPDATA%\ms-playwright.
  • The three remaining M9a items join M10.1: a "run location" filter in run reports, a warning when a scenario URL is a local address, and a "waiting for a worker" hint.

Packaging and builds

M10.0
  • Child-process commands in one place.Ten places currently start child processes with sys.executable -m … (runner, sign-in check, recording, debugging, codegen). rpa_runner.commands produces them instead: python -m module in development, App --rpa-module module when packaged; Python script scenarios become App --rpa-script file; codegen calls the driver shipped with Playwright directly.
  • PyInstaller, folder mode (onedir).macOS builds RPA Recorder.app and wraps it in a DMG; Windows uses Inno Setup for RPA-Worker-Setup.exe, which installs into the user profile. No one-file mode (it unpacks hundreds of MB on every launch and is more often flagged by antivirus).
  • Build info.The version, code fingerprint and protocol version are written into the app at build time (a packaged app has no source files to fingerprint). Version rules follow M9a: a different protocol is refused, a different fingerprint is only flagged.
  • Browsers.On first launch the Playwright driver inside the app downloads them, so the versions always match; they go to Playwright's default user cache. An internal mirror can be set in settings (PLAYWRIGHT_DOWNLOAD_HOST). Chromium is required and Firefox optional, for both apps.
  • Python script scenarios.A packaged app runs them with its own Python, which can import only the standard library and the packages shipped inside the app (Playwright, Pydantic and so on).
  • CI.A new desktop build workflow builds the recorder on macOS (Apple silicon) and the worker on Windows, then runs a self-test: the packaged app downloads Chromium, starts the test site and runs BA-001 headless, proving the packaged child-process path really works. The DMG and installer are attached to that build.
  • Sizes (measured in CI for M10.0).The recorder DMG is 68 MB (166 MB unpacked); the worker zip is 58 MB (139 MB unpacked). The first Chromium download (headless shell included) takes about 570 MB (macOS) to 710 MB (Windows) unpacked; Firefox comes on top.

Signing and first launch

No signing in the MVP
  • macOS.Only an ad-hoc signature (required on Apple silicon; PyInstaller handles it), no notarization. The first launch after downloading in a browser is blocked: in System Settings › Privacy & Security, find the app near the bottom, choose to open it anyway and enter your password. Since macOS 15, Control-clicking "Open" no longer skips this step. Terminal users can instead run xattr -dr com.apple.quarantine "/Applications/RPA Recorder.app".
  • Windows.No code-signing certificate: when SmartScreen shows "Windows protected your PC", choose "More info › Run anyway"; the browser may also ask to keep the download.
  • Later.With an Apple Developer account, add Developer ID signing and notarization; on Windows, add a code-signing certificate. Only the CI build steps change.

EndpointPurpose
POST /pairExchange an invitation code and app kind for a device token; returns device id, name and server version

POST /processes/{id}/outputLines of standard output; the exit code when the child process ends

Risks to test

  • WebView2.Built into Windows 11 and usually present on Windows 10 through Edge updates; the installer installs it if missing.
  • macOS local network permission.Confirm that the Chromium started by Playwright reaching intranet sites counts against the app's permission.
  • Antivirus false positives.The PyInstaller launcher is occasionally flagged; folder mode is flagged less, and reports go to the vendor if needed.
  • Private Playwright command."Continue recording" uses codegen's internal enableRecorder; the packaged app must use the same driver, and a Playwright upgrade that breaks it is caught by the self-test.
  • New windows and downloads in pywebview.WKWebView and WebView2 behave differently; both need a manual check.
