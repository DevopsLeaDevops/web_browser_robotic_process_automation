Scenario DSL

The single source of truth for scenarios. Written in YAML, stored as JSON, validated with Pydantic models; it includes the scenario contract of inputs, outputs and independent assertions. This page specifies schemaVersion 1.

schemaVersion 1 · M1.1
The models live in packages/rpa_core/src/rpa_core/dsl/, examples in scenarios/, and the JSON Schema in schema/scenario.v1.json. For the background see ADR 0001 and ADR 0009.

Example

Excerpt from scenarios/demo/ba-001.yaml (BA-001 of the MVP prototype)
# yaml-language-server: $schema=../../schema/scenario.v1.json
schemaVersion: 1
id: ba-001
name: Create a sample record
category: Sample data
inputs:
  title: { type: string, minLength: 1, maxLength: 60 }
  quantity: { type: integer, minimum: 1, maximum: 30, default: 12 }
outputs:
  recordId:
    pattern: '^DEMO-[A-Z0-9]+$'
    from: '{{ facts.record.recordId }}'
browser: { engine: firefox, baseUrl: http://127.0.0.1:8765 }
deadline: 45000
steps:
  - id: open
    action: goto
    url: /
  - id: fill-title
    action: fill
    target: { label: Title, exact: true }
    value: '{{ inputs.title }}'
  - id: submit
    action: click
    target: { role: button, name: Create record }
  - id: read-record
    action: extract
    target: { css: '#receipt' }
    as: record
    fields:
      recordId: { target: { css: '#record-id' } }
      status: { target: { css: '#record-status' } }
verify:
  - name: Status is created
    value: '{{ facts.record.status }}'
    equals: Created

Design principles

  • Success needs evidence. Steps only operate the page and record page facts; the independent assertions in verify decide success, and outputs are published only after they pass. "The script did not fail" is not success.
  • Inputs and outputs are a contract. Inputs are validated before the browser starts; outputs can feed the next scenario's inputs. Both can be exported as JSON Schema.
  • Every step has a stable id. Results, screenshots and logs are filed by step, so inserting or deleting steps never shifts them.
  • Locators have a priority order. testId → role + name → label → placeholder → text → altText → title → css → xpath. The recorder keeps several candidates in fallback as the basis for self-healing.
  • Only conditional waits. There is no fixed-duration sleep; use waitFor. The whole run is bound by deadline.
  • Mistakes are caught early. Unknown fields, wrong types and YAML's implicit conversions are reported during validation with the file line, step and field.
  • Secrets are referenced by name only. Values are injected at run time and masked in logs and screenshot captions.
  • Python nodes cover what the browser cannot. Work the DSL cannot express or a browser cannot do (files, data processing, network calls) goes into a Python node (script) under the same contract, and can sit next to browser scenarios in one composite scenario; flagged in review.

Scenario contract

inputs → steps → page facts → independent assertions → outputs
inputs
Each input has a type (string, number, integer, boolean, array, object, file; default string; array and object are JSON arrays and objects, so an upstream node's output of the same type connects directly, and they take no enum, length or numeric range), a default, a description and constraints: enum, minLength, maxLength, pattern (strings), minimum, maximum (numbers). An input without a default must be supplied at run time. Defaults must satisfy the constraints too; they can be dynamic values (e.g. {{today}}), evaluated on every run.
facts
Page facts: extract with as: name stores facts.name. A step may only use facts produced by earlier steps; verify and outputs may use them all.
verify
Each rule has a value (which must contain {{ }}) and exactly one comparison: equals, contains, matches (regular expression) or notEmpty: true; its name appears in the report. Both sides are compared as text after substitution.
outputs
Types add array and object; constraints are the same as for inputs. from says where the value comes from, for example {{ facts.record.recordId }}. With a single {{ }} the original type is kept (for example a list); otherwise the text is converted to the declared type.
script
A Python node: the automation and the independent assertion are written in Python under the same contract; see the next section.

For the order of a run and what happens on failure, see ADR 0009; the execution engine arrives in M2. rpa schema SCENARIO --part inputs or --part outputs prints the JSON Schema of one scenario's inputs or outputs.

Python nodes script

ADR 0020: files, data processing and network calls, combined with browser scenarios in composite scenarios

One scenario file plus a few .py files. Inputs, outputs, Secrets, the deadline and the publishing gate are the same as for DSL scenarios; the difference is that automation.py does the automation: it reads the inputs, does the work and writes what it observed as facts, without deciding success. The independent assertion (verify or assertion.py) decides.

# scenes/merge-branch-sales/revisions/1/scenario.yaml
schemaVersion: 1
id: merge-branch-sales
name: Merge branch sales reports
inputs:
  reports: { type: file, multiple: true, accept: [.xlsx] }   # downloaded upstream or uploaded
  options: { type: object, default: { sheet: Sales } }
outputs:
  total:    { type: number, from: '{{ facts.total }}' }
  byBranch: { type: object, from: '{{ facts.byBranch }}' }
deadline: 600000
script:
  runtime: "1"                       # RPA Python runtime 1; without it, compatible mode
  automation: automation.py
  files: [helpers.py, query.sql]     # other text files the scripts use
  platforms: [windows, macos, linux] # optional
verify:
  - name: At least one report merged
    value: '{{ facts.fileCount }}'
    matches: '^[1-9][0-9]*$'

File inputsNot allowedAllowed: the script gets the real paths from RPA_INPUT_FILES (or run.input_files)

automation, assertion
Relative paths of Python files (relative to the scenario file's folder, ending in .py, without ..). automation.py takes --input --facts --screenshot --target-url and assertion.py takes --input --facts --output (the MVP prototype's command-line contract; in runtime mode --target-url is empty). A non-zero exit code from assertion.py fails the assertion.
files
Other text files the scripts use (for example helpers.py, SQL or JSON templates), at most 16, same path rules, any extension; stored with the version and included in the scenario hash, and scripts can import .py files from the same folder. Binary files (Excel templates) belong in the scenario attachments files/, not here. The Portal's whole scenario file editor can add and remove these files.
platforms
A subset of windows, macos and linux; only Workers on those systems get the node. Without it, any system.
Environment variables
Both modes get RPA_DEADLINE_SECONDS (time left), RPA_LANG (interface language) and the declared Secrets (same names). Runtime mode adds RPA_WORKSPACE (the shared workspace, also the working directory), RPA_OUTPUT_DIR (produced files, the run folder's outputs/, uploaded with it), RPA_INPUT_FILES (paths of file inputs, a JSON file), RPA_STEPS, RPA_RUNTIME and RPA_PLATFORM; the computer's PYTHONPATH, VIRTUAL_ENV and similar variables are removed. The browser variables of compatible mode are under rpa run.
Shared workspace
Nodes of one composite run stay on one Worker and share a workspace folder: files the previous node downloaded or wrote are readable by path in the next one (path inputs may point there too). It is deleted when the composite run ends; a standalone run uses a temporary folder deleted at the end. Files meant for people go into RPA_OUTPUT_DIR.
Not a sandbox
A Python node runs arbitrary code on the Worker as that user. Only trusted people edit it, reviews flag it, and Workers should run under a dedicated account.

rpa_script (optional)

Runtime mode starts the script with python -m rpa_script automation.py …: scripts that read and write the files of the contract themselves need no change; scripts with @automation get a Run, and the report shows their steps, data previews and produced files. Compatible-mode scripts can import it too (with rpa_script.current()).

from pathlib import Path

import pandas as pd

from rpa_script import Run, StepError, automation


@automation
def main(run: Run) -> None:
    with run.step("read", "Read branch reports"):      # a step: time, result, error, source line
        paths = run.input_files["reports"]
        if not paths:
            raise StepError("No reports received")      # the report shows only the message
        frames = [pd.read_excel(path).assign(branch=Path(path).stem) for path in paths]
    with run.step("merge", "Merge and total"):
        merged = pd.concat(frames, ignore_index=True)
        run.preview("Merged", merged)                   # data preview: first 50 rows, 30 columns
        merged.to_excel(run.output_dir / "merged.xlsx", index=False)
        run.facts.update(fileCount=len(paths), total=float(merged["amount"].sum()),
                         byBranch=merged.groupby("branch")["amount"].sum().to_dict())

run.inputs (the resolved inputs), run.input_files, run.secrets, run.facts, with run.step(id, name) (the same id in a loop counts as the nth time), run.output_dir, run.workspace, run.preview(name, value), run.log(message), StepError, run.remaining_seconds, run.platform, run.runtime, run.lang. Secret values are masked in console output and errors. run.input_files[name] is a list of files (Path); file changes before and after each step are recorded with the step.

Passing files between nodes: the download step and file outputs

steps:                                   # browser node: download
  - id: export
    action: download                     # click and wait until the download finishes
    target: { role: button, name: 匯出 CSV }
    as: report                           # facts.report = {"workspace", "name", "size", "sha256"}
    fileName: '銷售-{{ inputs.month }}.csv'   # optional: the saved file name
outputs:
  report: { type: file, from: '{{ facts.report }}' }
  • download saves the file to downloads/ in the composite run's shared workspace (a temporary folder of this run when run alone). Recordings convert expect_download into this step.
  • type: file outputs: from (or assertion.py) gives a path (relative paths are relative to the shared workspace) or the download fact; the file must be in the shared workspace or this run's outputs/. The output stage copies it into the run's outputs/ (downloadable from the report) and the value becomes {"workspace", "name", "size", "sha256"}. The per-file and total limits of file inputs apply. Compatible-mode Python nodes cannot use them.
  • Downstream: a composite scenario binds a file output straight to a downstream file input (same Worker, same shared workspace); a downstream Python node gets the file from run.input_files, a browser node hands it to the page with upload. Run alone, such a value is explained as "only available in a composite run".
  • Reports: produced files, file changes (files.json) and data previews; Python nodes replay as a step timeline. Example: scenarios/examples/browser-python/ (download → summarize in Python → upload, workflow.json).

Dynamic input values

Replaced with the current date or a random number when each run starts

Input values can contain {{ … }} dynamic values: a scenario's default, the inputs JSON of the Portal's run form and the API, rpa run -i／--input, fixed values of playground nodes and the inputs of step-by-step debugging. Spaces inside {{ }} are allowed and names are case-insensitive; dynamic values can sit inside text, e.g. CG-001 created on {{today}}.

Written asResult (for a run at 2026-10-21 07:30:05)
{{today}}2026-10-21
{{today+1}}, {{today-7}}2026-10-22, 2026-10-14 (days later or earlier)
{{today:YYYY/MM/DD}}, {{today+1:yyyyMMdd}}, {{today:DD.MM.YYYY}}2026/10/21, 20261022, 21.10.2026
{{now}}, {{now:HH:mm}}, {{now:yyyyMMddHHmmss}}2026-10-21 07:30:05, 07:30, 20261021073005
{{random:10:30}}A random integer from 10 to 30 inclusive; each random is drawn separately
{{"{{"}}Quoted text is kept as is, which is how to write {{ itself
Format
yyyy／YYYY year, MM month, dd／DD day, HH hour, mm minute, ss second (all zero-padded); other characters are written as they are. today has no time of day, so hours, minutes or seconds in its format are an error (most often a month written as lower-case mm).
When
When each run starts (the input stage, before the browser starts), in the local time zone of the computer that runs it. All inputs of one run share the same “now”, so {{today}} is the same day in every input. The run keeps the values as written, so running it again evaluates them again; input.json and the report show the values actually used.The script, subsequent steps, assertions and report share these runtime inputs; referring to an input does not draw again.
Types
When the result is a number written as text (for example the whole value is {{random:10:30}}), integer and number inputs get a number; everything else is text. The result is then checked against the input's type and constraints.
Checks
Any {{ … }} in a value is a dynamic value; invalid syntax such as {{tody}} or {{random:30:10}} is rejected. Saving and queuing preserve the configured expressions: dynamic values are checked for syntax without reading the clock, drawing random numbers or enumerating possible results. Ordinary values still undergo type and constraint checks. At execution start, expressions are expanded once and the resulting runtime inputs are checked against type, enum, pattern, length and numeric bounds. An invalid result fails that run before the browser starts; it is never redrawn until valid. For example, maximum: 20 with {{random:10:30}} can be saved: a draw of 26 fails, while a draw of 18 proceeds.
Recorded text
Recorded fill values are preserved literally. Text containing {{today}} or other braces is escaped automatically; edit the input default afterward to use a dynamic value.
Upstream outputs
When the playground passes an upstream node's output to a downstream node it is always used as is, even if its text happens to contain {{.
In steps
Step {{ }} are expressions and cannot use today, now or random directly; add an input whose default is the dynamic value and refer to it with {{ inputs.NAME }}.
Remote runs
Dynamic values are evaluated on the device that runs the scenario, including step debugging and continued recording. Reloading a debug session preserves resolved inputs and evaluates only new defaults; the Portal displays the values actually used by the recorder. Runs that use them only go to Worker／recorder apps that report dynamicValues; older apps get a message asking for an update (as in M7a).
inputs:
  arrivalDate: { default: "{{today}}" }
  expiryDate: { default: "{{today+1}}" }
  purchaseQuantity: { type: integer, minimum: 10, maximum: 30, default: "{{random:10:30}}" }
  remark: { default: "CG-001 created on {{today}}" }

In YAML, values starting with { need quotes. You can also click Edit on the Inputs panel of a scene in the Portal and change a default to {{today}}; quotes are added when saving.

File uploads

M7c: inputs with type: file and the upload step

Files to upload are always inputs: the scenario only says “this step uploads that input”, and each run decides which file it is. The page sees the file's original name (or the name given in the input), never a temporary path on the machine that runs the scenario.

inputs:
  orderFile:
    type: file
    accept: [.xlsx, .xls, .csv]
    maxSize: 20MB
    default: { attachment: files/orders.csv, name: 訂單匯入.csv }
  photos: { type: file, multiple: true, accept: [image/*], default: [files/product.png] }
steps:
  - { id: open, action: goto, url: /upload }
  - id: choose-orders
    action: upload
    target: { label: 匯入檔案 }            # the file input itself, hidden ones too
    files: '{{ inputs.orderFile }}'
  - id: attach
    action: upload
    trigger: { role: button, name: 選擇附件 }   # a button that opens the file dialog when clicked
    files: '{{ inputs.orderFile }}'
  - id: drop
    action: upload
    dropzone: { text: 把檔案拖到這裡 }      # a drop zone without a file input
    files: '{{ inputs.photos }}'
type: file
Can have accept (a list of .extension or MIME types such as image/*), maxSize (for example 20MB or 500KB), multiple (several files at once; default false), description and default; enum, pattern, lengths and numeric ranges are not allowed. Outputs have no file type yet (it comes with the download step).
Values
Three sources: a file uploaded to the Management Portal, {"file": "id", "name": "October orders.xlsx"} (the id comes back from the upload; size and sha256 are the server's); a scene attachment of this revision, files/name or {"attachment": "files/name", "name": "name the page sees"}; a path on the machine that runs the scenario, {"path": "D:/reports/{{today}}.xlsx"} (paths can use dynamic values). With multiple: true write a list; one input cannot mix uploaded files and paths. A default cannot be an uploaded file (uploads expire).
Scene attachments
Stored under files/ in the revision folder, kept with the revision, synced with git and included in the scenario hash (the hash of a scenario without attachments does not change), so the validated files are the published files. Names use only letters, digits, _, . and -; write name in the value when the page should see another name. Each attachment can be up to 20 MB, and up to 50 MB per revision. Add and delete them under “Scene attachments” on the scenario page of the Management Portal; rpa pack check checks them too.
Paths on the machine
Only allowed folders can be read: in the RPA Worker app's settings (“Folders that file inputs may read”) or the environment variable RPA_INPUT_FOLDERS (several separated by the path separator) on Workers and on the server for local runs; without either, path cannot be used. rpa run runs on your own computer and is not restricted.
upload
files is '{{ inputs.name }}' or a list of such references (file inputs only); [] clears the file input and only works with target. target points to the input type=file (hidden or inside an iframe is fine; within a surrounding button works too); trigger is clicked and the files are handed to the file dialog it opens; dropzone simulates a drop in the page, so the files are sent into the page first and can be up to 20 MB in total. Giving several files to an input that takes one fails with an explanation.
Waiting for the upload
upload is done once the page has the files; how long the page then takes to send them to its server varies, so wait for the result on the page with a later waitFor or expect rather than a fixed delay.
At run time
The input stage (before the browser starts) finds each file, checks accept, maxSize and the total limit, and puts it in a temporary folder under the name the page should see; the folder is deleted after the run. input.json, the report and {{ inputs.name }} see {name, size, sha256} (a list for multiple), never local paths; verify can compare {{ inputs.orderFile.sha256 }} with what the page received.
File dialogs
Every page catches file dialogs: one not opened by upload (for example a recording that clicked an upload button and only has the click) is closed, the step continues, and a note says “change this step to upload with this element as trigger”.
Converting recordings
set_input_files becomes upload plus a file input (named after the element, accept from the recorded extensions, multiple: true for several files), and a preceding click on the same element is removed; recordings only have file names, so put a file in the input (for example as a scene attachment).
Limits and retention
By default an uploaded file can be up to 50 MB and a run up to 200 MB in total (RPA_UPLOAD_MAX_FILE_MB, RPA_UPLOAD_MAX_RUN_MB). Uploads unused for 24 hours are deleted; used ones are kept for 90 days after their last use (RPA_UPLOAD_KEEP_DAYS); above 10 GB in total (RPA_UPLOAD_MAX_TOTAL_GB) the longest-unused go first; fixed files on composite scenario nodes are kept. Only the content is deleted; run records still show the name and sha256.
Command line
rpa run scene -i orderFile=data/orders.xlsx -i photos=files/a.png -i photos=b.png: a value starting with files/ is a scene attachment, anything else a path on this computer; repeating a multiple input gives several files.
Remote runs
Workers and recorders download uploaded files separately and check size and sha256; scene attachments travel with the revision's files. Scenarios that use upload or file inputs only go to apps that report upload and fileInputs; older apps get an explanation to update. Only Python nodes in runtime mode can use file inputs.

Common step fields

id
Required and unique within the scenario. Same format as the scenario id.
action
Required; the action name, see the action table below.
name
A step description for people.
timeout
The timeout of this step as an integer number of milliseconds, greater than 0 and at most 3,600,000 (one hour). Falls back to defaults.timeout, and never exceeds what remains of the deadline.
page
The tab this step runs in (M7b): the name of a tab opened by an earlier step's popup; without it the step runs in the starting tab. The tab must be opened by an earlier step, or validation points at this step.
popup
Only on click, fill, select, check and press (M7b): this step opens a new tab (a pop-up, for example a link with target="_blank" or window.open); the run waits for it and gives it this name, and later steps refer to it with page. Each name can be opened only once. If no tab opens, the step times out and fails. For example { action: click, target: { role: link, name: 開啟商品明細 }, popup: items }, then { action: fill, page: items, target: { placeholder: 請選擇 }, value: … }.

retry and onError are added in M7; retries apply only to steps without side effects, so actions such as submitting a form are never retried automatically.

String matching

match sets how expect's text, value, url, title and waitFor's url are compared:

contains
The default. The text only has to appear, so text: Welcome matches “Welcome back, Alex”.
equals
Exactly equal.
regex
A regular expression in Python re syntax; it is compiled during validation and reported if invalid.

Writing YAML

  • Only YAML 1.2 core rules. yes, no and on are strings, not booleans; 2026-09-01 is a string, not a date; 12:30 is a string, not a base-60 number.
  • No implicit conversion. A number or true/false in a string field is an error; quote it, for example value: "0123".
  • Quote values that start with {{. For example value: "{{ inputs.title }}" or default: "{{today}}"; without quotes YAML reads them as objects, and validation asks for quotes.
  • No duplicate keys. A key that appears twice at the same level is reported with the line of its first occurrence.
  • Unknown fields are errors. When a name is close to a valid one, the correct spelling is suggested, for example fullpage → fullPage.
  • Only plain tags. !!python/…, !!binary and custom tags are rejected; anchors and aliases are allowed, << merges are not supported.
  • Files are UTF-8. A BOM is allowed.

Expressions {{ }}

Jinja2; evaluated in a sandbox from M2
  • The only variables are inputs, secrets, facts and env; Jinja2 filters work, for example {{ inputs.title | upper }}.
  • Validation already checks syntax, unknown variables and filters, undeclared inputs and secrets, and facts that no extract produces or that are produced only later.
  • facts cannot be used in browser settings, because the page has not been touched yet at that point.
  • today, now and random are dynamic input values, not variables here; when they appear in a step, validation suggests moving them to an input.
  • The name and description of scenarios, steps and assertions are text for people; they are neither checked nor substituted.

Running: rpa run

M2
$ uv run python -m testsite --port 8765          # in another terminal: the local test site
$ rpa --lang en run scenarios/demo/ba-001.yaml -i title=Test -i quantity=3
ba-001 建立範例紀錄: Passed (1.4 s)
Outputs: runs/ba-001-20261010-123405-164e7e/output.json
Report: runs/ba-001-20261010-123405-164e7e/report.html
$ rpa run scenarios/demo/ba-002.yaml --input runs/ba-001-…/output.json   # unknown inputs are rejected; use -i recordId=… instead
Order
Input validation (the browser is not started if anything is wrong) → login check (only for scenarios with login: open the role's check URL; when the logged-in element is not visible, log in automatically, or stop at “login required” needs_login without running any step when that is not possible) → the steps or automation.py in a subprocess → independent assertions (verify or assertion.py) → output conversion and validation → output.json. A failure at any stage leaves no successful outputs.
Deadline
Measured with a monotonic clock; each step may use only the time that remains. A subprocess that runs past the deadline is terminated with its whole process group, and the result is "timed out".
Options
-i NAME=VALUE (converted to the declared type, repeatable; JSON for array and object), --input FILE.json, --base-url, --browser chromium|firefox, --headed, --video (record video.webm in the run folder, M12; DSL scenarios only), --deadline MS, --out FOLDER (default runs/), --format json, --storage-state STATE.json (for scenarios with login, load this storageState as is without checking it; checks and manual login are in the management portal). Exit code: 0 passed, 1 not passed.
Run directory
input.json, facts.json, steps.json, output.json (only when passed), screenshot.png and the screenshots taken by screenshot steps, automation.log (the automation log: it starts with this run's browser, window mode, start URL and start time, then one line per step (time, step number, name and action, passed or failed, duration; the URL for opened pages and failures); on failure it names the failed step, the skipped steps, where the evidence is and the full original error; times are local to the computer that ran it, URLs and errors mask secrets, and input values are not written), diagnostic.json (on failure), scenario/ (this run's scenario snapshot), result.json, report.html; with a login check also login.json, login.log and login.png. The login state itself is never copied there.
Secrets
The command line reads them from environment variables of the same name (for example ERP_PASSWORD); the management portal uses the values set under “Logins & secrets” first and falls back to environment variables. They are passed only to the subprocess and masked in logs and reports; M8 stores them encrypted.
Python nodes
Runtime mode adds a “runtime” stage after the inputs (preparing the runtime, not counted against the deadline); see Python nodes. Compatible mode: the remaining deadline is in the environment variable RPA_DEADLINE_SECONDS, the browser in RPA_BROWSER and the current language in RPA_LANG (useful when a script writes messages for people) and whether to show the browser window in RPA_HEADLESS (0 headed, 1 headless), and for scenarios with login the path of the login state file in RPA_STORAGE_STATE (for browser.new_context(storage_state=…)); see scenarios/demo/ba-001-script/. Scripts start their own browser and do not use the warmed profile below.
Firefox profile
When Firefox starts with a brand-new profile, it stops responding for a few seconds while it sets the profile up (on a busy Windows machine this can exceed a step's timeout). So each computer keeps one already-initialized empty profile per Firefox version; each run uses its own copy, which is deleted afterwards, so every run still starts clean. It is created the first time a run uses Firefox, which takes about 7–10 seconds longer. It lives in the cache folder RPA_CACHE_DIR, by default %LOCALAPPDATA%\rpa\cache on Windows, ~/Library/Caches/rpa on macOS and ~/.cache/rpa on Linux; deleting it is safe, it is rebuilt next time.

Recording: rpa record

M4
$ rpa record https://erp.example.com/login --out erp-login.py --scenario erp-login.yaml
$ rpa record --from recorded-elsewhere.py --out erp-login.py --scenario erp-login.yaml   # convert only, no recording
Recording
Uses Playwright codegen: the browser window and the Inspector open on this computer and recording ends when you close the window; a display is required. --browser chromium|firefox; --load-storage state.json loads a login state first.
Output
--out is the recording with passwords masked as *** (the temporary raw recording, which may contain passwords, is deleted after conversion); --scenario is the DSL draft, with --id and --name for its id and name.
Conversion
goto, click, fill, press, select_option, check and the common expect assertions; the Inspector's “Assert text” and “Assert value” become an extract step plus an output plus a verify check (equals the input when the recorded value equals a typed value, otherwise has content); typed values become inputs (defaulting to the recorded value), password fields become secrets (named after the scenario id plus _PASSWORD), and lines that cannot be converted stay as comments with their line numbers listed. The management portal's recording uses the same conversion.

Validation: rpa validate

$ rpa --lang en validate scenarios/
scenarios/login.yaml:14:9: Step 3 (login-pass) › target.css: Specify only one way to locate the element, found: label, css; put alternatives in fallback
scenarios/login.yaml:31:15: Step 5 (read) › value: facts.total is only produced by a later extract step
Files checked: 5. Failed: 1. Problems: 2.
Location
file:line:column, the same format compilers use, so editors and CI can jump to the problem. Lines and columns start at 1.
Arguments
One or more files or directories; a directory is searched for all .yaml and .yml files (hidden directories are skipped). For script scenarios, the script files must exist.
--format json
Each problem has line, column, step, stepId, field, path, code and message, for programs and AI auto-repair (M5).
Exit code
0 when everything passes; 1 when a file fails or a directory has no YAML; 2 for invalid arguments.
rpa pack check
Checks domain folders (M11): manifest formats, revision content against the hash in each revision file, validation records, the publication gate, role definitions, and login states, Secrets or private keys that must not be in a folder; the same rules the management portal uses when loading them. --id requires the id in pack.yaml; --format json is for programs. Exits with 1 on errors (warnings do not count), so it fits in the CI of a data repository.
rpa schema
Prints the DSL's JSON Schema. schema/scenario.v1.json in the repository is generated by it; add # yaml-language-server: $schema=… as the first line of a scenario and the VS Code YAML extension provides completion and live checks. With a scenario file, it prints that scenario's input or output schema.
Python
rpa_core.dsl.validate_file(), validate_text() and validate_data() return the scenario model and every problem; inputs_json_schema() and outputs_json_schema() produce one scenario's contract. The management interface and API use the same functions.
