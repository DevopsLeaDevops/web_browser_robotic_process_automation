Scenario DSL

The single source of truth for scenarios. Written in YAML, stored as JSON, validated with Pydantic models; this page specifies schemaVersion 1.

schemaVersion 1 · finalized in M1
The models live in packages/rpa_core/src/rpa_core/dsl/, complete examples in examples/, and the JSON Schema in schema/scenario.v1.json. For the background of the decision see ADR 0001.

Example

Excerpt from examples/erp-login.yaml
# yaml-language-server: $schema=../schema/scenario.v1.json
schemaVersion: 1
id: erp-login
name: Log in to the ERP
params:
  user: { type: string, description: Login account }
secrets: [ERP_PASSWORD]
browser:
  baseUrl: https://erp.example.internal
  viewport: { width: 1280, height: 800 }
defaults:
  timeout: 10000
steps:
  - id: open
    action: goto
    url: /login
  - id: fill-user
    action: fill
    target: { role: textbox, name: Account }
    value: "{{ params.user }}"
  - id: fill-password
    action: fill
    target: { label: Password }
    value: "{{ secrets.ERP_PASSWORD }}"
  - id: submit
    action: click
    target:
      role: button
      name: Log in
      fallback: [{ testId: login-submit }]
  - id: check-welcome
    action: expect
    target: { text: Welcome back }
    state: visible

Design principles

  • Every step has a stable id. Results, screenshots and logs are filed by step, so inserting or deleting steps never shifts them.
  • Locators have a priority order. testId → role + name → label → placeholder → text → altText → title → css → xpath. The recorder keeps several candidates in fallback as the basis for self-healing.
  • Only conditional waits. There is no fixed-duration sleep; use waitFor to wait for an element, a URL or a load state.
  • Mistakes are caught early. Unknown fields, wrong types and YAML's implicit conversions are reported during validation with the file line, step and field.
  • Secrets are referenced by name only. Values are injected at run time and masked in logs and screenshot captions.
  • Expressions are evaluated in a sandbox. {{ }} is handled by a Jinja2 sandboxed environment (M3) that can read only params, env, secrets and the outputs of earlier steps.
  • An escape hatch remains. What the DSL cannot express goes into a controlled script step (after M3), which is flagged during review.

A URL starting with / is appended to browser.baseUrl, so moving a scenario to another environment (test, production) only means changing baseUrl.

Common step fields

id
Required and unique within the scenario. Same format as the scenario id.
action
Required; the action name, see the action table below.
name
A step description for people.
timeout
The timeout of this step as an integer number of milliseconds, greater than 0 and at most 3,600,000 (one hour). Falls back to defaults.timeout.

retry and onError (continue, fail, jump to a step) are added in M3.

String matching

match sets how expect's text, value, url, title and waitFor's url are compared:

contains
The default. The text only has to appear, so text: Welcome matches “Welcome back, Alex”.
equals
Exactly equal.
regex
A regular expression in Python re syntax; it is compiled during validation and reported if invalid.

The accessible name for role, such as the text on a button. Only with role.

Which element to take when several match: 0 is the first, -1 the last.

Another locator: find the outer element (a table, a dialog) first and search inside it.

Alternative locators tried in order when the primary one fails (used when running in M2 and self-healing in M5). A fallback locator cannot have its own fallback.

Writing YAML

  • Only YAML 1.2 core rules. yes, no and on are strings, not booleans; 2026-09-01 is a string, not a date; 12:30 is a string, not a base-60 number.
  • No implicit conversion. A number or true/false in a string field is an error; quote it, for example value: "0123".
  • No duplicate keys. A key that appears twice at the same level is reported with the line of its first occurrence.
  • Unknown fields are errors. When a name is close to a valid one, the correct spelling is suggested, for example fullpage → fullPage.
  • Only plain tags. !!python/…, !!binary and custom tags are rejected; anchors and aliases are allowed, << merges are not supported.
  • Files are UTF-8. A BOM is allowed.

Expressions {{ }}

Static checks only in M1
  • String fields can use {{ params.name }}, {{ secrets.NAME }} and {{ env.NAME }}; evaluation is added in M3.
  • Validation checks that every {{ has a matching }}, that the expression is not empty, and that referenced params and secrets are declared.
  • The name and description of scenarios and steps are text for people; they are neither checked nor substituted.

Location
file:line:column, the same format compilers use, so editors and CI can jump to the problem. Lines and columns start at 1.
Arguments
One or more files or directories; a directory is searched for all .yaml and .yml files (hidden directories are skipped).
--format json
Each problem has line, column, step, stepId, field, path, code and message, for programs and AI auto-repair (M5).
Exit code
0 when everything passes; 1 when a file fails or a directory has no YAML; 2 for invalid arguments.
rpa schema
Prints the JSON Schema. schema/scenario.v1.json in the repository is generated by it; add # yaml-language-server: $schema=… as the first line of a scenario and the VS Code YAML extension provides completion and live checks.
Python
rpa_core.dsl.validate_file(), validate_text() and validate_data() return the scenario model and every problem; the Web UI and API use the same functions.
