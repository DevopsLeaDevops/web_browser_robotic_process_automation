Scenario DSL

The single source of truth for scenarios. Written in YAML, stored as JSON, validated with Pydantic models.

Draft · finalized in M1
This page is a draft of the direction; field names and the action list are finalized after discussion in M1. For the background of the decision see ADR 0001.

Example

Illustrative; download is added in M3
id: erp-export-report
name: Log in to the ERP and export the monthly report
params:
  month: { type: string, default: "2026-09" }
secrets: [ERP_PASSWORD]
browser: { engine: chromium, headless: true }
steps:
  - id: open
    action: goto
    url: https://erp.example.internal/login
  - id: login-user
    action: fill
    target: { role: textbox, name: Username }
    value: "{{ env.ERP_USER }}"
  - id: login-pass
    action: fill
    target: { label: Password }
    value: "{{ secrets.ERP_PASSWORD }}"
  - id: submit
    action: click
    target:
      role: button
      name: Sign in
      fallback: [{ css: "#login-btn" }]
  - id: check
    action: expect
    target: { text: Welcome back }
    state: visible
  - id: export
    action: download
    trigger:
      action: click
      target: { role: button, name: Export }
    saveAs: "report-{{ params.month }}.xlsx"

Design principles

  • Every step has a stable id. Results, screenshots and logs are filed by step, and nothing gets misaligned when the scenario is edited in the UI.
  • Locators have a priority order. testId → role + name → label → text → css / xpath. Recording keeps several candidates at once as the basis for self-healing.
  • Conditional waits only. Fixed-duration sleeps are not allowed; use waitFor to wait for an element, a URL or the network state.
  • Error handling per step. Each step can set retry, timeout and onError (continue, fail, or jump to another step).
  • Secrets are referenced by name only. Values are injected at run time and masked automatically in logs and screenshot captions.
  • Expressions are evaluated in a sandbox. {{ }} is handled by a sandboxed Jinja2 environment and can only read params, env, secrets and the output of earlier steps.
  • Keep an escape hatch. When the DSL cannot express something, use a controlled script step, which is flagged during review.
