Management portal

Create scenarios, validate, publish and run them, and read the reports in the browser (M3); recording, step debugging, login roles and input/output forms (M4); playground DAGs (M6). Single machine, single user (ADR 0010), FastAPI + Jinja (ADR 0011), SQLite (ADR 0008); the layout follows the MVP prototype and design system v1.1.

M6
Start it with uv run rpa serve and open http://127.0.0.1:8080. It also starts the local test site at 127.0.0.1:8765, so the “Test site automation” cases run right away. Data is kept in data/ (or the folder given with --data; see Data folder). There is no sign-in, so by default only this computer can connect.

Data folder

Everything the management portal keeps is in one folder
  • What it is. Domains, scenarios and the files of every revision, runs and their reports, the login states of login roles, secrets and recordings are all stored in one folder (its contents are listed under Data below). A different folder is a separate, brand-new management portal.
  • Default and choosing one. The default is data in the folder where you run the command (the project's data when you run it in the project folder). uv run rpa serve --data FOLDER or the environment variable RPA_DATA_DIR picks another one, for example --data data-m4; a relative path is taken from the folder where you run the command, and the folder is created if it does not exist.
  • Use the same one every time. To see the same content, start with the same folder every time; without --data you are back to data.
  • A new folder. On the first start (when there are no domains yet) “Test site automation” is created with the examples and login roles from scenarios/demo. Handy for trying a new version without touching the data you normally use.
  • An existing folder. A new version upgrades the database the first time it opens the folder and keeps the existing scenarios and records; examples added by the new version are imported with “Import examples” in “Test site automation”.
  • Domain folders (M11). Scenarios, revisions, roles and the validation and publication records live in domains/<domain>/, one folder per domain that can be checked on its own (rpa pack check). The first time a folder from before M11 is opened, the old scenes/ is moved into domain folders after the database and scenes/ are backed up to backups/<time>-before-domains/; scenarios without a domain and roles no scenario uses go into “Unassigned”. Composite scenarios kept in the database (M11 PR 2) move into the “Composite scenarios” domain with the code wf-<old id>, and the current definition becomes revision 1; the database is backed up to backups/<time>-before-composites/ first.
  • Git sync (M11 PR 3). A domain can be synced with a directory in a git repository: Domains › Sync sets the repository URL, branch, directory and authentication (none for a public repository, pull only; HTTPS with a username and access token; SSH with a deploy key the Portal generates), and Add from git creates a domain from one. Only the server pulls and pushes; recorders and workers still get the files they need from the server. Local changes are the difference between the folder and the last synced commit, so saving does not commit. Pulls and pushes merge file by file; a file changed differently on both sides stops with three choices (revision files with the same content hash count as the same revision and the remote copy is kept, so two servers that each imported the examples do not conflict on their first pull) (cancel, push to a new branch rpa/<domain>-<time>, or use the remote after a backup to backups/), and nothing is ever force-pushed. Pushing is blocked by file names that look like login states, Secrets or private keys, by non-definition files, by files over 1 MB and by files containing a saved Secret value; you are warned when a composite scenario depends on revisions not yet pushed in another domain. On start, the server pulls domains with Pull on start in the background and keeps the last local data if the remote cannot be reached.
  • Starting over and backups. Stop the management portal first (Ctrl+C in its terminal): deleting the folder starts over, copying the whole folder is a backup.
  • Do not commit or share it. It holds login states and secret values (readable only by you). Git already ignores data/ and data-*/ in the project; take care yourself with other names or locations.

Domains

The side menu of Scenarios
  • Scenarios are grouped by target system or business area. For example “Test site automation”, “Google automation” or “Microsoft automation”. Each domain is an item in the Scenarios side menu; the last item is “Domains”.
  • A domain page shows scenario cards. Four per row at 1440 pixels wide (each at least 272px). Each card has the name and the category (DSL scenario or Python script when there is none), the screenshot of the latest run, the description, five links (automation, assertions, reports, inputs, outputs), and the scenario ID, the latest result, “Debug” (step debugging for DSL scenarios, where you can go on to validate; Python script scenarios validate the latest revision directly) and “Run” (run the published revision; “Draft” until one is published).
  • Managing domains. Create a domain (its ID is used in addresses and cannot change), rename it or edit its description, and delete domains without scenarios. A scenario's Run settings move it to another domain.
  • Test site automation. Created on the first start with real cases that run against the test site: create a record (BA-001), look it up (BA-002, whose input is BA-001's output), look up a record that does not exist (BA-003), the Python script version of creating a record, and two login examples (BA-004 regular user, BA-005 manager). Its name and description follow the interface language until someone edits them; scenario names and descriptions come from the scenario files and are not translated.

Flow

Acceptance: walk through it once in the browser
1 Create or import2 Edit3 Validate4 Publish5 Run6 Read the report
  1. Create or import. A new scenario starts as a v1 draft that only opens a page; the examples in scenarios/demo can also be imported with one click. The scenario ID is the DSL id; it cannot be changed or reused.
  2. Edit. Edit the YAML directly (script scenarios also have their two scripts). Before saving, the files are checked with the same rules as rpa validate; problems are listed with their line, step and field, and no revision is created.
  3. Validate. Runs the chosen revision in a real browser; inputs, browser, browser window and URL can be adjusted in the form.
  4. Publish. Only a revision that passed validation can be published, and the user confirms it in a dialog.
  5. Run. Runs always use the published revision; new drafts do not affect them.
  6. Read the report. Filter by category, scenario, result and purpose: each filter is a button showing the current choice; open it, tick one or more items, and the list updates when you press Apply or close the menu; nothing ticked means all. every run has the M2 report.html, a screenshot and the full run folder.

Revisions and the publishing gate

  • Revisions are immutable. Every save is a new revision (v1, v2…); its files are written to the data folder and made read-only. A save names the revision it started from and gets a 409 if that is not the latest, so nobody overwrites someone else's change.
  • Status. Draft → validating → validated / validation failed; the status is the result of the latest validation record. Publishing points the scenario at that revision; earlier published revisions stay in the history.
  • What was validated is what gets published. Each revision records a content hash computed the same way as the scenarioHash rpa-runner writes to result.json. Publishing requires all of: the files on disk hash to that value, the revision file records the same hash, and the domain folder has a passed validation record with a matching hash.
  • Records travel with the domain folder (M11). Every validation writes a validation record (passed or failed: who, which server, which worker, result, hash), and publishing is written to scene.yaml. The records sync with the domain folder, so a passed record from any server can back a publication; the scenario page lists all validation records.
  • Changed content needs validation again. A new revision always starts as a draft; earlier validation results cannot be used to publish new content.

Runs

  • Check first, then queue. Inputs are checked when a run is requested; invalid inputs get a 422 and nothing is queued. Otherwise the answer is 202 with the run ID.
  • Background worker. rpa-worker runs in a background thread of the server process and takes one run at a time in creation order (SQLite allows a single process). It calls the M2 rpa_runner.run.execute, so the overall deadline, subprocess and process-group termination are the same as in M2.
  • Headed and headless mode. The run form’s “Browser window” option: Show (headed mode) opens a browser window on the computer running the Portal so you can watch every step; Hide (headless mode) runs in the background. Headed is the default; on a computer without a graphical desktop (not Windows or macOS, and no DISPLAY or WAYLAND_DISPLAY) only headless is available and an API request for headed mode gets a 422. The run page records which mode was used. The rpa run command stays headless unless you add --headed.
  • Progress. The run page checks the status every second and reloads when the stage or status changes.
  • Cancellation. A queued run is cancelled right away; a running one has its subprocess and browser terminated at once and ends as "Cancelled". Actions already completed on the target site are not undone.
  • No double submission. Each form load creates an idempotencyKey; submitting twice returns the same run.
  • Run again. Any finished run can be repeated with the same inputs and options (validation uses the same revision, production runs the currently published one).
  • Server restarts. On start-up, runs that were interrupted are marked as failed; queued runs continue.
  • Recording (M12). The automation stage of a DSL scenario is recorded, headed or headless, as video.webm and video.json in the run folder; steps.json records when each step started and ended and the page URL after it, so replay can line them up with the video. The video is as large as the page, at most 1280 wide. Cancelled, timed-out and failed runs get a complete video too (on Windows, cancelling leaves the recording's ffmpeg running to finish the file; a broken file is remuxed with Playwright's own ffmpeg). Login checks, step-by-step debugging, recording sessions and Python script scenarios are not recorded. By default everything is recorded; passed runs keep the video for 7 days, failed, timed-out, cancelled and needs-login runs for 30 days, and all videos together use at most 20 GB (the oldest are deleted first); pinned videos are kept. Clean-up only deletes videos: run records, reports and screenshots stay. See ADR 0016.

Logins and roles

M4: one login state per role, checked before every run
  • Scenarios only name the role. A scenario that needs to log in writes login: { role: ROLE_ID } (DSL). How to log in and how to tell the role is logged in is registered under “Scenarios › Logins & secrets”: the login URL, a check URL, an element that is only visible when logged in (a DSL locator) and optional automatic login steps.
  • Manual login first. “Log in” opens a browser window at the login URL on the computer you are working from (the one running the Portal when you open it directly, the recorder’s computer when you go through a recorder) and you log in yourself, so SSO, captchas and phone or app two-factor all work. Press “Finish login” or just close the window; the computer that opened the window then loads the new login state into a headless browser, opens the check URL, and only when the logged-in element is visible sends the state to the server to replace the stored one, so the server needs no browser. If you press “Finish login” before you are logged in, the page says where the check URL ended up and the window stays open; log in and press it again. Closing the window before logging in ends the attempt and keeps the previous login state. Manual login needs a computer with a display. Older recorders do not confirm the login themselves; the server confirms it instead (and asks you to update the recorder if it has no browser).
  • Automatic login (optional). Only for plain username/password systems: the role gets a few DSL steps and uses {{ secrets.NAME }} for the password. When a run finds the role logged out, it logs in automatically once.
  • Check. A role’s “Check” confirms in a headless browser that its login state is still valid (logging in automatically when the role has automatic login steps). It runs on the server when the server has downloaded the role’s browser; otherwise (for example a server installed with the Linux installer) it runs on the recorder when you open the Portal through one, and the button is grey when you open the Portal directly. The check works on a copy of the login state and replaces the stored state only after passing; if a manual login or a run updated the state meanwhile, the newer one is kept. Checking first is optional: every run checks on the computer running it first.
  • Login required (needs_login). Every run starts with a “Login check” stage that opens the check URL: if the element is visible the run continues; if not (for example after a redirect to the login page) and automatic login is not possible, the run stops at “Login required” without running any step and keeps a screenshot of the check. The run page offers “Log in as …” and “Run again”, which repeats the run with the same inputs once you have logged in.
  • Roles never mix. Each role keeps its own login state (a Playwright storageState) in roles/<role>/state.json in the data folder, readable only by you; every run opens a fresh browser context and loads only the role the scenario names. Login states are never copied into run directories nor served by pages or the API. Run results also update the role's status (logged in, login required).
  • Secrets. The same page sets secret values: they are stored in secrets.json in the data folder (readable only by you; encrypted in M8), and pages and the API only show names and update times, never values. Runs receive the values the scenario and its role use; anything not set there is looked up in an environment variable with the same name. The page also lists secrets that scenarios use but nobody has set.
  • The test site's two roles. Importing the examples also creates the roles used by BA-004 (regular user) and BA-005 (manager) from scenarios/demo/roles.json; the demo accounts are shown on the test site's login page. The two accounts see different to-dos, which shows that the roles do not mix.

Recording

M4: raw recording → DSL draft
1 Record a draft2 Debug and edit3 Validate4 Publish
  • Record on this computer. “Production › Script recording” → “Start recording” opens Playwright codegen's browser and Inspector on the computer running the Portal; work as usual and close the browser window when you are done. With a login role selected, its login state is loaded first. On the command line: rpa record URL --out recording.py --scenario draft.yaml.
  • Three targets. A new scenario (saved as v1); an existing scenario, “continue after the existing steps”: the recording browser first runs the latest revision's steps with the default inputs and stops on the last step's page, then recording starts, and the recorded steps, outputs and checks are appended to the existing content (which stays as it is, comments included; if an existing step fails, recording stops and nothing is saved); or an existing scenario, “replace with the recording”: record again from the start URL and save it as a new revision. With an existing scenario, the start URL, browser and login role are filled in from its settings.
  • The Inspector's code cannot be edited. The code on the right of the Inspector is generated live by Playwright from your actions and is read-only (Playwright's own design, not a restriction of this project); the Locator tab accepts and tests locators. To change the result, edit the scenario's “Automation script” and “Assertion script” after conversion.
  • Paste a recording. A codegen recording made elsewhere (sync, async or pytest style) can be pasted and converted directly, for example when the Portal runs on a computer without a display.
  • Assertions become outputs. The Inspector's “Assert text” and “Assert value” (expect(…).to_contain_text, to_have_value, to_have_text) are not kept as checks inside the steps. Instead the automation script gets an extract that reads the element (after waiting for it), the outputs get an entry taken from that page fact, and the assertion script (verify:) gets a check: “equals that input” when the recorded value equals a typed value, otherwise “has content”. Output names come from the element's ASCII name and can be changed later.
  • What is converted. goto, click, fill, press, select_option, check and the other common expect assertions, with get_by_role, label, placeholder, text, test_id, CSS, XPath, first, nth and filter(has_text) locators. The origin of the first URL becomes browser.baseUrl. Lines that cannot be converted (hover, uploads, iframes, new tabs…) stay in the draft as comments and are listed on the recording page.
  • Inputs from typed values. Every typed value becomes an input whose default is the recorded value; the name comes from the field's ASCII name (field, field_2… when there is none) and the field's label goes into the description, so you can rename it later in the scenario's form.
  • Passwords never stored. Password fields (label, placeholder or selector containing password, 密碼 and similar words) become secret references, and the raw recording is saved with the value masked as ***; the temporary raw recording is deleted after conversion.
  • Drafts only. The result is saved as v1 of a new scenario or a new revision of an existing one; the recording is only the source and still has to be debugged and validated before publishing. The recording page counts the steps, inputs, outputs, checks and lines not converted.

Step debugging

M4: one browser, one step at a time
  • Start. “Step debugging” on the scenario page or “Debug” on the card asks for the revision, inputs, browser and window mode. With a display, the browser window opens on this computer; in both modes the page shows a screenshot, the URL and the page facts after every step. DSL scenarios only.
  • Run. Each step has “Run this step” and “Run to here” (which runs only steps that have not run yet and stops at the first failure). Steps with side effects (click, fill, select, check, press) ask for confirmation before running a second time; no step is ever repeated automatically. “Start over” opens a new page and reloads the login state.
  • Locator test. Enter a DSL locator (for example { role: button, name: Log in }) to see how many elements match and the text of the first few, outlined in red in the screenshot.
  • Edit. Edit the YAML below and save it as a new revision to keep debugging with it; the browser and page facts stay, and steps that already ran keep their state by id.
  • Limits. One session per scenario at a time; sessions close after 15 idle minutes and when the server stops. Debugging really operates the target site, so use a test environment.

Section editing: automation script, assertion script, inputs, outputs

M4
  • Automation and assertion scripts are separate. DSL scenarios have “Automation script” (steps:) and “Assertion script” (verify:) on the card and the scenario page, each showing and rewriting only its section of the scenario file. A run executes the automation steps first, then checks the page facts with the assertion script, and publishes the outputs only when every check passes. The assertion script page inserts notEmpty, equals, contains and matches checks with one click, and clicking a page fact or input name inserts it at the cursor. Saving validates first and reports problems with line numbers inside the section.
  • Edit inputs and outputs side by side. The contract workspace appears first on the scenario page, with two YAML source panes by default. Tables remain available for adding, sorting, renaming and setting constraints. Switching views preserves both drafts. “Save inputs and outputs” validates them together and creates one revision; either side failing prevents a partial save. Errors identify the section and line. A revision conflict returns 409 and preserves the draft.
  • Three read-only previews. “Default inputs”, “Output sample” and “Output extraction” are tiled below the two editors: three columns on desktop, stacked on narrow screens, always visible without switching tabs. Defaults and extraction maps refresh automatically from the draft; invalid drafts clear stale previews and show an unavailable state. Defaults come from the current draft, with required fields without defaults listed separately. Samples show only actual outputs of the latest successful run of the saved revision, identified by revision and run ID. Missing results have an explicit empty state; edited drafts are marked as unvalidated. Extraction maps come from the draft’s outputs.from; Python scenes identify assertion.py as the producer. These three views cannot be edited or saved directly.
  • Edit, validate, publish. Contract, whole-file and section saves stay on the page, update the revision and offer “Validate this revision”. Publishing stays on the report and offers running the published revision. Leaving a modified editor prompts before discarding changes. Contract saves replace inputs/outputs while retaining other sections and comments. Table renames update DSL references; source renames require updating references manually. New revisions still require validation and publishing; Python scripts are not rewritten.

Playground and composite scenarios

DAGs with forks and joins; successful outputs feed downstream inputs; stop on failure
  • Management and production. “Scenarios › Composite automation” uses the test-site scenario card style, with DAG thumbnails drawn from saved positions and dependencies, names, nodes, problems and recent runs. “Run composite scene” opens engine, execution location and window settings directly from the card. “Production › Playground” creates and edits canvases. Production navigation lists recording, playground, run reports and devices (called remote workers before M10.1) in that order.
  • Dependency canvas. Click a library item or drag it into the canvas to add a scene. Drag nodes or use arrow keys to adjust positions. Click an upstream right port and then a downstream left port to connect them. Select an edge to configure downstream inputs, or add a dependency from node settings. Zoom and fit change only the view. Coordinates are saved; positions and array order do not determine dependencies. The title and actions share one toolbar; help is in a popover and run history is collapsed initially. A full-width, independently scrolling panel below the canvas shows upstream outputs, downstream inputs, match mode and value/source. Selecting a DAG edge selects its upstream/downstream pair; a selector switches between multiple upstream nodes.
  • Four input sources. Name matching checks only directly connected upstream nodes: one compatible match uses that output, none uses the scenario default, multiple matches require an explicit choice. Scenario default ignores matching outputs. A fixed value overrides only this node. Explicit output binding can connect different field names and creates a dependency. One output can feed multiple nodes; an input has one source. Integers may feed numbers; other types must match.
  • Parameter wires. Drag an output port to an input, or select both ports with the mouse or keyboard. Incompatible types leave the binding unchanged. Four mode buttons share one row; a dropdown also allows precise output selection. Unique automatic matches and explicit bindings draw wires, while ambiguous, default and manual sources do not draw misleading connections. Contract buttons inspect the pinned revision in place. Editing explicitly opens a new tab and explains validation, publishing and selecting the new revision on the canvas.
  • Run and return. Canvas runs display snapshot revision, progress and node states in place. Select a run node to inspect inputs, successful outputs or errors; cancellation is available in place. Full and node reports open only when requested. Returning to the canvas restores the selected node, source, zoom and scroll position. Card quick runs still open the report directly. Canvas edits do not alter an existing run snapshot.
  • Dependencies and cleanup. Both explicit edges and output bindings create dependencies. Disconnecting clears the associated output bindings and rechecks sources; removing a node clears its edges and downstream references. Resetting inputs restores name matching. Cycles, self-dependencies, duplicate edges and missing endpoints block execution.
  • Codes, domains and revisions (M11 PR 2). A composite scenario has an alphanumeric code (wf-<number> when left empty, unique across all domains) and lives in composites/<code>/ of a domain folder, or in the “Composite scenarios” domain when no domain is chosen. Every save that changes the definition is a new revision (revisions/<n>/workflow.json, read-only); its revision file pins the scenario revision each node uses (domain, scenario, revision, hash). Changing the name or description only rewrites composite.yaml and makes no revision. Other domains it uses are added to requires in pack.yaml.
  • Validate, publish and run (M11 PR 2). A run has a purpose. “Validate” runs a revision (the latest by default) and writes a validation record at the end (scenario, revision, hash, status and run id of every node); “Run” only runs the published revision and writes no record. Publishing needs a passed record with a matching hash, every node must have run the pinned scenario revision, and those revisions must still exist with the same hash; the publication is written to composite.yaml. Every run writes workflow-runs/<run id>/run.json with the definition snapshot, revision, purpose and the state of each node.
  • Dependency check (M11 PR 2). The composite scenario page lists the dependency problems of the latest and the published revision with a way to fix each: a missing domain (add the domain), a missing scenario or revision, or a revision that cannot run (reload the domain), a hash mismatch or an unpinned node (save again) are errors that block running and publishing; a role that is not logged in or missing Secrets are warnings. Cards show “Dependencies incomplete” or “Dependency warnings”. A domain with composite scenarios cannot be deleted. Given several folders, rpa pack check also checks the dependencies between them.
  • Completing dependencies and management (M11 wrap-up). Once a domain is connected to git, the pack.yaml of domains that depend on it records a source under requires (repository, directory and branch, no credentials); when someone lacks that domain, the dependency hint's Add from git is filled in from it, and a domain with a source but missing scenarios or revisions gets a Pull hint. The Domains page lists which composite scenarios depend on each domain. A composite scenario's page can change its code, move it to another domain (the folder moves with its revisions and validation records) or archive it (it cannot run), and validate an older revision.
  • Saving and preflight. Invalid drafts may be saved. Saves carry baseVersion; conflicts return 409 and keep the draft available for export. Before execution, the entire graph, pinned published revisions, fields, types, required sources and fixed values are checked. A problem prevents even the first node from queuing. The problem list and blocking dialog show the node, scene, input and specific reason, with actions to locate the affected node or field; invalid fields are highlighted. “Check” requests validation manually, and running from a card fetches current problems first. Adding a node does not automatically connect it to the previous one.
  • Forks and joins. Topological ordering waits for all dependencies to pass. Ready nodes are selected stably by definition order and queued one at a time. Each node has a real run, resolved inputs, successful outputs and reports. Actual downstream inputs are validated before starting its browser; invalid output values stop execution without falling back to defaults.
  • Snapshots and recovery. Starting a run freezes the graph, scenario revisions and resolved name matches. Later edits do not affect it. Failure, timeout, cancellation, required login or lost worker stops the entire graph. Resume reuses successful results in the topological prefix without repeating successful external actions. Every node stays on the same worker. Cancellation does not roll back external actions.
  • Format and compatibility. New definitions use version: 2, mode: "dag", onFailure: "stop", nodes and edges: [{"source":"n1","target":"n2"}]. Nodes may include position: {"x":40,"y":60}. Input bindings are {"auto":true}, {"value":7} or {"node":"n1","output":"quantity"}; omitted inputs use scenario defaults. Legacy serial definitions and snapshots remain supported. Opening a legacy canvas prepares equivalent ordered edges for the next save without rewriting historical runs. JSON import and export preserve positions and bindings.
  • Scope. Up to 50 nodes, with ordinary forks and joins. Conditional routing and concurrent execution are excluded. Input types remain the current DSL strings, integers, numbers and booleans. The reference prototype’s repetitions, date/random tokens and composite input types are outside these five requested changes. Prototype JSON is a reference contract, not a Portal import format.

Remote workers

M9a: hand runs to another computer so browser windows no longer take over this one (ADR 0012)
  • Two ports. rpa serve --worker-port 8081 opens a second port, the external port (its name from M10 on), that only serves the Worker API (/worker-api/v1) and the desktop apps' Client API (/client-api/v1; only pairing in M10.1), and listens on all network interfaces by default; the portal pages and /api stay on --host (127.0.0.1 by default). Each port blocks the other's paths: the external port shows no portal pages, and the portal port cannot call the Worker API or the Client API.
  • Devices and invitations (M10.1). “Production › Devices” (formerly the remote workers page; the old /workers address redirects to /devices) adds a device (ID and name; workers are the only kind for now) and creates an invitation: one line, rpa://pair?server=…&app=worker&code=…, whose code is single use, valid for 24 hours and tied to one app; only its hash is stored. The server and code are also shown separately. Paste it into RPA Worker on that computer (or use rpa worker --invite) to exchange it for a token through the Client API's /pair. “Invite again” ends the old token and any earlier invitation immediately. Invitations need the external port; without it “Add device” is disabled. A device can be disabled or deleted (not while running; queued runs assigned to it are marked failed). The page lists each device's status (online, busy, offline, disabled), last report, operating system, browsers, whether it can run headed, its app version, and whether its code matches the portal's.
  • Claiming. The worker runs rpa worker --server …. When it comes online it reports its protocol version (a mismatch is refused), code fingerprint (a mismatch only warns), browsers and whether it can show windows, then long-polls (up to 25 seconds) for jobs. It only gets jobs it can run: placed on remote or any, using a browser it has, headed only if it can show windows, and those pinned to it. First in, first out.
  • What a job carries. The revision's files (sent byte for byte, so the hash matches the portal's), inputs, browser, URL, window mode and language; for scenarios with a login role, the login settings and current login state, plus the values of the secrets it uses. The worker keeps them only in memory and in private temporary files during the run, deleted afterwards.
  • Heartbeats, cancelling, losing contact. While running, the worker sends a heartbeat every 5 seconds with the current stage; cancelling in the portal stops the browser at the next heartbeat. Claiming grants a 60-second lease that each heartbeat extends; when it expires the run is marked failed (“worker lost”) and is not retried automatically (it may already have had side effects), and anything the worker reports later is refused. When the portal restarts, remote runs get one lease period to report again; local runs are still marked interrupted.
  • Results. The worker uploads the whole run directory as a zip (only safe relative paths, with limits on file count and size) and then reports the contents of result.json; it is recorded with the same rules as a local run, including the hash check for validations. A login state refreshed by automatic login is sent back to the role.
  • Where to run. Once a remote worker is registered, the validation, run and “Run sequence” forms gain “Where to run”: this computer, remote worker or any; the default is set on the devices page (this computer when unset). Whether headed mode is available follows the chosen place. When the scenario's URL points to this computer (127.0.0.1, localhost, ::1; the test site's 8765 excepted) and the place is not this computer, the form warns that it means the worker itself. Run reports and run pages show which computer ran it, and run reports can be filtered by where they ran (this computer and each worker). When a queued run has no online remote worker to take it (including when the worker a sequence is pinned to is offline), the run page and the sequence run page explain what it is waiting for and link to the devices page.
  • Playground sequences. The whole sequence uses one place to run, and whichever worker claims the first node gets all later nodes (so the test site's data and login states match); if it goes offline the later nodes wait and can be cancelled. “Continue from the stopped node” stays on the same worker too.
  • Workers only. --no-local-worker: this computer runs nothing, “this computer” cannot be chosen, and the default becomes any.
  • What stays on this computer. Recording, step-by-step debugging and manual logins need a person, so they still run on the computer running the portal.

Manual acceptance

M4, M6, M9a: recording, manual login, the playground and remote workers need a person; the automated tests use a pre-recorded script

On a computer with a graphical desktop (macOS, Windows, or Linux with a desktop), go through this once with a fresh folder; it takes about twenty minutes:

  1. Start. uv run rpa serve --data data-check, then open http://127.0.0.1:8080; “Test site automation” already holds BA-001 to BA-005.
  2. Record a new scenario. In “Production › Recording”, choose “A new scenario”, start URL http://127.0.0.1:8765/, and press “Start recording”. On the test page fill in the title and quantity, press “Create record”, click the record number with “Assert text” in the Inspector, and close the browser. The recording details should show goto, two fills, a click and an extract, with 2 inputs, 1 output and 1 assertion.
  3. Debug, validate, publish, run. Press “Debug” on the new scenario, step through to the last step and look at the screenshots; back on the scenario page validate v1, publish it once it passes, then press “Run” on the card: the report says “Passed” and the outputs include the record number.
  4. Continue recording. Choose “A new revision of a scenario” with the scenario you just made, then “Continue after the existing steps”: the browser first replays the existing steps and stops on the result page, then record one more action; the new revision appends the steps after the existing content and keeps the original comments.
  5. Two roles. In “Scenarios › Logins & secrets” press “Log in” for testsite-user, log in as user / user-pass in the window that opens and press “Finish login”; use manager / manager-pass for testsite-manager. Then run BA-004 and BA-005: the two reports show different to-do items.
  6. Needs login and run again. Press “Log out” for testsite-user and run BA-004: it stops at “Login required” without running any step; follow the login role on the run page back to “Logins & secrets”, log in again, return to the run page and press “Run again”: the result is “Passed”.
  7. Playground. Validate and publish BA-001 and BA-002. Create a composite with one BA-001, two BA-002 nodes and another BA-001 as a join. Connect “create → two lookups → join”. Match each lookup’s recordId to its upstream output, and bind the join’s title and quantity to different lookup nodes. Drag, save and reload to confirm positions persist. Run all four nodes and verify their actual inputs. Reject a reverse edge that would create a cycle. Open the latest report from the composite management card.
  8. Remote worker (two computers, M9a). Start the portal with uv run rpa serve --data data-check --worker-port 8081 instead; add win-01 under “Production › Devices” and start rpa worker --invite … on the other computer with the invitation from the dialog (once the M10.1 RPA Worker app ships, paste it into the app instead; steps in Remote workers); the devices page shows it online. Run BA-001 on “Remote worker” in headed mode: the browser window appears on the worker computer and nothing pops up on this one; the report passes, the run page says “Ran on: win-01” and the screenshot is there. Then run the composite from step 7 on “Remote worker”: all four nodes run on win-01. Press Ctrl+C on the worker computer during a run: that run becomes “Cancelled” in the portal.

Afterwards stop the management portal and delete the data-check folder; the worker-data folder on the worker computer can be deleted too.

Data

By default the project's data/; the folder given with --data otherwise (see Data folder). It contains:

rpa.db
SQLite database (tables below)
domains/<domain>/
domain folder (M11): pack.yaml; in scenes/<scenario>/, scene.yaml, revisions/<n>/ (scenario.yaml, plus two scripts for script scenarios) with the revision file revisions/<n>.yaml, and validation records in verifications/<n>/; role definitions in roles/<role>.yaml; composite scenarios in composites/<code>/ (composite.yaml, revisions/<n>/workflow.json with revision files, validation records). Format: rpa_core.pack
runs/<run ID>/
the M2 run folder (input.json, report.html…); run.json records the server, domain, scenario, revision, hash, times and the sha256 of every file; the recording video.webm and video.json (M12; when the retention rules delete the video, removed in run.json records when and why)
workflow-runs/<run id>/
composite scenario runs (M11 PR 2): run.json with the definition snapshot, revision, purpose, and each node's state and run id
work/<run id>/
snapshot of the revision files for a local run (M11 wrap-up): copied from the domain folder at the start so pulls and reloads do not affect the run; deleted at the end and cleared when the server starts
roles/<role>/state.json
a role's login state (readable only by you)
recordings/<recording ID>/
masked raw recording and converted draft
debug/<session>/
debugging screenshots (deleted when the session ends)
secrets.json
secret values (readable only by you)
backups/
the database and scenes/ from before the upgrade to domain folders; the database from before composite scenarios moved into folders; a domain folder before “use the remote” after a conflict
git/
git sync (M11 PR 3, readable only by you): repos/<domain>.git bare repositories (only used to fetch and create commits), credentials.json (HTTPS tokens), keys/<domain> (SSH deploy keys), known_hosts. git runs without the system and user configuration or credential helpers; a token reaches only that one git process through GIT_ASKPASS

Database tables:

domains
ID, name, description, order; when the domain folder was last loaded and its load problems; the git source (without the token) and the sync state (last synced commit, last seen remote commit, branch, error, conflicting files)
scenes
ID, name and category (from the latest revision), domain, default URL, latest and published revision numbers, archived, source missing
revisions
Scenario, revision number (unique), content hash, kind, status, note, publishing time; source missing, the problem that prevents running it, whether a passed validation record with a matching hash exists
runs
Run ID, scenario and revision, the name and category at the time, purpose, status and stage, headed or headless mode, inputs and outputs, error, hash, times; for playground nodes, the sequence run and node ID; where to run, the pinned worker, the worker that ran it and its lease; the recording's length and size, pin, and when and why it was deleted (M12)
roles
Id, name, login URL, check URL and element, browser, automatic login steps, the latest status and check time; domain, source missing
recordings
Recording ID, target scenario and revision, mode (new scenario, continue after the existing steps, replace everything) and the revision it continues, source (recorded or pasted), URL, browser, role, status, lines not converted
workflows
Composite scenarios: code, domain, name, description, the latest revision's definition (JSON) and number, published revision, archived, source missing
workflow_revisions
Composite scenario revisions (an index of the folder): number, hash, status, whether a passed record with a matching hash exists, the problem that stops it from running, note, publication time
workflow_runs
Sequence runs: the sequence and its name, code, revision and purpose at the time, a snapshot of the definition, status, the node it stopped at and why, reused nodes (when continuing from a stopped node), browser and window mode, times; where to run and the pinned worker
workers
Remote workers: ID, name, token hash, disabled, the details reported when coming online (the app version from M10.1), current run, last report time
device_invites
Device invitations (M10.1): hash of the code, app, device ID, creation time, expiry, time used
settings
Settings (the default place to run, this server's ID and name, the folder format, recording)

The models use SQLAlchemy 2; schema changes go through Alembic migrations, applied automatically when the server starts. A test checks that the migrations match the models.

Settings

--host, --port
Default 127.0.0.1:8080; without --port, if another program uses 8080 the next free port up to 8089 is used. If the port is taken by the management portal itself, only its address is shown and no second one is started
RPA_DATA_DIR
Data folder, default data; or use --data (see Data folder)
RPA_DATABASE_URL
SQLite by default; PostgreSQL comes in M8
RPA_LANG
Default language, also used for run reports; pages can switch at the top right
--no-testsite
Do not start the test site (by default it starts at 127.0.0.1:8765, or the running one is reused)
RPA_EXAMPLES_DIR
Examples folder of “Test site automation”, default scenarios/demo
Secrets
Set them under “Logins & secrets”; anything not set there is read from an environment variable of the same name in the server process (in the worker process when a remote worker runs it)
--worker-port, --worker-host
Open the external port to devices (M9a; called the external port from M10): a separate port, listening on 0.0.0.0 by default; only /worker-api (token required) and /client-api (pairing with an invitation code). The server address in invitations is this computer's guessed LAN address when listening on all interfaces, otherwise the address it listens on
--no-local-worker
This computer runs nothing; every job goes to remote workers

Security and limits

  • No sign-in. By default it only listens on 127.0.0.1; rpa serve warns when another address is used. Authentication and permissions come in M8.
  • Cross-site requests are blocked. A write request that carries an Origin header must come from the same origin, so other websites cannot call the local API in the background.
  • Files in run folders. Only files inside the run folder are served; only report.html is shown as a web page, with a content security policy that allows nothing but inline styles and the screenshots.
  • Script scenarios run arbitrary code. As in M2, only trusted people should edit Python script scenarios.
  • Login states and secrets are stored on this computer. Both live in the data folder, readable only by you; they are never served by pages or /api nor written to run directories, reports or logs, and passwords in recordings are masked before saving. M8 encrypts them.
  • Remote workers receive the secrets and login states a run needs. Only in the claim response; the worker keeps them in memory and in private temporary files during the run, deleted afterwards. Over HTTP the Worker API is plain text on the LAN: use it only on a trusted network; tokens are stored only as hashes and can be disabled or replaced at any time.
