Management portal

Create scenarios, validate, publish and run them, and read the reports in the browser (M3); recording, step debugging, login roles and input/output forms (M4); playground sequences (M6). Single machine, single user (ADR 0010), FastAPI + Jinja (ADR 0011), SQLite (ADR 0008); the layout follows the MVP prototype and design system v1.1.

M6
Start it with uv run rpa serve and open http://127.0.0.1:8080. It also starts the local test site at 127.0.0.1:8765, so the “Test site automation” cases run right away. Data is kept in data/ (or the folder given with --data; see Data folder). There is no sign-in, so by default only this computer can connect.

Data folder

Everything the management portal keeps is in one folder
  • What it is. Domains, scenarios and the files of every revision, runs and their reports, the login states of login roles, secrets and recordings are all stored in one folder (its contents are listed under Data below). A different folder is a separate, brand-new management portal.
  • Default and choosing one. The default is data in the folder where you run the command (the project's data when you run it in the project folder). uv run rpa serve --data FOLDER or the environment variable RPA_DATA_DIR picks another one, for example --data data-m4; a relative path is taken from the folder where you run the command, and the folder is created if it does not exist.
  • Use the same one every time. To see the same content, start with the same folder every time; without --data you are back to data.
  • A new folder. On the first start (when there are no domains yet) “Test site automation” is created with the examples and login roles from scenarios/demo. Handy for trying a new version without touching the data you normally use.
  • An existing folder. A new version upgrades the database the first time it opens the folder and keeps the existing scenarios and records; examples added by the new version are imported with “Import examples” in “Test site automation”.
  • Starting over and backups. Stop the management portal first (Ctrl+C in its terminal): deleting the folder starts over, copying the whole folder is a backup.
  • Do not commit or share it. It holds login states and secret values (readable only by you). Git already ignores data/ and data-*/ in the project; take care yourself with other names or locations.

Domains

The side menu of Scenarios
  • Scenarios are grouped by target system or business area. For example “Test site automation”, “Google automation” or “Microsoft automation”. Each domain is an item in the Scenarios side menu; the last item is “Domains”.
  • A domain page shows scenario cards. Four per row at 1440 pixels wide (each at least 272px). Each card has the name and the category (DSL scenario or Python script when there is none), the screenshot of the latest run, the description, five links (automation, assertions, reports, inputs, outputs), and the scenario ID, the latest result, “Debug” (step debugging for DSL scenarios, where you can go on to validate; Python script scenarios validate the latest revision directly) and “Run” (run the published revision; “Draft” until one is published).
  • Managing domains. Create a domain (its ID is used in addresses and cannot change), rename it or edit its description, and delete domains without scenarios. A scenario's Run settings move it to another domain.
  • Test site automation. Created on the first start with real cases that run against the test site: create a record (BA-001), look it up (BA-002, whose input is BA-001's output), look up a record that does not exist (BA-003), the Python script version of creating a record, and two login examples (BA-004 regular user, BA-005 manager). Its name and description follow the interface language until someone edits them; scenario names and descriptions come from the scenario files and are not translated.

Flow

Acceptance: walk through it once in the browser
1 Create or import2 Edit3 Validate4 Publish5 Run6 Read the report
  1. Create or import. A new scenario starts as a v1 draft that only opens a page; the examples in scenarios/demo can also be imported with one click. The scenario ID is the DSL id; it cannot be changed or reused.
  2. Edit. Edit the YAML directly (script scenarios also have their two scripts). Before saving, the files are checked with the same rules as rpa validate; problems are listed with their line, step and field, and no revision is created.
  3. Validate. Runs the chosen revision in a real browser; inputs, browser, browser window and URL can be adjusted in the form.
  4. Publish. Only a revision that passed validation can be published, and the user confirms it in a dialog.
  5. Run. Runs always use the published revision; new drafts do not affect them.
  6. Read the report. Filter by category, scenario, result and purpose: each filter is a button showing the current choice; open it, tick one or more items, and the list updates when you press Apply or close the menu; nothing ticked means all. every run has the M2 report.html, a screenshot and the full run folder.

Revisions and the publishing gate

  • Revisions are immutable. Every save is a new revision (v1, v2…); its files are written to the data folder and made read-only. A save names the revision it started from and gets a 409 if that is not the latest, so nobody overwrites someone else's change.
  • Status. Draft → validating → validated / validation failed; the status is the result of the latest validation. Publishing points the scenario at that revision; earlier published revisions stay in the history.
  • What was validated is what gets published. Each revision records a content hash computed the same way as the scenarioHash rpa-runner writes to result.json. Publishing requires all of: the latest validation passed, a passing validation run has the same hash as the revision, and the files on disk still hash to that value.
  • Changed content needs validation again. A new revision always starts as a draft; earlier validation results cannot be used to publish new content.

Runs

  • Check first, then queue. Inputs are checked when a run is requested; invalid inputs get a 422 and nothing is queued. Otherwise the answer is 202 with the run ID.
  • Background worker. rpa-worker runs in a background thread of the server process and takes one run at a time in creation order (SQLite allows a single process). It calls the M2 rpa_runner.run.execute, so the overall deadline, subprocess and process-group termination are the same as in M2.
  • Headed and headless mode. The run form’s “Browser window” option: Show (headed mode) opens a browser window on the computer running the Portal so you can watch every step; Hide (headless mode) runs in the background. Headed is the default; on a computer without a graphical desktop (not Windows or macOS, and no DISPLAY or WAYLAND_DISPLAY) only headless is available and an API request for headed mode gets a 422. The run page records which mode was used. The rpa run command stays headless unless you add --headed.
  • Progress. The run page checks the status every second and reloads when the stage or status changes.
  • Cancellation. A queued run is cancelled right away; a running one has its subprocess and browser terminated at once and ends as "Cancelled". Actions already completed on the target site are not undone.
  • No double submission. Each form load creates an idempotencyKey; submitting twice returns the same run.
  • Run again. Any finished run can be repeated with the same inputs and options (validation uses the same revision, production runs the currently published one).
  • Server restarts. On start-up, runs that were interrupted are marked as failed; queued runs continue.

Logins and roles

M4: one login state per role, checked before every run
  • Scenarios only name the role. A scenario that needs to log in writes login: { role: ROLE_ID } (DSL). How to log in and how to tell the role is logged in is registered under “Scenarios › Logins & secrets”: the login URL, a check URL, an element that is only visible when logged in (a DSL locator) and optional automatic login steps.
  • Manual login first. “Log in” opens a browser window at the login URL on the computer running the Portal and you log in yourself, so SSO, captchas and phone or app two-factor all work. Press “Finish login” or just close the window; the Portal first checks in a headless browser that the login really worked before replacing the stored login state. Manual login needs a computer with a display.
  • Automatic login (optional). Only for plain username/password systems: the role gets a few DSL steps and uses {{ secrets.NAME }} for the password. When a run finds the role logged out, it logs in automatically once.
  • Login required (needs_login). Every run starts with a “Login check” stage that opens the check URL: if the element is visible the run continues; if not (for example after a redirect to the login page) and automatic login is not possible, the run stops at “Login required” without running any step and keeps a screenshot of the check. The run page offers “Log in as …” and “Run again”, which repeats the run with the same inputs once you have logged in.
  • Roles never mix. Each role keeps its own login state (a Playwright storageState) in roles/<role>/state.json in the data folder, readable only by you; every run opens a fresh browser context and loads only the role the scenario names. Login states are never copied into run directories nor served by pages or the API. Run results also update the role's status (logged in, login required).
  • Secrets. The same page sets secret values: they are stored in secrets.json in the data folder (readable only by you; encrypted in M8), and pages and the API only show names and update times, never values. Runs receive the values the scenario and its role use; anything not set there is looked up in an environment variable with the same name. The page also lists secrets that scenarios use but nobody has set.
  • The test site's two roles. Importing the examples also creates the roles used by BA-004 (regular user) and BA-005 (manager) from scenarios/demo/roles.json; the demo accounts are shown on the test site's login page. The two accounts see different to-dos, which shows that the roles do not mix.

Recording

M4: raw recording → DSL draft
1 Record a draft2 Debug and edit3 Validate4 Publish
  • Record on this computer. “Production › Script recording” → “Start recording” opens Playwright codegen's browser and Inspector on the computer running the Portal; work as usual and close the browser window when you are done. With a login role selected, its login state is loaded first. On the command line: rpa record URL --out recording.py --scenario draft.yaml.
  • Three targets. A new scenario (saved as v1); an existing scenario, “continue after the existing steps”: the recording browser first runs the latest revision's steps with the default inputs and stops on the last step's page, then recording starts, and the recorded steps, outputs and checks are appended to the existing content (which stays as it is, comments included; if an existing step fails, recording stops and nothing is saved); or an existing scenario, “replace with the recording”: record again from the start URL and save it as a new revision. With an existing scenario, the start URL, browser and login role are filled in from its settings.
  • The Inspector's code cannot be edited. The code on the right of the Inspector is generated live by Playwright from your actions and is read-only (Playwright's own design, not a restriction of this project); the Locator tab accepts and tests locators. To change the result, edit the scenario's “Automation script” and “Assertion script” after conversion.
  • Paste a recording. A codegen recording made elsewhere (sync, async or pytest style) can be pasted and converted directly, for example when the Portal runs on a computer without a display.
  • Assertions become outputs. The Inspector's “Assert text” and “Assert value” (expect(…).to_contain_text, to_have_value, to_have_text) are not kept as checks inside the steps. Instead the automation script gets an extract that reads the element (after waiting for it), the outputs get an entry taken from that page fact, and the assertion script (verify:) gets a check: “equals that input” when the recorded value equals a typed value, otherwise “has content”. Output names come from the element's ASCII name and can be changed later.
  • What is converted. goto, click, fill, press, select_option, check and the other common expect assertions, with get_by_role, label, placeholder, text, test_id, CSS, XPath, first, nth and filter(has_text) locators. The origin of the first URL becomes browser.baseUrl. Lines that cannot be converted (hover, uploads, iframes, new tabs…) stay in the draft as comments and are listed on the recording page.
  • Inputs from typed values. Every typed value becomes an input whose default is the recorded value; the name comes from the field's ASCII name (field, field_2… when there is none) and the field's label goes into the description, so you can rename it later in the scenario's form.
  • Passwords never stored. Password fields (label, placeholder or selector containing password, 密碼 and similar words) become secret references, and the raw recording is saved with the value masked as ***; the temporary raw recording is deleted after conversion.
  • Drafts only. The result is saved as v1 of a new scenario or a new revision of an existing one; the recording is only the source and still has to be debugged and validated before publishing. The recording page counts the steps, inputs, outputs, checks and lines not converted.

Step debugging

M4: one browser, one step at a time
  • Start. “Step debugging” on the scenario page or “Debug” on the card asks for the revision, inputs, browser and window mode. With a display, the browser window opens on this computer; in both modes the page shows a screenshot, the URL and the page facts after every step. DSL scenarios only.
  • Run. Each step has “Run this step” and “Run to here” (which runs only steps that have not run yet and stops at the first failure). Steps with side effects (click, fill, select, check, press) ask for confirmation before running a second time; no step is ever repeated automatically. “Start over” opens a new page and reloads the login state.
  • Locator test. Enter a DSL locator (for example { role: button, name: Log in }) to see how many elements match and the text of the first few, outlined in red in the screenshot.
  • Edit. Edit the YAML below and save it as a new revision to keep debugging with it; the browser and page facts stay, and steps that already ran keep their state by id.
  • Limits. One session per scenario at a time; sessions close after 15 idle minutes and when the server stops. Debugging really operates the target site, so use a test environment.

Section editing: automation script, assertion script, inputs, outputs

M4
  • Automation and assertion scripts are separate. DSL scenarios have “Automation script” (steps:) and “Assertion script” (verify:) on the card and the scenario page, each showing and rewriting only its section of the scenario file. A run executes the automation steps first, then checks the page facts with the assertion script, and publishes the outputs only when every check passes. The assertion script page inserts notEmpty, equals, contains and matches checks with one click, and clicking a page fact or input name inserts it at the cursor. Saving validates first and reports problems with line numbers inside the section.
  • Inputs and outputs: table and YAML source views. “Edit” on the scenario page's inputs or outputs opens a table with one row per entry where you change the name, type, required flag, default, the outputs' from and the description directly; constraints sit on the row below (minLength, pattern, minimum, enum… depending on the type), and rows can be added, moved up or down and removed. “YAML source” edits the section's raw text, which is validated before switching back to the table.
  • Only that section is rewritten. Saving replaces only that section of the scenario file, leaving everything else, comments included, untouched; renaming an input also renames {{ inputs.OLD }} references in the steps. It creates a new revision like any other save, with validation and the “409 if not the latest revision” check, and the new revision has to be validated again. Outputs of Python script scenarios come from assertion.py, and renames do not touch the scripts.

Playground

M6: pinned revisions of published scenarios in a sequence; upstream outputs feed downstream inputs; stop on failure
  • Sequences. In “Production › Playground” create a sequence and add scenarios from the library on the left to its end; the middle shows the nodes (n1, n2…) in run order, and the right side sets up the selected node, which can be moved up or down or removed. Changes stay on the page until you press “Save”; a save carries the save count it started from and gets 409 if another tab saved first.
  • Published revisions only, and pinned. The library lists only published scenarios; a node is pinned to the revision published when it is added, and later publishes do not change the sequence (the node settings point out the newer revision, and you switch when you want it). Only published revisions can be chosen, so every node runs content that passed validation.
  • Where inputs come from. Each input takes one of three sources: the scenario's default, a fixed value, or an output of an earlier node (only compatible types can be chosen; an integer can feed a number). When a node is added, inputs with the same name and a compatible type are connected to the nearest upstream output, e.g. BA-002's recordId to BA-001's output. Required inputs must have a source.
  • Check first, then run. Every change is checked: the scenario exists and is not archived, the revision was published, sources are earlier nodes, the output exists, the types are compatible, required inputs have a source and fixed values satisfy the input rules. Problems are listed at the top and on the nodes, and the sequence cannot run until they are fixed.
  • In order, stop on failure. “Run sequence” lets you pick the browser (each scenario's own by default) and the window mode. The nodes are queued one at a time; each node is an ordinary run (purpose “Playground”) with its own run directory and report, and it appears in the run reports. Only after a node passes are its published outputs taken and the next node queued; a node that does not pass (failed, timed out, cancelled, login required) stops the sequence there and the later nodes are skipped. When a bound value breaks the downstream input rules, the downstream node stops without starting a browser.
  • Sequence run page. Each node's status, input values and their sources (fixed value, default, ← n1.recordId), outputs, and links to its run and report; it updates every second while running. A snapshot of the sequence is taken when the run starts, so later edits do not affect it.
  • Continue from the stopped node, or run again from the start. “Continue from n2” reuses the outputs of the nodes that already passed and starts at the node that stopped, without repeating earlier actions (such as creating the record again), which suits continuing after a login; “Run again from the start” uses the same snapshot from the first node. Cancelling stops the current node; actions already completed on the target site are not undone.
  • Export and import. “Export JSON” downloads the sequence's name, description and definition; “Import JSON” on the list page creates a new sequence from it. The definition looks like {"version": 1, "mode": "serial", "onFailure": "stop", "nodes": [{"id": "n1", "sceneId": "ba-001", "revision": 1, "inputs": {"title": {"value": "trial"}}}, {"id": "n2", "sceneId": "ba-002", "revision": 1, "inputs": {"recordId": {"node": "n1", "output": "recordId"}}}]}. Inputs that are left out use their defaults; value is a fixed value, and node with output is an output of an earlier node. The rules live in rpa_core.workflow.
  • Scope. The MVP has sequences only, without conditions, branches or parallel runs; nodes share the queue with other runs, one at a time. Deleting a sequence keeps its run history (each sequence run has a snapshot of the definition).

Manual acceptance

M4, M6: recording, manual login and the playground screens need a person; the automated tests use a pre-recorded script

On a computer with a graphical desktop (macOS, Windows, or Linux with a desktop), go through this once with a fresh folder; it takes about twenty minutes:

  1. Start. uv run rpa serve --data data-check, then open http://127.0.0.1:8080; “Test site automation” already holds BA-001 to BA-005.
  2. Record a new scenario. In “Production › Recording”, choose “A new scenario”, start URL http://127.0.0.1:8765/, and press “Start recording”. On the test page fill in the title and quantity, press “Create record”, click the record number with “Assert text” in the Inspector, and close the browser. The recording details should show goto, two fills, a click and an extract, with 2 inputs, 1 output and 1 assertion.
  3. Debug, validate, publish, run. Press “Debug” on the new scenario, step through to the last step and look at the screenshots; back on the scenario page validate v1, publish it once it passes, then press “Run” on the card: the report says “Passed” and the outputs include the record number.
  4. Continue recording. Choose “A new revision of a scenario” with the scenario you just made, then “Continue after the existing steps”: the browser first replays the existing steps and stops on the result page, then record one more action; the new revision appends the steps after the existing content and keeps the original comments.
  5. Two roles. In “Scenarios › Logins & secrets” press “Log in” for testsite-user, log in as user / user-pass in the window that opens and press “Finish login”; use manager / manager-pass for testsite-manager. Then run BA-004 and BA-005: the two reports show different to-do items.
  6. Needs login and run again. Press “Log out” for testsite-user and run BA-004: it stops at “Login required” without running any step; follow the login role on the run page back to “Logins & secrets”, log in again, return to the run page and press “Run again”: the result is “Passed”.
  7. Playground. Validate and publish BA-001, then validate and publish BA-002 with the record number created by that validation. In “Production › Playground” press “New sequence” and add BA-001 and BA-002 from the library: BA-002's recordId is connected to n1's output. Press “Run sequence”: both nodes pass, and n2 finds the record n1 just created. Then move n2 to the top: the sequence reports that recordId can only use outputs of earlier nodes and cannot run.

Afterwards stop the management portal and delete the data-check folder.

Data

By default the project's data/; the folder given with --data otherwise (see Data folder). It contains:

rpa.db
SQLite database (tables below)
scenes/<scenario id>/<n>/
scenario.yaml (script scenarios also have two scripts)
runs/<run ID>/
the M2 run folder (input.json, report.html…)
roles/<role>/state.json
a role's login state (readable only by you)
recordings/<recording ID>/
masked raw recording and converted draft
debug/<session>/
debugging screenshots (deleted when the session ends)
secrets.json
secret values (readable only by you)

Database tables:

domains
ID, name, description, order
scenes
ID, name and category (from the latest revision), domain, default URL, latest and published revision numbers, archived
revisions
Scenario, revision number (unique), content hash, kind, status, note, publishing time
runs
Run ID, scenario and revision, the name and category at the time, purpose, status and stage, headed or headless mode, inputs and outputs, error, hash, times; for playground nodes, the sequence run and node ID
roles
Id, name, login URL, check URL and element, browser, automatic login steps, the latest status and check time
recordings
Recording ID, target scenario and revision, mode (new scenario, continue after the existing steps, replace everything) and the revision it continues, source (recorded or pasted), URL, browser, role, status, lines not converted
workflows
Playground sequences: name, description, definition (JSON), save count
workflow_runs
Sequence runs: the sequence and its name at the time, a snapshot of the definition, status, the node it stopped at and why, reused nodes (when continuing from a stopped node), browser and window mode, times

The models use SQLAlchemy 2; schema changes go through Alembic migrations, applied automatically when the server starts. A test checks that the migrations match the models.

Settings

--host, --port
Default 127.0.0.1:8080; without --port, if another program uses 8080 the next free port up to 8089 is used. If the port is taken by the management portal itself, only its address is shown and no second one is started
RPA_DATA_DIR
Data folder, default data; or use --data (see Data folder)
RPA_DATABASE_URL
SQLite by default; PostgreSQL comes in M8
RPA_LANG
Default language, also used for run reports; pages can switch at the top right
--no-testsite
Do not start the test site (by default it starts at 127.0.0.1:8765, or the running one is reused)
RPA_EXAMPLES_DIR
Examples folder of “Test site automation”, default scenarios/demo
Secrets
Set them under “Logins & secrets”; anything not set there is read from an environment variable of the same name in the server process

Security and limits

  • No sign-in. By default it only listens on 127.0.0.1; rpa serve warns when another address is used. Authentication and permissions come in M8.
  • Cross-site requests are blocked. A write request that carries an Origin header must come from the same origin, so other websites cannot call the local API in the background.
  • Files in run folders. Only files inside the run folder are served; only report.html is shown as a web page, with a content security policy that allows nothing but inline styles and the screenshots.
  • Script scenarios run arbitrary code. As in M2, only trusted people should edit Python script scenarios.
  • Login states and secrets stay on this computer. Both live in the data folder, readable only by you; they are never served by pages or the API nor written to run directories, reports or logs, and passwords in recordings are masked before saving. M8 encrypts them.
