Agent API

A third-party agent system works only through the server's /agent-api/v1: it writes scenarios and their inputs and outputs, opens a browser on a chosen recorder to debug step by step, has Workers validate and run them, combines scenarios in projects and runs them, and follows run progress. The new layer only adds authentication, permissions and auditing; business rules and the publishing gate stay in the existing services.

Phase 1 in progress
The decision and the options not chosen are in ADR 0017; how an agent calls the API is in the Agent API guide. The user confirmed the design on 2026-10-23, and phase 1 was built the same day (in review). On 2026-10-24 the user asked to bring projects and composite scenarios into phase 1 and to write a test plan guide and a test report guide for agents. The server's /agent-api/v1/openapi.json is the reference for endpoints, and /agent-api/v1/docs lets you try them directly.

Architecture

The agent only talks to the server
The blue box is the new layer; grey boxes are outside the platform; the dashed webhook comes in phase 2. The recorder and the Worker connect exactly as before: they open no ports, and the agent never needs to know where they are. /api is not opened up as is: it has no authentication and changes with the Portal's pages, whereas a separate /agent-api/v1 can stay stable and be versioned on its own.

API clients, permissions and auditing

Each agent system is an "API client", registered in the admin area, which receives an API key shown only once; the server stores only its hash, as it does for device tokens. Requests carry Authorization: Bearer <API key>.

  • No taking over a person's session: if someone else (a person or another agent) is already debugging the scenario, the API returns 409 debug_in_use instead of closing their session; an agent can see and use only sessions it opened (the Portal still closes the old session when a person starts on another device). debug_busy keeps its existing meaning: the previous command in the same session has not finished.
  • Audit log: every write request is recorded (time, client, action, target, result code); administrators can filter it in the admin area but cannot edit or delete it. Revisions saved by an agent are noted "Created by agent ‹name›", and runs record the client that started them.
  • Transport: the external port speaks HTTP, so keys travel in clear text. The user confirmed (2026-10-23) that the agent system and the server share a local network, so phase 1 does not require HTTPS. If the agent later moves off that network, put a reverse proxy with HTTPS in front of the server; the program itself does not do TLS.

  • Events: queued, claimed (which Worker), stage (inputs, login, automation, verification, outputs), step (a step started or ended, its result and duration), finished (final status, outputs, error summary). Sequence numbers increase, so after resumes without gaps after a disconnect.
  • Where step progress comes from: the runner's child process already writes steps.json after every step. The local worker reads the file and updates the database; a remote Worker adds the current step to its heartbeat and sends one extra heartbeat when the step changes. Older Workers without these fields keep working and only show stages.
  • Long polling first: Workers and recorders already work this way, it passes through proxies, and the server never has to connect to the agent. The agent system shares a local network with the server (confirmed by the user on 2026-10-23), so phase 2 webhooks can connect from the server to the agent directly.
  • Debugging needs no events: each debug command answers only when it has finished, with the result of that step.

Typical flow

  1. Read /meta, /dsl/schema, the available recorders and roles.
  2. Create the scenario and save the first revision (open the URL, declare the login role if needed).
  3. Open a debug session on the chosen recorder.
  4. Read the page structure, take screenshots, test locators.
  5. Write the next few steps and save a new revision.
  6. Switch to the new revision and run to the last step; if a step fails, go back to step 4.
  7. Complete inputs, outputs and independent verification, checking with /dsl/check.
  8. Have a Worker validate; if it fails, go back to debugging.
  9. Publish (an agent with the scope publishes itself; otherwise ask a person to publish in the Portal).
  10. Run it and read the status and outputs. When a run stops at "needs login", ask a person to log in manually on a recorder, then call rerun.
  11. To build a flow, create a composite scenario in a project (nodes are published scenario revisions), check, validate and publish it, then run it and read progress and each node's run through /composite-runs. When this is used for testing, the agent writes the test plan and test report for people to accept; the platform does not read them.

Page snapshots

Phase 1, needs a recorder app update
  • How: the debug process rpa_runner.debug gets a snapshot command returning the current tab's accessibility tree (Playwright's ARIA snapshot), form fields (label, name, type, required), the iframe hierarchy and the open tabs. The agent writes role / label / text locators from it.
  • Masking: values of fields filled with a secret and of password fields are always masked, using the runner's existing masking.
  • Size: above a limit the snapshot is truncated and marked so; the agent can pass within to look at part of the page only.
  • Compatibility: the recorder reports snapshot support when it comes online; when an older app does not, the API returns 422 recorder_outdated with a message to update the RPA recorder (the same approach and status code as M7a).

Security and data leaving the network

  • Page content leaves the server: screenshots, page snapshots, page facts and outputs all go to the agent; if the agent uses an external model, that content goes outside. This is the same open question as M5's data destination, so "page content" is off by default.
  • Secrets: referenced by name only; values are never returned.
  • The publishing gate is unchanged: scenarios written by an agent go through real validation just like a person's, and the published revision must be the one that passed.
  • Debugging has side effects: it really clicks and types in the target system; give agents a recorder of their own and a role with a test account.
  • Runaway protection: limits keep the queue and the recorders from being swamped; a key can be disabled in one click.

Database and compatibility

The phase 1 migration is 0016_agent_api (after the project space's 0015_projects) and uses only generic types that run on both SQLite and PostgreSQL (ADR 0008). /api, the Client API and the Worker API do not change; older apps keep working.

Testing and acceptance

  • Automated tests: keys and scopes (403 for a missing scope, 401 for disabled or expired keys, 429 above limits), forwarding of every endpoint, not taking over a person's debug session, idempotency keys, the audit log; projects and composite scenarios from creation to run, rerun and cancel, and the allowed project and domain limits; recorders and Workers simulated with the existing test helpers.
  • Browser tests: the whole flow on the test site (create → page snapshot → debug → validate → publish → run → read results), registered in tools/ci_roles.py.
  • Manual acceptance: Linux server + macOS recorder + Windows Worker, with a script on another computer going through the whole flow; requests are refused after "Allow agent debugging" is switched off.
