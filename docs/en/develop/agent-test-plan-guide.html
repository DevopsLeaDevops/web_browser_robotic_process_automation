Test plan guide

For third-party agents connected to the platform: how to design scenes and projects from requirements, design composites with the TestCase methods common in software engineering, and write a test plan for people to review (XMind, plus JSON for the agent's own use).

Phase 1 released (v0.6.0)
The test plan is the agent's deliverable, for people to review and accept. The platform does not read, upload or store it, and has no API for it. The agent uses the API in the Agent API guide to create scenes, projects and composites on the platform, then writes the design and the results up in this document. Running, tracking and the test report are in the test report guide. Written on 2026-10-24 at the user's request and released in v0.6.0.

Who does what

Agent
Analyses requirements, designs TestCases, creates and debugs scenes, creates composites in a project and writes the test plan; after sign-off, runs them and writes the test report.
People (reviewers)
Review the test plan: is the scope right, are there enough TestCases, are the test data and side effects acceptable, how to settle the open questions. Formal runs start only after sign-off. At the end they accept against the test report.
Platform
Keeps the revisions of scenes, projects and composites, runs them on workers and keeps each run's steps, checks and artifacts. It does not know the words "test plan" or "TestCase" and does not judge whether testing is sufficient.

Do not confuse this with the platform's "validation": a validation hands one revision to a worker for one run, as the basis for publishing; a test plan is a document for people.

Overall flow

  1. Read the requirements and the platform: GET /meta (scopes, allowed projects and domains), GET /projects, GET /composites/library (scene revisions you can use), GET /roles, GET /secrets.
  2. Design TestCases: list the features and requirement IDs to verify, pick test design methods and write the TestCase list. Nothing is created yet.
  3. Split into scenes: turn the TestCase steps into reusable scenes; use what the library already has and create only what is missing.
  4. Hand over a draft: write a draft XMind plan (status "draft") with the open questions in the central topic's notes. Debugging a scene really clicks and types in the target system, so have people look at the scope and test data first; go straight on only when the user has clearly authorised it.
  5. Create scenes: create, debug, validate and publish the missing scenes, see the Agent API guide.
  6. Create the project and composites: one composite per TestCase; check with POST /composites/check until there are no problems, then save.
  7. Finish the plan: fill in the codes and revisions of scenes and composites, produce test-plan.xmind and test-plan.json, set the status to "pending sign-off" and hand the XMind over.
  8. After sign-off, run it as described in the test report guide.

TestCase design methods

MethodWhenHow to express it with composites
Equivalence partitioningInputs have clear valid and invalid rangesOne TestCase per valid class; invalid classes use scenes that expect a rejection (see negative tests below).
Boundary value analysisQuantities, amounts, lengths, datesOne TestCase each for minimum, minimum + 1, maximum − 1, maximum and out of range, with the value as a fixed node input.
Decision tables, cause-effect graphsSeveral conditions decide the result together (tier × amount × discount)One TestCase per rule; conditions are inputs and the result is in the scene's verify.
State transitionsStateful objects such as documents, orders, approvalsOne composite per transition path to cover, e.g. create → submit → approve → close, chained by outputs (the document number).
Use-case (business flow) testingMain and alternative flows of an end-to-end processOne TestCase for the main flow and one per alternative flow (cancel, return, resubmit), sharing the first nodes and changing the rest.
PairwiseMany parameters, too many combinationsPick representative combinations pairwise, one TestCase each; state how they were picked in the plan.
Error guessingKnown weak spots: double submit, blanks, special characters, missing permissionExtra TestCases, each with its reason.
  • Priority: P1 smoke and core paths (run every time), P2 main features and common error handling, P3 minor and rare cases. In XMind, markers priority-1 to priority-3.
  • Write negative tests so that a rejection passes: a composite stops at the first failure and a failed node means a failed TestCase, so you cannot expect a run to "fail". "Quantity over the limit shows an error" becomes a scene that types the bad value, submits, and whose verify checks that the error appears and no document was created.
  • Input rules reject invalid fixed values: the composite check validates fixed values against the scene's input rules such as minimum, maxLength and enum. To submit an invalid value, the scene's input must not have those rules (for example a separate scene whose input is an unrestricted string).
  • Every TestCase must be repeatable: when it creates data, use dynamic values for unique data (e.g. Test customer {{now:yyyyMMddHHmmss}}); add a clean-up node at the end when needed.
  • Traceability: every TestCase maps to at least one requirement ID; every requirement has TestCases, or a stated reason why it is not tested.
  • Side effects: runs really create and change data in the target system. Use roles with test accounts and test data; record unavoidable ones as risks for people to confirm.

Splitting scenes

  • One business action per scene: create an order, look up an order, approve. Do not write a whole TestCase as one scene: separate scenes can be shared by TestCases and show which action a failure stopped at.
  • Inputs and outputs: data that varies are inputs; values needed downstream (document number, amount) are outputs. Related scenes use the same names for outputs and inputs so that {"auto": true} can connect them.
  • Checks are the expected results: each scene's verify compares page facts with inputs to check the business result of the action, not just "no step failed".
  • Check the library first: GET /composites/library lists published scene revisions in allowed domains with each revision's inputs, outputs and login role. Use what fits; for changes, save a new revision, validate and publish it, then use the new number. TestCases on older revisions are not affected.
  • Only published revisions: without scenes:publish, list the scenes and revisions to publish under the plan's open questions and ask people to publish them in the Portal.

Project IDs follow the domain rules (lower-case letters and digits, -, _; fixed once created). A key limited to some projects cannot create projects (403 project_create_forbidden); use an existing one or ask an administrator. Deleting and reordering are only in the admin pages.

2. Composite definition

{"version": 2, "mode": "dag", "onFailure": "stop",
 "nodes": [
   {"id": "create", "sceneId": "order-create", "revision": 6,
    "inputs": {"customer": {"value": "Test customer {{now:yyyyMMddHHmmss}}"},
               "quantity": {"value": 99}}},
   {"id": "query", "sceneId": "order-query", "revision": 3,
    "inputs": {"orderId": {"node": "create", "output": "orderId"}}}
 ],
 "edges": [{"source": "create", "target": "query"}]}
  • At most 50 nodes; node ids are unique within a composite.
  • Input sources: {"value": …} a fixed value (dynamic values allowed); {"node": "create", "output": "orderId"} an output of an upstream node; {"auto": true} the single output with the same name on a direct upstream node. Inputs left out use the scene's default; inputs without a default must be given.
  • Output bindings already order the nodes; add edges only for an order without a data dependency.
  • Nodes ready at the same time run one by one in definition order; when a node does not pass, the run stops and later nodes are marked skipped.

3. Check, create, change

POST /agent-api/v1/composites/check   {"definition": {…}}
→ {"ok": false, "problems": [{"code": "workflow.input_missing", "message": "…",
                               "node": "query", "input": "orderId"}]}

POST /agent-api/v1/projects/order-regression/composites      (projects:write)
{"code": "tc-order-003", "name": "TC-ORDER-003 Quantity at the limit (99) can be created",
 "description": "Goal: an order with the maximum quantity can be created. Requirement: REQ-12. Plan: TP-ORDER-2026-10",
 "domainId": "sales", "definition": {…},
 "note": "Test plan TP-ORDER-2026-10 v1", "idempotencyKey": "TP-ORDER-2026-10/tc-order-003"}
→ 201 {"code": "tc-order-003", "latestRevision": 1, "publishedRevision": null, "problems": [],
       "dependency": "complete", "portalPath": "/playground/12", …}

PUT /agent-api/v1/composites/tc-order-003
{"baseRevision": 1, "definition": {…}, "note": "Quantity changed to 99"}
→ {"latestRevision": 2, …}
  • Only an empty problems can be validated and run; fix by node and input. Only dependency complete can be published.
  • The code is the TestCase ID: lower-case letters and digits, -, _, e.g. tc-order-003; the name starts with the upper-case ID, e.g. "TC-ORDER-003 Quantity at the limit (99) can be created"; the description holds the goal, requirement IDs and plan ID.
  • domainId is the domain folder that holds the composite; without it the composite goes in the "Composite scenarios" domain. A key limited to some domains must give an allowed one. Scenes used by the nodes must be in allowed domains too, otherwise 403 composite_scenes_forbidden.
  • Saving with a baseRevision that is not the latest returns 409 stale_workflow (latest is the latest revision): read GET /composites/{code}, reapply your change and save again; never overwrite people's changes. When the definition is unchanged only the name and description are updated, with no new revision.
  • Move to another project with PATCH /composites/{code} {"projectId": "…"}.
  • GET /projects/{id} lists a summary of each composite in the project (latest and published revisions, problem count, last run); GET /composites/{code} has the full definition, revisions, validation records and dependencies.

Test plan format

XMind for people, JSON for the agent
test-plan.xmind
The test plan itself, for people to review and sign off: one TestCase per composite, with the plan-level text (scope, environment, criteria, open questions, sign-off) in the central topic's notes; common TestCase tools can import it.
test-plan.json
The same content as structured data, read by the agent when it runs the plan and writes the report; people need not read it.

Generate both from the same data; TestCase IDs and counts must match. Name the folder after the plan ID, e.g. TP-ORDER-2026-10/. A plan that has been handed over gets a new version when changed, with the change noted in the change log in the notes.

XMind levelContent
Central topicTitled with the plan ID and project name, e.g. "TP-ORDER-2026-10 Order regression". Its notes hold the plan-level text, in the format below.
Level 1: modulesTest suites, e.g. "Order creation"; notes may say what the module verifies.
Level 2: TestCaseOne topic per composite titled "ID title", and it must have a priority marker priority-1 to priority-3 (tools use it to recognise TestCases). Labels: auto (automated), composite code and revision (e.g. tc-order-003 v2), requirement IDs, design method. Notes: preconditions, test data, Portal path.
Level 3: stepsOne topic per node, "node ID: what it does (scene ID vN)", in run order.
Level 4: expected resultExactly one expected-result topic under each step; join several checks with "; ".

The central topic's notes hold these paragraphs in order (plain text, one paragraph per line). After review, people fill in the sign-off line and hand the file back, or reply to the agent directly; the agent records it under signoff in test-plan.json:

Document: TP-ORDER-2026-10 v2; status: pending sign-off; generated by ERP assistant at 2026-10-24T08:00Z; server srv-linux-01 (0.6.0); project order-regression; requirements: order spec v3
1. Goals and scope: verify the quantity rules of order creation and the approval flow. Not covered: refunds, reports
2. Test environment: https://erp-test.example.internal; Chromium; placement any; roles sales, manager; secrets: erp-password (name only)
3. Test strategy: boundary values, state transitions; P1 smoke and core paths, P2 main features, P3 minor; validate before publishing, one formal round; at most one rerun for environment causes
4. Scenes: order-create v6 (published), order-query v3 (published), order-submit-raw v2 (to publish)
5. Requirements not covered: REQ-15 printing (the platform cannot drive print dialogs)
6. Test data and clean-up: customer names carry a timestamp; about 6 test orders per round, not deleted automatically
7. Entry and exit criteria: entry: plan signed off, no composite has problems, roles logged in; exit: all P1 pass, P2 pass rate ≥ 95%, no open critical defects
8. Risks and open questions: order-submit-raw v2 needs a person to publish; role manager needs a manual login
9. Sign-off: reviewer __; date __; conclusion (approved / approved with changes / rejected) __; comments __
Change log: v1 first draft; v2 added TC-ORDER-004
  • Do not start topic titles with # or !; common tools treat those as comments and skip them.
  • Keep plan-level text only in the central topic's notes, not in extra sheets or topics: common XMind-to-TestCase tools treat a topic without children as a TestCase.
  • The test report reuses this map and adds result markers to TestCases (see the test report guide).

Writing the XMind file

An .xmind file is a ZIP. content.json is for XMind 2020 and later; content.xml is for XMind 8 and common XMind-to-TestCase tools (such as xmind2testcase). Both hold the same content; this Python writes both with the standard library only:

import json, uuid, zipfile
from xml.etree import ElementTree as ET


def topic(title, children=(), *, priority=None, markers=(), labels=(), notes=None):
    marks = ([f"priority-{priority}"] if priority else []) + list(markers)
    return {"id": uuid.uuid4().hex, "title": title, "markers": marks,
            "labels": list(labels), "notes": notes, "children": list(children)}


def _json(node):
    data = {"id": node["id"], "class": "topic", "title": node["title"]}
    if node["markers"]:
        data["markers"] = [{"markerId": mark} for mark in node["markers"]]
    if node["labels"]:
        data["labels"] = node["labels"]
    if node["notes"]:
        data["notes"] = {"plain": {"content": node["notes"]}}
    if node["children"]:
        data["children"] = {"attached": [_json(child) for child in node["children"]]}
    return data


def _xml(parent, node):
    element = ET.SubElement(parent, "topic", id=node["id"])
    ET.SubElement(element, "title").text = node["title"]
    if node["markers"]:
        refs = ET.SubElement(element, "marker-refs")
        for mark in node["markers"]:
            ET.SubElement(refs, "marker-ref", {"marker-id": mark})
    if node["labels"]:
        labels = ET.SubElement(element, "labels")
        for label in node["labels"]:
            ET.SubElement(labels, "label").text = label
    if node["notes"]:
        ET.SubElement(ET.SubElement(element, "notes"), "plain").text = node["notes"]
    if node["children"]:
        attached = ET.SubElement(ET.SubElement(element, "children"), "topics", type="attached")
        for child in node["children"]:
            _xml(attached, child)


def write_xmind(path, sheet_title, root):
    sheet_id = uuid.uuid4().hex
    content = [{"id": sheet_id, "class": "sheet", "title": sheet_title, "rootTopic": _json(root)}]
    xmap = ET.Element("xmap-content", xmlns="urn:xmind:xmap:xmlns:content:2.0", version="2.0")
    sheet = ET.SubElement(xmap, "sheet", id=sheet_id)
    _xml(sheet, root)
    ET.SubElement(sheet, "title").text = sheet_title
    manifest = ('<?xml version="1.0" encoding="UTF-8" standalone="no"?>'
                '<manifest xmlns="urn:xmind:xmap:xmlns:manifest:1.0">'
                '<file-entry full-path="content.xml" media-type="text/xml"/>'
                '<file-entry full-path="META-INF/" media-type=""/>'
                '<file-entry full-path="META-INF/manifest.xml" media-type="text/xml"/>'
                '</manifest>')
    with zipfile.ZipFile(path, "w", zipfile.ZIP_DEFLATED) as archive:
        archive.writestr("content.json", json.dumps(content, ensure_ascii=False))
        archive.writestr("metadata.json", json.dumps({"creator": {"name": "agent", "version": "1"}}))
        archive.writestr("manifest.json",
                         json.dumps({"file-entries": {"content.json": {}, "metadata.json": {}}}))
        archive.writestr("content.xml", ET.tostring(xmap, encoding="unicode", xml_declaration=True))
        archive.writestr("META-INF/manifest.xml", manifest)

Read it back to check: unzip, read content.json and confirm the number of TestCase topics equals testCases in test-plan.json. When people import it into a specific TestCase tool, that tool's documentation wins.

Before handing it over

  • TestCase IDs and counts match between the XMind and the JSON; every TestCase has a composite code and revision, and GET /composites/{code} shows empty problems.
  • Every requirement has TestCases or a stated reason it is not tested; every TestCase has a priority and expected results.
  • No API keys, passwords or secret values in the documents; no real personal data in the test data.
  • Everything people must do is under "risks and open questions" in the central topic's notes: which scenes to publish, which roles to log in, which steps have side effects, which permissions are missing.
  • Status, version and generation time are right; the project page in the Portal (portalPath) shows the same composites.
