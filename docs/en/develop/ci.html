CI & pipelines

When GitHub Actions runs, which tests it runs and roughly how long it takes; how to trigger runs by hand, and where to look up the duration of past runs. Regular PRs only test each system in its production role; every other combination is left to the full run early every morning. The same inputs are verified only once, and desktop apps whose shell did not change are not repackaged.

Layered builds: verify the same inputs only once

Since 2026-10-27

ADR 0018 splits every package into a shell (Python, third-party packages, everything PyInstaller bundles, and rpa_update) and a code layer (the seven workspace packages). CI follows the same split:

  • Inputs that already passed are not run again. Each heavy job (the three desktop apps, the server packages, the setup scripts and the Windows worker tests in CI) has its own list of inputs; their content becomes an input fingerprint. When the same fingerprint has already passed in this repository, the job is skipped and reuses that result. A PR that only touches the server does not touch macOS, and a merge to main whose content matches what the PR tested does not run again.
  • Version numbers are not changes. The version in pyproject.toml files and the workspace package versions in uv.lock are left out of the fingerprint, so a release PR that only bumps versions no longer rebuilds three apps, four setup-script runs and the Windows tests.
  • An unchanged shell is not repackaged. When a desktop app has to run, its shell key is checked first. If the shell matches the cache, the DMG or zip built last time is taken from the cache, an update file is built from this commit's code and installed, and then the tests run (the code-layer path). That is exactly how devices upgrade in the field: an old shell with new code. Only a changed shell triggers a full build.
  • macOS queues only when needed. The recorder (macOS) runs only when recording, step debugging, the local gateway, macOS-only code or the shell changes; the worker (macOS) only when the shell or its macOS parts change. Other code changes are covered by the nightly macOS code-layer check, visible by the next day at the latest, and every release is a full build.

Input fingerprint
The first 16 hex characters of the SHA-256 of a job's input files (paths and content) plus the job name. The lists are GROUPS in tools/ci_changes.py; every job includes the dependencies (without version numbers), its own workflow file and tools/ci_changes.py itself.
Pass record
A tiny artifact pass-<job>-<fingerprint> uploaded when a job succeeds, kept for 30 days. Only runs of this repository count; a PR from a fork cannot claim a pass for anyone else.
Shell key
A hash of the shell's inputs (dependencies, .python-version, packages/rpa_update/src, apps/desktop/packaging, tools/build_desktop.py) and the target. The cache key is desktop-shell-v1-<target>-<shell key>-<CI key ID>; it holds the DMG or zip, runtime.json and the downloaded browsers.
Code-layer path
Take the app from the cache (tools/desktop_shell.py restore), build an update file from this commit (tools/build_update.py, signed with the CI key) and install it into the app's folder; the self-test, window self-test and end-to-end tests all use that layer, and afterwards the layer must be confirmed and not rolled back. No installer is built and no trial package is uploaded.
Full-build path
All the original steps, including the "next commit" update and automatic rollback. When it passes, the DMG or zip is saved to the cache (not for version tags).

When everything runs and nothing is reused

Scheduled runs (nightly tests, setup scripts, the Saturday desktop full build), manual runs and version tags. They still leave pass records, since the full scope covers the regular one. When a pass record expires (30 days) or is deleted by "清理產物" (clean up artifacts), the same inputs are verified once more.

How to use it

  • See what ran: the scope job of every workflow writes a table to the run summary with each job's fingerprint, shell key, and whether it ran or which run it reused (linked); the same goes into annotations. The summary of each desktop app starts with "程式碼層路徑" (code-layer path) or "完整建置" (full build) and which version the shell came from.
  • Need trial packages (DMG, installer): the code-layer path builds no new packages. A manual desktop build is a full build by default: gh workflow run desktop.yml --ref branch -f build=full; add -f targets=recorder-macos-arm64 for a single app.
  • Verify again instead of reusing: run that workflow by hand (manual runs never reuse).
  • Changed the build steps in desktop.yml: add 1 to SHELL_EPOCH in tools/ci_changes.py so every cached shell is rebuilt once. When the fingerprint algorithm or the way inputs are written changes, add 1 to EPOCH to invalidate all pass records.
  • New files: files under a registered folder are included automatically. A new macOS-only module goes into RECORDER or WORKER_MACOS; tests/ci/test_ci_changes.py checks that every pattern still matches a file (a rename cannot silently drop it) and that all desktop app sources are inputs of the Windows worker.
  • Fingerprints locally: python3 tools/ci_changes.py --workflow desktop.yml --show (also server-package.yml, setup-scripts.yml, ci.yml).

When the code-layer path fails

  • "裝不上更新檔" (cannot install the update file): the signature or runtime ID does not match. Check that the "測試更新檔用的金鑰" step used RPA_UPDATE_CI_KEY, and the target in runtime.json.
  • "提交不是…" (wrong commit) or "active.json 用的是內建的程式" (the built-in code was used): the launcher did not use the layer; read app/boot.log in the app's folder.
  • New code cannot import some third-party module: this is exactly what devices would hit after the upgrade; the shell does not bundle that module. Add it to a list such as FULL_PACKAGES in apps/desktop/packaging/rpa_desktop.spec: the shell key changes, this run is a full build, and that release needs the full installers.

The schedules sit in the quietest hours of the repository: 20:17 UTC is 13:17 PDT (UTC−07:00) / 12:17 PST (UTC−08:00) in America/Los_Angeles, 04:17 in Singapore. A failed scheduled run opens (or updates) an issue labeled ci-schedule; so does a job that is cancelled because it never got a runner (the annotation says "The job was not acquired by Runner", more common on macOS). The comment then notes that this system was not tested this time, that it is not a test failure, and that "Re-run failed jobs" on the run page fills the gap (since 2026-10-29; before that such a run was red but opened no issue). PRs are compared by their merged content (GitHub tests the PR merged into main); a new push to the same branch cancels the older run. Dependency-update PRs are opened by GitHub Actions and only trigger CI automatically; the other workflows run once someone pushes to that branch. The Linux tests and the Windows worker tests in CI each run for at most 30 minutes, so a stuck run fails instead of running on (since 2026-10-21; before that there was no limit and a stuck run on Windows kept going until GitHub's 6-hour cap).

Before the nightly full tests on Windows, the dynamic port range is widened from the default 49152–65535 (16,384 ports) to 10000–65535. A closed connection only returns its port after TIME_WAIT, so over three passes the short connections between the local sites, the management portal and the browsers can use them all up, and Chromium reports net::ERR_NO_BUFFER_SPACE (pass 3 on 2026-10-27, issue #99). The fixed ports used by the tests and the product (the management portal from 8080, the test site) are all below 10000 and are not affected. After each pass an annotation also records the TCP connections by state and the Chromium, Firefox and Node processes still running, so a repeat shows whether the ports ran out or processes did not exit (since 2026-10-29).

Pushes that only change docs

The Linux tests in CI: the first job of every workflow, “執行範圍” (scope, tools/ci_changes.py), compares this push with the previous one. When only handoff/, docs/ or *.md changed and the previous push already passed in the same workflow, only the static checks and the tests that need no browser run (including the docs and translation checks); the browser tests reuse that result, and an annotation says which run. If the previous run failed, was cancelled or has not finished, everything runs as usual.

The other heavy jobs need no special case: docs are not inputs of any of them, so their fingerprints stay the same and the result is reused (layered builds). The collaboration rule is in section 5 of the shared collaboration workflow.

Manual runs

On GitHub's Actions page pick a workflow, press "Run workflow" and choose the branch and options. Or use gh:

# Full run: all tests on three systems, browser tests twice more (about 30 min)
gh workflow run nightly.yml --ref branch-name
# Windows only, no repeats
gh workflow run nightly.yml --ref branch-name -f systems=windows -f extra=0
# CI: role = same as PRs; full = all tests on Linux
gh workflow run ci.yml --ref branch-name -f scope=full
# Setup scripts: full (default) = all tests plus from scratch; role = same as PRs
gh workflow run setup-scripts.yml --ref branch-name
# Desktop builds: manual runs always run; a full build by default (with trial packages)
gh workflow run desktop.yml --ref branch-name
# Recorder only, only the code layer when the shell is cached (no trial packages)
gh workflow run desktop.yml --ref branch-name -f targets=recorder-macos-arm64 -f build=auto
# Server packages (Linux x64, arm64)
gh workflow run server-package.yml --ref branch-name

Run a role locally: uv run pytest -m "browser and (role_worker or smoke)" (worker), uv run pytest -m "not browser or ((smoke or role_server or role_recorder) and not firefox)" (same as CI on Linux).

Artifacts and storage quota

The repository has been private since 2026-10-22, so Actions artifacts count toward the account plan's storage quota. Once the quota is used up, artifact uploads fail and a release cannot create its draft (this is what happened to v0.5.0). Desktop builds and server packages therefore keep their artifacts for 3 days on PRs and main and for 1 day on releases, and the release workflow deletes its run's artifacts after creating the draft. Test reports and Portal traces are only for diagnosis, so a failed upload does not fail the job.

Layered builds leave two more things behind: pass records (pass-* artifacts, under 1 KB each, kept for 30 days) and the shell cache (the Actions cache, which does not count toward the artifact quota; up to 10 GB per repository, evicted after 7 days without use, and saved again by the next full build).

To free the quota in one go, run "清理產物" (cleanup-artifacts.yml) by hand. By default it only lists the artifacts, with counts and sizes by name in the summary; after checking, run it again with "只列出、不刪" (list only) unticked. Deleting cannot be undone; the files of published versions live on Releases and are not affected, and deleting pass-* only means those inputs are verified once more. The quota goes down only after GitHub recalculates the usage.

# List all artifacts only
gh workflow run cleanup-artifacts.yml
# Delete artifacts created more than 3 days ago
gh workflow run cleanup-artifacts.yml -f older-than-days=3 -f dry-run=false

Update signing key

ADR 0018

The RPA-Update-<version>.zip built by a release is signed with an Ed25519 private key; the server, devices and the desktop launcher verify it with the public key inside their package and refuse it when verification fails. The private key lives only in the GitHub secret RPA_UPDATE_SIGNING_KEY: never in the repository, a chat or an issue. The public key is listed in RELEASE_KEYS in packages/rpa_update/src/rpa_update/keys.py and ships with the full packages. When RELEASE_KEYS is empty, the secret is missing, or the two do not match, the release workflow fails instead of publishing a version devices cannot verify. Builds on pull requests and main use the CI test key (below) and never touch the real one.

Creating the key

  1. On a computer with OpenSSL 1.1.1 or later, create the private key and print the public key (one line of base64). Check with openssl version: OpenSSL 1.0.2 on CentOS 7 and the LibreSSL built into macOS have no Ed25519 and print Algorithm ed25519 not found; use another computer or the project tool below.
openssl genpkey -algorithm ed25519 -out rpa-update-signing.pem
openssl pkey -in rpa-update-signing.pem -pubout -outform DER | tail -c 32 | base64
  1. In the repository, open Settings › Secrets and variables › Actions › New repository secret, name it RPA_UPDATE_SIGNING_KEY, and paste the whole content of rpa-update-signing.pem (including the -----BEGIN PRIVATE KEY----- and -----END PRIVATE KEY----- lines).
  2. Add the public key to RELEASE_KEYS through a pull request. The public key is not secret.
  3. Back up the private key file somewhere only you can reach (for example a password manager), then delete it from that computer. If the private key is lost, later versions cannot be signed and devices need a full installer with a new public key; the same applies if it leaks.

The project's own tool works too: uv run python -m rpa_update.build keygen --private rpa-update-signing.pem prints the public key, and the file has the same format as OpenSSL's.

Rotating the key

Add the new public key to RELEASE_KEYS (keep the old one) and publish a full release; once the server and devices run that release, replace the secret with the new private key, and finally remove the old public key. Changing RELEASE_KEYS changes the runtime ID, so both releases are installed from full packages.

CI test key (RPA_UPDATE_CI_KEY)

A separate Ed25519 private key used only for testing in CI. Desktop apps built on PRs, main and schedules (trial packages) trust it; release packages do not (the release workflow's --release check makes sure). The code-layer path needs it: a cached shell was built earlier, so the key it trusts must still be available in later runs to sign an update file it accepts. Without this secret, the desktop build falls back to a new temporary key every time and always builds in full, and the "測試更新檔用的金鑰" (test update key) step leaves a warning. PRs from forks and Dependabot get no secrets and behave the same way.

Check whether it is set: in the repository's Settings › Secrets and variables › Actions, look for RPA_UPDATE_CI_KEY in the Repository secrets list (only the name and update time are shown, never the value), or run gh secret list on a computer with access. After setting it, run a desktop build: an annotation “測試更新檔的金鑰 <ID>（RPA_UPDATE_CI_KEY）” on that step means it was read.

Create and set it (different from the release key, never shared; the public key does not go into the repository):

uv run python -m rpa_update.build keygen --private rpa-update-ci.pem
gh secret set RPA_UPDATE_CI_KEY < rpa-update-ci.pem   # or paste it under New repository secret
rm rpa-update-ci.pem

Rotating this key needs no coordination: after the secret changes, the key ID in the cache key differs, so the first build is a full one and saves a new cache entry. A leak only affects CI trial packages (whoever has the key can sign update files they accept); release packages are not affected. Create a new key and replace the secret.

Run duration records

After every CI, desktop build, server package, setup-script, nightly and release run, the "Run duration records" workflow (tools/ci_metrics.py) appends the results to the repository's ci-metrics branch. It does not touch main or trigger other workflows. Switch to the ci-metrics branch on GitHub to see the overview in README.md: each workflow over the last 7 days compared with the 7 before, daily runner time per system, the slowest test files and the latest runs.

data/runs.jsonl
One line per run (and per re-run): trigger, branch, result, duration including queueing, longest queue, runner time per system
data/jobs.jsonl
Queue and run time of each job
data/test-files.jsonl
Time of each test file in the JUnit reports of CI and the nightly run

To add history, run "Run duration records" by hand with since set to a UTC date such as 2026-10-09; runs already recorded are not added twice. Each test run's annotations also include a “pytest 耗時” (pytest timing) note with the slowest files and tests.
