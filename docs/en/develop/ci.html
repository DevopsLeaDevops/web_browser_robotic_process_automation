CI & pipelines

When GitHub Actions runs, which tests it runs and roughly how long it takes; how to trigger runs by hand, and where to look up the duration of past runs. Regular PRs only test each system in its production role; every other combination is left to the full run early every morning.

Tests assigned by role

The main runtime paths for now (confirmed 2026-10-19, see Deployment & operations): Linux only runs the website, macOS only runs the recorder, Windows only runs the worker. All three use Python 3.13; the one-command setup scripts install a development environment and are not on a main path.

Tests are marked role_server, role_worker or role_recorder automatically from their file path, and parameter sets that use Firefox are marked firefox (tools/ci_roles.py, the root conftest.py). When you add a file with browser tests, register its role in ROLES in tools/ci_roles.py; a browser test without a role makes tests/ci/test_ci_roles.py fail. Python 3.12 stays as before: only tests that need no browser on PRs, everything on merges to main.

The schedules sit in the quietest hours of the repository: 20:17 UTC is 13:17 PDT (UTC−07:00) / 12:17 PST (UTC−08:00) in America/Los_Angeles, 04:17 in Singapore. A failed scheduled run opens (or updates) an issue labeled ci-schedule. Path filters on PRs look at the whole PR; a new push to the same branch cancels the older run. Dependency-update PRs are opened by GitHub Actions and only trigger CI automatically; the other workflows run once someone pushes to that branch. The Linux tests and the Windows worker tests in CI each run for at most 30 minutes, so a stuck run fails instead of running on (since 2026-10-21; before that there was no limit and a stuck run on Windows kept going until GitHub's 6-hour cap).

Pushes that only change docs

The first job of every workflow, “執行範圍” (scope, tools/ci_changes.py), compares this push with the previous one. When only handoff/, docs/ or *.md changed and the previous push already passed in the same workflow, the code is identical: the heavy jobs are skipped and reuse that result, and an annotation says which run. CI still runs the static checks and the tests that need no browser (including the docs and translation checks). If the previous run failed, was cancelled or has not finished, everything runs as usual. The collaboration rule is in section 5 of the shared collaboration workflow.

Manual runs

On GitHub's Actions page pick a workflow, press "Run workflow" and choose the branch and options. Or use gh:

# Full run: all tests on three systems, browser tests twice more (about 30 min)
gh workflow run nightly.yml --ref branch-name
# Windows only, no repeats
gh workflow run nightly.yml --ref branch-name -f systems=windows -f extra=0
# CI: role = same as PRs; full = all tests on Linux
gh workflow run ci.yml --ref branch-name -f scope=full
# Setup scripts: full (default) = all tests plus from scratch; role = same as PRs
gh workflow run setup-scripts.yml --ref branch-name
# Desktop builds
gh workflow run desktop.yml --ref branch-name
# Server packages (Linux x64, arm64)
gh workflow run server-package.yml --ref branch-name

Run a role locally: uv run pytest -m "browser and (role_worker or smoke)" (worker), uv run pytest -m "not browser or ((smoke or role_server or role_recorder) and not firefox)" (same as CI on Linux).

Artifacts and storage quota

The repository has been private since 2026-10-22, so Actions artifacts count toward the account plan's storage quota. Once the quota is used up, artifact uploads fail and a release cannot create its draft (this is what happened to v0.5.0). Desktop builds and server packages therefore keep their artifacts for 3 days on PRs and main and for 1 day on releases, and the release workflow deletes its run's artifacts after creating the draft. Test reports and Portal traces are only for diagnosis, so a failed upload does not fail the job.

To free the quota in one go, run "清理產物" (cleanup-artifacts.yml) by hand. By default it only lists the artifacts, with counts and sizes by name in the summary; after checking, run it again with "只列出、不刪" (list only) unticked. Deleting cannot be undone; the files of published versions live on Releases and are not affected. The quota goes down only after GitHub recalculates the usage.

# List all artifacts only
gh workflow run cleanup-artifacts.yml
# Delete artifacts created more than 3 days ago
gh workflow run cleanup-artifacts.yml -f older-than-days=3 -f dry-run=false

Run duration records

After every CI, desktop build, server package, setup-script, nightly and release run, the "Run duration records" workflow (tools/ci_metrics.py) appends the results to the repository's ci-metrics branch. It does not touch main or trigger other workflows. Switch to the ci-metrics branch on GitHub to see the overview in README.md: each workflow over the last 7 days compared with the 7 before, daily runner time per system, the slowest test files and the latest runs.

data/runs.jsonl
One line per run (and per re-run): trigger, branch, result, duration including queueing, longest queue, runner time per system
data/jobs.jsonl
Queue and run time of each job
data/test-files.jsonl
Time of each test file in the JUnit reports of CI and the nightly run

To add history, run "Run duration records" by hand with since set to a UTC date such as 2026-10-09; runs already recorded are not added twice. Each test run's annotations also include a “pytest 耗時” (pytest timing) note with the slowest files and tests.
