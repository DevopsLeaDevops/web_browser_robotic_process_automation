Deployment & operations

Where the server, the workers (RPA Worker) and the recorders (RPA Recorder) go, how to start them, how to use them day to day, and where to look when something goes wrong. Step-by-step pairing and app installation are in Remote workers; this page links there instead of repeating them. The design is in ADR 0012 and ADR 0014.

Three roles

RoleWhat it doesWhat to installStart
ServerHolds the management portal, the database, scene versions, run reports, sign-in state and secrets; it can also run jobs itself (the local worker).The development environment (one-line script) on macOS, Linux or Windows.uv run rpa serve --worker-port 8081
WorkerPicks up and runs scenarios; headed browser windows open on this computer, and reports, screenshots and traces go back to the server.Windows: the RPA Worker app; other systems use the development environment.The app starts when you sign in; on the command line uv run rpa worker
RecorderWhen you use the portal through it, the browsers for recording, step-by-step debugging and manual login open on this computer; recordings, screenshots and sign-in state go back to the server. It does not run scenarios.macOS (Apple silicon): the RPA Recorder app; other systems use the development environment.Open the app; on the command line uv run rpa recorder

Connections go one way only: workers and recorders connect to the server's external port (8081 by default); the server never connects to them. All of them must reach the sites under test. The three roles can share one computer or each have their own.

Common layouts

One Mac does everything
uv run rpa serve, then open http://127.0.0.1:8080. Recording, debugging, manual login and runs all happen on this Mac; no devices need pairing.
Linux server + Mac recorder + Windows worker
The server lives on an always-on Linux machine (no desktop needed). On the Mac, the RPA Recorder app shows the portal, and the windows for recording, debugging and manual login open on the Mac; headed runs go to RPA Worker on Windows. Linux can still run headless jobs itself; add --no-local-worker to send everything to Windows.
Mac server + Windows worker
Work on port 8080 of the Mac and record there; runs go to Windows, so headed windows no longer take over the Mac.

When the server has no desktop, pages opened from port 8080 (through an SSH tunnel, say) cannot record, step-debug or log in manually: those buttons are grey, and hovering over them suggests the recorder. To record, debug or log in on the Mac, always open the portal through the recorder; pasting a recording and all other management work still work.

Server

Install

Use the one-line script (it installs uv, downloads the code, installs dependencies, downloads Chromium and Firefox and runs the tests). On Linux, if the browsers lack system libraries the script has Playwright install them with sudo (automatic only on Debian and Ubuntu). Run the commands below in the project folder.

Start

cd ~/code/web_browser_robotic_process_automation
uv run rpa serve --worker-port 8081                      # with remote devices
uv run rpa serve --worker-port 8081 --no-local-worker    # everything runs on remote workers
uv run rpa serve --worker-port 8081 --data ~/rpa-data    # keep the data outside the project

The start-up message shows the portal address, the data folder and “External port: http://LAN IP:8081”. Press Ctrl+C to stop.

OptionEffect
--worker-port 8081Opens the external port for workers and recorders. Without it only this computer can be used, and the Devices page cannot create invitations.
--worker-hostThe address the external port listens on, 0.0.0.0 (all interfaces) by default. Give one network card's IP to accept connections only there.
--no-local-workerThis computer runs no jobs; everything goes to remote workers.
--data folderWhere the data lives, data in the project by default (or the RPA_DATA_DIR environment variable). See Management portal › Data folder.
--port, --hostThe port and address of the management pages, 127.0.0.1:8080 by default. Do not change it to 0.0.0.0: the management pages have no login.
--no-testsiteDoes not start the test site on 127.0.0.1:8765.
--testsite-host 0.0.0.0Opens the test site to other computers (by default only 127.0.0.1). See Sharing the server’s test site below.
RPA_LANGEnvironment variable: the language of messages the server creates (zh-Hant, zh-Hans, en).

Two ports

  • 8080, the management pages. No login; it listens on 127.0.0.1 only, so only the server itself can open it.
  • 8081, the external port. Every request needs a token or a one-time invitation: workers use the Worker API, recorders use the Client API and open the management pages with the recorder's token. Unpaired computers only get 401. Open only this port in the firewall, and only to the LAN (or VPN), for example on Ubuntu: sudo ufw allow from 192.168.1.0/24 to any port 8081 proto tcp.
  • It is plain HTTP. Secrets and sign-in state cross the network, so use it only on a trusted LAN or VPN. When the server is in the cloud or on another network, an SSH tunnel can bring the external port to the device: ssh -N -L 8081:127.0.0.1:8081 user@server, then use http://127.0.0.1:8081 as the server when pairing.

Sharing the server’s test site

By default every computer runs its own test site on 127.0.0.1:8765, and records and logins are not shared: a record created on the Mac cannot be found on Windows. To let the recorder and the worker use the single copy on the server:

  1. Start the server with --testsite-host 0.0.0.0. With the Linux installer, set export RPA_TESTSITE_HOST=0.0.0.0 in .rpa-server.env and restart (settings files created earlier lack this line; add it yourself). The startup message prints “Test site: http://LAN-IP:8765/”; the address is a guess.
  2. Open port 8765 in the firewall only to the recorder and worker computers: the test site has no protection, so anyone who can reach it can create records and log in with the demo accounts. For example on RHEL-family systems: sudo firewall-cmd --permanent --add-rich-rule='rule family=ipv4 source address=192.168.1.0/24 port port=8765 protocol=tcp accept', then sudo firewall-cmd --reload.
  3. Use http://server:8765/ as the recording start URL. To run the example scenes against it, set the “Default URL” on the scene pages of BA-001 to BA-005 to http://server:8765, and under “Login and credentials” change the login and check URLs of the two test-site roles to http://server:8765/login and http://server:8765/account.

After that, a record created by BA-001 can be found by BA-002 on any computer, and role sign-in state works on every one of them.

Opening the portal from another computer

  • Through a recorder (recommended). Once the recorder is paired on the Mac, the app window is the management portal, and the browsers for recording, debugging and manual login open on the Mac.
  • SSH tunnel. ssh -N -L 8080:127.0.0.1:8080 user@server, then open http://127.0.0.1:8080. All management works, but browsers open on the server (see the layouts above).

Linux: start at boot (systemd)

Use the account that ran the one-line script (the browsers are downloaded into its home folder). Create /etc/systemd/system/rpa-portal.service, replacing rpa with that account:

[Unit]
Description=RPA management portal
After=network-online.target
Wants=network-online.target

[Service]
User=rpa
WorkingDirectory=/home/rpa/code/web_browser_robotic_process_automation
ExecStart=/home/rpa/.local/bin/uv run rpa serve --worker-port 8081 --data /home/rpa/rpa-data
Restart=on-failure

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now rpa-portal     # start now and at every boot
sudo systemctl status rpa-portal
journalctl -u rpa-portal -f                # start-up messages and logs
sudo systemctl restart rpa-portal          # restart after an update

Updating

  1. Check “Run reports” for jobs still running, and make sure no recording or debugging is in progress on a recorder.
  2. Stop the server (Ctrl+C or sudo systemctl stop rpa-portal); a backup first is a good idea.
  3. git pull, then run ./scripts/setup.sh (it installs only what changed; use uv sync to update just the dependencies).
  4. Start the server. The database is upgraded on start, and existing scenes and history are kept.
  5. Bring workers and recorders to the same version: the apps take the installer or DMG of that version, and command-line machines git pull and restart.

When the server restarts, recordings, debugging and manual logins in progress on recorders end; workers and recorders reconnect by themselves without pairing again.

Backup and moving

All data is in the data folder (its contents are in Management portal › Data folder). Stop the server and copy the whole folder to back it up, for example tar czf rpa-data-$(date +%Y%m%d).tgz -C ~ rpa-data. To move to a new server, install the same version there, put the folder back and start with the same --data. Device tokens are in the folder too, so no pairing is needed while the server address stays the same; if the address changes (a new IP), choose “Invite again” on the Devices page and pair that device with the new invitation. The folder holds secret values and sign-in state, so keep backups readable only by you.

Managing devices

Management portal › Production › Devices
  • Add. “Add device”, choose the kind (RPA Worker or RPA Recorder) and create a one-time invitation (valid for 24 hours) to paste into that computer's app or command line. Steps in Remote workers › Add the device.
  • Status. Online, Busy, Offline or Disabled, plus the operating system, app version and downloaded browsers. A version that differs from the server is flagged.
  • Disable, enable. A disabled device cannot connect at once. The command-line worker and recorder stop; run them again after enabling. Both apps forget the pairing when they are refused, so after enabling pair them again with a new invitation.
  • Invite again. The old token stops working at once; pair that computer again with the new invitation. Use it when a token may have leaked or the device is replaced.
  • Delete. The device can no longer connect; queued runs assigned to it are marked failed, and run history is kept.
  • Default place to run. This computer, a remote worker, or any. When Windows does most of the runs, set it to “Remote worker” so you do not have to choose every time.

Recorders day to day

First-time installation and pairing: macOS: the RPA Recorder app (command line: Recorders).

  1. Open. Double-click “RPA Recorder”; once connected the window is the management portal and the header shows “Via recorder “name””. On the command line, run uv run rpa recorder in the project folder; it opens in the default browser.
  2. Record. In “Production › Recording”, choose a new or existing scene, the start URL, the browser and the role, then “Start recording”. The browser and the Playwright Inspector open on the Mac; close the browser window when you are done and the draft is created. The start URL is the website to automate (for example the Mac’s own test site http://127.0.0.1:8765/ or your business system), not the server’s 8080 or 8081: those are the portal itself and are refused.
  3. Debug step by step. On the scene page choose “Step debugging”; the headed window opens on the Mac, and a screenshot after every step also appears on the page.
  4. Log in manually. In “Scenarios › Logins & secrets” choose the role's “Log in”, log in in the window that opens on the Mac, then press “Finish login” or close the window; the sign-in state is saved on the server.
  5. Run. In the “place to run” of validate and run forms, “Server” is the server itself and “Remote worker” is a worker. Recorders do not run scenarios.
  6. Quit. Close the app window or press ⌘Q; you are asked first if a recording, debugging or manual login is in progress. On the command line press Ctrl+C.
  • The “RPA Recorder › Status and settings” menu shows the connection, the version and work in progress, and has Firefox, the browser download mirror, language, “Open the log folder” and pairing again.
  • Each computer can have one recording at a time; a scene has a single step-by-step debugging session, so starting it on another computer closes the one on the first.

Workers day to day

First-time installation and pairing: Windows: the RPA Worker app (command line: Worker computer: start).

  1. Leave it running. The app starts when you sign in to Windows and waits for jobs in the notification area; closing the window does not stop it. On the command line, run uv run rpa worker in the project folder and keep the terminal open.
  2. Send jobs. When you validate, run or run a sequence in the portal, set “place to run” to “Remote worker” or “Any”, or make Remote worker the default on the Devices page.
  3. See results. Run reports are in “Run reports” on the server, marked “Ran on win-01”.
  4. Pause. “Pause jobs” in the notification-area menu: it finishes the current job and takes no new ones. For a long break, choose “Disable” on the Devices page.
  5. Quit. “Quit” in the notification-area menu; with a job running you are asked first, and the cancelled job is reported. On the command line press Ctrl+C.
  • Headed windows open on the signed-in Windows desktop; the app starts after the user signs in, and signing out or shutting down cancels and reports the running job.
  • The sign-in state a run needs is sent by the server and deleted afterwards; manual login does not happen on workers.

Where the logs are

Server
The terminal it was started from; with systemd, journalctl -u rpa-portal. Each run's log and report are in runs/<run id>/ of the data folder and can also be opened from “Run reports”.
RPA Recorder app
~/Library/Application Support/rpa/recorder/logs/recorder.log; “Status and settings › Open the log folder”.
RPA Worker app
%LOCALAPPDATA%\rpa\worker\logs; “Settings › Open log folder” in the window.
Command-line worker and recorder
The terminal running them.

Troubleshooting

SymptomWhat to do
A device cannot reach the serverCheck that the server has --worker-port, that the IP and port are right, and that the server's firewall allows 8081. How to test is in Remote workers › Troubleshooting. The address in the invitation is a guess and is often wrong on servers with several network cards: enter the server URL and the code separately.
The recording, step-debugging and manual-login buttons are grey, and hovering suggests the recorderThe page was opened from port 8080 of a server without a desktop (through an SSH tunnel, say): open it through the recorder instead. If it happens through the recorder, the recorder computer has no desktop.
Starting a recording says the start URL is the management portal itselfThe start URL is the server’s 8080 or 8081. The recording opens a fresh browser without the recorder’s token, so those ports only answer 401 (recorder_unauthorized). Enter the website to automate instead.
“Start recording” is grey and a recording is shown above itThis computer already has a recording in progress: close that browser window first, or choose “Cancel recording”.
The recorder says the portal no longer accepts its tokenThis device was invited again, disabled or deleted on the Devices page. Create a new recorder invitation there (choose “Enable” first if it was disabled) and paste it under “Status and settings” to pair again.
A version-mismatch warningA different program version still works, but updating to the same version is safer; a different protocol version cannot connect and must be updated. See Updating.
A recording or debugging session ended because contact was lostThe recorder stopped, slept or was disconnected for more than 30 seconds, or the server restarted. Open it again and start over.
Jobs stay queuedSee Remote workers › Troubleshooting.
