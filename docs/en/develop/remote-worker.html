Remote workers

Hand runs to another computer: the management portal, database and files stay on your computer, browser windows appear on the worker computer, and headed runs no longer take over your own machine. The example uses a Windows worker; the macOS and Linux commands are listed alongside. The design is in ADR 0012.

Both computers must be on the same LAN (or VPN), and the worker computer must be able to reach your computer; your computer never needs to reach the worker. Both must reach the sites under test. Secrets and role login states cross the LAN over HTTP, so use this only on a trusted network.

1. Your computer: open the external port

Stop the running rpa serve with Ctrl+C, then start it again with --worker-port:

uv run rpa serve --worker-port 8081

The start-up messages gain a line like External port: http://192.168.1.10:8081 (the address is a guess at your LAN IP). The first time, macOS asks whether Python may accept incoming connections; choose “Allow”. The Windows firewall asks as well.

The portal pages stay on http://127.0.0.1:8080 only; port 8081, the external port, serves just the Worker API and pairing, and every request needs a token or an invitation.

2. Add the device and get an invitation

  1. In the portal, open “Production › Devices” and choose “Add device”.
  2. Use an ID such as win-01 and a name such as “Windows test PC”, then choose “Create invitation”.
  3. The dialog shows a one-line invitation (rpa://pair?…, already copied to the clipboard), the server and code separately, and how to use it on the command line. The invitation is shown only this once, valid for 24 hours, and single use; if you lose it or it expires, choose “Invite again” (the old pairing stops working immediately).

The server address in the invitation is a guess; if the worker cannot connect, use your computer's LAN IP instead (macOS: System Settings › Network; Windows: ipconfig) and give it separately from the code. An invitation can be exchanged for a token, so do not share it.

3. Worker computer: install

Same as a normal install

Use the one-command script from Run locally (in PowerShell):

irm https://raw.githubusercontent.com/DevopsLeaDevops/web_browser_robotic_process_automation/main/scripts/setup.ps1 -OutFile $env:TEMP\rpa-setup.ps1
powershell -ExecutionPolicy Bypass -File $env:TEMP\rpa-setup.ps1

The code goes to %USERPROFILE%\code\web_browser_robotic_process_automation, and Chromium and Firefox are downloaded. Both computers must run the same version: whenever you git pull on your computer, also git pull on the worker and run the script again. The devices page flags a version mismatch.

4. Worker computer: start

The first time, pair with the invitation and start in the project folder (quote the whole line):

# Windows PowerShell
cd $env:USERPROFILE\code\web_browser_robotic_process_automation
uv run rpa worker --invite "rpa://pair?server=…&app=worker&code=…"

# macOS, Linux (also in the project folder)
uv run rpa worker --invite 'rpa://pair?server=…&app=worker&code=…'

# When the server address needs changing: give the code separately
uv run rpa worker --server http://192.168.1.10:8081 --invite (code)

Once it says it is paired and connected to the portal you are done; the devices page shows it online. The token it receives is saved in the working folder as worker-data\pairing.json (readable only by you; do not commit it to git), so from then on just run uv run rpa worker. Press Ctrl+C to stop: a running job is cancelled and its result reported.

The earlier way still works: create a new token through the API (POST /api/workers/{id}/token), put it in the RPA_WORKER_TOKEN environment variable or in --token-file token.txt, and add --server. On Windows you can also paste the invitation into the RPA Worker app instead, with no development setup needed.

Windows: the RPA Worker app

M10.1: no uv, git or Python needed
  1. From the GitHub repository's Releases, download RPA-Worker-Setup-VERSION-windows-x64.exe (the installer) for the same version as the management portal. To test a version that is not released yet, download worker-windows-latest under Artifacts of the “Desktop build” run of a PR or of main instead (it contains the installer and the portable zip).
  2. Run the installer. It is not code-signed: when SmartScreen says “Windows protected your PC”, choose “More info › Run anyway”. Pick a language (Traditional Chinese by default) and choose Next through the pages: it installs for the current user only, without administrator rights, into %LOCALAPPDATA%\Programs\RPA Worker, with a Start menu shortcut (a desktop shortcut is optional), and opens RPA Worker when it finishes. If the WebView2 Runtime is missing, the installer installs it too (this needs an internet connection).
  3. When the window opens, paste the invitation from step 2 into the Invitation box (if you paste only the code, also enter the portal address), tick Firefox if you need it, and choose Pair.
  4. The first time it downloads Chromium (about 600 MB unpacked) and shows the progress in the window. Once the status says Online you are done; the devices page shows it online with its app version.
  • Upgrading: run the new version's installer. If RPA Worker is running, the installer first asks it to quit (a running job is cancelled and reported to the management portal) and then replaces the files; pairing, settings and auto-start are kept. When the window says the program version differs from the management portal, the Download the new version button next to it opens the latest release.
  • Uninstalling: find RPA Worker under Windows Settings › Apps. After you confirm, it first asks whether to also delete the pairing, settings and logs: No (keep them) is the default, so a reinstall does not need pairing again; Yes also removes the token from Credential Manager. It then quits RPA Worker (a running job is cancelled and reported) and removes the program, shortcuts and auto-start. Browsers (%LOCALAPPDATA%\ms-playwright) and the Firefox template cache (%LOCALAPPDATA%\rpa\cache) may be used by other programs too, so they are not deleted. A silent uninstall from the command line (unins000.exe /VERYSILENT) does not ask and keeps the data; add /REMOVEDATA=yes to delete it.
  • Portable version: each release also has RPA-Worker-VERSION-windows-x64.zip. Unzip it into any folder (for example %USERPROFILE%\RPA Worker) and double-click rpa-worker.exe; it works like the installed version. To upgrade, quit it from the notification area first, then unzip the new version over it. The portable and installed versions share the same data folder and pairing, so do not use both at once.
  • Closing the window does not stop it. RPA Worker moves to the notification area and keeps taking jobs (it tells you the first time). The tray icon's menu has Open window, Pause jobs and Quit; the dot on the icon is green (online), yellow (paused) or red (offline or needs attention). Quitting while a job runs asks first, then cancels the job and reports it to the portal.
  • Start when you sign in to Windows: turned on after the first successful pairing, tray only; turn it off under Settings in the window. If you move the folder, open RPA Worker once and auto-start follows the new location.
  • Pause jobs: no new jobs are taken after the current one; the portal shows the computer as offline after about a minute. Resume jobs brings it back online right away.
  • One copy only: double-clicking again brings up the window of the copy that is already running.
  • Settings: language (Traditional Chinese by default), also download Firefox (ticked while running, it downloads the next time RPA Worker starts), an internal mirror for browser downloads (PLAYWRIGHT_DOWNLOAD_HOST), open the log folder, and pair again.
  • Where data lives: %LOCALAPPDATA%\rpa\worker (the paired server and device in pairing.json, settings in settings.json, logs in logs\, and job files). The token is kept in Windows Credential Manager (RPA Worker under Generic Credentials); if Credential Manager is unavailable it falls back to pairing.json (readable only by you), and the window's “Token stored in” says so. A token saved in the file by the step-one preview is moved into Credential Manager the first time you open the app. Browsers live in %LOCALAPPDATA%\ms-playwright. Logs never contain the token or invitation code.
  • Microsoft Edge WebView2 is required: built into Windows 11, and usually installed with Edge updates on Windows 10; the installer installs it when it is missing. If it is still missing (for example with the portable version, or with no internet during setup), RPA Worker explains how to install it and keeps taking jobs from the notification area in the meantime.
  • Signing out or shutting down Windows: a running job is cancelled and reported right away; if there is no time to report, the portal marks the worker lost after about a minute.
  • Troubleshooting: rpa-child.exe --worker in the same folder is the console version (the same as the step-one preview, with every message visible); rpa-worker.exe --no-window --invite … --log FILE runs without a window (for automation; to stop it, put a file named stop.request in the data folder, and the running job is cancelled and reported). Both share the window version's pairing, and only one copy can run at a time.

5. Hand runs to the worker

  • Where to run. Once a remote worker is registered, the validation, run and “Run sequence” forms gain “Where to run”: this computer, remote worker, or any (whichever is free). Headed browser windows appear on the computer that runs the job.
  • Default place to run. Set it on the devices page; it is this computer by default (as before). If you mostly use the worker, set it to “Remote worker” so you do not have to choose each time.
  • Reports. When done, the worker sends the whole run directory (report, screenshots, trace, logs) back; run reports say “on win-01” and otherwise look the same as local runs.
  • Test site. rpa worker also starts its own test site (127.0.0.1:8765) on the worker computer, so the “Test site automation” examples still run; its data is separate from the test site on your computer. Any other URL written as 127.0.0.1 or localhost means the worker itself when run there.
  • Playground sequences run entirely on one worker: whichever worker claims the first node gets all later nodes.
  • Login roles. Manual logins still happen on your computer (they need a person); the login state is sent to the worker for the run and deleted afterwards. A state refreshed by the worker's automatic login is sent back.
  • Workers only. rpa serve --worker-port 8081 --no-local-worker: your computer runs nothing and every job goes to workers.

Start automatically after sign-in (Windows, optional)

With the RPA Worker app you do not need this: tick it under Settings in the app (it is on by default after pairing). The steps below are for the command-line worker.

Headed mode needs a signed-in desktop, so start the worker at sign-in rather than as a system service. Pair once as in step 4, then create start-worker.cmd in the project folder (do not commit it to git):

@echo off
cd /d %USERPROFILE%\code\web_browser_robotic_process_automation
uv run rpa worker

Then press Win+R, enter shell:startup, and put a shortcut to start-worker.cmd in the folder that opens.

Troubleshooting

SituationWhat to do
“Cannot reach the portal” keeps retryingCheck that the portal was started with --worker-port, that the IP and port in the URL are right, and that your computer's firewall allows incoming connections. Open http://IP:8081/worker-api/v1/hello in a browser on the worker computer: 405 or Method Not Allowed means it can connect.
“The portal rejected this worker”The token is wrong or the device was invited again, or it is disabled. Choose “Invite again” on the devices page and run rpa worker --invite with the new invitation, or choose “Enable”.
“Pairing failed”The invitation was already used, has expired (24 hours), was meant for another app, or the device is disabled: follow the message and create a new invitation on the devices page.
A run stays queuedThe run page says which worker it is waiting for. Check on the devices page that it is online; headed jobs only go to workers that can show windows; the browser the scenario uses must be downloaded on the worker computer (run the install script again).
A run failed as “considered lost”The worker did not report for over a minute (shut down, network loss, program closed). The run is not retried automatically because some actions may already have happened on the site; check, then run it again.
The devices page shows a version mismatchgit pull both computers to the same version, run the install script on the worker computer and restart rpa worker.
You want to stop using the worker for a whileChoose “Disable” on the devices page or press Ctrl+C on the worker computer; set the default place to run back to this computer.
