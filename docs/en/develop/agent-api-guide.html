Agent API guide

For agent systems that connect to the platform, and the people who write their integrations: how to use /agent-api/v1 to build a scene from nothing, debug it on a recorder, have workers validate it, publish and run it, combine scenes into composites in a project and run them, and what to do when something goes wrong.

Phase 1 in progress
This guide follows the design confirmed on 2026-10-23 and the phase 1 implementation (2026-10-23, in review); projects and composites were added on 2026-10-24. When testing through the API, see the test plan guide and the test report guide for writing test plans and test reports. The server's GET /agent-api/v1/openapi.json is the source of truth for fields; /agent-api/v1/docs is interactive documentation you can try directly. Neither needs a key.

Basics

Address
http://<server>:8081/agent-api/v1; use the proxy's address when an HTTPS reverse proxy sits in front of the server.
Authentication
Send Authorization: Bearer <API key> with every request. An administrator creates the key under "API clients" in the admin area and it is shown only once; keep it out of logs and scenes.
Format
JSON with camelCase fields; times are ISO 8601 (UTC).
Errors
{"error": {"code": "…", "message": "…", …}}. Programs decide by code; message is for people. Some errors carry details such as issues, problems or latest.
Language
?lang=zh-Hant, zh-Hans or en sets the language of message; without it the server default is used.
Idempotency
Requests that create something (create scenes, projects and composites, save revisions, validate, run, rerun) accept idempotencyKey. After a timeout or dropped connection, resend with the same value and you get the earlier result; nothing is created or run twice. Keys for validate, run and rerun are stored with the run; keys for creating things and saving revisions are kept in server memory for 24 hours and are forgotten when the server restarts, in which case a resend gets scene_exists, project_exists, workflow_code_exists, stale_base or stale_workflow and you should read the latest state. Different clients using the same value do not affect each other.
Polling
Checking run status every 2 to 5 seconds is enough; phase 2 switches to event long polling.

Before you start

Call GET /meta first to see what this key can do. Ask an administrator for anything missing rather than finding permissions by trial and error.

GET /agent-api/v1/meta

{
  "apiVersion": "1",
  "serverVersion": "0.6.0",
  "server": {"id": "srv-linux-01", "name": "Linux server"},
  "client": {"id": "agent-erp", "name": "ERP assistant"},
  "scopes": ["scenes:read", "scenes:write", "debug", "runs:validate", "runs:read",
             "projects:read", "projects:write"],
  "pageContent": true,
  "limits": {"debugSessions": 2, "queuedRuns": 20},
  "domains": ["sales"],
  "projects": ["order-regression"],
  "recorders": ["agent-mac"],
  "target": null,
  "workers": null,
  "expiresAt": null,
  "dslFeatures": ["anyFrame", "dynamicValues", "frame", "page", "popup"]
}
  • No scenes:publish in scopes: stop once validation passes and ask a person to publish in the Portal.
  • pageContent is false: screenshots, page structure and video are unavailable, so write the scene from locator tests and step results only.
  • domains lists the domains you can read and write and projects the projects you can use (null means all); recorders lists the recorders you can debug on; target and workers are the fixed run location and the workers you may choose (null means no restriction).
  • Then read GET /dsl/schema (JSON Schema for scene YAML), GET /recorders (available recorders: online or not, allowAgent, headlessOnly, and whether capabilities includes debugSnapshot), GET /roles (login roles and their state), GET /secrets (names only) and GET /workers (workers you may choose).

What a scene looks like

A scene is one YAML file (scenario.yaml). Steps only operate the page and extract "page facts"; verify decides success independently, and outputs are published only when every check passes. See Scene DSL for the full specification.

schemaVersion: 1
id: order-create
name: Create order
category: Orders
inputs:
  customer: { type: string, minLength: 1 }
  quantity: { type: integer, minimum: 1, maximum: 99, default: 1 }
outputs:
  orderId: { type: string, pattern: '^SO-\d+$', from: '{{ facts.order.orderId }}' }
login: { role: sales }
browser:
  engine: chromium
  baseUrl: https://erp.example.internal
defaults:
  timeout: 10000
steps:
  - id: open
    action: goto
    url: /orders/new
  - id: fill-customer
    action: fill
    target: { label: Customer, exact: true }
    value: '{{ inputs.customer }}'
  - id: fill-quantity
    action: fill
    target: { label: Quantity, exact: true }
    value: '{{ inputs.quantity }}'
  - id: submit
    action: click
    target: { role: button, name: Create, exact: true }
  - id: read-order
    action: extract
    target: { css: '#order-summary' }
    as: order
    fields:
      orderId: { target: { testId: order-id } }
      customer: { target: { testId: order-customer } }
verify:
  - name: Order number received
    value: '{{ facts.order.orderId }}'
    matches: '^SO-\d+$'
  - name: Customer matches input
    value: '{{ facts.order.customer }}'
    equals: '{{ inputs.customer }}'
  • Keep step ids stable: when debugging switches revisions, steps already run are matched by id. Change the content, not the id.
  • Locator order: role with name, label, text, testId, and only then css or xpath; add fallback for fragile ones. Use frame for elements inside an iframe, and popup with page when a click opens a new tab.
  • Make changing values inputs: do not hard-code customers, dates or quantities in steps.
  • Keep passwords out of scenes: declare names under secrets and reference them with {{ secrets.name }}; for systems that need a login use login: { role }, and the platform manages the login state.
  • verify compares page facts with inputs: "no step failed" does not mean success.

From nothing to a production run

1. Create the scene and save the first revision

POST /agent-api/v1/scenes
{"id": "order-create", "name": "Create order", "category": "Orders", "domainId": "sales",
 "idempotencyKey": "order-create"}
→ 201 {"id": "order-create", "latestRevision": 1, …}

POST /agent-api/v1/scenes/order-create/revisions
{"baseRevision": 1, "files": {"scenario.yaml": "schemaVersion: 1\nid: order-create\n…"},
 "note": "Open the page only", "idempotencyKey": "order-create-r2"}
→ 201 {"sceneId": "order-create", "number": 2, "status": "draft",
       "note": "Agent <ERP assistant>: Open the page only", …}

Creating a scene saves revision 1 (a template with only the name) first, so the first save uses baseRevision 1. Without domainId the scene goes to "Unassigned"; if your key is limited to certain domains, give one. Before saving you can call POST /dsl/check {"yaml": "…", "sceneId": "order-create"}; the ok and issues (line, step, field) in the response match the checks made when saving. This revision needs only goto (and login if required); write later steps after looking at the page.

2. Open a debug session on a recorder

POST /agent-api/v1/scenes/order-create/debug
{"recorderId": "agent-mac", "revision": 2,
 "inputs": {"customer": "Test customer", "quantity": 2}}
→ 202 {"id": "a1b2c3d4e5f6", "status": "starting", "deviceId": "agent-mac",
       "headless": true, "clientId": "agent-erp", …}

GET /agent-api/v1/debug/a1b2c3d4e5f6
→ {"status": "ready", "nextIndex": 0, "steps": [{"index": 0, "id": "open", "status": "pending", …}], …}

Wait until status is ready (the first Firefox launch can take a minute or two). Sessions are headless by default; you can omit recorderId when your key allows exactly one recorder. A scene has only one session at a time: if you already have one, it is returned (send "restart": true to start again with another revision or inputs); if someone else (a person or another agent) is debugging it, you get 409 debug_in_use. You can see and use only sessions you opened (GET /debug lists them), and an idle session closes after 15 minutes.

3. Look at the page, then write the next steps

POST /agent-api/v1/debug/a1b2c3d4e5f6/run-to/0
POST /agent-api/v1/debug/a1b2c3d4e5f6/snapshot
→ {"url": "https://erp.example.internal/orders/new", "title": "New order",
   "tabs": [{"page": null, "url": "…", "title": "New order", "active": true}],
   "frames": [],
   "fields": [{"tag": "input", "type": "text", "role": "textbox", "label": "Customer",
               "name": "customer", "required": true, "disabled": false, "visible": true, "value": ""},
              {"tag": "input", "type": "number", "role": "spinbutton", "label": "Quantity", …}],
   "aria": "- heading \"New order\" [level=1]\n- textbox \"Customer\"\n- spinbutton \"Quantity\"\n- button \"Create\"",
   "truncated": false}

POST /agent-api/v1/debug/a1b2c3d4e5f6/locate
{"locator": {"role": "button", "name": "Create", "exact": true}}
→ {"located": {"locator": "…", "ok": true, "count": 1,
               "matches": [{"tag": "button", "text": "Create"}], "error": null}, …}

Use a locator from locate only when it finds exactly one element; with zero or several, change the locator. In tabs, page is the name of a tab opened by a step with popup (the first tab is null); frames lists iframes, and parent points to the enclosing frame's position in that list. fields lists the form fields on the current page; values of password fields and fields filled with a secret are always ***. On large pages aria is cut off and marked truncated; send {"within": {"css": "#main"}} to look at part of the page (within is a locator, so use frame for content inside an iframe). Use screenshot when you need to see the screen; the screenshotUrl in the response downloads the image. Page structure and screenshots both need page content turned on, and the recorder needs the latest app.

4. Save a new revision, switch to it, and continue

POST /agent-api/v1/scenes/order-create/revisions
{"baseRevision": 2, "files": {"scenario.yaml": "…adds fill-customer, fill-quantity, submit…"}}
→ 201 {"number": 3, …}

POST /agent-api/v1/debug/a1b2c3d4e5f6/reload   {"revision": 3}
POST /agent-api/v1/debug/a1b2c3d4e5f6/run-to/3
→ {"steps": [… {"index": 3, "id": "submit", "status": "failed", "error": "…"}], …}

The browser and the steps already run are kept; run-to runs only steps that have not run and stops on failure. Fix, save another revision, reload and run-to until every step is passed. Use reset to start over from the beginning.

Click, fill, select, check and press are side-effect steps: they really happen in the target system. Running a side-effect step again with POST /debug/{sid}/steps/{index} after it has run once returns 409 confirm_required and requires {"force": true}; do this only when you are sure redoing it will not create duplicate data. run-to returns 409 already_executed when its target comes before the next step that has not run.

5. Complete inputs, outputs and independent checks

Use GET/PUT /scenes/{id}/sections/steps, verify, inputs or outputs to read or write one section ({"baseRevision": n, "text": "verify:\n - …"}), or PUT /scenes/{id}/contract to edit inputs and outputs as tables; each call saves a new revision. If you already have a Playwright (Python) script, POST /scenes/{id}/import {"source": "…", "mode": "replace"} converts it to DSL and lists what it could not convert in warnings. When finished, DELETE /debug/{sid} ends the session and frees the recorder.

6. Have a worker validate it

POST /agent-api/v1/scenes/order-create/revisions/6/validate
{"inputs": {"customer": "Test customer", "quantity": 2}, "idempotencyKey": "order-create-v6-1"}
→ 202 {"id": "order-create-20261023-…", "purpose": "validation", "status": "queued", …}

GET /agent-api/v1/runs/order-create-20261023-…
→ {"status": "running", "stage": "automation", …}
→ {"status": "failed", "error": "…", "finished": true, …}
GET /agent-api/v1/runs/order-create-20261023-…/steps

On failure, read error, result (the full result after the run: stages, steps, checks), the first failed step in /steps and, when page content is on, the screenshots listed in files and reportUrl; then go back to debugging. Validation can use any revision; production runs use only the published revision. You can choose a worker with workerId (local is the server itself) or set target; if your key has a fixed run location, you cannot choose another. In phase 1, /steps is complete only after the run ends; while it runs, watch status and stage.

7. Publish and run in production

POST /agent-api/v1/scenes/order-create/revisions/6/publish      (needs scenes:publish)

POST /agent-api/v1/scenes/order-create/runs
{"inputs": {"customer": "Alex Chen", "quantity": 3}, "idempotencyKey": "job-8812"}
→ 202 {"id": "…", "purpose": "execution", "status": "queued", …}
GET /agent-api/v1/runs/…
→ {"status": "passed", "output": {"orderId": "SO-10231"}, …}

output is present only when status is passed. Without publish permission, tell the user which revision of which scene passed validation and ask a person to publish it in the Portal. GET /runs?scene=…&status=…&purpose=…&mine=true lists the runs you can see (scenes in your domains; mine limits it to runs you started); POST /runs/{id}/cancel cancels only runs you started.

Projects and composites

Projects in the project space hold composites (composite scenes); a composite chains published scene revisions into a flow (a DAG), where outputs of earlier nodes can be bound to inputs of later ones. When testing through the API, one composite is one TestCase; see the test plan guide.

EndpointPurposeScope
GET /projects, GET /projects/{id}Projects you can use; a project with a summary of its compositesprojects:read
POST /projects, PATCH /projects/{id}Create a project (not with a key limited to some projects); change name and descriptionprojects:write
GET /composites/libraryScene revisions you can put in a composite, with inputs, outputs and login roleprojects:read
POST /composites/checkCheck a definition without saving; returns problems (node, input)projects:read
GET /composites?project=, GET /composites/{code}Composite summaries; full definition, problems, revisions, validation records, dependencies and recent runsprojects:read
POST /projects/{id}/compositesCreate a composite in a project (with a definition, that is revision 1)projects:write
PUT /composites/{code}, PATCH /composites/{code}Save a new revision (with baseRevision); move to another projectprojects:write
POST /composites/{code}/revisions/{n}/validateHave a worker validate this revisionruns:validate
POST /composites/{code}/revisions/{n}/publishPublish a validated revision with complete dependenciesprojects:publish (off by default)
POST /composites/{code}/runsFormally run the published revisionruns:execute
POST /projects/{id}/runsQueue the composites of a project (or those listed in composites) one by one; those that cannot start are in skippedBy purpose: runs:validate or runs:execute
GET /composite-runs, GET /composite-runs/{id}Composite runs: status, progress (progress), each node's status and runruns:read
POST /composite-runs/{id}/cancel, /rerunCancel your own; run again from the start or from the stopping node ("resume": true)By the run's purpose
  • What you can see: a composite must be in an allowed project and its domain must be allowed; composites in no project are not available to agents. Anything you cannot see returns 404. Scenes used by the nodes must be in allowed domains, otherwise 403 composite_scenes_forbidden.
  • No inputs at run time: inputs are bound in the definition (fixed values, dynamic values, upstream outputs); the same flow with other data is another composite.
  • Node details: each node's run is an ordinary run; read its steps, checks and artifacts with /runs/{id} and /runs/{id}/steps. A node cannot be rerun on its own (409 rerun_workflow); rerun the composite run.
  • Portal paths: responses carry portalPath (e.g. /playground/runs/…) for people to see the same record in the Portal; include it in test reports.
  • Limits: composite nodes count towards the queued-and-running limit.

A run's own result is not an HTTP error: failed, timed_out, cancelled and needs_login all appear in status from GET /runs/{id}.

When a person is needed

  • Login needed: the run stops at needs_login, or GET /roles shows a role needs to log in again. Ask the user to log in manually on a recorder, then call POST /runs/{id}/rerun.
  • No publish permission: give the user the scene or composite code and the revision number that passed validation, and ask a person to publish it in the Portal.
  • Missing secret: needs in GET /scenes/{id} lists secrets not set yet. A person fills in the values in the Portal; agents can neither write nor read them.
  • Recorder offline or too old: ask a person to open or update the RPA Recorder app.

Rules

  • Send the baseRevision you last read every time you save a revision (scenes and composites), so you never overwrite a person's changes.
  • DELETE a debug session when you are done with it; do not hold the recorder.
  • Do not repeat side-effect steps against production data; use roles with test accounts when you can.
  • Screenshots, page structure and outputs may contain business data. Use them only for the current task; do not store or forward them elsewhere.
  • Every write is in the audit log, and revision notes show your client's name; say clearly in note what each revision changed.
