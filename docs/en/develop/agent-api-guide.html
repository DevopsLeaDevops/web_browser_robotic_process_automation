Agent API guide

For agent systems that connect to the platform, and the people who write their integrations: how to use /agent-api/v1 to build a scene from nothing, debug it on a recorder, have workers validate it, publish and run it, and what to do when something goes wrong.

Design confirmed, not built
This guide follows the design confirmed on 2026-10-23; phase 1 is not built yet. Once implemented, the server's GET /agent-api/v1/openapi.json is the source of truth for fields, and this page will be updated to match.

Basics

Address
http://<server>:8081/agent-api/v1; use the proxy's address when an HTTPS reverse proxy sits in front of the server.
Authentication
Send Authorization: Bearer <API key> with every request. An administrator creates the key under "API clients" in the admin area and it is shown only once; keep it out of logs and scenes.
Format
JSON with camelCase fields; times are ISO 8601 (UTC).
Errors
{"error": {"code": "…", "message": "…", …}}. Programs decide by code; message is for people. Some errors carry details such as issues, problems or latest.
Language
?lang=zh-Hant, zh-Hans or en sets the language of message; without it the server default is used.
Idempotency
POSTs that create something (create scene, save revision, validate, run, rerun) accept idempotencyKey. After a timeout or dropped connection, resend with the same value and nothing is created or run twice.
Polling
Checking run status every 2 to 5 seconds is enough; phase 2 switches to event long polling.

Before you start

Call GET /meta first to see what this key can do. Ask an administrator for anything missing rather than finding permissions by trial and error.

GET /agent-api/v1/meta

{
  "apiVersion": "1",
  "serverVersion": "0.6.0",
  "client": {"id": "agent-erp", "name": "ERP assistant"},
  "scopes": ["scenes:read", "scenes:write", "debug", "runs:validate", "runs:read"],
  "pageContent": true,
  "limits": {"debugSessions": 2, "queuedRuns": 20},
  "dslFeatures": ["frame", "popup"]
}
  • No scenes:publish in scopes: stop once validation passes and ask a person to publish in the Portal.
  • pageContent is false: screenshots, page structure and video are unavailable, so write the scene from locator tests and step results only.
  • Then read GET /dsl/schema (JSON Schema for scene YAML), GET /recorders (available recorders), GET /roles (login roles and their state) and GET /secrets (names only).

What a scene looks like

A scene is one YAML file (scenario.yaml). Steps only operate the page and extract "page facts"; verify decides success independently, and outputs are published only when every check passes. See Scene DSL for the full specification.

schemaVersion: 1
id: order-create
name: Create order
category: Orders
inputs:
  customer: { type: string, minLength: 1 }
  quantity: { type: integer, minimum: 1, maximum: 99, default: 1 }
outputs:
  orderId: { type: string, pattern: '^SO-\d+$', from: '{{ facts.order.orderId }}' }
login: { role: sales }
browser:
  engine: chromium
  baseUrl: https://erp.example.internal
defaults:
  timeout: 10000
steps:
  - id: open
    action: goto
    url: /orders/new
  - id: fill-customer
    action: fill
    target: { label: Customer, exact: true }
    value: '{{ inputs.customer }}'
  - id: fill-quantity
    action: fill
    target: { label: Quantity, exact: true }
    value: '{{ inputs.quantity }}'
  - id: submit
    action: click
    target: { role: button, name: Create, exact: true }
  - id: read-order
    action: extract
    target: { css: '#order-summary' }
    as: order
    fields:
      orderId: { target: { testId: order-id } }
      customer: { target: { testId: order-customer } }
verify:
  - name: Order number received
    value: '{{ facts.order.orderId }}'
    matches: '^SO-\d+$'
  - name: Customer matches input
    value: '{{ facts.order.customer }}'
    equals: '{{ inputs.customer }}'
  • Keep step ids stable: when debugging switches revisions, steps already run are matched by id. Change the content, not the id.
  • Locator order: role with name, label, text, testId, and only then css or xpath; add fallback for fragile ones. Use frame for elements inside an iframe, and popup with page when a click opens a new tab.
  • Make changing values inputs: do not hard-code customers, dates or quantities in steps.
  • Keep passwords out of scenes: declare names under secrets and reference them with {{ secrets.name }}; for systems that need a login use login: { role }, and the platform manages the login state.
  • verify compares page facts with inputs: "no step failed" does not mean success.

From nothing to a production run

1. Create the scene and save the first revision

POST /agent-api/v1/scenes
{"id": "order-create", "name": "Create order", "category": "Orders", "domainId": "sales"}

POST /agent-api/v1/scenes/order-create/revisions
{"baseRevision": 0, "files": {"scenario.yaml": "schemaVersion: 1\nid: order-create\n…"},
 "note": "First revision: open the page only", "idempotencyKey": "order-create-r1"}
→ 201 {"sceneId": "order-create", "number": 1, "status": "draft", …}

Before saving you can call POST /dsl/check {"yaml": "…"}; the issues in the response carry line, step and field. The first revision needs only goto (and login if required); write later steps after looking at the page.

2. Open a debug session on a recorder

POST /agent-api/v1/scenes/order-create/debug
{"recorderId": "agent-mac", "revision": 1, "headless": true,
 "inputs": {"customer": "Test customer", "quantity": 2}}
→ 202 {"id": "a1b2c3d4e5f6", "status": "starting", "deviceId": "agent-mac", …}

GET /agent-api/v1/debug/a1b2c3d4e5f6
→ {"status": "ready", "nextIndex": 0, "steps": [{"index": 0, "id": "open", "status": "pending", …}], …}

Wait until status is ready (the first Firefox launch can take a minute or two). A scene has only one session at a time, and an idle session closes after 15 minutes.

3. Look at the page, then write the next steps

POST /agent-api/v1/debug/a1b2c3d4e5f6/run-to/0
POST /agent-api/v1/debug/a1b2c3d4e5f6/snapshot
→ {"url": "https://erp.example.internal/orders/new", "title": "New order",
   "tabs": [{"pageId": "main", "url": "…", "active": true}],
   "frames": [],
   "fields": [{"role": "textbox", "label": "Customer", "required": true},
              {"role": "spinbutton", "label": "Quantity"}],
   "aria": "- heading \"New order\" [level=1]\n- textbox \"Customer\"\n- spinbutton \"Quantity\"\n- button \"Create\"",
   "truncated": false}

POST /agent-api/v1/debug/a1b2c3d4e5f6/locate
{"locator": {"role": "button", "name": "Create", "exact": true}}
→ {"located": {"count": 1, "texts": ["Create"]}, …}

Use a locator from locate only when it finds exactly one element; with zero or several, change the locator or add within. On large pages, snapshot can take {"within": {"css": "#main"}} to look at part of the page. Use screenshot when you need to see the screen; the screenshotUrl in the response downloads the image.

4. Save a new revision, switch to it, and continue

POST /agent-api/v1/scenes/order-create/revisions
{"baseRevision": 1, "files": {"scenario.yaml": "…adds fill-customer, fill-quantity, submit…"}}
→ 201 {"number": 2, …}

POST /agent-api/v1/debug/a1b2c3d4e5f6/reload   {"revision": 2}
POST /agent-api/v1/debug/a1b2c3d4e5f6/run-to/3
→ {"steps": [… {"index": 3, "id": "submit", "status": "failed", "error": "…"}], …}

The browser and the steps already run are kept; run-to runs only steps that have not run and stops on failure. Fix, save another revision, reload and run-to until every step is passed. Use reset to start over from the beginning.

Click, fill, select, check and press are side-effect steps: they really happen in the target system. Running a side-effect step again after it has run once requires {"force": true}; do this only when you are sure redoing it will not create duplicate data.

5. Complete inputs, outputs and independent checks

Use PUT /scenes/{id}/sections/verify, /inputs or /outputs to change one section, or PUT /scenes/{id}/contract to edit inputs and outputs as tables; each call saves a new revision. When finished, DELETE /debug/{sid} ends the session and frees the recorder.

6. Have a worker validate it

POST /agent-api/v1/scenes/order-create/revisions/5/validate
{"inputs": {"customer": "Test customer", "quantity": 2}, "idempotencyKey": "order-create-v5-1"}
→ 202 {"id": "order-create-20261023-…", "purpose": "validation", "status": "queued", …}

GET /agent-api/v1/runs/order-create-20261023-…
→ {"status": "running", "stage": "automation", …}
→ {"status": "failed", "error": "…", "finished": true, …}
GET /agent-api/v1/runs/order-create-20261023-…/steps

On failure, read error, the first failed step in /steps and, when allowed, /files/screenshot.png; then go back to debugging. Validation can use any revision; production runs use only the published revision.

7. Publish and run in production

POST /agent-api/v1/scenes/order-create/revisions/5/publish      (needs scenes:publish)

POST /agent-api/v1/scenes/order-create/runs
{"inputs": {"customer": "Alex Chen", "quantity": 3}, "idempotencyKey": "job-8812"}
→ 202 {"id": "…", "purpose": "execution", "status": "queued", …}
GET /agent-api/v1/runs/…
→ {"status": "passed", "output": {"orderId": "SO-10231"}, …}

output is present only when status is passed. Without publish permission, tell the user which revision of which scene passed validation and ask a person to publish it in the Portal.

Handling errors

StatuscodeMeaningWhat the agent should do
401unauthorizedKey missing, wrong, disabled or expiredStop and ask an administrator; do not retry
403scope_missingThis key lacks the required scopeAsk for authorization or have a person do this step
403content_disabled"Return page content" is offUse locate and step results instead, or ask an administrator to turn it on
403domain_forbidden, recorder_forbiddenThis domain or recorder is not allowedUse an allowed one, or ask an administrator to add it
409stale_basebaseRevision is not the latest; someone changed the sceneRead the latest revision, apply your change to it and save again
409debug_busySomeone is debugging this sceneTry again later; do not take it over
409already_executedA side-effect step has already runSend force only if redoing is safe; otherwise reset
409recorder_offlineThe recorder is offlineUse another one, or ask a person to open the Recorder app
409recorder_outdatedThe Recorder app is too old (for example, it cannot read page structure)Ask a person to update RPA Recorder
409not_validatedThis revision has no passed validationValidate first
409not_publishedThe scene has no published revision and cannot run in productionPublish, or ask a person to publish
422display_unavailableThat machine has no display, so headed mode is unavailableUse "headless": true
422revision_invalidYAML validation failed; issues lists whereFix according to issues and save again
422inputs_invalidInputs break their type or limits; problems says whichFix the inputs
429limit_reachedOver the limit for concurrent debug sessions or queued runsWait for current ones to finish, or end sessions you no longer need

A run's own result is not an HTTP error: failed, timed_out, cancelled and needs_login all appear in status from GET /runs/{id}.

When a person is needed

  • Login needed: the run stops at needs_login, or GET /roles shows a role needs to log in again. Ask the user to log in manually on a recorder, then call POST /runs/{id}/rerun.
  • No publish permission: give the user the scene id and the revision number that passed validation, and ask a person to publish it in the Portal.
  • Missing secret: needs in GET /scenes/{id} lists secrets not set yet. A person fills in the values in the Portal; agents can neither write nor read them.
  • Recorder offline or too old: ask a person to open or update the RPA Recorder app.

Rules

  • Send the baseRevision you last read every time you save a revision, so you never overwrite a person's changes.
  • DELETE a debug session when you are done with it; do not hold the recorder.
  • Do not repeat side-effect steps against production data; use roles with test accounts when you can.
  • Screenshots, page structure and outputs may contain business data. Use them only for the current task; do not store or forward them elsewhere.
  • Every write is in the audit log, and revision notes show your client's name; say clearly in note what each revision changed.
