Test report guide

For third-party agents connected to the platform: how to run the composites of a project according to a signed-off test plan, track progress, handle failures and reruns, and finally write a test report for people to accept (a single HTML file, plus JSON for the agent's own use) that traces back to every step.

Phase 1 in progress
The test report is the agent's deliverable, for people to accept. The platform does not read, upload or store it. The platform keeps the record of each run (status, steps, checks, screenshots); the report points to them with run IDs and Portal paths. How to write the test plan and TestCases is in the test plan guide; API conventions are in the Agent API guide. Written on 2026-10-24 at the user's request (in review).

Before running

  • The plan is signed off: the test plan's status is "signed off"; if not, ask people first and do not start formal runs.
  • Scopes: scopes in GET /meta include projects:read, runs:read and the runs:validate or runs:execute you need (publishing composites yourself needs projects:publish); note limits.queuedRuns.
  • Composites match the plan: in GET /projects/{id} every TestCase's composite has 0 problems; the revision to validate is the one in the plan, and for formal runs publishedRevision is the one in the plan. If not, stop and ask people whether to update the plan.
  • Roles are logged in: the roles used by the plan are logged_in in GET /roles; for needs_login or none, ask people to log in on a recorder.
  • Workers are online: GET /workers shows at least one online, or the one the plan names.
  • Record the environment: start time, server ID and version (/meta), for the report.

  • Run only the plan's TestCases: list their codes in composites; without it, every composite in the project that is not archived runs.
  • What did not start is in skipped: act on error.code: workflow_unpublished validate and publish first; limit_reached wait for earlier runs to finish; composite_scenes_forbidden, target_forbidden ask people to adjust the permissions.
  • Resend the same request: after a timeout, a dropped connection or fixing skipped, send it again with the same idempotency key: runs that started are returned as they are, only the rest start now; nothing runs twice.
  • Limits: each running composite takes one slot of queuedRuns for its current node. With many TestCases, send them in batches or let the extra ones land in skipped and resend later.
  • Record every run ID: it is where tracing in the report starts.

GET /agent-api/v1/composite-runs?project=order-regression&mine=true&status=running
  • How often: every 3–5 seconds for running ones; with several at once use the list in one call instead of polling each one quickly. When nothing changes for a long time, back off to 30 seconds.
  • Done: only finished true means done; status is then passed, failed, timed_out, cancelled or needs_login. failedNode is the node it stopped at; resumable means it can continue from there.
  • Node statuses: pending (not its turn yet), queued, running, passed, reused (a continued run kept the earlier passing result), failed, timed_out, cancelled, needs_login, skipped (skipped because the run stopped earlier). A node's error says why it did not start, e.g. a bound value broke an input rule.
  • Report progress to people: after each TestCase or every 5 minutes, e.g. "12 TestCases: 5 done (4 passed, 1 failed), 1 running, 6 queued".
  • Stuck: when a node stays queued, check GET /workers; if workers are offline or busy, tell people rather than cancelling on your own. To cancel, POST /composite-runs/{id}/cancel works only on runs you started; the current node stops and later ones do not run.

Failures, blocks and reruns

StatusMeaningWhat the agent does
needs_loginA node's login role must log in againTell people the role and ask them to log in on a recorder; then POST /composite-runs/{id}/rerun {"resume": true}, keeping the nodes that passed
failedA node's step or check did not passCollect evidence first (next section) and find the cause; do not just rerun to get a pass
timed_outA node timed outCollect evidence; when the environment was slow, rerun once and record it
cancelledCancelledRecord who cancelled it and why
  • Cause is the environment (worker offline, network, temporary error in the target system): rerun once; record both results and the cause.
  • Cause is a product defect: do not rerun until it passes; record it as failed and write up the defect.
  • Cause is a mistake in a scene or composite (locator, check, data): fix it, save a new revision and validate again; record it as a "test script issue". The TestCase result is the run after the fix; note the revision change under deviations from the plan.
  • Continue or start over: use "resume": true only while the earlier nodes' results still hold (e.g. after a manual login); when the fixed node is before the stopping node, start over with "resume": false.
  • Reruns take a new idempotency key, e.g. TR-ORDER-2026-10-R1/tc-order-003/2. A run still going returns 409 workflow_run_active; a run with no node to continue from returns 409 workflow_not_resumable, so start over instead.

  • Failed and blocked TestCases: save the whole chain as evidence under evidence/<TestCase ID>/<run ID>/: the composite run, each node's run, steps and result.json, plus screenshots when allowed.
  • Passed TestCases: record the run ID, duration and key outputs; people use the Portal path for details.
  • Portal paths: portalPath is only a path. People open it in the Portal on the server itself (http://127.0.0.1:8080) or inside the recorder app; do not guess the server's address.
  • Sensitive data: the platform always shows secret values as ***; do not try to recover them. Screenshots and outputs may hold business data: keep them only in the report folder handed to people and do not pass them elsewhere.
  • Time: API times are UTC; write UTC in the report and add local time when you know the reviewer's time zone. The server may clean up old run artifacts under its retention settings, so download evidence soon after the runs.

A TestCase may run several times in a round: its result is the last valid run, and every attempt is listed in the report. What did not run never counts as passed.

Test report format

One folder per round, named after the report ID, e.g. TR-ORDER-2026-10-R1/:

TR-ORDER-2026-10-R1/
  test-report.html      the test report itself, opened in a browser for acceptance
  test-report.json      the same content as structured data, for the agent
  test-report.xmind     (optional) the test plan's XMind with result markers
  evidence/             full evidence for failed and blocked TestCases, linked from the HTML by relative paths
    TC-ORDER-004/tc-order-004-20261024-081530-1a2b3c/
      composite-run.json
      reject/run.json  reject/steps.json  reject/result.json  reject/screenshot.png

2. Scope runTestCases in the plan, how many ran, which did not and why
3. StatisticsBy result, priority and module; total duration
4. TestCase detailsID, title, priority, result, composite and revision, run ID, attempts, duration, Portal path

Writing the HTML

  • One file that opens offline: styles go in <style>; load no external fonts, scripts or CDNs (the reviewer's computer may be on an internal network); it must read in full without JavaScript, with long traces folded in <details>.
  • Hand over the whole folder: screenshots and evidence are linked by relative paths into evidence/, e.g. <img src="evidence/…/screenshot.png">; people unzip it and open test-report.html.
  • Cross-links: one anchor per TestCase (id="TC-ORDER-004"); the summary, details, defects and trace link to each other with #.
  • Escaping: HTML-escape every text that comes from the API (error messages, actual values, words on the page) before putting it in the page; never embed a run's report.html or page source wholesale, link to the evidence file instead.
  • Results in words: write passed, failed and blocked out; never rely on colour alone, and keep it readable when printed.
  • Portal: write portalPath as text; make it a link only when people have given you the Portal's address.

Results in XMind

Copy the test plan's XMind (see the test plan guide) and on each TestCase topic:

  • Add a result marker: symbol-right, symbol-wrong, symbol-pause, symbol-minus (see the table above); none for not run.
  • Add a label such as "Result: passed": markers are a visual aid, and tools that do not know a marker rely on the label.
  • Append the run ID and Portal path to the notes; add defect IDs to failed ones.
  • For a failed step, you can add symbol-wrong to its expected-result topic to show where it stopped.

Before handing it over

  • Every TestCase in the plan has a result in the report; the statistics match the details.
  • Open test-report.html in a browser on a computer without network access: the layout is intact and in-page links and screenshots work.
  • Every failure has a defect or a cause; every block says what people need to do.
  • Every run ID can be found with GET /composite-runs/{id} and has the status the report says.
  • The evidence contains no API keys, passwords or secret values; personal data are handled as the plan says.
  • The conclusion matches the exit criteria without overstating: runs that did not happen or were skipped never count as passed.
