測試報告指南

寫給接入平台的第三方 Agent：依簽核的測試方案執行專案裡的組合場景、跟蹤進度、處理失敗與重跑，最後寫出交給人驗收的測試報告（單一 HTML 檔，另附給 Agent 自己用的 JSON），並能從報告回溯到每一步的細節。

第一期已發布（v0.6.0）
測試報告是 Agent 的交付物，給人驗收；平台不讀取、不上傳、不保存它。平台保存的是每次執行的紀錄（狀態、步驟、斷言、截圖），報告用執行代號與 Portal 路徑指向它們。測試方案與 TestCase 的寫法見測試方案指南，API 的基本約定見 Agent 使用指南。本指南 2026-10-24 依使用者的要求撰寫，隨 v0.6.0 發布。

執行前檢查

  • 方案已簽核：測試方案的狀態是「已簽核」；還沒簽核時先問人，不要直接正式執行。
  • 權限：GET /meta 的 scopes 有 projects:read、runs:read，以及要用的 runs:validate 或 runs:execute（自己發布組合場景要 projects:publish）；記下 limits.queuedRuns。
  • 組合場景與方案一致：GET /projects/{id} 列出的每個 TestCase 的組合場景 problems 是 0；要驗證的版本是方案寫的版本，正式執行時 publishedRevision 是方案寫的版本。不一致時停下，請人決定要不要更新方案。
  • 角色已登入：GET /roles 裡方案用到的角色是 logged_in；needs_login 或 none 時請人在錄製端登入。
  • Worker 在線：GET /workers 至少一台在線；方案指定了 Worker 時是那一台。
  • 記下環境：開始時間、伺服器代號與版本（/meta），寫進報告。

執行

驗證、發布、正式執行
目的呼叫跑哪個版本權限
驗證（新寫或剛改的 TestCase）POST /composites/{code}/revisions/{n}/validate；整批用 POST /projects/{id}/runs，"purpose": "validation"指定的版本；整批時是每個組合場景的最新版本runs:validate
發布POST /composites/{code}/revisions/{n}/publish驗證通過、依賴完整的版本projects:publish；沒有時請人在 Portal 發布
正式執行（回歸）POST /composites/{code}/runs；整批用 POST /projects/{id}/runs，"purpose": "execution"發布的版本runs:execute

一份報告對應一輪執行。一輪用一個編號當冪等鍵，例如 TR-ORDER-2026-10-R1：

  • 只跑方案裡的 TestCase：用 composites 列出代號；不給時是專案裡全部沒有封存的組合場景。
  • 沒排進去的在 skipped：依 error.code 處理：workflow_unpublished 先驗證、發布；limit_reached 等前面的結束；composite_scenes_forbidden、target_forbidden 請人調整權限。
  • 重送同一個請求：逾時、斷線或處理完 skipped 之後，用同一個冪等鍵再送一次：已經開始的回傳原本那次執行，沒排進去的這次才排入，不會重複執行。
  • 限額：每個執行中的組合場景占用正在跑的那個節點的名額（queuedRuns）。TestCase 多時分批送，或讓超過的留在 skipped 稍後再送。
  • 記下每個執行代號：它是報告回溯的起點。

GET /agent-api/v1/composite-runs?project=order-regression&mine=true&status=running
  • 頻率：執行中的每 3～5 秒查一次；同時有好幾個時用列表一次查，不要每個都高頻查。長時間沒有變化時逐步拉長到 30 秒。
  • 結束：finished 是 true 才算結束；status 是 passed、failed、timed_out、cancelled 或 needs_login。failedNode 是停下的節點；resumable 表示可以從那裡繼續。
  • 節點的狀態：pending（還沒輪到）、queued、running、passed、reused（接著執行時沿用上一次通過的結果）、failed、timed_out、cancelled、needs_login、skipped（前面停下而略過）。節點的 error 是沒有開始的原因，例如綁定的值不符合入參規則。
  • 向人回報進度：每完成一個 TestCase 或每 5 分鐘一次，例如「12 個 TestCase：完成 5（通過 4、失敗 1），執行中 1，排隊 6」。
  • 卡住：節點一直是 queued 時看 GET /workers：Worker 不在線或忙碌時告訴人，不要自己取消。要取消用 POST /composite-runs/{id}/cancel，只能取消自己觸發的；目前的節點停止，後面的不執行。

失敗、阻塞與重跑

狀態意思Agent 該做什麼
needs_login某個節點的登入角色要重新登入告訴人角色名稱，請人在錄製端登入；完成後 POST /composite-runs/{id}/rerun {"resume": true}，前面通過的節點沿用
failed節點的步驟或斷言沒有通過先取證（下一節）、判斷原因，不要為了通過而直接重跑
timed_out節點逾時取證；原因是環境慢時可以重跑一次並記錄
cancelled被取消記錄誰取消、為什麼
  • 原因是環境（Worker 離線、網路、目標系統暫時錯誤）：可以重跑一次；兩次的結果與原因都寫進報告。
  • 原因是產品缺陷：不要重跑到通過為止；記為失敗並寫缺陷。
  • 原因是場景或組合場景寫錯（定位器、斷言、資料）：修正後存新版本、重新驗證；報告記為「測試腳本問題」，TestCase 的結果以修正後的執行為準，並在「偏離方案」說明版本改了。
  • 從頭或接著："resume": true 只在前面節點的結果仍然有效時用（例如人工登入之後）；修正的節點在停下的節點之前時，用 "resume": false 從頭再跑。
  • 重跑帶新的冪等鍵，例如 TR-ORDER-2026-10-R1/tc-order-003/2。還在執行時回 409 workflow_run_active；沒有可以接著的節點時回 409 workflow_not_resumable，改用從頭執行。

  • 失敗與阻塞的 TestCase：整條鏈都存成證據檔，放在 evidence/<TestCase 編號>/<執行代號>/：組合場景執行、每個節點的運行、步驟、result.json，有權限時加截圖。
  • 通過的 TestCase：記執行代號、耗時、關鍵的出參即可；人要看細節時用 Portal 路徑。
  • Portal 路徑：portalPath 只是路徑。人在伺服器本機的 Portal（http://127.0.0.1:8080）或錄製端 App 裡打開；不要猜伺服器的網址。
  • 敏感資料：Secret 的值平台一律顯示為 ***，不要設法還原。截圖與出參可能含業務資料，只放在交給人的報告資料夾，不另外轉傳。
  • 時間：API 的時間是 UTC；報告用 UTC，知道驗收者的時區時另外標當地時間。伺服器可能依保留設定清理舊的運行產物，結束後儘快下載證據。

TestCase 的結果

結果什麼時候JSONXMind 標記
通過組合場景的執行是 passed（接著執行時含沿用的節點）passedsymbol-right
失敗failed 或 timed_out，原因是產品或測試腳本failedsymbol-wrong
阻塞needs_login 沒等到登入；原因是環境或平台、重跑後仍然不行；被取消blockedsymbol-pause
跳過人決定這一輪不跑skippedsymbol-minus
未執行沒能開始：skipped 清單裡的錯誤、權限不足、沒有發布的版本not_run不加

一個 TestCase 在一輪裡可能跑了好幾次：結果以最後一次有效的執行為準，每一次都列在報告裡。沒跑的不能算通過。

測試報告的格式

一輪一個資料夾，名稱用報告編號，例如 TR-ORDER-2026-10-R1/：

TR-ORDER-2026-10-R1/
  test-report.html      測試報告本身，給人用瀏覽器打開、驗收
  test-report.json      同樣內容的結構化資料，給 Agent 用
  test-report.xmind     （可選）測試方案的 XMind 加上結果標記
  evidence/             失敗與阻塞的 TestCase 的完整證據，HTML 用相對路徑連過來
    TC-ORDER-004/tc-order-004-20261024-081530-1a2b3c/
      composite-run.json
      reject/run.json  reject/steps.json  reject/result.json  reject/screenshot.png
test-report.html 的章節內容
文件資訊報告編號、對應的方案編號與版本、輪次、狀態（草稿、待驗收、已驗收）、產生的 Agent 與時間、伺服器代號與版本、執行期間
1. 結論摘要建議（通過、有條件通過、不通過），逐條對照方案的退出準則；通過率；重大缺陷與阻塞；一段話寫給驗收者
2. 執行範圍方案有幾個 TestCase、執行了幾個、沒執行的與原因
3. 結果統計依結果、優先級、模組；總耗時
4. TestCase 明細編號、標題、優先級、結果、組合場景與版本、執行代號、執行次數、耗時、Portal 路徑
5. 缺陷與問題編號、嚴重程度（嚴重、一般、輕微）、類別（產品缺陷、測試腳本問題、環境問題、測試資料問題、平台問題）、TestCase、節點與步驟、預期與實際、證據檔、建議
6. 執行時間線開始、重跑、請人登入、取消、修正版本等事件，含時間與誰做的
7. 詳細回溯每個失敗與阻塞的 TestCase：組合場景執行 → 節點 → 運行 → 階段 → 步驟 → 斷言 → 證據檔
8. 偏離方案改了哪些場景或組合場景的版本、增減了哪些 TestCase、為什麼
9. 風險與遺留沒測到的、只在特定環境驗證過的、建議下一輪補的
10. 人工驗收建議抽查的執行（全部失敗與阻塞的、每個 P1、其他的抽一部分）及 Portal 路徑；簽核欄（驗收者、日期、結論、意見）留空給人填

HTML 的寫法

  • 單一檔案、可以離線打開：樣式寫在 <style> 裡，不載入外部的字型、腳本或 CDN（驗收的電腦可能在內網）；不需要 JavaScript 也能完整閱讀，長的回溯用 <details> 摺疊。
  • 整個資料夾一起交：截圖與證據用相對路徑連到 evidence/，例如 <img src="evidence/…/screenshot.png">；人解壓後直接打開 test-report.html。
  • 互相連結：每個 TestCase 一個錨點（id="TC-ORDER-004"），結論、明細、缺陷與回溯之間用 # 連結。
  • 跳脫：從 API 拿到的文字（錯誤訊息、實際值、頁面上的字）一律做 HTML 跳脫再放進頁面；不要把運行的 report.html 或頁面原始碼整段嵌進來，要看時連到證據檔。
  • 結果要有文字：通過、失敗、阻塞要寫出來，不能只靠顏色；列印時也看得清楚。
  • Portal：portalPath 寫成文字；人給過 Portal 的網址時再做成連結。
