測試方案指南

寫給接入平台的第三方 Agent：怎麼依需求設計場景與專案，用軟體工程常用的 TestCase 方法設計組合場景，並寫出交給人審閱的測試方案（XMind，另附給 Agent 自己用的 JSON）。

第一期已發布（v0.6.0）
測試方案是 Agent 的交付物，給人審閱與驗收；平台不讀取、不上傳、不保存它，也沒有對應的 API。Agent 用 Agent 使用指南的 API 在平台上建立場景、專案與組合場景，再把設計與結果整理成這份文件。執行、跟蹤與測試報告見測試報告指南。本指南 2026-10-24 依使用者的要求撰寫，隨 v0.6.0 發布。

誰做什麼

Agent
分析需求、設計 TestCase、建立與調試場景、在專案裡建立組合場景、寫測試方案；簽核後執行並寫測試報告。
人（驗收者）
審閱測試方案：範圍對不對、TestCase 夠不夠、測試資料與副作用能不能接受、待確認的事項怎麼處理；簽核後才正式執行。最後依測試報告驗收。
平台
保存場景、專案與組合場景的版本，在 Worker 上執行，保留每次運行的步驟、斷言與產物。平台不知道「測試方案」「TestCase」這些詞，也不判斷測試夠不夠。

別和平台的「驗證」混淆：平台的驗證是把某個版本交給 Worker 跑一次、作為發布的依據；測試方案是寫給人看的文件。

測試步驟組合場景的節點每個節點是某個場景的固定版本；先後由出參綁定與 edges 決定。
預期結果節點的場景的 verify（獨立斷言）斷言不通過，節點就失敗；組合場景失敗即停，TestCase 就失敗。
前置條件角色已登入、Secrets 已設定、Worker 在線、測試資料存在平台在執行前查得到的（角色、Worker）寫查詢方式；查不到的寫清楚請人確認。
測試資料節點入參的固定值、動態值、上游的出參動態值如 {{today}}、{{now:yyyyMMddHHmmss}}、{{random:1:99}}，執行時才求值。
可重用的操作（關鍵字）場景一個場景做一個業務動作，有自己的入參、出參與斷言，給好幾個 TestCase 共用。
一次測試執行組合場景的執行見測試報告指南。

整體流程

  1. 讀需求與平台現況：GET /meta（權限、可用的專案與領域）、GET /projects、GET /composites/library（可以用的場景版本）、GET /roles、GET /secrets。
  2. 設計 TestCase：列出要驗證的功能點與需求編號，選測試設計方法，寫出 TestCase 清單。這一步還不建立任何東西。
  3. 拆場景：把 TestCase 的步驟歸納成可重用的場景，對照場景庫，能用就用、缺的才建。
  4. 交草稿：寫出測試方案的 XMind 草稿（狀態「草稿」），在中心主題的備註列出待人確認的事項。調試場景會在目標系統上真的點擊與填寫，建議先請人看過範圍與測試資料；使用者已經明確授權時可以直接往下做。
  5. 建立場景：建立、調試、驗證、發布缺的場景，見 Agent 使用指南。
  6. 建立專案與組合場景：每個 TestCase 一個組合場景，用 POST /composites/check 檢查到沒有問題再存。
  7. 完成方案：填入場景與組合場景的代號和版本，產出 test-plan.xmind 與 test-plan.json，狀態改為「待簽核」，把 XMind 交給人。
  8. 人簽核後依測試報告指南執行。

設計 TestCase 的方法

方法什麼時候用在組合場景怎麼表達
等價類劃分入參有明確的有效與無效範圍每個有效類一個 TestCase；無效類用「預期被拒絕」的場景（見下方負向測試）。
邊界值分析數量、金額、長度、日期最小、最小＋1、最大−1、最大、超出各一個 TestCase，值寫在節點入參的固定值。
判定表、因果圖好幾個條件一起決定結果（等級 × 金額 × 優惠）判定表的每條規則一個 TestCase；條件是入參，結果寫在場景的 verify。
狀態轉換單據、訂單、審批等有狀態的物件每條要涵蓋的轉換路徑一個組合場景，例如建立 → 送審 → 核准 → 結案；節點之間用出參（單號）串起來。
場景法（業務流程）端到端流程的基本流與備選流基本流一個 TestCase；每個備選流（取消、退回、補件）各一個，共用前段節點、換後段。
成對組合（pairwise）參數多、全部組合太多用成對組合挑出代表的組合，每組一個 TestCase；在方案寫明挑選方式。
錯誤推測常見的易錯點：重複送出、空白、特殊字元、權限不足補充的 TestCase，標出依據。
  • 優先級：P1 冒煙與核心路徑（每次都要跑）、P2 主要功能與常見的錯誤處理、P3 次要與少見的情況。XMind 用標記 priority-1～priority-3 表示。
  • 負向測試寫成「預期被拒絕而通過」：組合場景失敗即停，節點失敗就代表 TestCase 失敗，不能期待執行「失敗」。「數量超過上限要顯示錯誤」要做成一個場景：填入錯誤的值、送出，verify 斷言錯誤訊息出現、沒有建立單據。
  • 入參限制會擋掉不合法的固定值：組合場景的檢查會依場景入參的 minimum、maxLength、enum 等規則檢查固定值。要送出不合法的值，那個場景的入參就不能有這些限制（例如另做一個入參是字串、不設範圍的場景）。
  • 每個 TestCase 都要能重跑：會建立資料的，用動態值產生不重複的資料（例如 測試客戶-{{now:yyyyMMddHHmmss}}）；需要時在最後加清理的節點。
  • 追溯：每個 TestCase 至少對應一個需求編號；每個需求都要有 TestCase，沒有的寫明不測的原因。
  • 副作用：執行會在目標系統上真的建立、修改資料。用測試帳號的角色與測試資料；避免不了的寫進風險，請人確認。

場景怎麼拆

  • 一個場景一個業務動作：建立訂單、查詢訂單、核准。不要把整個 TestCase 寫成一個場景：拆開才能被不同的 TestCase 共用，失敗時也知道停在哪個動作。
  • 入參與出參：會變的資料是入參，下游要用的值（單號、金額）是出參。相關的場景用一致的出參與入參名稱，{"auto": true} 才能自動接上。
  • 斷言就是預期結果：每個場景的 verify 比對頁面事實與入參，斷言這個動作的業務結果，而不是「步驟沒有出錯」。
  • 先查場景庫：GET /composites/library 列出可用領域裡發布過的場景版本，以及每個版本的入參、出參與登入角色。合用的直接用；要改的存新版本、驗證、發布後用新的版本號，已經用舊版本的 TestCase 不受影響。
  • 只能用發布過的版本：沒有 scenes:publish 時，把要發布的場景與版本列在方案的「待人確認」，請人在 Portal 發布。

建立專案與組合場景

1. 專案

GET /agent-api/v1/projects                                 （projects:read）
→ {"projects": [{"id": "order-regression", "name": "訂單回歸測試", "compositeCount": 4,
                 "portalPath": "/projects/order-regression", …}]}

POST /agent-api/v1/projects                                （projects:write）
{"id": "order-regression", "name": "訂單回歸測試",
 "description": "測試方案 TP-ORDER-2026-10", "idempotencyKey": "TP-ORDER-2026-10"}
→ 201 {"id": "order-regression", …}

PATCH /agent-api/v1/projects/order-regression  {"description": "…"}

專案代號的規則和領域相同（小寫英數、-、_，建立後不能改）。金鑰限定了可用的專案時不能新增專案（403 project_create_forbidden），用已有的或請管理員建立。刪除與排序只在管理後台。

2. 組合場景的定義

{"version": 2, "mode": "dag", "onFailure": "stop",
 "nodes": [
   {"id": "create", "sceneId": "order-create", "revision": 6,
    "inputs": {"customer": {"value": "測試客戶-{{now:yyyyMMddHHmmss}}"},
               "quantity": {"value": 99}}},
   {"id": "query", "sceneId": "order-query", "revision": 3,
    "inputs": {"orderId": {"node": "create", "output": "orderId"}}}
 ],
 "edges": [{"source": "create", "target": "query"}]}
  • 最多 50 個節點；節點 id 在組合場景裡不能重複。
  • 入參的來源：{"value": …} 固定值（可以是動態值）；{"node": "create", "output": "orderId"} 上游節點的出參；{"auto": true} 從直接上游找唯一同名的出參。沒寫的入參用場景的預設值，沒有預設值的一定要給。
  • 出參綁定本身就形成先後；沒有資料關係但要有先後時才加 edges。
  • 同時就緒的節點依定義的順序逐個執行；任何節點沒有通過就停，後面的節點標為略過。

3. 檢查、建立、修改

POST /agent-api/v1/composites/check   {"definition": {…}}
→ {"ok": false, "problems": [{"code": "workflow.input_missing", "message": "…",
                               "node": "query", "input": "orderId"}]}

POST /agent-api/v1/projects/order-regression/composites      （projects:write）
{"code": "tc-order-003", "name": "TC-ORDER-003 數量上限 99 可以建立",
 "description": "目的：數量等於上限時可以建立。需求：REQ-12。方案：TP-ORDER-2026-10",
 "domainId": "sales", "definition": {…},
 "note": "測試方案 TP-ORDER-2026-10 v1", "idempotencyKey": "TP-ORDER-2026-10/tc-order-003"}
→ 201 {"code": "tc-order-003", "latestRevision": 1, "publishedRevision": null, "problems": [],
       "dependency": "complete", "portalPath": "/playground/12", …}

PUT /agent-api/v1/composites/tc-order-003
{"baseRevision": 1, "definition": {…}, "note": "數量改為 99"}
→ {"latestRevision": 2, …}
  • problems 是空的才能驗證與執行；依 node、input 修正。dependency 是 complete 才能發布。
  • 代號就是 TestCase 編號：小寫英數、-、_，例如 tc-order-003；名稱以大寫編號開頭，例如「TC-ORDER-003 數量上限 99 可以建立」；說明寫目的、需求編號與方案編號。
  • domainId 是放組合場景的領域資料夾，沒給時放「組合場景」領域；金鑰限定了領域時要給可用的。節點用到的場景也要在可用的領域，否則 403 composite_scenes_forbidden。
  • 存檔時 baseRevision 不是最新會回 409 stale_workflow（latest 是最新版本）：讀 GET /composites/{code}，把修改套上去再存，不要蓋掉人的修改。定義沒變時只更新名稱與說明，不會多一個版本。
  • 移到另一個專案：PATCH /composites/{code} {"projectId": "…"}。
  • GET /projects/{id} 列出專案裡每個組合場景的摘要（最新與發布的版本、問題數、最近一次執行）；GET /composites/{code} 有完整的定義、版本、驗證紀錄與依賴。

測試方案的格式

XMind 給人，JSON 給 Agent
test-plan.xmind
測試方案本身，給人審閱與簽核：每個組合場景一個 TestCase，方案層級的說明（範圍、環境、準則、待確認、簽核）放在中心主題的備註；也能匯入常見的 TestCase 管理工具。
test-plan.json
同樣內容的結構化資料，Agent 之後執行與寫報告時讀它；人不必看。

兩個檔案從同一份資料產生，TestCase 的編號與數量要一致。資料夾名稱用方案編號，例如 TP-ORDER-2026-10/。修改已經交出的方案要升版本，並在備註的修改紀錄寫改了什麼。

XMind 的層放什麼
中心主題標題是方案編號與專案名稱，例如「TP-ORDER-2026-10 訂單回歸測試」。備註是方案層級的說明，格式見下方。
第一層：模組測試套件，例如「訂單建立」；備註可以寫這個模組驗證什麼。
第二層：TestCase每個組合場景一個主題，標題是「編號 標題」，一定要有優先級標記 priority-1～priority-3（工具靠它認出 TestCase）。標籤：auto（自動執行）、組合場景代號與版本（如 tc-order-003 v2）、需求編號、設計方法。備註：前置條件、測試資料、Portal 路徑。
第三層：步驟每個節點一個主題：「節點代號：做什麼（場景代號 v版本）」，依執行順序排列。
第四層：預期結果每個步驟底下只放一個預期結果主題；好幾個斷言用「；」連在一起。

中心主題的備註依序寫這些段落（純文字，一段一行開頭；人審閱後把簽核那一段填好交回，或直接回覆 Agent，Agent 記進 test-plan.json 的 signoff）：

文件資訊：TP-ORDER-2026-10 v2；狀態：待簽核；ERP 助理 2026-10-24T08:00Z 產生；伺服器 srv-linux-01（0.6.0）；專案 order-regression；需求來源：訂單規格 v3
1. 目標與範圍：驗證訂單建立的數量規則與審批流程。不驗證：退款、報表
2. 測試環境：https://erp-test.example.internal；Chromium；執行位置 any；角色 sales、manager；Secrets：erp-password（只有名稱）
3. 測試策略：邊界值、狀態轉換；P1 冒煙與核心路徑、P2 主要功能、P3 次要；先驗證再發布，一輪正式執行；環境原因最多重跑一次
4. 場景：order-create v6（已發布）、order-query v3（已發布）、order-submit-raw v2（待發布）
5. 未涵蓋的需求：REQ-15 列印（平台不支援列印對話框）
6. 測試資料與清理：客戶名稱帶時間戳記；每輪約建立 6 張測試訂單，不自動刪除
7. 進入與退出準則：進入：方案已簽核、組合場景沒有問題、角色已登入；退出：P1 全部通過、P2 通過率 ≥ 95%、沒有未處理的嚴重缺陷
8. 風險與待人確認：order-submit-raw v2 要人發布；manager 角色要人工登入
9. 簽核：審閱者＿＿；日期＿＿；結論（同意／修改後同意／不同意）＿＿；意見＿＿
修改紀錄：v1 初稿；v2 加入 TC-ORDER-004
  • 主題標題不要以 # 或 ! 開頭，常見工具會把它當成註解略過。
  • 方案層級的說明只放在中心主題的備註，不要另開工作表或主題：常見的 XMind 轉 TestCase 工具會把沒有子主題的主題當成 TestCase。
  • 測試報告用同一張圖，在 TestCase 上加結果標記（見測試報告指南）。

寫出 XMind 檔

.xmind 是 ZIP。content.json 給 XMind 2020 以後的版本，content.xml 給 XMind 8 與常見的 XMind 轉 TestCase 工具（例如 xmind2testcase）。兩份內容相同，下面的 Python 只用標準函式庫就能同時寫出：

import json, uuid, zipfile
from xml.etree import ElementTree as ET


def topic(title, children=(), *, priority=None, markers=(), labels=(), notes=None):
    marks = ([f"priority-{priority}"] if priority else []) + list(markers)
    return {"id": uuid.uuid4().hex, "title": title, "markers": marks,
            "labels": list(labels), "notes": notes, "children": list(children)}


def _json(node):
    data = {"id": node["id"], "class": "topic", "title": node["title"]}
    if node["markers"]:
        data["markers"] = [{"markerId": mark} for mark in node["markers"]]
    if node["labels"]:
        data["labels"] = node["labels"]
    if node["notes"]:
        data["notes"] = {"plain": {"content": node["notes"]}}
    if node["children"]:
        data["children"] = {"attached": [_json(child) for child in node["children"]]}
    return data


def _xml(parent, node):
    element = ET.SubElement(parent, "topic", id=node["id"])
    ET.SubElement(element, "title").text = node["title"]
    if node["markers"]:
        refs = ET.SubElement(element, "marker-refs")
        for mark in node["markers"]:
            ET.SubElement(refs, "marker-ref", {"marker-id": mark})
    if node["labels"]:
        labels = ET.SubElement(element, "labels")
        for label in node["labels"]:
            ET.SubElement(labels, "label").text = label
    if node["notes"]:
        ET.SubElement(ET.SubElement(element, "notes"), "plain").text = node["notes"]
    if node["children"]:
        attached = ET.SubElement(ET.SubElement(element, "children"), "topics", type="attached")
        for child in node["children"]:
            _xml(attached, child)


def write_xmind(path, sheet_title, root):
    sheet_id = uuid.uuid4().hex
    content = [{"id": sheet_id, "class": "sheet", "title": sheet_title, "rootTopic": _json(root)}]
    xmap = ET.Element("xmap-content", xmlns="urn:xmind:xmap:xmlns:content:2.0", version="2.0")
    sheet = ET.SubElement(xmap, "sheet", id=sheet_id)
    _xml(sheet, root)
    ET.SubElement(sheet, "title").text = sheet_title
    manifest = ('<?xml version="1.0" encoding="UTF-8" standalone="no"?>'
                '<manifest xmlns="urn:xmind:xmap:xmlns:manifest:1.0">'
                '<file-entry full-path="content.xml" media-type="text/xml"/>'
                '<file-entry full-path="META-INF/" media-type=""/>'
                '<file-entry full-path="META-INF/manifest.xml" media-type="text/xml"/>'
                '</manifest>')
    with zipfile.ZipFile(path, "w", zipfile.ZIP_DEFLATED) as archive:
        archive.writestr("content.json", json.dumps(content, ensure_ascii=False))
        archive.writestr("metadata.json", json.dumps({"creator": {"name": "agent", "version": "1"}}))
        archive.writestr("manifest.json",
                         json.dumps({"file-entries": {"content.json": {}, "metadata.json": {}}}))
        archive.writestr("content.xml", ET.tostring(xmap, encoding="unicode", xml_declaration=True))
        archive.writestr("META-INF/manifest.xml", manifest)
