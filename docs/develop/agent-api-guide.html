Agent 使用指南

寫給接入平台的 Agent 系統（以及替它寫整合的人）：怎麼用 /agent-api/v1 從空白建立場景、在錄製端調試、交給 Worker 驗證、發布並正式執行，在專案裡把場景組成組合場景並執行，遇到錯誤時怎麼處理。

第一期實作中
本指南依 2026-10-23 確認的設計與第一期的實作撰寫（2026-10-23，審閱中）；專案與組合場景 2026-10-24 加入。用 API 做測試時，測試方案與測試報告的寫法見測試方案指南與測試報告指南。欄位以伺服器的 GET /agent-api/v1/openapi.json 為準；/agent-api/v1/docs 是可以直接試的互動式文件，兩者都不需要金鑰。

基本約定

位址
http://<伺服器>:8081/agent-api/v1；伺服器前有 HTTPS 反向代理時用代理的位址。
認證
每個請求帶 Authorization: Bearer <API 金鑰>。金鑰由管理員在管理後台的「API 用戶端」建立，只顯示一次；不要寫進日誌或場景。
格式
JSON，欄位 camelCase；時間是 ISO 8601（UTC）。
錯誤
{"error": {"code": "…", "message": "…", …}}。程式依 code 判斷，message 給人看；有些錯誤另帶細節，例如 issues、problems、latest。
語言
?lang=zh-Hant、zh-Hans 或 en 決定 message 的語言；沒給時用伺服器預設。
冪等
會建立東西的請求（建立場景、專案與組合場景，存版本，驗證、執行、重跑）接受 idempotencyKey。逾時或斷線後用同一個值重送，回傳的是上次的結果，不會重複建立或重複執行。驗證、執行、重跑的冪等鍵記在運行紀錄裡；建立與存版本的冪等鍵記在伺服器的記憶體 24 小時，伺服器重新啟動後就忘了，這時重送會收到 scene_exists、project_exists、workflow_code_exists、stale_base 或 stale_workflow，讀最新狀態即可。不同用戶端用同一個值互不影響。
輪詢
查運行狀態每 2～5 秒一次即可；第二期改用事件長輪詢。

開始之前

先呼叫 GET /meta，確認這把金鑰能做什麼，缺的請管理員補，不要用試錯的方式找出權限。

GET /agent-api/v1/meta

{
  "apiVersion": "1",
  "serverVersion": "0.6.0",
  "server": {"id": "srv-linux-01", "name": "Linux 伺服器"},
  "client": {"id": "agent-erp", "name": "ERP 助理"},
  "scopes": ["scenes:read", "scenes:write", "debug", "runs:validate", "runs:read",
             "projects:read", "projects:write"],
  "pageContent": true,
  "limits": {"debugSessions": 2, "queuedRuns": 20},
  "domains": ["sales"],
  "projects": ["order-regression"],
  "recorders": ["agent-mac"],
  "target": null,
  "workers": null,
  "expiresAt": null,
  "dslFeatures": ["anyFrame", "dynamicValues", "frame", "page", "popup"]
}
  • scopes 沒有 scenes:publish：做到驗證通過為止，再請人在 Portal 發布。
  • pageContent 是 false：截圖、頁面結構、錄影都拿不到，只能靠定位器測試與步驟結果寫場景。
  • domains 是可以讀寫的領域、projects 是可以用的專案（null 不限）；recorders 是可以開調試的錄製端；target、workers 是固定的執行位置與可以指定的 Worker（null 不限）。
  • 接著讀 GET /dsl/schema（場景 YAML 的 JSON Schema）、GET /recorders（可用的錄製端：是否在線、allowAgent、headlessOnly、capabilities 有沒有 debugSnapshot）、GET /roles（登入角色與狀態）、GET /secrets（只有名稱）、GET /workers（可以指定的 Worker）。

場景長什麼樣

一個場景是一份 YAML（scenario.yaml）。步驟只負責操作頁面、抽取「頁面事實」；成功與否由 verify 獨立判斷，全部通過才發布出參。完整規格見場景 DSL。

schemaVersion: 1
id: order-create
name: 建立訂單
category: 訂單
inputs:
  customer: { type: string, minLength: 1 }
  quantity: { type: integer, minimum: 1, maximum: 99, default: 1 }
outputs:
  orderId: { type: string, pattern: '^SO-\d+$', from: '{{ facts.order.orderId }}' }
login: { role: sales }
browser:
  engine: chromium
  baseUrl: https://erp.example.internal
defaults:
  timeout: 10000
steps:
  - id: open
    action: goto
    url: /orders/new
  - id: fill-customer
    action: fill
    target: { label: 客戶, exact: true }
    value: '{{ inputs.customer }}'
  - id: fill-quantity
    action: fill
    target: { label: 數量, exact: true }
    value: '{{ inputs.quantity }}'
  - id: submit
    action: click
    target: { role: button, name: 建立, exact: true }
  - id: read-order
    action: extract
    target: { css: '#order-summary' }
    as: order
    fields:
      orderId: { target: { testId: order-id } }
      customer: { target: { testId: order-customer } }
verify:
  - name: 取得訂單編號
    value: '{{ facts.order.orderId }}'
    matches: '^SO-\d+$'
  - name: 客戶與入參相同
    value: '{{ facts.order.customer }}'
    equals: '{{ inputs.customer }}'
  • 步驟 id 要穩定：調試換版本時，已執行的步驟靠 id 對應；改內容不要改 id。
  • 定位器的優先順序：role＋name、label、text、testId，最後才是 css／xpath；容易變的加 fallback。元素在 iframe 裡用 frame，點擊開出新分頁用 popup 與 page。
  • 會變的值寫成入參：不要把客戶、日期、數量寫死在步驟裡。
  • 密碼不寫進場景：用 secrets 宣告名稱、{{ secrets.名稱 }} 引用；需要登入的系統用 login: { role }，登入狀態由平台管理。
  • verify 要比對頁面事實與入參：「步驟沒有出錯」不等於成功。

從空白到正式執行

1. 建立場景並存第一版

POST /agent-api/v1/scenes
{"id": "order-create", "name": "建立訂單", "category": "訂單", "domainId": "sales",
 "idempotencyKey": "order-create"}
→ 201 {"id": "order-create", "latestRevision": 1, …}

POST /agent-api/v1/scenes/order-create/revisions
{"baseRevision": 1, "files": {"scenario.yaml": "schemaVersion: 1\nid: order-create\n…"},
 "note": "只開頁面", "idempotencyKey": "order-create-r2"}
→ 201 {"sceneId": "order-create", "number": 2, "status": "draft",
       "note": "Agent〈ERP 助理〉：只開頁面", …}

建立場景時伺服器會先存第 1 版（只有名稱的範本），所以第一次存檔的 baseRevision 是 1。沒給 domainId 時場景放進「未分類」，金鑰限定了領域時就要給。存檔前可以先 POST /dsl/check {"yaml": "…", "sceneId": "order-create"}，回應的 ok 與 issues（行號、步驟、欄位）和存檔時的檢查相同。這一版只放 goto（和需要的 login）就好，後面的步驟看了頁面再寫。

2. 在錄製端開調試工作階段

POST /agent-api/v1/scenes/order-create/debug
{"recorderId": "agent-mac", "revision": 2,
 "inputs": {"customer": "測試客戶", "quantity": 2}}
→ 202 {"id": "a1b2c3d4e5f6", "status": "starting", "deviceId": "agent-mac",
       "headless": true, "clientId": "agent-erp", …}

GET /agent-api/v1/debug/a1b2c3d4e5f6
→ {"status": "ready", "nextIndex": 0, "steps": [{"index": 0, "id": "open", "status": "pending", …}], …}

等 status 變成 ready（第一次用 Firefox 可能要一兩分鐘）。預設無頭；這把金鑰只允許一台錄製端時可以不給 recorderId。一個場景同時只有一個工作階段：自己已經開了就回傳原本那個（要換版本或入參重開時帶 "restart": true），別人（人或其他 Agent）正在調試時回 409 debug_in_use。你只看得到、只能操作自己開的工作階段（GET /debug 列出），閒置 15 分鐘自動關閉。

3. 看頁面，再寫下一段步驟

POST /agent-api/v1/debug/a1b2c3d4e5f6/run-to/0
POST /agent-api/v1/debug/a1b2c3d4e5f6/snapshot
→ {"url": "https://erp.example.internal/orders/new", "title": "新增訂單",
   "tabs": [{"page": null, "url": "…", "title": "新增訂單", "active": true}],
   "frames": [],
   "fields": [{"tag": "input", "type": "text", "role": "textbox", "label": "客戶",
               "name": "customer", "required": true, "disabled": false, "visible": true, "value": ""},
              {"tag": "input", "type": "number", "role": "spinbutton", "label": "數量", …}],
   "aria": "- heading \"新增訂單\" [level=1]\n- textbox \"客戶\"\n- spinbutton \"數量\"\n- button \"建立\"",
   "truncated": false}

POST /agent-api/v1/debug/a1b2c3d4e5f6/locate
{"locator": {"role": "button", "name": "建立", "exact": true}}
→ {"located": {"locator": "…", "ok": true, "count": 1,
               "matches": [{"tag": "button", "text": "建立"}], "error": null}, …}

locate 找到剛好 1 個才用它；0 個或好幾個就換定位器。tabs 的 page 是步驟用 popup 開出、取了名字的分頁（一開始的分頁是 null）；frames 是 iframe，parent 指向上一層在清單裡的位置。fields 列出目前頁面的表單欄位，密碼欄位與填了 Secret 的值一律是 ***。頁面很大時 aria 會截斷並標 truncated，用 {"within": {"css": "#main"}} 只看一部分（within 是定位器，iframe 裡的用 frame）。需要看畫面時用 screenshot，回應裡的 screenshotUrl 可以下載圖片。讀頁面結構與截圖都要「回傳頁面內容」，錄製端也要是新版 App。

4. 存新版本、換過去、接著跑

POST /agent-api/v1/scenes/order-create/revisions
{"baseRevision": 2, "files": {"scenario.yaml": "…加上 fill-customer、fill-quantity、submit…"}}
→ 201 {"number": 3, …}

POST /agent-api/v1/debug/a1b2c3d4e5f6/reload   {"revision": 3}
POST /agent-api/v1/debug/a1b2c3d4e5f6/run-to/3
→ {"steps": [… {"index": 3, "id": "submit", "status": "failed", "error": "…"}], …}

瀏覽器與已執行的步驟會保留，run-to 只執行還沒執行過的步驟，失敗就停。改好再存一版、reload、run-to，直到每一步都是 passed。想從頭重跑用 reset。

錄製端在另一台電腦時，reload 要伺服器與錄製端都是 0.6.3 以上：0.6.2 以前在錄製端換版本一定回 422 revision_invalid「場景校驗失敗」（伺服器把自己的檔案路徑交給錄製端，錄製端讀不到）。伺服器已更新、錄製端還沒更新時回 422 recorder_outdated；這時請人更新錄製端，或改用 POST /scenes/{id}/debug 帶新的 revision 與 "restart": true 重新開始（從第 1 步重跑，有副作用的步驟會再做一次）。

點擊、填寫、選擇、勾選、按鍵是有副作用的步驟，會在目標系統上真的發生。執行過一次的有副作用步驟用 POST /debug/{sid}/steps/{index} 再執行時回 409 confirm_required，必須帶 {"force": true}；只在確定重做不會造成重複資料時才這樣做。run-to 的目標在下一個還沒執行的步驟之前時回 409 already_executed。

5. 補齊入參、出參與獨立斷言

用 GET／PUT /scenes/{id}/sections/steps、verify、inputs、outputs 只讀寫一段（{"baseRevision": n, "text": "verify:\n - …"}），或 PUT /scenes/{id}/contract 以表格形式改入參與出參；每次都會存成新版本。已經有 Playwright（Python）腳本時，可以用 POST /scenes/{id}/import {"source": "…", "mode": "replace"} 轉成 DSL，轉不了的寫在 warnings。完成後 DELETE /debug/{sid} 結束工作階段，釋放錄製端。

6. 交給 Worker 驗證

POST /agent-api/v1/scenes/order-create/revisions/6/validate
{"inputs": {"customer": "測試客戶", "quantity": 2}, "idempotencyKey": "order-create-v6-1"}
→ 202 {"id": "order-create-20261023-…", "purpose": "validation", "status": "queued", …}

GET /agent-api/v1/runs/order-create-20261023-…
→ {"status": "running", "stage": "automation", …}
→ {"status": "failed", "error": "…", "finished": true, …}
GET /agent-api/v1/runs/order-create-20261023-…/steps

失敗時看 error、result（結束後的完整結果：階段、步驟、斷言）、/steps 中第一個失敗的步驟，以及（有「回傳頁面內容」時）files 列出的截圖與 reportUrl；回到調試修正。驗證可以用任何版本，正式執行只用已發布版本。可以帶 workerId 指定 Worker（local 是伺服器本機）或 target；金鑰固定了執行位置時不能指定別的。第一期的 /steps 在運行結束後才完整，執行中請看 status 與 stage。

7. 發布與正式執行

POST /agent-api/v1/scenes/order-create/revisions/6/publish      （需要 scenes:publish）

POST /agent-api/v1/scenes/order-create/runs
{"inputs": {"customer": "王小明", "quantity": 3}, "idempotencyKey": "job-8812"}
→ 202 {"id": "…", "purpose": "execution", "status": "queued", …}
GET /agent-api/v1/runs/…
→ {"status": "passed", "output": {"orderId": "SO-10231"}, …}

只有 status 是 passed 時才有 output。沒有發布權限時，告訴使用者哪個場景的哪個版本已驗證通過，請人在 Portal 發布。GET /runs?scene=…&status=…&purpose=…&mine=true 列出看得到的運行（可用領域裡的場景，mine 只列自己觸發的）；POST /runs/{id}/cancel 只能取消自己觸發的。

專案與組合場景

專案空間裡的專案收納組合場景；組合場景把發布過的場景版本接成一個流程（DAG），前面節點的出參可以綁到後面節點的入參。用 API 做測試時，一個組合場景就是一個 TestCase，見測試方案指南。

端點用途權限範圍
GET /projects、GET /projects/{id}可用的專案；專案與它的組合場景摘要projects:read
POST /projects、PATCH /projects/{id}新增專案（限定了可用專案的金鑰不能新增）；改名稱與說明projects:write
GET /composites/library可以放進組合場景的場景版本，與入參、出參、登入角色projects:read
POST /composites/check不存檔檢查定義，回傳 problems（節點、入參）projects:read
GET /composites?project=、GET /composites/{code}組合場景摘要；完整的定義、問題、版本、驗證紀錄、依賴、最近的執行projects:read
POST /projects/{id}/composites在專案裡建立組合場景（帶定義時就是第 1 版）projects:write
PUT /composites/{code}、PATCH /composites/{code}存新版本（帶 baseRevision）；移到另一個專案projects:write
POST /composites/{code}/revisions/{n}/validate交給 Worker 驗證這個版本runs:validate
POST /composites/{code}/revisions/{n}/publish發布驗證通過、依賴完整的版本projects:publish（預設不給）
POST /composites/{code}/runs正式執行發布的版本runs:execute
POST /projects/{id}/runs把專案裡的組合場景（或 composites 列出的）逐一排入；排不進去的在 skipped依 purpose：runs:validate 或 runs:execute
GET /composite-runs、GET /composite-runs/{id}組合場景的執行：狀態、進度（progress）、每個節點的狀態與那次運行runs:read
POST /composite-runs/{id}/cancel、/rerun取消自己觸發的；從頭或從停下的節點（"resume": true）再執行依執行的目的
  • 看得到哪些：組合場景要在可用的專案裡，放的領域也要可用；不屬於任何專案的組合場景不給 Agent。看不到的一律回 404。節點用到的場景要在可用的領域，否則 403 composite_scenes_forbidden。
  • 沒有執行時的入參：入參在定義裡綁定（固定值、動態值、上游的出參）；同一個流程換一組資料就是另一個組合場景。
  • 節點的細節：每個節點的 run 是一次普通的運行，步驟、斷言與產物用 /runs/{id}、/runs/{id}/steps 讀；節點不能單獨重跑（409 rerun_workflow），要重跑組合場景的執行。
  • Portal 路徑：回應帶 portalPath（例如 /playground/runs/…），人在 Portal 看同一筆資料用；寫測試報告時附上。
  • 限額：組合場景的節點也算進「排隊中與執行中」的限額。

錯誤怎麼處理

狀態碼code意思Agent 該做什麼
401unauthorized金鑰缺少、錯誤、停用、到期，或不能從這個位址使用停止，請管理員處理；不要重試
403scope_missing這把金鑰沒有需要的權限範圍（scopes 列出缺哪個）請人授權或改由人完成這一步
403content_disabled「回傳頁面內容」沒開改用 locate 與步驟結果；或請管理員打開
403domain_forbidden、recorder_forbidden不能用這個領域或錄製端換一個允許的，或請管理員加上
403recorder_agent_off錄製端沒有打開「允許 Agent 調試」或已停用請人在裝置頁打開，或換一台
403recorder_headless_only這台錄製端只允許無頭不要帶 "headless": false
403target_forbidden、worker_forbidden這把金鑰固定了執行位置，或不能指定這台 Worker不要指定，或換允許的
403run_forbidden想取消別人觸發的運行請人處理
403project_forbidden、project_create_forbidden不能用這個專案；限定了可用專案的金鑰不能新增專案用允許的專案，或請管理員處理
403composite_scenes_forbidden組合場景的節點用到不可用領域的場景（scenes 列出哪些）換場景，或請管理員加上領域
404debug_not_found、run_not_found、project_not_found、workflow_not_found、workflow_run_not_found 等找不到，或不是你看得到的確認代號
409stale_basebaseRevision 不是最新版，有人改過讀 latest 那一版，把修改套上去再存
409scene_exists場景代號已經有了換代號，或讀現有的場景
409debug_in_use這個場景有別人正在調試稍後再試，不要搶
409debug_busy、debug_starting上一個命令還在跑，或瀏覽器還在啟動等它完成再送下一個命令
409debug_closed工作階段已經結束（閒置、出錯或被關掉）重新開始調試
409confirm_required有副作用的步驟已執行過確定可以重做才帶 force；否則 reset
409already_executedrun-to 的目標已經執行過用單步執行或 reset
409recorder_offline錄製端不在線換一台，或請人開啟錄製端 App
409not_validated、content_changed這個版本沒有驗證通過的紀錄，或內容和驗證時不同先驗證
409not_published場景沒有已發布版本，不能正式執行發布，或請人發布
409rerun_workflow組合場景的節點不能單獨重跑重跑組合場景的執行：POST /composite-runs/{id}/rerun
409stale_workflow組合場景的 baseRevision 不是最新版讀 latest 那一版，把修改套上去再存
409project_exists、workflow_code_exists專案或組合場景的代號已經有了換代號，或讀現有的
409workflow_unpublished組合場景沒有發布的版本，不能正式執行先驗證、發布，或請人發布
409workflow_invalid、workflow_not_validated、workflow_dependencies定義有問題不能執行；這個版本沒有驗證通過的紀錄；依賴不完整（problems）不能發布依 problems 修正、先驗證
409workflow_run_active、workflow_not_resumable組合場景的執行還沒結束；沒有可以接著的節點等它結束；改用從頭執行
422request_invalid請求的格式不對，problems 列出欄位依 problems 修正
422recorder_required這把金鑰允許好幾台錄製端，沒給 recorderId帶上 recorderId
422recorder_outdated錄製端 App 太舊（例如不支援讀頁面結構、調試時換版本，或看不懂場景用到的寫法）請人更新 RPA 錄製端
422display_unavailable那台沒有畫面，不能有頭改用 "headless": true
422revision_invalidYAML 校驗失敗，issues 列出位置（存版本時，或 reload 時錄製端校驗不過）依 issues 修正後再存
422inputs_invalid入參不符合型別或限制，problems 列出哪一個修正入參
422worker_target_mismatch指定的 Worker 和執行位置不一致只給其中一個
429limit_reached超過同時調試或排隊、執行中的限額（limit）等現有的完成，或結束不用的工作階段

運行本身的結果不是 HTTP 錯誤：failed、timed_out、cancelled、needs_login 都在 GET /runs/{id} 的 status。

需要人的時候

  • 需要登入：運行停在 needs_login，或 GET /roles 顯示角色要重新登入。請使用者在錄製端做人工登入，完成後呼叫 POST /runs/{id}/rerun。
  • 沒有發布權限：告訴使用者場景或組合場景的代號與驗證通過的版本號，請人在 Portal 發布。
  • 缺 Secret：GET /scenes/{id} 的 needs 列出還沒設定的 Secrets；值由人在 Portal 填，Agent 不能寫入也讀不到。
  • 錄製端不在線或太舊：請人開啟或更新 RPA 錄製端 App。

守則

  • 每次存版本（場景與組合場景）都帶上次讀到的 baseRevision，不要覆蓋人的修改。
  • 用完調試工作階段就 DELETE，不要占住錄製端。
  • 不要在正式資料上反覆執行有副作用的步驟；能用測試帳號的角色就用。
  • 截圖、頁面結構與出參可能含業務資料，只用在當前的任務，不要另外保存或轉傳。
  • 所有寫入都會記在稽核紀錄，版本說明會標出你的用戶端名稱；在 note 寫清楚這一版改了什麼。
