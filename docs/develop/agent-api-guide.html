Agent 使用指南

寫給接入平台的 Agent 系統（以及替它寫整合的人）：怎麼用 /agent-api/v1 從空白建立場景、在錄製端調試、交給 Worker 驗證、發布並正式執行，遇到錯誤時怎麼處理。

設計已確認，未實作
本指南依 2026-10-23 確認的設計撰寫，第一期尚未實作。實作後欄位以伺服器的 GET /agent-api/v1/openapi.json 為準，本頁會同步更新。

基本約定

位址
http://<伺服器>:8081/agent-api/v1；伺服器前有 HTTPS 反向代理時用代理的位址。
認證
每個請求帶 Authorization: Bearer <API 金鑰>。金鑰由管理員在管理後台的「API 用戶端」建立，只顯示一次；不要寫進日誌或場景。
格式
JSON，欄位 camelCase；時間是 ISO 8601（UTC）。
錯誤
{"error": {"code": "…", "message": "…", …}}。程式依 code 判斷，message 給人看；有些錯誤另帶細節，例如 issues、problems、latest。
語言
?lang=zh-Hant、zh-Hans 或 en 決定 message 的語言；沒給時用伺服器預設。
冪等
會建立東西的 POST（建立場景、存版本、驗證、執行、重跑）接受 idempotencyKey。逾時或斷線後用同一個值重送，不會重複建立或重複執行。
輪詢
查運行狀態每 2～5 秒一次即可；第二期改用事件長輪詢。

開始之前

先呼叫 GET /meta，確認這把金鑰能做什麼，缺的請管理員補，不要用試錯的方式找出權限。

GET /agent-api/v1/meta

{
  "apiVersion": "1",
  "serverVersion": "0.6.0",
  "client": {"id": "agent-erp", "name": "ERP 助理"},
  "scopes": ["scenes:read", "scenes:write", "debug", "runs:validate", "runs:read"],
  "pageContent": true,
  "limits": {"debugSessions": 2, "queuedRuns": 20},
  "dslFeatures": ["frame", "popup"]
}
  • scopes 沒有 scenes:publish：做到驗證通過為止，再請人在 Portal 發布。
  • pageContent 是 false：截圖、頁面結構、錄影都拿不到，只能靠定位器測試與步驟結果寫場景。
  • 接著讀 GET /dsl/schema（場景 YAML 的 JSON Schema）、GET /recorders（可用的錄製端）、GET /roles（登入角色與狀態）、GET /secrets（只有名稱）。

場景長什麼樣

一個場景是一份 YAML（scenario.yaml）。步驟只負責操作頁面、抽取「頁面事實」；成功與否由 verify 獨立判斷，全部通過才發布出參。完整規格見場景 DSL。

schemaVersion: 1
id: order-create
name: 建立訂單
category: 訂單
inputs:
  customer: { type: string, minLength: 1 }
  quantity: { type: integer, minimum: 1, maximum: 99, default: 1 }
outputs:
  orderId: { type: string, pattern: '^SO-\d+$', from: '{{ facts.order.orderId }}' }
login: { role: sales }
browser:
  engine: chromium
  baseUrl: https://erp.example.internal
defaults:
  timeout: 10000
steps:
  - id: open
    action: goto
    url: /orders/new
  - id: fill-customer
    action: fill
    target: { label: 客戶, exact: true }
    value: '{{ inputs.customer }}'
  - id: fill-quantity
    action: fill
    target: { label: 數量, exact: true }
    value: '{{ inputs.quantity }}'
  - id: submit
    action: click
    target: { role: button, name: 建立, exact: true }
  - id: read-order
    action: extract
    target: { css: '#order-summary' }
    as: order
    fields:
      orderId: { target: { testId: order-id } }
      customer: { target: { testId: order-customer } }
verify:
  - name: 取得訂單編號
    value: '{{ facts.order.orderId }}'
    matches: '^SO-\d+$'
  - name: 客戶與入參相同
    value: '{{ facts.order.customer }}'
    equals: '{{ inputs.customer }}'
  • 步驟 id 要穩定：調試換版本時，已執行的步驟靠 id 對應；改內容不要改 id。
  • 定位器的優先順序：role＋name、label、text、testId，最後才是 css／xpath；容易變的加 fallback。元素在 iframe 裡用 frame，點擊開出新分頁用 popup 與 page。
  • 會變的值寫成入參：不要把客戶、日期、數量寫死在步驟裡。
  • 密碼不寫進場景：用 secrets 宣告名稱、{{ secrets.名稱 }} 引用；需要登入的系統用 login: { role }，登入狀態由平台管理。
  • verify 要比對頁面事實與入參：「步驟沒有出錯」不等於成功。

從空白到正式執行

1. 建立場景並存第一版

POST /agent-api/v1/scenes
{"id": "order-create", "name": "建立訂單", "category": "訂單", "domainId": "sales"}

POST /agent-api/v1/scenes/order-create/revisions
{"baseRevision": 0, "files": {"scenario.yaml": "schemaVersion: 1\nid: order-create\n…"},
 "note": "第一版：只開頁面", "idempotencyKey": "order-create-r1"}
→ 201 {"sceneId": "order-create", "number": 1, "status": "draft", …}

存檔前可以先 POST /dsl/check {"yaml": "…"}，回應的 issues 帶行號、步驟與欄位。第一版只放 goto（和需要的 login）就好，後面的步驟看了頁面再寫。

2. 在錄製端開調試工作階段

POST /agent-api/v1/scenes/order-create/debug
{"recorderId": "agent-mac", "revision": 1, "headless": true,
 "inputs": {"customer": "測試客戶", "quantity": 2}}
→ 202 {"id": "a1b2c3d4e5f6", "status": "starting", "deviceId": "agent-mac", …}

GET /agent-api/v1/debug/a1b2c3d4e5f6
→ {"status": "ready", "nextIndex": 0, "steps": [{"index": 0, "id": "open", "status": "pending", …}], …}

等 status 變成 ready（第一次用 Firefox 可能要一兩分鐘）。一個場景同時只有一個工作階段；閒置 15 分鐘自動關閉。

3. 看頁面，再寫下一段步驟

POST /agent-api/v1/debug/a1b2c3d4e5f6/run-to/0
POST /agent-api/v1/debug/a1b2c3d4e5f6/snapshot
→ {"url": "https://erp.example.internal/orders/new", "title": "新增訂單",
   "tabs": [{"pageId": "main", "url": "…", "active": true}],
   "frames": [],
   "fields": [{"role": "textbox", "label": "客戶", "required": true},
              {"role": "spinbutton", "label": "數量"}],
   "aria": "- heading \"新增訂單\" [level=1]\n- textbox \"客戶\"\n- spinbutton \"數量\"\n- button \"建立\"",
   "truncated": false}

POST /agent-api/v1/debug/a1b2c3d4e5f6/locate
{"locator": {"role": "button", "name": "建立", "exact": true}}
→ {"located": {"count": 1, "texts": ["建立"]}, …}

locate 找到剛好 1 個才用它；0 個或好幾個就換定位器或加 within。頁面很大時 snapshot 可以帶 {"within": {"css": "#main"}} 只看一部分。需要看畫面時用 screenshot，回應裡的 screenshotUrl 可以下載圖片。

4. 存新版本、換過去、接著跑

POST /agent-api/v1/scenes/order-create/revisions
{"baseRevision": 1, "files": {"scenario.yaml": "…加上 fill-customer、fill-quantity、submit…"}}
→ 201 {"number": 2, …}

POST /agent-api/v1/debug/a1b2c3d4e5f6/reload   {"revision": 2}
POST /agent-api/v1/debug/a1b2c3d4e5f6/run-to/3
→ {"steps": [… {"index": 3, "id": "submit", "status": "failed", "error": "…"}], …}

瀏覽器與已執行的步驟會保留，run-to 只執行還沒執行過的步驟，失敗就停。改好再存一版、reload、run-to，直到每一步都是 passed。想從頭重跑用 reset。

點擊、填寫、選擇、勾選、按鍵是有副作用的步驟，會在目標系統上真的發生。執行過一次的有副作用步驟要再執行，必須帶 {"force": true}；只在確定重做不會造成重複資料時才這樣做。

5. 補齊入參、出參與獨立斷言

用 PUT /scenes/{id}/sections/verify、/inputs、/outputs 只改一段，或 PUT /scenes/{id}/contract 以表格形式改入參與出參；每次都會存成新版本。完成後 DELETE /debug/{sid} 結束工作階段，釋放錄製端。

6. 交給 Worker 驗證

POST /agent-api/v1/scenes/order-create/revisions/5/validate
{"inputs": {"customer": "測試客戶", "quantity": 2}, "idempotencyKey": "order-create-v5-1"}
→ 202 {"id": "order-create-20261023-…", "purpose": "validation", "status": "queued", …}

GET /agent-api/v1/runs/order-create-20261023-…
→ {"status": "running", "stage": "automation", …}
→ {"status": "failed", "error": "…", "finished": true, …}
GET /agent-api/v1/runs/order-create-20261023-…/steps

失敗時看 error、/steps 中第一個失敗的步驟，以及（有權限時）/files/screenshot.png；回到調試修正。驗證可以用任何版本，正式執行只用已發布版本。

7. 發布與正式執行

POST /agent-api/v1/scenes/order-create/revisions/5/publish      （需要 scenes:publish）

POST /agent-api/v1/scenes/order-create/runs
{"inputs": {"customer": "王小明", "quantity": 3}, "idempotencyKey": "job-8812"}
→ 202 {"id": "…", "purpose": "execution", "status": "queued", …}
GET /agent-api/v1/runs/…
→ {"status": "passed", "output": {"orderId": "SO-10231"}, …}

只有 status 是 passed 時才有 output。沒有發布權限時，告訴使用者哪個場景的哪個版本已驗證通過，請人在 Portal 發布。

錯誤怎麼處理

狀態碼code意思Agent 該做什麼
401unauthorized金鑰缺少、錯誤、停用或到期停止，請管理員處理；不要重試
403scope_missing這把金鑰沒有需要的權限範圍請人授權或改由人完成這一步
403content_disabled「回傳頁面內容」沒開改用 locate 與步驟結果；或請管理員打開
403domain_forbidden、recorder_forbidden不能用這個領域或錄製端換一個允許的，或請管理員加上
409stale_basebaseRevision 不是最新版，有人改過讀 latest 那一版，把修改套上去再存
409debug_busy這個場景有人正在調試稍後再試，不要搶
409already_executed有副作用的步驟已執行過確定可以重做才帶 force；否則 reset
409recorder_offline錄製端不在線換一台，或請人開啟錄製端 App
409recorder_outdated錄製端 App 太舊（例如不支援讀頁面結構）請人更新 RPA 錄製端
409not_validated這個版本沒有驗證通過的紀錄先驗證
409not_published場景沒有已發布版本，不能正式執行發布，或請人發布
422display_unavailable那台沒有畫面，不能有頭改用 "headless": true
422revision_invalidYAML 校驗失敗，issues 列出位置依 issues 修正後再存
422inputs_invalid入參不符合型別或限制，problems 列出哪一個修正入參
429limit_reached超過同時調試或排隊執行的限額等現有的完成，或結束不用的工作階段

運行本身的結果不是 HTTP 錯誤：failed、timed_out、cancelled、needs_login 都在 GET /runs/{id} 的 status。

需要人的時候

  • 需要登入：運行停在 needs_login，或 GET /roles 顯示角色要重新登入。請使用者在錄製端做人工登入，完成後呼叫 POST /runs/{id}/rerun。
  • 沒有發布權限：告訴使用者場景代號與驗證通過的版本號，請人在 Portal 發布。
  • 缺 Secret：GET /scenes/{id} 的 needs 列出還沒設定的 Secrets；值由人在 Portal 填，Agent 不能寫入也讀不到。
  • 錄製端不在線或太舊：請人開啟或更新 RPA 錄製端 App。

守則

  • 每次存版本都帶上次讀到的 baseRevision，不要覆蓋人的修改。
  • 用完調試工作階段就 DELETE，不要占住錄製端。
  • 不要在正式資料上反覆執行有副作用的步驟；能用測試帳號的角色就用。
  • 截圖、頁面結構與出參可能含業務資料，只用在當前的任務，不要另外保存或轉傳。
  • 所有寫入都會記在稽核紀錄，版本說明會標出你的用戶端名稱；在 note 寫清楚這一版改了什麼。
