CI 與流水線

GitHub Actions 什麼時候跑、跑哪些測試、大約多久；怎麼手動觸發，以及到哪裡看歷次的運行耗時。平常的 PR 只在每個系統上測它在生產環境的角色，其他組合交給每天凌晨的完整測試；同一組輸入只驗證一次，外殼沒變的桌面 App 不重新打包。

依層建置：同一組輸入只驗證一次

2026-10-27 起

ADR 0018 把安裝包拆成外殼（Python、第三方套件、PyInstaller 收進去的一切、rpa_update）與程式碼層（七個工作區套件）。CI 照同一條線拆：

  • 同一組輸入已經通過就不重跑。每個重的工作（三個桌面 App、伺服器分發包、一鍵安裝腳本、CI 的 Windows Worker 測試）有自己的輸入清單；這些檔案的內容算成輸入指紋，同一個指紋已經在這個倉庫通過，就略過、沿用那次的結果。只改伺服器的 PR 不碰 macOS；合併到 main 時內容和 PR 測過的相同，也不再跑一次。
  • 版本號不算改動。pyproject.toml 的 version 與 uv.lock 裡工作區套件的版本不算進指紋：發布 PR 只改版本號，不必重建三個 App、四個安裝腳本與 Windows 測試。
  • 外殼沒變就不重新打包。桌面 App 要跑時，先看外殼鍵：外殼和快取裡的相同，就從快取取出上次建好的 DMG／zip，用這次的程式建更新檔、裝上去再測（程式碼層路徑）。這正是裝置在現場升級的方式：舊外殼加新程式。外殼變了才完整建置。
  • macOS 只在需要時排隊。錄製端（macOS）只在錄製、逐步調試、本機閘道、macOS 專屬的程式或外殼改了時跑；Worker（macOS）只在外殼或它的 macOS 部分改了時跑。一般的程式改動由每晚的 macOS 程式碼層檢查補上，最晚隔天看得到；發布一律完整建置。
推送／PR → 執行範圍（Linux，幾秒；tools/ci_changes.py）：每個重的工作算輸入指紋
  ├─ 這個指紋已經有通過紀錄 → 略過，註記沿用哪一次（macOS 不必排隊）
  └─ 要跑 → 桌面 App 再看外殼鍵在不在快取裡
        ├─ 在 → 程式碼層路徑：取出快取的 DMG／zip → 用這次的程式建更新檔、裝上
        │        → 自我測試、視窗自我測試、端到端（不跑 PyInstaller、不下載瀏覽器）
        └─ 不在 → 完整建置（PyInstaller、DMG、安裝檔、升級與退回）→ 成功後存進快取
發布（v* 標籤）、每週六的完整建置：一律完整建置，不沿用
輸入指紋
一個工作的輸入檔案（路徑與內容）加上工作名稱的 SHA-256 前 16 個字元。清單在 tools/ci_changes.py 的 GROUPS，每個工作都包含依賴（版本號不算）、自己的 workflow 檔與 tools/ci_changes.py 本身。
通過紀錄
工作成功時上傳的小產物 pass-<工作>-<指紋>，保留 30 天。只認這個倉庫自己的運行，fork 的 PR 不能替別人宣告通過。
外殼鍵
外殼的輸入（依賴、.python-version、packages/rpa_update/src、apps/desktop/packaging、tools/build_desktop.py；RPA Worker 另加它附帶的 RPA Python 運行環境：runtimes/python/、tools/build_python_runtime.py）加上目標的雜湊。快取鍵是 desktop-shell-v1-<目標>-<外殼鍵>-<CI 金鑰代號>，內容是 DMG 或 zip、runtime.json 與下載好的瀏覽器。
程式碼層路徑
從快取取出 App（tools/desktop_shell.py restore），用這次的程式建更新檔（tools/build_update.py，CI 金鑰簽章），裝進 App 的資料夾；自我測試、視窗自我測試、端到端都用這一層，跑完確認這一層已經確認、沒有被退回。不建安裝檔，也不上傳試用包。
完整建置路徑
原本的全部步驟，外加「下一個提交」的更新與自動退回。成功時把 DMG 或 zip 存進快取（推版本標籤時不存）。
工作改了這些才跑（另加依賴、workflow 與 ci_changes.py）說明
RPA 錄製端（macOS）外殼；錄製端的程式（recorder_*、本機閘道、互動子程序、配對、debug.py、record.py、commands.py）；兩個 App 共用、有系統分支的程式（入口、自我測試、更新、下載瀏覽器、鑰匙圈）；macos.py；Client API 與裝置更新端點；測試網站與範例；端到端窄的範圍（2026-10-27 決定）：其他程式碼的改動交給 Linux 的 role_recorder 測試、Windows 的程式碼層測試與每晚的 macOS 檢查
RPA Worker（Windows）外殼；它會執行的全部程式碼（rpa_core、rpa_runner、rpa_worker、rpa_desktop 的原始碼、測試網站）；Worker API、Client API、裝置管理與更新端點；範例；建置前的單元測試生產角色：程式碼一改就跑（大多走程式碼層路徑）
RPA Worker（macOS）外殼；選單列、LaunchAgent、鑰匙圈、視窗（macos.py、autostart.py、credentials.py、gui.py）；建置前的單元測試不是生產角色；每晚的 macOS 檢查也跑它
伺服器分發包（x64、arm64）原本的路徑：伺服器、命令列、Worker、測試網站與套件的原始碼、範例、建置工具；RPA Python 運行環境（分發包附帶一份）Linux，約 2 分；在 Rocky 8 另外執行範例 Python 節點
RPA Python 運行環境（Linux x64、arm64、Windows、macOS）runtimes/python/、tools/build_python_runtime.py、rpa_script、rpa_runner、rpa_core 的原始碼與 Python 節點的測試（2026-10-29 起，ADR 0020）每個平台建一份、跑自我測試、解壓到快取，再用它跑 Python 節點的測試；Linux 另在 Rocky 8 容器解壓、自我測試
一鍵安裝腳本（Rocky 8 兩種、三個系統的專案內執行）原本的路徑：腳本、依賴、Python 版本、相關工具與測試排程時照常跑完整範圍
CI 的 Worker 測試（Windows）原本的 Worker 路徑（packages/、apps/worker、apps/cli、apps/testsite、apps/desktop、scenarios/ 等）CI 的 Linux 測試每次照跑

一律執行、不沿用的時候

排程（每晚完整測試、一鍵安裝腳本、每週六的桌面完整建置）、手動觸發、推版本標籤。這些照樣留下通過紀錄（完整範圍涵蓋一般範圍）。通過紀錄過期（30 天）或被「清理產物」刪掉時，同一組輸入再驗證一次。

怎麼用

  • 看這次跑了什麼：每個流程的「執行範圍」工作在運行摘要寫一張表：每個工作的指紋、外殼鍵、執行還是沿用哪一次（連到那次運行）；同樣的內容也寫成註記。桌面端建置每個 App 的摘要第一行寫「程式碼層路徑」或「完整建置」，以及外殼來自哪一版。
  • 要試用包（DMG、安裝檔）：程式碼層路徑不產生新的安裝包。手動觸發桌面端建置，預設就是完整建置：gh workflow run desktop.yml --ref 分支 -f build=full，只要其中一個 App 時加 -f targets=recorder-macos-arm64。
  • 不想沿用、重新驗證一次：手動觸發那個流程（手動觸發一律執行）。
  • 改了 desktop.yml 的建置步驟：把 tools/ci_changes.py 的 SHELL_EPOCH 加 1，快取的外殼全部重建一次。改了指紋的算法或輸入的寫法時，把 EPOCH 加 1，所有通過紀錄失效。
  • 新增檔案：放在已登記的資料夾下就自動算進去。新的 macOS 專屬模組要加到 RECORDER 或 WORKER_MACOS；tests/ci/test_ci_changes.py 會檢查每個模式都還對得到檔案（改名不會悄悄失效），以及桌面 App 的原始碼都在 Windows Worker 的輸入裡。
  • 本機看指紋：python3 tools/ci_changes.py --workflow desktop.yml --show（另有 server-package.yml、setup-scripts.yml、ci.yml、python-runtime.yml）。

程式碼層路徑失敗時

  • 「裝不上更新檔」：簽章或環境代號不符。看「測試更新檔用的金鑰」步驟用的是不是 RPA_UPDATE_CI_KEY，以及 runtime.json 的目標。
  • 「提交不是…」或「active.json 用的是內建的程式」：啟動器沒有用這一層，看 App 資料夾的 app/boot.log。
  • 新程式匯入不到某個第三方模組：這正是裝置升級後會遇到的問題，外殼沒有收進那個模組。把它加進 apps/desktop/packaging/rpa_desktop.spec 的 FULL_PACKAGES 之類的清單：外殼鍵改變，這次完整建置，發布時這一版要用完整的安裝包。

依角色分配測試

短期的主要運行路徑（2026-10-19 確認，見部署與操作）：Linux 只跑網站，macOS 只跑錄製端，Windows 只跑 Worker。三條路徑都用 Python 3.13；一鍵安裝腳本裝的是開發環境，不在主要路徑上。

系統生產角色PR 與合併到 main 時跑什麼只在完整測試跑
Linux網站（管理 Portal）靜態檢查；全部不需瀏覽器的測試；網站、錄製端協定的瀏覽器測試與冒煙測試，只用 Chromium（CI，4 個程序平行）Firefox 的組合；Worker 的瀏覽器測試
WindowsWorkerWorker 的瀏覽器測試（執行、登入、Firefox 範本、領取任務）與冒煙測試，兩種瀏覽器；Worker App 的端到端（外殼沒變時只換程式碼層，見依層建置）網站、錄製端的瀏覽器測試
macOS錄製端錄製端 App 的端到端（配對、本機閘道、逐步調試）：只在錄製、調試、閘道、macOS 專屬的程式或外殼改了時全部 pytest；每晚的 macOS 程式碼層檢查

測試依檔案路徑自動加上 role_server、role_worker、role_recorder，用 Firefox 的參數組合加上 firefox（tools/ci_roles.py、根目錄的 conftest.py）。新增瀏覽器測試的檔案時，在 tools/ci_roles.py 的 ROLES 登記它屬於哪個角色；沒有角色的瀏覽器測試會讓 tests/ci/test_ci_roles.py 失敗。Python 3.12 維持原狀：PR 上只跑不需瀏覽器的測試，合併到 main 時跑全部；跑全部時和每晚完整測試一樣在 xvfb-run 底下，有頭模式的錄影測試才有螢幕（2026-10-28）。

觸發節點與時間

節點跑哪些流程大約多久
往 PR 推送、合併到 mainCI（Linux）每次都跑；其他重的工作只在它的輸入指紋還沒通過時跑（依層建置）：Windows 的 Worker 測試、三個桌面 App（外殼沒變時只換程式碼層）、伺服器分發包（建置 x64、arm64，在 Rocky 8 容器裡安裝、啟動、升級）、一鍵安裝腳本（只驗證腳本與冒煙測試）約 2.5～3 分（CI 是下限）；要建桌面 App 時約 4 分
只改 handoff/、docs/ 的推送見下一節約 1 分
推版本標籤 v*發布：確認版本、建桌面 App 與伺服器分發包、產生並簽署更新檔（金鑰）、草稿 Release約 4 分
每天 20:17 UTC每晚完整測試：三個系統、兩種瀏覽器、Python 3.12 與 3.13 的全部測試，瀏覽器測試連跑三遍約 30 分
每天 20:17 UTC（同上）macOS 程式碼層檢查：每晚完整測試呼叫桌面端建置，兩個 macOS App 走程式碼層路徑（外殼不在快取裡時完整建置）約 3 分
每天 20:47 UTC一鍵安裝腳本的完整範圍：專案內執行跑全部測試，加上從零開始約 15 分
每週六 22:47 UTC桌面 App 每週完整建置：三個 App 完整建置（不用快取、不沿用），抓 GitHub 映像的變化；由每晚完整測試的流程執行，失敗時開在同一個 issue約 5 分
每週日 22:17 UTCPython 依賴更新：有更新時開 PR 並觸發 CI不到 1 分；CI 另計

排程放在倉庫最空閒的時段：20:17 UTC 是 America/Los_Angeles 13:17 PDT（UTC−07:00）／12:17 PST（UTC−08:00），新加坡 04:17。排程失敗時自動開（或更新）一個 ci-schedule 標籤的 issue；一直排不到機器而被取消的工作（註記寫「The job was not acquired by Runner」，macOS 較常見）也算，留言會註明那個系統這次沒有測、不是測試失敗，可以在運行頁按「Re-run failed jobs」補跑（2026-10-29 起；之前這種情況不開 issue，整個運行是紅的卻沒有通知）。PR 上比的是合併後的內容（GitHub 測的是 PR 合併進 main 的結果）；同一個分支推了新版本，舊的運行會被取消。依賴更新的 PR 由 GitHub Actions 開，只自動觸發 CI，其他流程要等有人往那個分支推送。CI 的 Linux 測試與 Windows 的 Worker 測試各最多跑 30 分鐘，卡住時直接失敗（2026-10-21 起；之前沒有上限，Windows 上卡住的運行會一直跑到 GitHub 的 6 小時上限）。

Windows 的每晚完整測試開跑前，把動態連接埠從預設的 49152～65535（16384 個）放大到 10000～65535：連線關閉後還要等 TIME_WAIT 才放回去，連跑三遍時本機網站、管理 Portal 與瀏覽器之間的短連線可能把它用完，Chromium 回報 net::ERR_NO_BUFFER_SPACE（2026-10-27 第 3 遍，issue #99）。測試與產品的固定連接埠（8080 起的管理 Portal、測試網站）都在 10000 以下，不受影響。每一遍結束時另外註記 TCP 連線依狀態的數量與還在跑的 Chromium、Firefox、Node 程序，再遇到時分得出是連接埠用完還是程序沒有結束（2026-10-29 起）。

只改文件的推送

CI 的 Linux 測試：每個流程的第一個工作「執行範圍」（tools/ci_changes.py）比較這次推送和上一次推送，只改了 handoff/、docs/ 或 *.md，而且上一次推送在同一個流程的運行已經通過時，只跑靜態檢查與不需瀏覽器的測試（含文檔與翻譯的檢查），瀏覽器測試沿用那次的結果，註記裡寫明是哪一次。上一次的運行失敗、取消或還沒跑完時照常執行。

其他重的工作不必另外判斷：文件不在任何一個的輸入裡，指紋和上一次相同，自然沿用（依層建置）。協作規則見共用協作流程的第 5 節。

手動觸發

在 GitHub 的 Actions 頁面選流程，按「Run workflow」，選分支與選項。也可以用 gh：

# 大全量：三個系統的全部測試，瀏覽器測試再跑兩遍（約 30 分）
gh workflow run nightly.yml --ref 分支名稱
# 只跑 Windows，不重跑
gh workflow run nightly.yml --ref 分支名稱 -f systems=windows -f extra=0
# CI：role＝同 PR；full＝Linux 跑全部測試
gh workflow run ci.yml --ref 分支名稱 -f scope=full
# 一鍵安裝腳本：full（預設）＝全部測試加從零開始；role＝同 PR
gh workflow run setup-scripts.yml --ref 分支名稱
# 桌面端建置：手動觸發一律執行；預設完整建置（產生試用包）
gh workflow run desktop.yml --ref 分支名稱
# 只建錄製端，外殼在快取裡就只換程式碼層（不產生試用包）
gh workflow run desktop.yml --ref 分支名稱 -f targets=recorder-macos-arm64 -f build=auto
# 伺服器分發包（Linux x64、arm64）
gh workflow run server-package.yml --ref 分支名稱
# RPA Python 運行環境（四個平台建置、自我測試、Python 節點的測試）
gh workflow run python-runtime.yml --ref 分支名稱

本機照角色跑：uv run pytest -m "browser and (role_worker or smoke)"（Worker）、uv run pytest -m "not browser or ((smoke or role_server or role_recorder) and not firefox)"（同 CI 的 Linux）。

產物與儲存額度

倉庫自 2026-10-22 起是私有的，Actions 的產物計入帳號方案的儲存額度；額度用完時上傳產物會失敗，發布也建不出草稿 Release（v0.5.0 就是這樣）。所以桌面端建置與伺服器分發包的產物在 PR 與 main 上留 3 天、發布時留 1 天，發布流程建好草稿後刪掉那次執行的產物；測試報告與 Portal 軌跡只是診斷用，上傳失敗不讓工作失敗。

依層建置另外留下兩種東西：通過紀錄（產物 pass-*，每個不到 1 KB，留 30 天）與外殼快取（Actions 的快取，不計入產物額度；每個倉庫上限 10 GB，7 天沒用到就被清掉，清掉之後下一次完整建置再存）。

要一次釋放額度時，手動執行「清理產物」（cleanup-artifacts.yml）：預設只列出，摘要裡依名稱統計個數與大小；確認後取消勾選「只列出、不刪」再執行一次。刪除不能復原；正式版的檔案在 Releases 上，不受影響；刪掉 pass-* 只會讓那些輸入再驗證一次。刪完要等 GitHub 重新計算用量，額度才會降下來。

# 只列出全部產物
gh workflow run cleanup-artifacts.yml
# 刪掉 3 天以前建立的產物
gh workflow run cleanup-artifacts.yml -f older-than-days=3 -f dry-run=false

更新檔的簽署金鑰

ADR 0018

發布時產生的 RPA-Update-<版本>.zip 用 Ed25519 私鑰簽章；伺服器、裝置與桌面 App 的啟動器用安裝包裡的公鑰驗證，驗證不過就不用。私鑰只放在 GitHub Secrets 的 RPA_UPDATE_SIGNING_KEY，不進倉庫、不貼到對話或 issue；公鑰寫在 packages/rpa_update/src/rpa_update/keys.py 的 RELEASE_KEYS，隨完整的安裝包發布。RELEASE_KEYS 是空的、Secret 沒設、或兩者對不上時，發布流程會失敗，不會發出裝置驗證不了的版本。PR 與 main 上的建置用 CI 的測試金鑰（下面），不碰正式金鑰。

第一次產生

  1. 在一台有 OpenSSL 1.1.1 以上的電腦產生私鑰，並印出公鑰（一行 base64）。用 openssl version 查看版本：CentOS 7 的 1.0.2 與 macOS 內建的 LibreSSL 沒有 Ed25519，會顯示 Algorithm ed25519 not found，請換一台電腦或改用下面專案的工具。
openssl genpkey -algorithm ed25519 -out rpa-update-signing.pem
openssl pkey -in rpa-update-signing.pem -pubout -outform DER | tail -c 32 | base64
  1. 到倉庫的 Settings › Secrets and variables › Actions › New repository secret，名稱填 RPA_UPDATE_SIGNING_KEY，值貼上 rpa-update-signing.pem 的全部內容（含 -----BEGIN PRIVATE KEY----- 與 -----END PRIVATE KEY----- 兩行）。
  2. 把公鑰加進 RELEASE_KEYS，用 PR 合併。公鑰可以公開。
  3. 私鑰檔另外備份到只有自己拿得到的地方（例如密碼管理器），再從那台電腦刪掉。遺失私鑰之後的版本簽不了，裝置要重新安裝帶新公鑰的完整安裝包；外洩時也一樣要換。

也可以用專案的工具產生：uv run python -m rpa_update.build keygen --private rpa-update-signing.pem，印出的就是公鑰；格式和 OpenSSL 相同。

換金鑰

先把新的公鑰加進 RELEASE_KEYS（舊的留著），發一版完整的安裝包；等伺服器與裝置都換上這一版，再把 Secret 換成新的私鑰，最後拿掉舊的公鑰。RELEASE_KEYS 改變會改變環境代號，所以這兩版都要用完整的安裝包安裝。

CI 的測試金鑰（RPA_UPDATE_CI_KEY）

另一把 Ed25519 私鑰，只給 CI 測試用。PR、main 與排程建的桌面 App（試用包）信任它；發布的安裝包不信任（發布流程的 --release 會核對）。程式碼層路徑要用它：快取裡的外殼是之前建的，它信任的金鑰在之後的運行也要拿得到，才簽得出它認得的更新檔。沒有這個 Secret 時，桌面端建置照舊每次產生臨時金鑰、一律完整建置，「測試更新檔用的金鑰」步驟會留下警告。fork 與 Dependabot 的 PR 拿不到 Secrets，也是這樣。

查有沒有設定：倉庫的 Settings › Secrets and variables › Actions，Repository secrets 列表裡有沒有 RPA_UPDATE_CI_KEY（只看得到名稱與更新時間，值看不到）；或在有權限的電腦執行 gh secret list。設定之後跑一次桌面端建置，「測試更新檔用的金鑰」步驟的註記寫「測試更新檔的金鑰 <代號>（RPA_UPDATE_CI_KEY）」就是讀到了。

產生並設定（和發布金鑰不同，不要共用；公鑰不必寫進倉庫）：

uv run python -m rpa_update.build keygen --private rpa-update-ci.pem
gh secret set RPA_UPDATE_CI_KEY < rpa-update-ci.pem   # 或貼到網頁上的 New repository secret
rm rpa-update-ci.pem

換這把金鑰不必通知任何人：換掉 Secret 之後，快取鍵裡的金鑰代號不同，第一次建置會完整建置並存一份新的快取。外洩時影響的只有 CI 的試用包（拿到私鑰的人簽得出試用包接受的更新檔），正式安裝包不受影響；重新產生、換掉 Secret 即可。

運行耗時紀錄

每次 CI、桌面端建置、伺服器分發包、一鍵安裝腳本、每晚完整測試、發布結束後，「運行耗時紀錄」流程（tools/ci_metrics.py）把結果追加到倉庫的 ci-metrics 分支，不碰 main，也不觸發其他流程。在 GitHub 切到 ci-metrics 分支就看得到總覽 README.md：各流程近 7 天與前 7 天的比較、每天各系統的機器時間、最慢的測試檔案、最近的運行。

data/runs.jsonl
每次運行（重跑各一行）：觸發方式、分支、結果、耗時（含排隊）、最長排隊、各系統的機器時間
data/jobs.jsonl
每個工作的排隊與執行時間
data/test-files.jsonl
CI 與每晚完整測試的 JUnit 報告裡，每個測試檔案的時間

補記歷史：手動觸發「運行耗時紀錄」，since 填 UTC 日期，例如 2026-10-09；已經記過的不會重複。每次測試的 annotations 也有一則「pytest 耗時」，列出最慢的檔案與測試。
