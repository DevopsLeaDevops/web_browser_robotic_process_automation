CI 與流水線

GitHub Actions 什麼時候跑、跑哪些測試、大約多久；怎麼手動觸發，以及到哪裡看歷次的運行耗時。平常的 PR 只在每個系統上測它在生產環境的角色，其他組合交給每天凌晨的完整測試。

依角色分配測試

短期的主要運行路徑（2026-10-19 確認，見部署與操作）：Linux 只跑網站，macOS 只跑錄製端，Windows 只跑 Worker。三條路徑都用 Python 3.13；一鍵安裝腳本裝的是開發環境，不在主要路徑上。

系統生產角色PR 與合併到 main 時跑什麼只在完整測試跑
Linux網站（管理 Portal）靜態檢查；全部不需瀏覽器的測試；網站、錄製端協定的瀏覽器測試與冒煙測試，只用 Chromium（CI，4 個程序平行）Firefox 的組合；Worker 的瀏覽器測試
WindowsWorkerWorker 的瀏覽器測試（執行、登入、Firefox 範本、領取任務）與冒煙測試，兩種瀏覽器；Worker App 的打包、安裝與端到端網站、錄製端的瀏覽器測試
macOS錄製端錄製端 App 的打包與端到端（配對、本機閘道、逐步調試）全部 pytest

測試依檔案路徑自動加上 role_server、role_worker、role_recorder，用 Firefox 的參數組合加上 firefox（tools/ci_roles.py、根目錄的 conftest.py）。新增瀏覽器測試的檔案時，在 tools/ci_roles.py 的 ROLES 登記它屬於哪個角色；沒有角色的瀏覽器測試會讓 tests/ci/test_ci_roles.py 失敗。Python 3.12 維持原狀：PR 上只跑不需瀏覽器的測試，合併到 main 時跑全部。

觸發節點與時間

節點跑哪些流程大約多久
往 PR 推送、合併到 mainCI（Linux）每次都跑；整個 PR 改到 Worker 的路徑時加跑 Windows 的 Worker 測試；改到 apps/、packages/ 時加跑桌面端建置；改到伺服器用到的套件或依賴時加跑伺服器分發包（建置 x64、arm64，在 Rocky 8 容器裡安裝、啟動、升級）；改到腳本或依賴時加跑一鍵安裝腳本（只驗證腳本與冒煙測試）約 4 分（桌面端建置是下限）；不觸發桌面端建置時約 2.5 分
只改 handoff/、docs/ 的推送見下一節約 1 分
推版本標籤 v*發布：確認版本、建兩個桌面 App、草稿 Release約 4 分
每天 20:17 UTC每晚完整測試：三個系統、兩種瀏覽器、Python 3.12 與 3.13 的全部測試，瀏覽器測試連跑三遍約 30 分
每天 20:47 UTC一鍵安裝腳本的完整範圍：專案內執行跑全部測試，加上從零開始約 15 分
每週日 22:17 UTCPython 依賴更新：有更新時開 PR 並觸發 CI不到 1 分；CI 另計

排程放在倉庫最空閒的時段：20:17 UTC 是 America/Los_Angeles 13:17 PDT（UTC−07:00）／12:17 PST（UTC−08:00），新加坡 04:17。排程失敗時自動開（或更新）一個 ci-schedule 標籤的 issue。PR 上的路徑條件看的是整個 PR 的改動；同一個分支推了新版本，舊的運行會被取消。依賴更新的 PR 由 GitHub Actions 開，只自動觸發 CI，其他流程要等有人往那個分支推送。CI 的 Linux 測試與 Windows 的 Worker 測試各最多跑 30 分鐘，卡住時直接失敗（2026-10-21 起；之前沒有上限，Windows 上卡住的運行會一直跑到 GitHub 的 6 小時上限）。

只改文件的推送

每個流程的第一個工作「執行範圍」（tools/ci_changes.py）比較這次推送和上一次推送：只改了 handoff/、docs/ 或 *.md，而且上一次推送在同一個流程的運行已經通過時，程式與上一次相同，重的工作改為略過、沿用那次的結果，註記裡寫明是哪一次。CI 仍跑靜態檢查與不需瀏覽器的測試（含文檔與翻譯的檢查）。上一次的運行失敗、取消或還沒跑完時照常執行。協作規則見共用協作流程的第 5 節。

手動觸發

在 GitHub 的 Actions 頁面選流程，按「Run workflow」，選分支與選項。也可以用 gh：

# 大全量：三個系統的全部測試，瀏覽器測試再跑兩遍（約 30 分）
gh workflow run nightly.yml --ref 分支名稱
# 只跑 Windows，不重跑
gh workflow run nightly.yml --ref 分支名稱 -f systems=windows -f extra=0
# CI：role＝同 PR；full＝Linux 跑全部測試
gh workflow run ci.yml --ref 分支名稱 -f scope=full
# 一鍵安裝腳本：full（預設）＝全部測試加從零開始；role＝同 PR
gh workflow run setup-scripts.yml --ref 分支名稱
# 桌面端建置
gh workflow run desktop.yml --ref 分支名稱
# 伺服器分發包（Linux x64、arm64）
gh workflow run server-package.yml --ref 分支名稱

本機照角色跑：uv run pytest -m "browser and (role_worker or smoke)"（Worker）、uv run pytest -m "not browser or ((smoke or role_server or role_recorder) and not firefox)"（同 CI 的 Linux）。

產物與儲存額度

倉庫自 2026-10-22 起是私有的，Actions 的產物計入帳號方案的儲存額度；額度用完時上傳產物會失敗，發布也建不出草稿 Release（v0.5.0 就是這樣）。所以桌面端建置與伺服器分發包的產物在 PR 與 main 上留 3 天、發布時留 1 天，發布流程建好草稿後刪掉那次執行的產物；測試報告與 Portal 軌跡只是診斷用，上傳失敗不讓工作失敗。

要一次釋放額度時，手動執行「清理產物」（cleanup-artifacts.yml）：預設只列出，摘要裡依名稱統計個數與大小；確認後取消勾選「只列出、不刪」再執行一次。刪除不能復原；正式版的檔案在 Releases 上，不受影響。刪完要等 GitHub 重新計算用量，額度才會降下來。

# 只列出全部產物
gh workflow run cleanup-artifacts.yml
# 刪掉 3 天以前建立的產物
gh workflow run cleanup-artifacts.yml -f older-than-days=3 -f dry-run=false

運行耗時紀錄

每次 CI、桌面端建置、伺服器分發包、一鍵安裝腳本、每晚完整測試、發布結束後，「運行耗時紀錄」流程（tools/ci_metrics.py）把結果追加到倉庫的 ci-metrics 分支，不碰 main，也不觸發其他流程。在 GitHub 切到 ci-metrics 分支就看得到總覽 README.md：各流程近 7 天與前 7 天的比較、每天各系統的機器時間、最慢的測試檔案、最近的運行。

data/runs.jsonl
每次運行（重跑各一行）：觸發方式、分支、結果、耗時（含排隊）、最長排隊、各系統的機器時間
data/jobs.jsonl
每個工作的排隊與執行時間
data/test-files.jsonl
CI 與每晚完整測試的 JUnit 報告裡，每個測試檔案的時間

補記歷史：手動觸發「運行耗時紀錄」，since 填 UTC 日期，例如 2026-10-09；已經記過的不會重複。每次測試的 annotations 也有一則「pytest 耗時」，列出最慢的檔案與測試。
