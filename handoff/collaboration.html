Claude 與 ChatGPT 共用協作流程

2026-10-14 建立。Claude、ChatGPT／Codex 與使用者共同維護同一個倉庫，讓任何一方取得分支後，都能知道目的、進度、證據與下一步。本頁是現行協作流程的唯一維護位置；入口為根目錄 AGENTS.md 與 CLAUDE.md。

同一任務可接力，獨立任務可並行

1. 資訊保存與判斷依據

資訊維護位置使用方式
需求與授權使用者當前指示；任務紀錄的需求摘要與決定遵循當前指示及仍有效的授權。引用日期、可取得的來源或明確標示「使用者於本次對話要求」。分清已確認、實作選擇、建議與待定；不把推測升格為決定。
協作與工程規範本頁；開發規範、文檔規則本頁管理多人協作，工程細則仍由原文維護。使用者明確的新要求優先；記錄差異，不默默改寫既有約定。
目前實作與外部狀態指定 SHA 的程式碼、PR、CI記錄查證時間與版本。文件和程式碼衝突時分開陳述「預期行為」與「實際行為」，再修正對應缺陷。
任務與接力任務索引、handoff/tasks/<日期>-<主題>.html、對應 PR一個任務一份紀錄；活躍分支上的紀錄可能尚未進 main。索引是快照，開始前仍須查看已知分支與開啟的 PR。
架構與產品決策相關 ADR、決定紀錄、正式設計頁重要決策先更新這些文件，任務紀錄只放摘要與連結；M5 模型及資料去向仍待使用者決定。
歷史原文materials、先前操作歷史保留原文與日期。新快照放新目錄，日誌追加更正，不覆蓋舊紀錄。Claude／ChatGPT 的私人記憶不能是唯一來源。

新的時間紀錄一律標明 Asia/Shanghai（UTC+08:00）；引用 GitHub UTC 或舊太平洋時間時保留時區。歷史日期不自行改寫。不要把憑證、登入狀態、業務資料或私人對話全文放入倉庫。

2. 開工：先確認接的是哪一份工作

  1. 讀 AGENTS.md、本頁、總入口與相關任務紀錄。只讀查詢不建任務卡；實作、流程修改與跨會話接力才建立。
  2. 檢查工作目錄、分支、未提交差異與 worktree。看到其他人的修改先辨識歸屬並保留，不直接 reset、clean、覆蓋或自動 stash 他人的工作。
  3. 可連線時 fetch，查看本任務 PR 的 base／head、CI、審閱與其他活躍任務。無法讀取的寫「未知」，不把本機舊的遠端追蹤分支當成最新狀態。
  4. 已有任務就核對交接提交並接續；新任務從最新 origin/main 建立分支。只有工作區乾淨且確認不在其他人使用的 checkout 時才切換分支。
  5. 用範本建立紀錄，寫需求、範圍、驗收條件、主責、檔案責任範圍、分支、起點 SHA、相依任務與第一個動作；在本分支的任務索引加連結。
  6. 簡述理解、採用的常規選項及驗證方式後開始工作。已授權的步驟不中途重問；缺少必要產品決定時，只暫停依賴該決定的部分，繼續獨立工作。
git status --short --branch
git log -5 --oneline
git worktree list
git fetch origin
git rev-parse HEAD
git log --oneline --left-right HEAD...origin/main

最後一行用於了解差異，不代表可以重置分支。離線或權限不足時記錄原因；只讀、設計整理及不相依的本地工作仍可進行。

3. 責任範圍與並行協作

  • 同一任務只有一位當前實作者。主責可為 Claude、ChatGPT／Codex 或使用者；另一方可以審閱。變更主責必須有明確交接；任務卡不是自動鎖，長時間沒有更新也不代表可以接管。
  • 並行任務用不同分支和 checkout／worktree。先約定各自修改的檔案。不同工作區避免覆蓋檔案，仍須處理共同 API／模型的整合；同一個 checkout 不同時切分支、rebase、commit 或執行會寫入的格式工具。
  • 共用檔案由一位整合者處理。資料庫遷移編號、uv.lock、多語言目錄、導航、任務索引與本流程容易衝突。任務卡列出整合者與合併順序；其他任務先記需求，合併後從最新 main 接續。遷移在整合前重新確認編號與 down_revision，不重寫已發布的遷移。
  • 執行環境也分開。並行測試用各自的測試資料目錄、連接埠和 worker；不讓兩個 Portal 存取同一份 SQLite，不使用使用者的正式資料做破壞性驗證。
  • 遠端協調以既有任務 PR／Issue 或使用者的明確分工為準。在授權範圍內公布主責、分支與檔案範圍；只有本機紀錄時標示尚未同步。若無法確認另一方是否在寫入，先做只讀分析或獨立範圍，不擅自接管。
  • 不要求每個任務都啟動第二個 AI。由使用者安排跨工具協作；審閱可以在後續會話接力完成。

4. Git、PR 與整合

  1. 沿用 m*/主題、fix/主題、docs/主題、chore/主題，名稱描述工作而非模型。同一任務換人時沿用原分支／PR；已合併後的新修正另開分支。
  2. 提交採 Conventional Commits，使用目前工具的真實署名，不冒用另一個模型。每個可獨立審閱的修改形成清楚的提交；提交前看 diff，明確選取檔案，不混入他人工作。
  3. 推送、開 PR、更新 GitHub 依使用者已給的授權辦理；同一任務已有授權不反覆確認。若確實缺少必要授權，先完成本地修改、檢查及 PR 草稿內容，再說明要核准的具體動作。文件本身不代表已獲授權。
  4. 現行持續授權（2026-10-14 UTC+08:00）：使用者在 DAG 交付對話明確要求「生成 PR，後續大的改動可以直接生成 PR」，並要求檢查 GitHub 流水線。Claude 與 ChatGPT／Codex 後續大的改動完成實作及本地檢查後，可直接推送功能分支、建立或更新本任務 PR 並確認最新 head 的 CI，不再逐次詢問。此授權不包含合併；合併仍由使用者決定。來源及本次交付見任務追加紀錄。
  5. PR 預設對 main，用共用 PR 範本連結任務卡，交代結果、驗證、缺口與相依關係。若刻意堆疊 PR，明列父 PR、舊 base SHA 與預定整合順序；合併前重新確認 base，避免重演 #21。
  6. bootstrap 也是分支寫入者。使用 [bootstrap] 後，等機器人完成，fetch 並檢查新增提交；無本地分叉時用 git pull --ff-only。若有分叉，保留兩邊後整合，不為了推送成功覆蓋機器人的產物。機器人有提交不等於檢查通過；確認最新 head 的 CI 已觸發。
  7. rebase 只在確認寫入權後進行。記錄舊 head／base、fetch 後的遠端 head，保留可恢復的引用；檢查 diff 或 range-diff 並重跑受影響的檢查。只有預期不改內容的 rebase 才要求 tree diff 為空。需要重寫遠端時使用綁定已核對遠端 SHA 的 --force-with-lease，不使用一般 --force。
  8. 遇到未預期的遠端強制更新，先查明作者與目的並比較兩邊工作；不自動 reset。已交出寫入權的一方只能讀取，直到再次接手。
  9. 審閱記錄對應 SHA、發現與處理結果。另一個 AI 的 review 可以補充檢查，但不代替使用者的合併決定；依既有規範 CI 全綠、有人 review 後，由使用者 squash 合併，除非另有明確授權。
  10. 合併後核對實際 merge SHA，保留任務紀錄並補上主線結果。索引或任務卡尚未回填時，以 GitHub 為準，下一個維護者同步更正。確認分支沒有後續獨有提交、沒有人使用，且在授權範圍內才清理分支。

5. 驗證與交付門檻

環境準備沿用 uv sync --locked。各環境自行確認工具、依賴與瀏覽器是否可用；舊 Claude 容器的離線替代做法、stub 錯誤與跳過測試，不能直接視為本次通過。

變更本地驗證仍需交代
流程／文字／文檔git diff --check；HTML 相對連結與錨點檢查；正式文檔變更跑 uv run pytest -q tests/docs tests/i18n，翻譯 stamp／sync／check人工閱讀順序；無法驗證的連結。tests/docs 目前只覆蓋 docs/，handoff/ 要另外檢查。不為純文字修改重跑全部瀏覽器測試。
程式行為Ruff、格式、Pyright strict、相關 pytest、i18n check；修 bug 先有重現證據／適當回歸測試正常與失敗路徑、相容性；涉及 Runner／Portal／worker 時補對應真實瀏覽器流程
資料庫／安裝／跨平台模型與遷移比對；安裝腳本及相關平台測試資料保留與恢復方式；一般 PowerShell 與受限語言模式分開記；CI 虛擬機與真實兩機測試分開記
 
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest -m "not browser"
uv run python tools/i18n.py check

以上是程式變更的基本檢查；CI 仍執行其設定中的完整矩陣。紀錄包含被測 SHA、命令、環境、結果與證據。未提交時寫「基準 SHA＋目前工作區差異」及檔案範圍；提交後在 PR 或追加紀錄連結對應版本，不用為了把自己的提交 SHA 寫進同一提交而反覆 amend。

只改驗證紀錄文字可以保留原證據並註明後續變更範圍；改動行為、生成檔或解衝突後重跑受影響檢查。CI 綁定最終 PR head；通過、失敗、跳過、取消、未執行各自記錄。環境缺失只能標「未執行／受阻」，不能報成通過。

「實作完成」「已合併」「自動測試通過」「人工驗收通過」是四個不同狀態。所有必要驗收通過才將任務標記完成；若拆出後續任務，必須明列範圍及使用者已接受的調整。

6. 交出與接收：以可取得的版本為準

  1. 交出方更新任務卡。寫清已做、未做、決定、驗證、失敗、下一個具體動作，並列出分支／PR、交接 SHA、未提交檔案、stash、ignored 產物與取得方式。工作日誌只追加；無法回復的舊記錄標明缺失。
  2. 先讓成果可取得。依授權提交並推送到任務分支，附上可讀取的連結；或在使用者指定的共享 checkout 交接本地差異。跨機器尚未推送時明寫「本地準備完成、尚未交付」，不可聲稱另一方已收到。不假設對方可讀取私人聊天。
  3. 交出後停止寫入。任務卡標「待接收」與接收方；同一分支後續修改要先重新約定。若尚無指定接收方，可標「可接續」，不得虛構對方確認。
  4. 接收方驗證再續做。fetch，核對指定 SHA 與工作區，閱讀任務卡及相關 diff；按影響執行最小可重現檢查。記錄「誰、何時、收到哪個 SHA、檢查結果、接受的範圍」。已確認交棒後才成為新實作者；若對不上，先記差異並保留現狀。
  5. 中斷也留下下一步。快到用量限制或會話結束前先保存進度。接收流程未完成就保留「待接收」，不要標為已完成或自行假設驗收通過。

每次給使用者的交付摘要包含：任務、分支／PR／提交、完成結果、驗證及缺口、下一步。審閱者的建議不自動成為已接受產品決定；需要變更範圍時回到同一任務紀錄。
