進度、決定與下一步

  • 原因（Claude 分析，沒有 Mac 可以重現，屬於推測）：
    • Playwright 替 Chromium 加了關掉背景節流的參數（例如 --disable-backgrounding-occluded-windows、--disable-renderer-backgrounding），Firefox 沒有對應的設定（查過 Playwright 的 browser_patches/firefox/preferences）。
    • macOS 上 Firefox 不是最前面的 App 時（錄製端 App 在前面），Firefox 會調低主執行緒與分頁程序的優先權（背景 QoS）；CPU 忙時剛開的分頁可能一直停在載入中，切到 Firefox 才恢復。Firefox 自己的自動化（Marionette、WebDriver BiDi）因此關掉 threads.lower_mainthread_priority_in_background.enabled、dom.ipc.processPriorityManager.enabled（Mozilla bug 1960734；Firefox 的 remote/shared/RecommendedPreferences.sys.mjs）。
    • 另一條可能的路：Playwright 的 Firefox 模擬固定視窗大小時，會調整視窗並等頁面尺寸完全相符（Juggler 的 updateViewportSize → awaitViewportDimensions），視窗在背景時可能等不到（同類問題：Playwright #43028，Firefox r1555 的尺寸出現小數）。
  • 決定（實作選擇）：每次啟動 Firefox 都加上 threads.lower_mainthread_priority_in_background.enabled=false、dom.ipc.processPriorityManager.enabled=false、widget.windows.window_occlusion_tracking.enabled=false（和 Firefox 自動化建議的設定相同；Windows 的有頭執行也受益）；人工登入的視窗不模擬固定大小（no_viewport，視窗用自己的大小，使用者也能拉大）。
  • 已完成：FIREFOX_PREFS 在 launch 與預熱設定檔的持久化 context 都加上；open_context(no_viewport=…)；capture 使用它。測試：test_contexts.py（假的 Playwright，不需瀏覽器）；test_login.py 的兩個 capture 測試改成 Chromium、Firefox 各跑一次（Firefox 在 CI，也證明這些偏好設定被 Firefox 接受）。
  • 未完成／阻礙：審閱、合併；人工驗收要更新後的 Mac 錄製端。
  • 下一個具體動作：使用者審閱並合併 #51；更新 Mac 錄製端後，App 留在最前面，多按幾次「登入」確認 Firefox 不再停住。
