分析：時間花在哪裡

  • CI 隨瀏覽器測試線性增長：每日成功執行的中位數從 10-09 的 0.7 分鐘到 10-19 的 9.6 分鐘。main 上瀏覽器測試函數從 15 個到 38 個時 CI 從 2.9 分鐘到 8.7 分鐘；10-18 一次加了 115 個不需瀏覽器的測試只多約 6 秒。bootstrap 的「檢查」（ruff、pyright 加上全部不需瀏覽器的測試）共 129 秒（run 39255728554），所以 pytest 的約 9 分鐘（run 39261604128）大部分是瀏覽器測試。
  • 全部逐一執行：沒有平行化；每個瀏覽器測試都啟動新的子程序與瀏覽器，Portal 測試另外啟動 uvicorn 與一個 Chromium。ubuntu-latest 有 4 核，只用了 1 核。
  • 一鍵安裝腳本每次跑全部測試 9 遍：腳本最後一步就是完整 pytest；專案內執行兩次、從零開始一次、三個系統。run 39261604093（2026-10-19 06:36 America/Los_Angeles（PDT，UTC−07:00）開始）：「再執行一次（應該很快）」Windows 11.8 分、macOS 11.0 分、Ubuntu 8.9 分；整個流程 40.0 分鐘。
  • macOS 並行名額：GitHub 每個帳號最多 5 個 macOS 工作同時執行。一鍵安裝腳本佔 2 個、桌面端建置佔 1 個，PR 重疊時排隊；上面那次 macOS 工作排隊 13.6 分鐘。
  • 2026-10-19 08:39 America/Los_Angeles（PDT，UTC−07:00）起的排隊：只有 3、4 個工作在執行，Ubuntu 工作也排隊超過 23 分鐘，main 的測試跑了 30 分鐘以上；倉庫設定解釋不了，看起來是 GitHub 端的延遲，未查到公開事故，記為未知。09:51 推送本分支時已恢復。
  • GitHub 的 macOS arm64 容量不足（目前排隊的主因）：macos-latest 的工作 15 分鐘內沒有分配到機器就被取消，註記為「The job was not acquired by Runner of type hosted even after multiple attempts」，並附 macOS arm64 容量受限的通知。本 PR 的 3 個 macOS 工作與重新執行都是這樣；#44 的 run 39263598303（08:05 開始）也一樣。其他公開倉庫自 2026-10-08 起回報相同情況。同時段 macos-14 的桌面端建置都在 0.1 分鐘內開始。倉庫設定改不了 GitHub 的容量，只能減少 PR 上的 macOS 工作數（待使用者決定，見下）。
