原因

  • 證據：每晚完整測試 run 40399471079 的「完整測試（windows-latest，Python 3.13）」與一鍵安裝腳本 run 40402544121 的「專案內執行（windows-latest）」，annotations 都列出這兩項；10-24、10-25 的排程沒有，10-26 合併 PR #83（ADR 0018 分層更新）後才出現。
  • test_update_file_rejects_changed_content：測試用 write_text("VALUE = 1\n") 產生來源檔，Windows 以文字模式寫成 CRLF（11 bytes）；替換的內容是 b"VALUE = 2\n"（10 bytes）。測試要驗證的是「大小相同、讀內容才發現不同」，但大小已經不同，UpdateFile() 建構時就在 manifest.py 的大小檢查丟出 file_mismatch，不在預期的 pytest.raises 裡。在 Linux 上把 write_text 改成 CRLF 可重現同一錯誤。
  • test_update_file_extracts_verified_tree：最後檢查解開的 server/bin/rpa 有可執行位元。write_update 依來源檔的 st_mode 記錄 0o755／0o644，Windows 上 chmod(0o755) 只能切換唯讀，沒有副檔名的檔案也不會回報可執行位元，所以來源和解開後都是 0o100666。
  • 影響：正式更新檔由 Linux 的發布流程建置；server/ 只在 Linux 伺服器上解開，桌面 App 在 Windows 只解開 app/。這兩項是測試的平台假設，不是 rpa_update 的缺陷。
  • 為什麼 PR 上沒抓到：PR 上的 CI 依生產角色分配，packages/rpa_update 的完整測試只在 Linux 跑；Windows 的全部測試只在每晚與一鍵安裝腳本的排程跑（docs/develop/ci.html）。

進度、決定與下一步

  • 已完成：分析與在 Linux 上重現換行的失敗。_tree() 與 test_verify_tree_rejects_extra_changed_and_missing 改用 write_bytes；test_update_file_extracts_verified_tree 改成比對解開後的內容，可執行位元移到新的 test_update_file_keeps_executable_bit（Windows 略過，另外確認 app/ 的檔案沒有被設成可執行）。
