1. 使用者的需求（2026-10-19 04:47 PDT）

  1. 領域各自一個資料夾：不同領域掛不同的資料夾（例如 testsite → 測試網站的資料夾、scm_purchase → 採購系統的資料夾），每個資料夾可以單獨載入、執行、調試。
  2. 組合場景有自己的資料檔，可以跨領域組合；啟動或拉取時校驗跨領域的資料依賴，不完整就提示補全。
  3. 組合場景的資料規範和領域場景一致；workflow 的 JSON 定義與執行紀錄存成檔案；資料庫只放其他中繼資料。
  4. 程式碼和資料分開；資料可以放在第三方 git 倉庫，按領域、按組合場景分別拉取資料夾，在「領域管理」設定（倉庫、目錄、使用者名稱、密碼）；拉取後熱載入、初始化場景與組合場景；手動「同步」把本機資料推送到 git。
  5. 常見用法：調試完一個資料夾就推送到遠端，遠端還沒有這個目錄也要能推送（自動新增）。
  6. 另外要一份 MVP 存放方案：資料分別放在伺服器、錄製端、worker 的哪裡。
  7. （06:05 PDT 補充）營運方式是分散式的多人協作：分散在各處錄製、多人驗證後發布、再分散在各處使用，所以發布狀態要記錄並同步；執行紀錄的回看是重要的後續設計，現在要預留方案。

3. 設計總覽

  • 領域資料夾（資料包）：一個領域一個資料夾，裡面放這個領域的全部定義——場景與版本、角色、組合場景，以及驗證與發布紀錄。資料夾自己就能載入（不需要其他領域），也是 git 推送與拉取的單位。
  • 組合場景資料夾就是一個只放組合場景的領域：格式、設定、同步方式完全一樣，只是沒有 scenes/；跨領域時在說明檔記下依賴哪些領域（D1）。
  • 檔案是定義與共享的狀態，資料庫是索引與本機狀態：會跟著 git 走的（定義、驗證紀錄、發布）都在資料夾；資料庫放這台伺服器自己的狀態（執行索引、網址覆寫、同步狀態、裝置），以及可以從資料夾重建的索引。
  • 分散式協作：甲在自己的伺服器錄製、推送；乙拉取後驗證，驗證紀錄推送回去；丙依驗證紀錄發布、推送；丁拉取後執行已發布的版本。每台伺服器都是完整的 Portal，透過同一個 git 目錄交換資料（第 8 節）。
  • 只有伺服器碰 git：錄製端和 worker 維持無狀態，不複製倉庫、不拿 git 憑證。
  • 兩層資料夾：正在使用的領域資料夾 domains/<領域>/ 和同步用的 git 工作副本 git/repos/<領域>/ 分開。拉取先在工作副本合併、校驗，通過才套用到正在使用的資料夾；推送時把正在使用的資料夾複製到工作副本的「目錄」再提交。失敗的 git 操作不會留下半套資料，沒設 git 的領域也能隨時接上遠端。

  pack.yaml                         領域說明檔（必須有）

by: 甲

  - { domain: scm_purchase, scene: po-create, revision: 5, hash: 77d0… }

規則

  • 版本不可變：存檔永遠是新的 revisions/<n>/。版本說明檔放在版本目錄旁邊（<n>.yaml），不放進版本目錄，所以版本內容與雜湊和現在完全一樣，遷移後發布門檻與舊的執行紀錄仍然對得上。
  • 紀錄只新增：驗證紀錄一次執行一個檔案，檔名是執行編號；不同伺服器同時驗證不會改到同一個檔案，git 不會衝突。
  • 組合場景和場景一樣有版本、驗證、發布：每次存檔一個新版本（現在的 version 就是存檔次數）；代號改成和場景一樣的英數代號（D2）。
  • 代號全域唯一：場景、角色、組合場景的代號在所有已載入的領域之間不能重複（現在的資料庫已經是這樣；不改 DSL）。重複時後載入的那一個不載入，列在領域的「載入問題」裡（D8）。
  • 資料夾裡沒有機密與業務資料：不放登入狀態、Secrets 的值、執行的入參與出參值、截圖、錄製稿。推送前另有檢查（第 10 節）。
  • 人可以直接讀：YAML／JSON、固定排序與縮排，在 GitHub 上看得懂、diff 乾淨。時間一律帶 UTC 偏移。

6. 載入與熱載入

  • 什麼時候載入：伺服器啟動時載入全部領域；拉取成功後、按「重新載入」時載入那一個領域；Portal 自己存檔、驗證、發布時只更新改到的項目。不需要重新啟動。MVP 不監看資料夾變化，在資料夾外面手動改了檔案要按「重新載入」（D10）。
  • 怎麼載入：掃描資料夾 → 逐項校驗（DSL、組合場景定義、雜湊、代號重複、驗證與發布紀錄）→ 一個交易更新索引 → 重新計算所有組合場景的依賴狀態。單一項目有問題只略過那一項並列出；pack.yaml 不見或代號和領域不同時，整個領域保持上一次的索引並顯示錯誤。
  • 版本內容和版本說明檔的雜湊不同（有人改了已存在的版本）：那個版本不能執行、不能發布，列為載入問題；它如果是已發布的版本，提示「發布的版本內容被改過」。
  • 發布紀錄不成立（發布的版本沒有雜湊相符的通過驗證紀錄）：這台伺服器不把它當成已發布，列為載入問題（第 8 節）。
  • 來源缺失：資料夾裡沒有了的場景或版本標為來源缺失：清單隱藏、不能執行，執行紀錄照樣保留。
  • 正在執行的任務不受影響：遠端 worker 的任務在領取時就帶走版本檔案；本機執行也改成開始時把版本檔案複製到執行目錄（和遠端一致）。套用拉取結果時逐檔新增、修改、刪除，不整個資料夾換掉，Windows 上開著的檔案也不會擋住。
  • 可以單獨載入：每個領域資料夾自給自足。新伺服器只設定 testsite 一個領域，拉取後就能錄製、調試、執行 testsite 的場景；另外提供 rpa pack check <資料夾>，不開 Portal 也能校驗一個資料夾（可以放在資料倉庫的 CI）。

7. 跨領域依賴的校驗

依賴是「組合場景的版本釘住的場景版本」與「場景用到的角色、Secrets、登入狀態」。組合場景每次存檔時由定義產生 requires（領域、場景、版本、雜湊），pack.yaml 彙總依賴哪些領域。

什麼時候校驗：伺服器啟動、任何一個領域拉取或重新載入之後（重算依賴它的組合場景）、組合場景存檔時、開始執行前、推送組合場景所在的領域前。只校驗每個組合場景的最新版本與已發布版本，舊版本不擋。

發現的問題等級提示怎麼補全
依賴的領域沒有設定（例如需要 scm_purchase）不能執行「新增領域 scm_purchase」，用 pack.yaml 的 source 預填倉庫與目錄
領域有設定，但還沒拉取或拉取失敗不能執行「拉取 scm_purchase」，並顯示上次的錯誤
領域裡沒有這個場景不能執行「拉取最新」；仍然沒有時提示「對方可能還沒推送或已刪除」
需要第 5 版，領域目前只到第 4 版不能執行「拉取最新」，或在組合場景把節點改用現有的版本後存成新版本
版本存在，但雜湊和組合場景存檔時不同不能執行提示版本內容被改過；重新選擇版本並存檔
場景用到的角色沒有定義不能執行指出應該由哪個領域提供角色；拉取或補上角色定義
角色沒有登入狀態提醒「登入」（人工登入或設定自動登入）；執行時會停在需要登入
Secrets 沒有值提醒列出名稱，連到 Secrets 頁
推送前：依賴的版本只在本機、還沒推送到它的領域推送前提醒「一起推送 testsite」或取消；不然別人拉取後依賴不完整

組合場景清單與畫布上方顯示「依賴完整／有提醒／不完整」，展開就是上表的清單與按鈕；領域管理頁顯示每個領域被哪些組合場景依賴。

8. 驗證與發布紀錄（D3，使用者 06:05 PDT：發布狀態要記錄）

使用者的營運方式是分散式的多人協作：分散在各處錄製，多人驗證後發布，再分散在各處使用。所以驗證與發布都寫進領域資料夾、跟著 git 同步；門檻的依據從「這台伺服器的驗證執行」改成「資料夾裡雜湊相符的通過驗證紀錄」，不管是哪一台驗證的。

# scenes/ba-001/verifications/2/ba-001-20261019-131500-a1b2c3.yaml
revision: 2
hash: 9f2c…                    # 執行時實際載入的場景雜湊（result.json 的 scenarioHash）
status: passed                 # passed、failed、timeout、cancelled、needs_login……
startedAt: 2026-10-19T06:15:00-07:00
finishedAt: 2026-10-19T06:15:42-07:00
by: 乙
server: { id: 5f3a…, name: yi-mac }
worker: { id: win-01, os: windows }   # 本機執行時是 local
engine: firefox
headless: false
run: { server: 5f3a…, id: ba-001-20261019-131500-a1b2c3 }   # 回看用（第 9 節）
summary: { steps: 12, durationSeconds: 42.1 }               # 不含入參與出參的值
  1. 甲錄製：錄製或編輯存成新版本 → 寫 revisions/<n>/ 與 <n>.yaml（建立者、伺服器）→ 推送。
  2. 乙驗證：拉取 → 在自己的伺服器（任何 worker）執行「驗證」→ 結束時寫一份驗證紀錄（通過或失敗都寫，失敗也讓別人看得到）→ 推送。
  3. 丙發布：拉取 → 頁面列出這個版本的全部驗證紀錄（誰、哪台、結果）→ 有雜湊相符的通過紀錄才能發布 → 寫 scene.yaml 的 published（依據的驗證紀錄、時間、操作者、伺服器）→ 推送。
  4. 丁使用：拉取 → 執行已發布的版本（之後 M9 的排程也用它）。
  • 發布門檻（任何一台都一樣）：磁碟上的版本內容雜湊 ＝ 版本說明檔的雜湊 ＝ 某一份 status: passed 驗證紀錄的雜湊。拉取時重新檢查，不成立就不當成已發布。也可以在自己這台「再驗證一次」，多一份紀錄。
  • 取消發布：published 改成 null；歷史看 git。
  • 組合場景一樣：驗證是一次目的為「驗證」的組合場景執行，全部節點通過才算通過；紀錄另外列出每個節點跑的場景、版本、雜湊與節點的執行編號。發布門檻再加上「節點釘住的場景版本雜湊都還相符」。
  • 伺服器代號與操作者：每台伺服器第一次啟動時產生代號（UUID），名稱預設是主機名稱，可以在設定改；操作者名稱在 M8 有登入之前是伺服器設定的名稱。紀錄寫的是這兩個。
  • 衝突：驗證紀錄一個執行一個檔案，不會衝突；兩台同時發布同一個場景才會改到同一個 scene.yaml，照 D6 停下來選擇。
  • 可信度：M8 之前，紀錄的真實性靠倉庫的寫入權限與 git 的提交歷史（誰推送的）；M8 加上使用者與稽核後，紀錄的 by 改成登入的使用者，可以再加簽章。

9. 執行紀錄的回看（D4：現在不進 git，預留方案）

使用者 06:05 PDT：執行紀錄先照建議不進 git，但之後要做，因為要回看，而且回看是重要的後續設計。MVP 只做「讓紀錄可以搬、可以找得到」的部分，歸檔與跨伺服器回看之後再做。

MVP 先做（成本低、之後不必改格式）

  • 執行目錄自己說明自己：每個場景執行目錄加一份 run.json（格式版本、伺服器、領域、場景、版本、雜湊、目的、執行位置、worker、瀏覽器、時間、狀態、檔案清單與每個檔案的 sha256 與大小）；組合場景的 workflow-runs/<編號>/run.json 同樣格式，另列節點的執行編號。不看資料庫也能知道這是什麼執行，搬到別處可以直接匯入。
  • 紀錄的位置全域可識別：用「伺服器代號＋執行編號」定位一次執行；驗證紀錄裡的 run 就是這個（之後歸檔時再填 archive 的位置）。
  • 入參、出參不進定義倉庫：驗證紀錄只有摘要，值留在執行目錄（可能是業務資料）。

之後做（預留方案）

  • 執行紀錄的存放處：在「領域管理」或系統設定加一個「執行紀錄存放處」，和定義的倉庫分開。建議用 S3 相容的物件儲存（M9 已規劃），路徑 runs/<伺服器代號>/<執行編號>/；只要輕量回看時也可以是另一個 git 倉庫，只放 run.json、報告與摘要，不放截圖與 Trace。
  • 歸檔：執行結束後依規則上傳（例如驗證執行一律上傳、一般執行依領域設定）；保留期限與清理；上傳前遮罩 Secrets（報告已經遮罩），截圖與 Trace 依 M8 的權限控管誰能看。
  • 回看：場景版本頁的「驗證與執行歷史」時間軸，列出所有伺服器的驗證紀錄；這台有的執行直接開報告，別台的從存放處取，都沒有時顯示「紀錄在 yi-mac，尚未歸檔」。組合場景的回看逐節點展開。
  • 匯入：從存放處或別台伺服器匯入執行紀錄成唯讀的索引（資料庫多記來源伺服器），不能重新執行別台的紀錄，只能用同樣的版本與入參另開一次。

10. git 同步

10.1 「領域管理」的資料來源設定

  • 倉庫網址：HTTPS 或 SSH。分支：選填，預設是遠端的預設分支（空倉庫時用 main）。目錄：倉庫裡的路徑，例如 testsite；同一個倉庫可以放多個領域，各自一個目錄。
  • 認證方式（D5）：
    • HTTPS：使用者名稱＋存取權杖（GitHub 不接受帳號密碼做 git 操作，要用 fine-grained personal access token，只開這個倉庫的 Contents 讀寫）。
    • SSH：部署金鑰。Portal 為這個領域產生一對金鑰並顯示公鑰，貼到倉庫的 Deploy keys 並勾選允許寫入；也可以貼上自己的私鑰。SSH 不使用使用者名稱與密碼。
    • 不需要：公開倉庫，只能拉取，不能推送。
  • 提交者：推送時 commit 的名稱與 Email（選填，預設是操作者名稱）。啟動時自動拉取：預設開；連不上時用本機上一次的資料照常啟動。
  • 按鈕：測試連線（可以連線、認證、遠端分支與目錄在不在）、拉取並重新載入、同步推送、重新載入、中斷 git 連結（資料夾保留，變成本機領域）。
  • 從 git 新增領域：先填倉庫與目錄、測試連線；目錄裡有 pack.yaml 就預填代號與名稱；目錄不存在就建立一個空的領域，第一次推送時建立目錄。

10.2 同步狀態

本機（沒有設定 git）／已同步／本機有 N 項變更未推送（版本、驗證紀錄、發布分開計數）／遠端有 N 個新提交／遠端還沒有這個目錄（第一次推送時建立）／空倉庫（第一次推送時建立分支）／衝突／錯誤（連線、認證、找不到倉庫）。「本機變更」＝正在使用的資料夾和「上次同步的提交」裡那個目錄的差異，所以不需要每次存檔都 commit。

10.3 拉取

  1. 在工作副本 git fetch。遠端是空倉庫或沒有這個目錄：狀態顯示「第一次推送時建立」，本機資料照用，不算錯誤。
  2. 本機沒有變更：工作副本切到遠端最新的提交。
  3. 本機有變更：在工作副本以「上次同步的提交」為基礎提交本機變更（不推送），再 rebase 到遠端最新的提交；有衝突就中止 rebase、什麼都不套用，顯示衝突的檔案與選項（10.5）。
  4. 校驗工作副本裡的目錄（第 6 節的規則）；通過才逐檔套用到正在使用的資料夾，更新「上次同步的提交」，重新載入與校驗依賴。

10.4 推送（含遠端目錄不存在、空倉庫）

  1. 推送前檢查：資料夾校驗沒有致命錯誤；只允許定義檔（yaml、json、py、md、txt）與大小上限；擋下 state.json、secrets*.json、.env、私鑰之類的檔名；檔案內容不能出現任何已保存的 Secrets 值；依賴的版本已經在遠端（第 7 節最後一列）。
  2. 顯示變更清單（新增的場景與版本、驗證紀錄、發布、角色、組合場景）與預設的提交說明（例如「testsite：ba-001 第 3 版、ba-002 驗證通過」），可以修改。
  3. 工作副本以「上次同步的提交」為基礎，把正在使用的資料夾複製到「目錄」，git add -A -- <目錄> 後提交；只提交這個目錄，倉庫的其他目錄不動。
  4. git fetch；遠端有新提交就 rebase，衝突時中止（10.5）。
  5. git push，永遠不強推：
    • 遠端沒有這個目錄：提交本身就新增了目錄，照常推送。這是「調試完推送到新目錄」的常見用法，不需要先到 GitHub 建目錄。
    • 空倉庫（還沒有任何提交，例如目前的測試倉庫）：建立第一個提交，推送時建立分支（push -u origin HEAD:main）。
    • 本機領域第一次接上遠端：遠端沒有目錄就直接推送整個資料夾；遠端已經有同一個領域的資料，就把兩邊當成合併：只有一邊有的檔案都保留，同一個路徑內容不同就是衝突（例如兩邊都有 ba-001 第 3 版但內容不同）。
  6. 更新「上次同步的提交」。

10.5 衝突時（D6）

不自動合併同一個檔案、不強推。停下來給三個選擇：取消（什麼都不改，本機照用）／推送到新分支 rpa/<領域>-<日期時間>（到 GitHub 開 PR 合併後再拉取）／以遠端為準（先把本機未推送的變更打包到 backups/，再套用遠端）。版本目錄不可變、驗證紀錄一次一個檔案，衝突只會發生在兩台伺服器同時替同一個場景建立同號的版本，或同時發布同一個場景；建議同一個場景同時只在一台伺服器上編輯。

10.6 憑證與安全

  • 使用伺服器上的 git 命令（2.25 以上，用稀疏複製只取設定的目錄）；沒有安裝時 git 功能停用，本機領域照常使用。
  • 帳密只經由 GIT_ASKPASS 交給那一次 git 子程序；不寫進網址、.git/config、資料庫或日誌；停用系統的憑證快取；GIT_TERMINAL_PROMPT=0；SSH 用 Portal 自己的 known_hosts，第一次連線記下主機指紋並顯示。
  • 每個領域同時只有一個 git 操作；操作期間 Portal 對這個領域的存檔、驗證紀錄、發布排隊等待；每個操作有逾時。
  • 提醒：公開倉庫的內容任何人都看得到。場景裡有內網網址、帳號名稱、預設值時，請用私有倉庫。

11. MVP 存放方案：伺服器、錄製端、worker

伺服器（管理 Portal）錄製端（macOS App）Worker（Windows App、rpa worker）

為什麼只放伺服器：資料庫索引只有一個寫入者；git 憑證只在一台機器；worker 與錄製端可能是一般桌面電腦，任務本來就自帶需要的檔案（M9a、M10.2 已經是這樣），不必改協定。之後 worker 變多、任務變大時，可以再讓 worker 依版本雜湊快取檔案，不影響這個格式。

程式碼和資料分開：程式碼倉庫裡只剩樣板（scenarios/demo/，第一次啟動時用來建立 testsite 領域）；執行時的資料都在資料目錄，領域資料夾各自進第三方倉庫。

12. 現有資料的遷移（D7）

  1. 升級後第一次啟動：資料庫遷移（0010，新增資料來源、同步狀態、來源缺失、組合場景代號等欄位）之後，自動做一次檔案遷移；先把 rpa.db 與 scenes/ 備份到 backups/<時間>-before-domains/。可以中斷後重跑。
  2. 產生伺服器代號；每個領域建立 domains/<領域>/pack.yaml；scenes/<場景>/<n>/ 搬到 domains/<領域>/scenes/<場景>/revisions/<n>/，依資料庫補上 scene.yaml 與 <n>.yaml。內容不變，雜湊照舊。
  3. 驗證與發布：資料庫裡目的為「驗證」的執行，依結果寫成驗證紀錄（伺服器是這台、操作者寫「遷移」）；已發布的版本寫進 scene.yaml 的 published，依據最近一次雜湊相符的通過驗證。找不到依據的已發布版本照樣保留並列為載入問題，請重新驗證。
  4. 沒有領域的場景放進新的領域「未分類」（unassigned）。
  5. 角色放進用到它的場景所在的領域；多個領域都用到時放進排序最前的那個，其他領域記為跨領域依賴；沒有場景用到的角色放進「未分類」。
  6. 組合場景放進新的領域「組合場景」（composites）：代號 wf-<原數字>，現在的定義成為第 1 版（說明寫「從資料庫遷移，原第 N 次存檔」），產生 requires。之後可以在頁面改代號或搬到其他領域。
  7. 組合場景的執行紀錄寫成 workflow-runs/<編號>/run.json，資料庫留索引欄位；已有的場景執行目錄補上 run.json。
  8. 遷移完成後舊的 scenes/ 移除（備份裡有）。全部遷移的領域一開始都是本機領域，之後再到領域管理設定 git。
