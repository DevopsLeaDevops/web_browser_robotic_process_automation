1. 使用者的需求（2026-10-19 04:47 PDT）

  1. 領域各自一個資料夾：不同領域掛不同的資料夾（例如 testsite → 測試網站的資料夾、scm_purchase → 採購系統的資料夾），每個資料夾可以單獨載入、執行、調試。
  2. 組合場景有自己的資料檔，可以跨領域組合；啟動或拉取時校驗跨領域的資料依賴，不完整就提示補全。
  3. 組合場景的資料規範和領域場景一致；workflow 的 JSON 定義與執行紀錄存成檔案；資料庫只放其他中繼資料。
  4. 程式碼和資料分開；資料可以放在第三方 git 倉庫，按領域、按組合場景分別拉取資料夾，在「領域管理」設定（倉庫、目錄、使用者名稱、密碼）；拉取後熱載入、初始化場景與組合場景；手動「同步」把本機資料推送到 git。
  5. 常見用法：調試完一個資料夾就推送到遠端，遠端還沒有這個目錄也要能推送（自動新增）。
  6. 另外要一份 MVP 存放方案：資料分別放在伺服器、錄製端、worker 的哪裡。

3. 設計總覽

  • 領域資料夾（資料包）：一個領域一個資料夾，裡面放這個領域的全部定義——場景與版本、角色、組合場景。資料夾自己就能載入（不需要其他領域），也是 git 推送與拉取的單位。
  • 組合場景資料夾就是一個只放組合場景的領域：格式、設定、同步方式完全一樣，只是沒有 scenes/。跨領域時在資料夾的說明檔記下依賴哪些領域。（決定點 D1）
  • 檔案是定義，資料庫是索引與本機狀態：定義（會跟著 git 走的）都在資料夾；資料庫只放這台伺服器自己的狀態（驗證、發布、執行索引、裝置、同步狀態），以及可以從資料夾重建的索引。
  • 只有伺服器碰 git：錄製端和 worker 維持無狀態，不複製倉庫、不拿 git 憑證。
  • 兩層資料夾：正在使用的領域資料夾 domains/<領域>/ 和同步用的 git 工作副本 git/repos/<領域>/ 分開。拉取先在工作副本合併、校驗，通過才套用到正在使用的資料夾；推送時把正在使用的資料夾複製到工作副本的「目錄」再提交。失敗的 git 操作不會留下半套資料，沒設 git 的領域也能隨時接上遠端。

4. 領域資料夾的格式

<領域資料夾>/                      ＝ git 倉庫裡設定的「目錄」，例如 testsite/
  pack.yaml                         領域說明檔（必須有）
  scenes/
    ba-001/
      scene.yaml                    場景說明檔：代號、是否封存
      revisions/
        1/scenario.yaml             版本內容，和現在的版本目錄完全一樣（雜湊不變）

        2/scenario.yaml、automation.py、assertion.py
        2.yaml
  roles/
    testsite-user.yaml              角色定義（不含登入狀態）
  composites/
    order-flow/

      revisions/

說明檔

# pack.yaml
specVersion: 1                 # 資料夾格式的版本
id: testsite                   # 和管理 Portal 的領域代號相同
name: 測試網站自動化
description: 範例場景，都對本機測試網站執行。
requires: []                   # 用到其他領域的場景或角色時，存檔與推送前自動更新

# 只放組合場景的領域（e2e-procure/pack.yaml）
specVersion: 1
id: e2e-procure
name: 採購到驗收（跨領域）
requires:
  - domain: testsite
    source: { repo: git@github.com:DevopsLeaDevops/web_browser_robotic_process_automation_site.git, directory: testsite }
  - domain: scm_purchase       # source 是提示，用來預填「新增領域」；不含帳號密碼，可以省略
# scenes/ba-001/revisions/3.yaml（組合場景的 revisions/<n>.yaml 欄位相同，另多 requires）
number: 3
hash: 9f2c…                    # 版本內容的雜湊（和 result.json 的 scenarioHash 同演算法）
createdAt: 2026-10-19T05:10:00-07:00
note: 從錄製建立

# composites/order-flow/revisions/2.yaml
number: 2
hash: 41ab…
createdAt: 2026-10-19T05:30:00-07:00
requires:                      # 存檔時由定義產生，載入時用來校驗
  - { domain: testsite, scene: ba-001, revision: 3, hash: 9f2c… }
  - { domain: scm_purchase, scene: po-create, revision: 5, hash: 77d0… }

規則

  • 版本不可變：存檔永遠是新的 revisions/<n>/。版本說明檔放在版本目錄旁邊（<n>.yaml），不放進版本目錄，所以版本內容與雜湊和現在完全一樣，遷移後發布門檻與舊的執行紀錄仍然對得上；兩台伺服器各自新增不同場景的版本也不會改到同一個檔案。
  • 組合場景和場景一樣有版本：每次存檔一個新版本（現在的 version 就是存檔次數）。組合場景的代號改成和場景一樣的英數代號（決定點 D2）。
  • 代號全域唯一：場景、角色、組合場景的代號在所有已載入的領域之間不能重複（現在的資料庫已經是這樣；不改 DSL）。重複時後載入的那一個不載入，列在領域的「載入問題」裡（決定點 D8）。
  • 資料夾裡只有定義：不放登入狀態、Secrets 的值、執行紀錄、截圖、錄製稿。推送前另有檢查（第 8 節）。
  • 人可以直接讀：YAML／JSON、固定排序與縮排，在 GitHub 上看得懂、diff 乾淨。

6. 載入與熱載入

  • 什麼時候載入：伺服器啟動時載入全部領域；拉取成功後、按「重新載入」時載入那一個領域；Portal 自己存檔時只更新改到的項目。不需要重新啟動。MVP 不監看資料夾變化，在資料夾外面手動改了檔案要按「重新載入」（決定點 D10）。
  • 怎麼載入：掃描資料夾 → 逐項校驗（DSL、組合場景定義、雜湊、代號重複）→ 一個交易更新索引 → 重新計算所有組合場景的依賴狀態。單一項目有問題只略過那一項並列出；pack.yaml 不見或代號和領域不同時，整個領域保持上一次的索引並顯示錯誤。
  • 版本內容和索引記的雜湊不同（有人改了已存在的版本）：那個版本退回草稿；如果它是已發布的版本，取消發布並提示。這是現有發布門檻「磁碟上的內容也還是同一個雜湊」的延伸。
  • 來源缺失：資料夾裡沒有了的場景或版本標為來源缺失：清單隱藏、不能執行，執行紀錄照樣保留。
  • 正在執行的任務不受影響：遠端 worker 的任務在領取時就帶走版本檔案；本機執行也改成開始時把版本檔案複製到執行目錄（和遠端一致）。套用拉取結果時逐檔新增、修改、刪除，不整個資料夾換掉，Windows 上開著的檔案也不會擋住。
  • 可以單獨載入：每個領域資料夾自給自足。新伺服器只設定 testsite 一個領域，拉取後就能錄製、調試、執行 testsite 的場景；另外提供 rpa pack check <資料夾>，不開 Portal 也能校驗一個資料夾（可以放在資料倉庫的 CI）。

7. 跨領域依賴的校驗

依賴是「組合場景的版本釘住的場景版本」與「場景用到的角色、Secrets、登入狀態」。組合場景每次存檔時由定義產生 requires（領域、場景、版本、雜湊），pack.yaml 彙總依賴哪些領域。

什麼時候校驗：伺服器啟動、任何一個領域拉取或重新載入之後（重算依賴它的組合場景）、組合場景存檔時、開始執行前、推送組合場景所在的領域前。只校驗每個組合場景的最新版本與已發布版本，舊版本不擋。

發現的問題等級提示怎麼補全
依賴的領域沒有設定（例如需要 scm_purchase）不能執行「新增領域 scm_purchase」，用 pack.yaml 的 source 預填倉庫與目錄
領域有設定，但還沒拉取或拉取失敗不能執行「拉取 scm_purchase」，並顯示上次的錯誤
領域裡沒有這個場景不能執行「拉取最新」；仍然沒有時提示「對方可能還沒推送或已刪除」
需要第 5 版，領域目前只到第 4 版不能執行「拉取最新」，或在組合場景把節點改用現有的版本後存成新版本
版本存在，但雜湊和組合場景存檔時不同不能執行提示版本內容被改過；重新選擇版本並存檔
場景用到的角色沒有定義不能執行指出應該由哪個領域提供角色；拉取或補上角色定義
角色沒有登入狀態提醒「登入」（人工登入或設定自動登入）；執行時會停在需要登入
Secrets 沒有值提醒列出名稱，連到 Secrets 頁
推送前：依賴的版本只在本機、還沒推送到它的領域推送前提醒「一起推送 testsite」或取消；不然別人拉取後依賴不完整

組合場景清單與畫布上方顯示「依賴完整／有提醒／不完整」，展開就是上表的清單與按鈕；領域管理頁顯示每個領域被哪些組合場景依賴。

8. git 同步

8.1 「領域管理」的資料來源設定

  • 倉庫網址：HTTPS 或 SSH。分支：選填，預設是遠端的預設分支（空倉庫時用 main）。目錄：倉庫裡的路徑，例如 testsite；同一個倉庫可以放多個領域，各自一個目錄。
  • 認證方式（決定點 D5）：
    • HTTPS：使用者名稱＋存取權杖（GitHub 不接受帳號密碼做 git 操作，要用 fine-grained personal access token，只開這個倉庫的 Contents 讀寫）。
    • SSH：部署金鑰。Portal 為這個領域產生一對金鑰並顯示公鑰，貼到倉庫的 Deploy keys 並勾選允許寫入；也可以貼上自己的私鑰。SSH 不使用使用者名稱與密碼。
    • 不需要：公開倉庫，只能拉取，不能推送。
  • 提交者：推送時 commit 的名稱與 Email（選填）。啟動時自動拉取：預設開；連不上時用本機上一次的資料照常啟動。
  • 按鈕：測試連線（可以連線、認證、遠端分支與目錄在不在）、拉取並重新載入、同步推送、重新載入、中斷 git 連結（資料夾保留，變成本機領域）。
  • 從 git 新增領域：先填倉庫與目錄、測試連線；目錄裡有 pack.yaml 就預填代號與名稱；目錄不存在就建立一個空的領域，第一次推送時建立目錄。

8.2 同步狀態

本機（沒有設定 git）／已同步／本機有 N 項變更未推送／遠端有 N 個新提交／遠端還沒有這個目錄（第一次推送時建立）／空倉庫（第一次推送時建立分支）／衝突／錯誤（連線、認證、找不到倉庫）。「本機變更」＝正在使用的資料夾和「上次同步的提交」裡那個目錄的差異，所以不需要每次存檔都 commit。

8.3 拉取

  1. 在工作副本 git fetch。遠端是空倉庫或沒有這個目錄：狀態顯示「第一次推送時建立」，本機資料照用，不算錯誤。
  2. 本機沒有變更：工作副本切到遠端最新的提交。
  3. 本機有變更：在工作副本以「上次同步的提交」為基礎提交本機變更（不推送），再 rebase 到遠端最新的提交；有衝突就中止 rebase、什麼都不套用，顯示衝突的檔案與選項（8.5）。
  4. 校驗工作副本裡的目錄（第 6 節的規則）；通過才逐檔套用到正在使用的資料夾，更新「上次同步的提交」，重新載入與校驗依賴。

8.4 推送（含遠端目錄不存在、空倉庫）

  1. 推送前檢查：資料夾校驗沒有致命錯誤；只允許定義檔（yaml、json、py、md、txt）與大小上限；擋下 state.json、secrets*.json、.env、私鑰之類的檔名；檔案內容不能出現任何已保存的 Secrets 值；依賴的版本已經在遠端（第 7 節最後一列）。
  2. 顯示變更清單（新增的場景與版本、角色、組合場景）與預設的提交說明（例如「testsite：ba-001 第 3 版、ba-002 第 2 版」），可以修改。
  3. 工作副本以「上次同步的提交」為基礎，把正在使用的資料夾複製到「目錄」，git add -A -- <目錄> 後提交；只提交這個目錄，倉庫的其他目錄不動。
  4. git fetch；遠端有新提交就 rebase，衝突時中止（8.5）。
  5. git push，永遠不強推：
    • 遠端沒有這個目錄：提交本身就新增了目錄，照常推送。這是「調試完推送到新目錄」的常見用法，不需要先到 GitHub 建目錄。
    • 空倉庫（還沒有任何提交，例如目前的測試倉庫）：建立第一個提交，推送時建立分支（push -u origin HEAD:main）。
    • 本機領域第一次接上遠端：遠端沒有目錄就直接推送整個資料夾；遠端已經有同一個領域的資料，就把兩邊當成合併：只有一邊有的檔案都保留，同一個路徑內容不同就是衝突（例如兩邊都有 ba-001 第 3 版但內容不同）。
  6. 更新「上次同步的提交」。

8.5 衝突時（決定點 D6）

不自動合併同一個檔案、不強推。停下來給三個選擇：取消（什麼都不改，本機照用）／推送到新分支 rpa/<領域>-<日期時間>（到 GitHub 開 PR 合併後再拉取）／以遠端為準（先把本機未推送的變更打包到 backups/，再套用遠端）。版本目錄不可變，衝突幾乎只會發生在兩台伺服器同時替同一個場景建立同號的版本；MVP 建議同一個領域同時只在一台伺服器上編輯。

8.6 憑證與安全

  • 使用伺服器上的 git 命令（2.25 以上，用稀疏複製只取設定的目錄）；沒有安裝時 git 功能停用，本機領域照常使用。
  • 帳密只經由 GIT_ASKPASS 交給那一次 git 子程序；不寫進網址、.git/config、資料庫或日誌；停用系統的憑證快取；GIT_TERMINAL_PROMPT=0；SSH 用 Portal 自己的 known_hosts，第一次連線記下主機指紋並顯示。
  • 每個領域同時只有一個 git 操作；操作期間 Portal 對這個領域的存檔排隊等待；每個操作有逾時。
  • 提醒：公開倉庫的內容任何人都看得到。場景裡有內網網址、帳號名稱、預設值時，請用私有倉庫。

10. 現有資料的遷移

  1. 升級後第一次啟動：資料庫遷移（0010，新增資料來源、同步狀態、來源缺失、組合場景代號等欄位）之後，自動做一次檔案遷移；先把 rpa.db 與 scenes/ 備份到 backups/<時間>-before-domains/。可以中斷後重跑。
  2. 每個領域建立 domains/<領域>/pack.yaml；scenes/<場景>/<n>/ 搬到 domains/<領域>/scenes/<場景>/revisions/<n>/，依資料庫補上 scene.yaml 與 <n>.yaml。內容不變，雜湊、發布狀態、執行紀錄都照舊。
  3. 沒有領域的場景放進新的領域「未分類」（unassigned）。
  4. 角色放進用到它的場景所在的領域；多個領域都用到時放進排序最前的那個，其他領域記為跨領域依賴；沒有場景用到的角色放進「未分類」。
  5. 組合場景放進新的領域「組合場景」（composites）：代號 wf-<原數字>，現在的定義成為第 1 版（說明寫「從資料庫遷移，原第 N 次存檔」），產生 requires。之後可以在頁面改代號或搬到其他領域。
  6. 組合場景的執行紀錄寫成 workflow-runs/<編號>/run.json，資料庫留索引欄位。
  7. 遷移完成後舊的 scenes/ 移除（備份裡有）。全部遷移的領域一開始都是本機領域，之後再到領域管理設定 git。
