0. 一頁摘要

  • 場景模型不換。腳本場景照舊是一份 scenario.yaml：入參、出參、Secrets、登入角色、瀏覽器、總期限都和 DSL 一樣；script: 指出自動化腳本，斷言可以用 DSL 的 verify:＋outputs.from（錄製產生這種），也可以照舊用 assertion.py。運行報告的格式（result.json、steps.json、facts.json、output.json）也一樣。
  • Python 運行環境分三層，每一層「已經有就沿用」。直譯器（Worker 自帶，或電腦上已裝的相容版本）→ 平台層（和 Worker 同版本的 Playwright＋腳本介面）→ 場景環境（場景鎖定的第三方套件）。用 uv 建立；同一組套件第二次直接沿用（實測 0.1 秒、檔案以硬連結共用，不多佔空間）。
  • 新的腳本介面 rpa_script。瀏覽器由平台照場景設定開好（登入狀態、視窗大小、Firefox 預熱、錄影），腳本用 with run.step("id", "名稱"): 標出步驟、把看到的寫進 run.facts。DSL 的子程序和腳本共用同一份開瀏覽器與錄影的程式，所以報告與回看和 DSL 場景一致。舊的命令列寫法照常可用。
  • 錄製直接產生腳本。沿用 Playwright codegen 與現在的錄製頁，多一個「產生：DSL 場景／Python 腳本場景」。codegen 的 Python 原稿轉成 rpa_script 的腳本：一個操作一步、輸入變成入參、密碼變成 Secret、Inspector 的 Assert 變成頁面事實＋獨立斷言；DSL 轉不了的寫法（hover、上傳、鍵盤、拖曳…）在腳本裡照樣能執行。
  • 運行過程多一個「運行環境」階段（不算進總期限），其餘照 ADR 0009：入參 → 運行環境 → 登入 → 自動化 → 斷言 → 出參。心跳帶著目前的步驟；取消、逾時、程序樹的終止與錄影收尾沿用 M2、M12。
  • 回看沿用 M12 的播放器，步驟詳細多了腳本原文與行號、主控台輸出、錯誤的呼叫堆疊；舊寫法的腳本沒有錄影，回看頁說明怎麼改。
  • 分四個 PR 交付（第 12 節）：運行環境 → 腳本介面＋報告＋回看 → 錄製 → 調試與接著錄製。

1. 目標與驗收

  • 同一個 Python 腳本場景，不改一行，在 Windows Worker App、macOS Worker App、Linux 的 rpa worker 都能驗證與執行；有頭、無頭都可以（Linux 沒有桌面時只能無頭）。
  • Worker 不需要事先裝 Python：第一次跑腳本時用自帶的環境，沒有網路也能跑只用標準函式庫與 Playwright 的腳本。同一台電腦已經準備好的環境（包括錄製端、命令列共用的）一律沿用，第二次運行的「運行環境」階段在 1 秒內。
  • 場景的入參、出參、獨立斷言、Secrets、登入角色、發布門檻和 DSL 場景用同一套規則；通過驗證的版本（含腳本、套件鎖定檔）就是發布的版本。
  • 在錄製端錄一段操作，可以直接存成 Python 腳本場景的草稿，交給 Worker 驗證、發布、執行成功。
  • 腳本的運行報告有步驟（名稱、結果、耗時、錯誤、原始碼行號）、頁面事實、斷言、出參、截圖、主控台輸出與運行環境；運行回看可以播放、拖曳、和步驟對上，失敗的運行打開就停在失敗步驟之前。
  • 舊的腳本場景（ba-001-script 這種命令列寫法）照常通過；舊版 Worker 不會領到它跑不了的腳本，而是看到要更新的說明。

2. 現況與技術驗證

程式以 main a8cde7f 查證；實測在 2026-10-24 20:40～21:00 America/Los_Angeles（PDT，UTC−07:00）

現在的 Python 腳本場景

  • DSL 的逃生門（ADR 0009、場景 DSL › script）：script: { automation, assertion } 兩支檔案，沿用 MVP 原型的命令列契約；腳本自己啟動瀏覽器，從環境變數拿到瀏覽器、剩餘期限、有頭／無頭與登入狀態檔（scenarios/demo/ba-001-script/）。
  • Runner 以子程序執行（rpa_runner.run 的 _automation_stage、_verify_stage），直譯器是 sys.executable；打包後是 App 自己的 rpa-child --rpa-script（rpa_runner.commands.script_command），所以只能 import 標準函式庫與 App 內附的套件（ADR 0014 的代價）。
  • 沒有步驟紀錄（steps.json 是空的）、不錄影（M12 D5「腳本場景暫不支援」）、逐步調試只支援 DSL（卡片的「調試」對腳本場景是直接驗證）；錄製與 AI 不產生腳本場景（ADR 0009）。
  • 腳本場景的雜湊包含場景檔與兩支腳本（rpa_core.dsl.sources）；版本、發布門檻、領域資料夾、Worker 任務（JobPayload.files）都已經能帶任意多個檔案。

3. 場景模型：沿用現有的契約

Python 腳本場景和 DSL 場景是同一種東西：同一份 scenario.yaml、同一套入參與出參的宣告、同一個發布門檻；差別只在「自動化」那一段是 Python。schemaVersion 維持 1，新欄位是增加的，舊場景不用改，雜湊也不變。

# scenes/ba-001-sdk/revisions/1/scenario.yaml
schemaVersion: 1
id: ba-001-sdk
name: 建立範例紀錄（Python 腳本）
inputs:                                 # 入參：和 DSL 相同（型別、限制、動態值）
  title: { type: string, minLength: 1, maxLength: 60, default: 介面驗證範例 }
  quantity: { type: integer, minimum: 1, maximum: 30, default: 12 }
outputs:                                # 出參：和 DSL 相同，from 取自頁面事實
  recordId: { pattern: '^DEMO-[A-Z0-9]+$', from: '{{ facts.record.recordId }}' }
browser: { engine: firefox, baseUrl: http://127.0.0.1:8765 }
deadline: 45000
script:
  api: 2                                # 新：2＝rpa_script 介面；沒寫是 1（現有的命令列寫法）
  automation: automation.py             # 自動化腳本
  python: "3.13"                        # 新，選用：沒寫就用 Worker 自帶的版本
  requirements: requirements.txt        # 新，選用：第三方套件
  lock: requirements.lock               # 新：有 requirements 就必須有，存檔時產生
  files: [helpers.py, data/codes.json]  # 新，選用：腳本會讀的其他檔案
  platforms: [windows, macos, linux]    # 新，選用：只在這些系統執行；沒寫是不限
verify:                                 # 獨立斷言：api 2 可以用 DSL 的 verify（和 assertion.py 二擇一）
  - name: 狀態是已建立
    value: '{{ facts.record.status }}'
    equals: 已建立
使用者說的現有的建模腳本場景怎麼用
自動化腳本DSL 的 steps:；卡片與場景頁的「自動化腳本」script.automation 指的 .py；同一個「自動化腳本」入口改成編輯這支檔案（加上 files 列出的其他檔案）。腳本只負責操作頁面、把看到的寫成頁面事實 facts，不判定成功。
斷言verify:（獨立斷言，「斷言腳本」入口，右側插入 notEmpty／equals／contains／matches）api 2 可以直接寫 verify:（錄製產生這種，編輯器與檢查完全相同）；需要程式判斷時改用 script.assertion 的 .py。兩者二擇一；有出參就必須有其中一個（ADR 0009 不變）。
入參inputs:：型別、限制、預設值、動態值；啟動瀏覽器前校驗完全相同。腳本從 run.inputs 讀到校驗後的運行態入參（動態值已求值，和 input.json 同一份）。
出參outputs:＋from；獨立斷言通過後才發布用 verify 時照舊寫 from；用 assertion.py 時由它回傳候選出參、不寫 from（現有規則）。出參校驗與 output.json 不變。
運行報告執行目錄：input.json、facts.json、steps.json、output.json、result.json、report.html、截圖、錄影同一份格式；steps.json 由腳本介面寫（第 8 節），多出的檔案是增加的（運行環境、主控台輸出）。

校驗規則（rpa validate、Portal 存檔、rpa pack check 相同）

  • api 是 1 或 2。api 1 的規則不變（不寫 verify、出參不寫 from、兩支腳本都要有）；python、requirements、files、platforms 兩種 api 都能寫。
  • api 2：assertion 與 verify 恰好一個（沒有出參時兩個都可以不寫，和 DSL 一樣）；verify 與 outputs.from 只能引用 inputs、secrets、facts、env。腳本會寫出哪些 facts 在校驗時看不出來，所以不檢查 facts 的名稱，執行時找不到就在那一條斷言報「沒有這個頁面事實」。
  • python 是 "3.12"、"3.13" 或 "3.14"（平台的最低版本仍是 3.12，ADR 0002）。platforms 是 windows、macos、linux 的子集。
  • 路徑都相對於場景檔的資料夾，不能用 .. 或絕對路徑（沿用 ScriptPath 的規則，files 也可以是 .py 以外的檔案）。每支 .py 在存檔時做語法檢查（依 python 的版本），錯誤指出檔案與行號。
  • requirements.txt 只能寫套件名稱與版本條件；不接受網址、VCS、本機路徑、-e、--index-url 之類的選項（套件來源只在伺服器設定，第 4 節）。不能列平台層的套件（playwright、rpa-script）。
  • lock 由伺服器產生（第 4 節），每一項都要 == 版本與雜湊；手動上傳的也照同樣規則檢查。

雜湊與檔案

  • scenario_sources 依序加上 assertion（有寫才加）、requirements、lock、files。沒有用到新欄位的場景，檔案清單與雜湊完全不變（ADR 0015「演算法改了會讓所有既有的雜湊對不上」）。
  • 「驗證的就是發布的」因此包含套件鎖定檔：換了套件版本就是新版本，要重新驗證。
  • 領域資料夾的版本目錄照樣放全部檔案；rpa pack check 多檢查上面的規則與每個檔案都在。單一檔案上限沿用 git 推送的 1 MB。

4. Python 運行環境：Worker 自帶，已經有就沿用

「運行環境」是腳本實際用的 Python：一個直譯器加上一個虛擬環境。分三層，每一層都以內容決定身分，已經有一模一樣的就直接沿用，沒有才建立。三層都放在這台電腦的快取資料夾，Worker App、錄製端 App 與命令列共用。

層內容怎麼認出「已經有」從哪裡來（依序）
1. 直譯器CPython 3.12 以上（python-build-standalone，或電腦上已裝的）版本、平台、架構相同的已準備直譯器(1) 這台已經準備好的；(2) Worker 自帶的（App 內附的壓縮檔解壓一次；Linux 分發包本身的 Python；開發環境 uv 管理的）；(3) 電腦上已裝的相容版本（設定允許時，第 4.3 節）；(4) 用 uv 下載（設定允許時，可以用鏡像）
2. 平台層和這個 Worker 同版本的 Playwright（含它的 greenlet、pyee）與腳本介面 rpa-script直譯器＋平台層清單（套件版本與雜湊）Worker 自帶的 wheel（離線可用）；開發環境從工作區建
3. 場景環境平台層＋場景 requirements.lock 的套件環境代號＝直譯器組建＋平台層清單＋鎖定檔內容的 sha256 前 16 碼uv 從伺服器設定的套件來源安裝（--no-deps --require-hashes）；下載過的 wheel 在 uv 的快取，之後的環境以硬連結共用

沒有第三方套件的腳本（大多數）直接用第 2 層的環境，每個直譯器只有一份。舊寫法（api 1）的腳本也改在這裡執行：它要的 Playwright 在平台層裡；唯一的差別是不能再 import App 內部的套件（Pydantic 等，ADR 0014 原本就說明只保證標準函式庫與 Playwright），需要時寫進 requirements。

4.3 「若已有則重複使用」：電腦上已裝的 Python

  • 本設計的理解（D1）：三層都「已經有就沿用」；電腦上已裝的 Python 只在 Worker 自帶的版本不符合場景的 python 時才用（例如場景要 3.12、自帶的是 3.13），而且優先於下載。這樣同一個場景在每台 Worker 上預設用同一個直譯器，結果最一致。
  • 怎麼找：uv python find 版本 --python-preference only-system。Windows 找 py launcher、登錄檔與 PATH，略過 Microsoft Store 的捷徑（沒安裝時只會打開商店）；macOS 找 PATH、python.org 與 Homebrew，不碰 /usr/bin/python3，除非 xcode-select -p 有結果（否則會跳出安裝開發工具的視窗）；Linux 找 PATH 與系統套件。找到的記在 machine.json，回報給伺服器。
  • 不用的情況：版本、架構不符；是虛擬環境裡的 python；設定關閉了「使用電腦上已裝的 Python」。

內部鏡像Worker 的「設定」沒有現有的瀏覽器下載鏡像旁邊，多套件來源與 Python 下載來源；有填就優先於伺服器送來的（Worker 所在的網路可能不同）。

4.5 套件的鎖定

  • 使用者只寫 requirements.txt（例如 openpyxl>=3.1）。存檔時伺服器以 uv 產生 requirements.lock：uv pip compile --universal --generate-hashes，以平台層的版本為限制條件，不輸出平台層的套件。鎖定檔和腳本一起成為新版本。
  • 伺服器連不到套件來源時存檔失敗並說明；也可以在別台電腦用頁面上顯示的命令產生、上傳鎖定檔（照第 3 節的規則檢查）。伺服器需要 uv：開發環境已有，Linux 分發包多附一份（第 4.1 節）。
  • Worker 安裝時一律 --no-deps --require-hashes：只裝鎖定檔列的、雜湊要對，不會因為來源上的新版本而變。
  • Worker 升級後平台層的 Playwright 和某個鎖定檔衝突時，那一次運行在「運行環境」階段失敗，說明要重新鎖定（開新版本並驗證）。

4.6 回報與派工

  • Worker 上線時（WorkerInfo）多回報：系統（windows／macos／linux）與架構、看得懂的擴充多一個 pythonRuntime、可用的直譯器（自帶、已裝、能不能下載）、平台層版本、腳本介面的版本。「裝置」頁顯示這些。
  • 伺服器只把腳本場景交給回報 pythonRuntime、系統在 platforms 裡、而且有（或能下載）符合 python 的直譯器的裝置；沒有時執行頁說明「沒有可以執行的 Worker：需要 Python 3.12」或「這個場景只在 Windows 執行」，同 M7a 的做法。舊版 Worker 不回報 pythonRuntime，只會領到舊寫法、沒有新欄位的腳本場景，照舊用 App 自己的直譯器執行。

5. 腳本介面 rpa_script（api 2）

新套件 packages/rpa_script（套件名稱 rpa-script）：只依賴 Playwright 與標準函式庫，裝在平台層。它負責腳本與平台之間的一切：讀入參與 Secrets、照場景設定開瀏覽器、記錄步驟、寫頁面事實、截圖、主控台輸出與錯誤。開瀏覽器與錄影的程式（現在 rpa_runner 的 contexts、profiles、video.mark_page、步驟紀錄、總期限）搬進這個套件，DSL 的子程序也改用它，兩種場景開出來的瀏覽器、錄到的影片與 steps.json 完全相同。

# automation.py（script.api: 2；錄製產生，之後可以手改）
from rpa_script import Run, automation


@automation
def main(run: Run) -> None:
    page = run.page  # 平台照場景設定開好的分頁：瀏覽器、視窗、語言、登入狀態、錄影
    with run.step("open", "開啟首頁"):
        page.goto("/")  # 以 / 開頭時接在 browser.baseUrl 後面（同 DSL）
    with run.step("fill-title", "填寫標題"):
        page.get_by_label("標題", exact=True).fill(run.inputs["title"])
    with run.step("fill-quantity", "填寫數量"):
        page.get_by_label("數量", exact=True).fill(str(run.inputs["quantity"]))
    with run.step("submit", "建立紀錄"):
        page.get_by_role("button", name="建立紀錄").click()
    with run.step("read-record", "讀取紀錄"):
        receipt = page.locator("#receipt")
        receipt.wait_for()
        run.facts["record"] = {
            "recordId": receipt.locator("#record-id").inner_text(),
            "status": receipt.locator("#record-status").inner_text(),
        }
介面說明
@automation標出進入點。平台以 python -E -s -m rpa_script automation … 載入這支檔案並呼叫它，腳本不寫啟動瀏覽器、讀參數的樣板。一支檔案只能有一個。
run.inputs、run.secrets運行態入參（唯讀，和 input.json 同一份）；場景 secrets 宣告的 Secrets（只有宣告的名稱）。Secrets 的值出現在錯誤、主控台、步驟名稱時自動遮罩。
run.facts頁面事實（dict），結束時寫成 facts.json；失敗時也寫出已經取得的部分，報告看得到。
run.page、run.context、run.playwright平台開好的分頁與 BrowserContext；可以照 Playwright 的寫法開新分頁、等彈出視窗。腳本可以自己再開其他瀏覽器，但只有這個 context 會錄影。
with run.step(id, name=None, *, timeout=None, page=None)標出一步。記下開始、結束的實際時間、結果、錯誤、原始碼行號、所在分頁（page 沒寫時是目前的分頁：剛開出的彈出視窗會成為目前的分頁）。進入一步時把 Playwright 的預設逾時設成「這一步的逾時、defaults.timeout 與總期限剩下的時間」中最小的。id 的格式同 DSL；在迴圈裡重複的 id 記成同一步的第 n 次；可以巢狀（報告縮排顯示，回看的步驟軌畫最外層）。
run.screenshot(name, *, page=None, full_page=False)、run.attach(path, name=None)截圖、把檔案（例如下載的報表）存進執行目錄，列在這一步的產物。
run.log(訊息)、print()都進主控台輸出，記下時間與當時的步驟（console.jsonl），原樣也寫進 automation.log。
run.remaining_ms、run.platform、run.lang、run.work_dir總期限剩下的毫秒；windows／macos／linux；介面語言；這次運行的暫存資料夾（結束後刪除，也是腳本的工作目錄）。
  • 步驟以外的程式照樣執行；在步驟外拋出的錯誤記成一個失敗的「步驟外的程式」，附行號。
  • 失敗時：記下錯誤（類型、訊息、呼叫堆疊，只保留場景自己的檔案的那幾層、遮罩 Secrets）到 diagnostic.json，截目前分頁的 screenshot.png，寫出 facts，關掉 context（讓錄影寫完），結束碼 1；總期限到了是 3（逾時，同 DSL）。
  • 本機試跑：作者可以在自己的電腦 python -m rpa_script automation automation.py --scenario scenario.yaml -i title=測試 --headed，或直接用 rpa run（同一套運行環境）。rpa-script 的 wheel 可以從 Portal 下載，讓編輯器有型別提示。

獨立斷言用 Python 時（assertion.py，選用）

from rpa_script import Check, assertion


@assertion
def check(c: Check) -> dict[str, object]:
    record = c.facts["record"]
    c.matches("紀錄編號格式", record["recordId"], r"^DEMO-[A-Z0-9]+$")
    c.equals("狀態是已建立", record["status"], "已建立")
    c.equals("標題與入參相同", record.get("title"), c.inputs["title"])
    return {"recordId": record["recordId"]}  # 候選出參；任何一條沒通過就不採用
  • 不開瀏覽器，只讀入參與頁面事實。每一條 equals、contains、matches、not_empty、true 都記成一條斷言結果，和 DSL 的 verify 同一個格式（名稱、比較方式、實際、預期、是否通過），報告與回看的「斷言」完全一樣。
  • 回傳的 dict 是候選出參，照舊經過出參校驗才發布。

舊寫法（api 1）

命令列契約（--input --facts --screenshot --target-url、--input --facts --output）與環境變數不變，改在運行環境的平台層執行。報告只有階段、截圖與日誌；沒有步驟與錄影。腳本可以只把 api 改成 2、換成 @automation 的寫法來取得步驟與回看。

6. 腳本錄製

錄製的部分不改：照舊是 Playwright codegen，瀏覽器與 Inspector 開在操作的那台（錄製端 App 或伺服器本機），錄完把原始稿交給伺服器。改的是轉換的目標：除了 DSL 草稿，也可以轉成 Python 腳本場景的草稿。腳本本來就是 Python，codegen 錄到的每一種操作都能照原樣執行，不會有「轉不了的行」。

  1. 「場景生產 › 自主腳本錄製」多一個選項「產生：DSL 場景（預設）／Python 腳本場景」。選既有場景時跟著那個場景的種類。貼上別台電腦錄的原始稿也一樣可以選。
  2. 錄製端錄製、關掉瀏覽器；原始稿（密碼遮罩成 ***）傳回伺服器，和現在相同。
  3. 伺服器轉換：產生 scenario.yaml（入參、出參、Secrets、verify、browser、登入角色）與 automation.py，存成新場景的 v1 或既有場景的新版本。錄製詳情列出步驟、入參、出參、斷言與提醒的數量。
  4. 之後照舊：（調試）→ 交給 Worker 驗證 → 人工發布。

  • 對外 Agent API：它的「匯入 Playwright 腳本」（#79）之後可以多一個目標「Python 腳本場景」，用同一套轉換；這次不改 Agent API。

7. 腳本的運行過程

順序照 ADR 0009，多一個「運行環境」階段；每一階段失敗都沒有成功出參。驗證、執行、組合場景的節點都走同一條路，本機 worker、遠端 Worker 也一樣。

  • 進度：執行頁顯示目前的階段；運行環境階段顯示最後一行進度（例如「下載 openpyxl 3.1.5」）；自動化階段顯示目前的步驟與第幾步。本機 worker 讀 steps.json，遠端 Worker 在心跳附上目前的步驟、步驟變化時多送一次——和 #79 第二期為 DSL 規劃的步驟進度是同一個來源，所以 DSL 與腳本一起得到。
  • 環境變數：照現在（RPA_DEADLINE_SECONDS、RPA_BROWSER、RPA_HEADLESS、RPA_LANG、RPA_STORAGE_STATE、Secrets、PYTHONIOENCODING=utf-8），再加 PYTHONUTF8=1（Windows 開檔預設也是 UTF-8）；拿掉 PYTHONHOME、PYTHONPATH、VIRTUAL_ENV 與打包 App 的內部變數。
  • 取消與逾時：沿用 M2 與 M12：Linux、macOS 終止程序群組；Windows 結束程序樹，錄影時先只結束瀏覽器讓影片寫完。腳本自己開的子程序一起被結束。有副作用的步驟不自動重試。
  • 腳本能做的事：和現在一樣等於在 Worker 上以那位使用者的身分執行任意程式（可以讀檔案、連網路、讀同一使用者的認證管理員／鑰匙圈）。所以腳本場景照舊只給信任的人編輯、審核時特別標示（卡片標「Python 腳本」，版本差異要看程式）；M8 再加權限。

執行目錄（增加的檔案以外和 DSL 相同）

  • 報告頁（report.html 與 /runs/{id}）依序：結果與錯誤摘要 → 階段（多了運行環境，標「沿用」或「新建，花了 …」）→ 步驟（同 DSL 的表格；多了原始碼行號，點了到編輯頁的那一行；迴圈的步驟顯示第幾次；腳本裡寫了、這次沒跑到的步驟標「未執行」，由伺服器從 automation.py 的 run.step("…", "…") 靜態列出）→ 頁面事實 → 斷言 → 出參 → 截圖與附件 → 主控台輸出（依步驟分組，可以只看錯誤）→ 運行環境（Python、來源、套件清單）。
  • 錯誤：失敗的步驟顯示錯誤訊息與呼叫堆疊，每一層連到腳本的那一行；Playwright 的錯誤保留它的 call log。
  • 運行報告的清單（/runs）多一個「場景類型：DSL／Python 腳本」篩選；其他欄位不變。
  • 相容：stages 多了 runtime、新檔案都是增加的；讀 result.json 的程式（報告頁、試驗場、#79 的 Agent API）不認得的階段照名稱顯示。伺服器只把需要運行環境的任務交給新版 Worker，所以舊版伺服器不會收到有 runtime 階段的結果。

10. 調試與接著錄製（第 4 期）

  • 腳本的逐步調試＝在步驟邊界暫停。任意的 Python 不能像 DSL 一樣單獨重跑某一步，所以改成：在錄製端（或伺服器本機）以調試模式執行腳本，每一個 run.step 開始前暫停，頁面顯示截圖、網址、目前的頁面事實與下一步的原文；「執行這一步」「執行到這裡」「執行到底」「從頭開始」（重新啟動子程序）。暫停時可以用定位器測試（DSL 定位器或 Playwright 的 selector）。改了腳本要存成新版本再從頭開始。
  • 沿用現有的互動子程序。一行一個 JSON 命令與回覆（同 rpa_runner.debug），經 Client API 交給錄製端；錄製端可以執行的模組多一個 rpa_script（只在運行環境裡、只用伺服器送來的檔案），所以錄製端 App 也帶運行環境（同 Worker）。
  • 接著錄製：先在錄製的瀏覽器裡執行既有的腳本（同調試），結束後在同一個 context 開始錄製（同 rpa_runner.record 的做法），錄到的步驟轉換後接在 @automation 函式的最後。
  • 這兩項在第 1～3 期之後做；在那之前，腳本場景的「調試」照舊是直接驗證最新版本。

13. 沒有選的方案

方案為什麼不選
繼續用 App 打包的直譯器（rpa-child --rpa-script）PyInstaller 打包的直譯器不能安裝套件，三個系統的行為也取決於打包時剛好帶了什麼。
Worker App 改成「自帶 Python＋site-packages」（像 Linux 分發包），App 與腳本共用一份直譯器只帶一份 Playwright driver、最省空間，但要重做 M10 的打包、安裝檔、自我測試與單一執行；App 自己的套件也會和腳本的套件互相影響。之後要縮小安裝檔時再評估。
一律用電腦上已裝的 Python每台的版本與套件不同，結果不一致；Windows 常常沒有、macOS 的系統 Python 會跳出安裝開發工具。保留為第 4.3 節的備用來源。
每次運行都建一個新環境最乾淨，但每次多幾秒到幾分鐘、需要網路；以內容決定身分的環境一樣乾淨（不可變），又能沿用。
標準函式庫的 venv＋pip不必多帶 uv，但慢很多、沒有跨環境共用的快取、不能產生跨平台的鎖定檔，找直譯器也要自己寫。
conda／Docker 隔離太重；Docker 在 Windows、macOS 的桌面上不一定有，有頭模式也很難。
自動把 Playwright 的每個呼叫記成步驟（包一層代理物件或用 Trace）代理物件跟著 Playwright 版本容易壞、型別檢查不友善；Trace 檔案大、要另開 Trace Viewer（ADR 0016 已不選）。改成錄製產生的腳本每個操作自動一步，手寫的由作者標。
錄製只產生 DSL，再轉成腳本多繞一層，DSL 轉不了的操作（hover、上傳…）在第一步就丟了。保留「另存為 Python 腳本場景」給已經是 DSL 的場景。
腳本的斷言只能用 assertion.py錄製的 Assert 得產生 Python 斷言，Portal 的斷言編輯器與報告的斷言就和 DSL 不同；用同一個 verify 才是「沿用現有的建模」。
