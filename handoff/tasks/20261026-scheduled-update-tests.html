原因

  • 時間線：issue #74（一鍵安裝腳本）10-22 起、#80（每晚完整測試）10-23 起，每天失敗都追加一則留言。10-22～10-25 的失敗（macOS 的 Bash 3.2 沒有 mapfile、Ubuntu 有頭 Chromium 沒有 X server、Windows Portal 辨識的 1 秒上限等）由 PR #81 修好，10-26 合併。同一天合併的 PR #83（伺服器分層更新，ADR 0018）新增的測試在 macOS、Windows 上失敗，所以 10-26 晚上的排程仍然失敗，只是原因換了。
  • macOS：tests/ci/test_server_package.py::test_serve_rolls_back_when_the_new_version_cannot_start 執行真的 bin/rpa serve，退回時用 mv -Tf 換 current 連結。macOS 的 BSD mv 沒有 -T（「illegal option -- T」），結束碼 3。PR #81 已經為 install.sh 的合成測試加了 mv 的替身（HOST_TOOLS），但那是 Bash 函式，只在 source install.sh 的同一個程序裡有效；這個測試另外啟動 bin/rpa，用不到。每晚 run 40399471079 的 macOS、一鍵安裝腳本 run 40402544121 的兩個 macOS 工作都是這一個測試。生產環境是 Linux（GNU mv），不受影響。
  • Windows：apps/server/tests/test_updates.py 裡會安裝更新檔的測試（7 項以上）都在 Layout.switch 失敗：.current.new 改名蓋過 current 時 WinError 5（存取被拒）。Windows 的改名（MoveFileEx）蓋不過指向資料夾的連結。每晚 run 40399471079 的 Windows、一鍵安裝腳本的「專案內執行（windows-latest）」都是這些測試。「從零開始（windows-latest）」只留下結束碼 1；它的日誌在這個環境下載不到（Azure blob 被代理擋），推測是同一批測試（它也跑全部測試，10-24、10-25 沒有失敗，10-26 PR #83 之後才失敗）。分發包只支援 Linux，不影響生產。
  • 為什麼 PR 上沒抓到：PR 上的 CI 依生產角色分配，Linux 跑網站、Windows 只跑 Worker 的瀏覽器測試，macOS 不跑 pytest（docs/develop/ci.html）。這兩個測試在 Linux 通過，只有每晚與一鍵安裝腳本在 macOS、Windows 跑全部測試，所以隔天才出現。

進度、決定與下一步

  • 已完成：macOS：host_env() 在 PATH 最前面放一個 mv，把 -Tf 換成 BSD 的 -hf（和 PR #81 的 HOST_TOOLS 同一個做法），用在 supervise() 與退回的測試；Linux 不加，繼續直接驗證 GNU mv。Windows：Layout.switch 在 Windows 先刪掉舊連結再改名（不是原子的，註解寫明只為開發環境與測試），連結加上 target_is_directory=True。
  • 決定（實作選擇）：Windows 改程式而不是略過測試：test_updates.py 測的是等閒置、遷移前備份、確認新版本這些和系統無關的邏輯，略過整個檔案會少掉 Windows 開發環境的覆蓋。
  • 下一個具體動作：推送、開 PR；手動觸發每晚完整測試（systems=macos,windows、extra=0）跑這個分支，確認兩個原因都消失。合併後下一次排程通過再關閉 issue #74、#80。
