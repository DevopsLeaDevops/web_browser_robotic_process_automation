1. 結論

  • 可以做，不需要新的外部元件。Playwright 本身就能把檔案交給網頁的上傳框，隱藏的、iframe 裡的、點擊時才建立的都行；錄製端（codegen）也已經錄得到選檔，只是轉換時被丟掉。第 3 節的實驗 13 項全部通過。
  • 做法：每個要上傳的檔案是場景的一個入參（新型別 file），步驟多一個 upload，指定交給哪個上傳框，或點哪個元素會開出選擇檔案的視窗。檔案在執行時從管理 Portal 上傳，伺服器存一份；執行的那台 Worker（或調試的錄製端）下載到自己的暫存資料夾，保留原始檔名，再交給瀏覽器。
  • 沿用 M7a／M7b 的模式：只多一種入參型別和一個步驟，不改場景契約與發布門檻；舊的 App 看不懂時提示更新，不會只回「場景校驗失敗」。
  • 分兩期（D1）：第一期打通「錄製 → 調試 → 驗證 → 發布 → 執行」；第二期做場景附帶的預設檔案、組合場景與 Agent API、拖拽區、Worker 本機資料夾。
  • 有一種情況錄製稿看不出來：點擊時才臨時建立、不放進頁面的上傳框，codegen 只錄到那一下點擊。Runner 會攔下這個選擇檔案的視窗，並在調試與驗證時提示把那一步改成 upload（第 4.3 節）。

3. 調研與實測

3.1 Playwright 交檔案給網頁的方式

本機網站放了五種常見的上傳元件，伺服器收到檔案後回傳名稱、大小與 sha256，和本機的檔案比對（Playwright 1.63.0、Chromium、無頭）。官方說明見 Playwright › Upload files：一般用 set_input_files，點擊時才建立的上傳框用 expect_file_chooser。

4. 設計

4.1 DSL：檔案入參與 upload 步驟（D2）

inputs:
  orderFile:
    type: file
    description: 訂單匯入檔
    accept: [.xlsx, .xls]         # 副檔名，或 MIME：image/*、image/png
    maxSize: 20MB                  # 單位 KB、MB、GB；沒寫用伺服器的上限（D4）
  photos:
    type: file
    multiple: true                 # 值是清單
    accept: [image/*]
steps:
  - id: import-orders
    action: upload
    target: { role: button, name: 匯入檔案 }          # 上傳框本身（隱藏的也可以）
    files: "{{ inputs.orderFile }}"
  - id: wait-imported
    action: expect
    target: { text: 匯入完成 }
    state: visible
  - id: add-photos
    action: upload
    trigger: { role: button, name: 選擇圖片 }          # 點了會開出選擇檔案視窗
    files: "{{ inputs.photos }}"
verify:
  - name: 頁面顯示匯入的檔名
    value: "{{ facts.importedName }}"
    equals: "{{ inputs.orderFile.name }}"
欄位規則
入參 type: file新的入參型別。可以寫 accept（清單；.副檔名 或 MIME，可用 image/*）、maxSize（文字，例如 20MB）、multiple（預設 false）、description。不能寫 enum、pattern、長度與數值範圍。第一期不能寫 default（場景附件在第二期，D1）。出參沒有 file 型別（等 M7 的下載）。
入參的值管理 Portal 與 API：檔案參照 {"file": "f_…", "name": "訂單匯入.xlsx", "size": 20000, "sha256": "aad9…"}，multiple 時是清單；只能參照已上傳到伺服器的檔案，不接受路徑（D5）。命令列 rpa run -i orderFile=./訂單.xlsx 給本機路徑，多檔就寫多次 -i。
表達式裡的檔案入參{{ inputs.orderFile }} 在表達式裡是 name、size、sha256 三個欄位（沒有路徑），verify 與出參可以引用 {{ inputs.orderFile.name }}。本機路徑只有 Runner 內部知道。
upload 的 target／trigger恰好一個。target 指向上傳框 <input type=file>（隱藏的也可以，不檢查可見性）；trigger 指向點了會開出選擇檔案視窗的元素（點擊時才建立上傳框的元件）。兩者都可以有 frame、within、fallback；步驟可以有 page（M7b），不能有 popup。
upload 的 files必填。整個值是一個 {{ inputs.名稱 }}，或這種寫法的清單；名稱必須是 file 型別的入參，校驗時檢查（同 facts 的前後關係檢查）。[] 代表清空已選的檔案，只能搭配 target。單檔上傳框配到 multiple 入參或清單時，執行時才知道上傳框收不收多檔，報看得懂的錯。
等上傳完成upload 在檔案交給網頁時就算完成；網頁之後送到伺服器要多久不一定，照 DSL 的原則用後面的 waitFor／expect 等畫面上的結果，不加固定秒數。

4.3 Runner

  • 入參校驗（啟動瀏覽器之前）：每個檔案存在、大小不超過 maxSize 與伺服器上限、副檔名或 MIME 符合 accept、單檔入參只有一個；不符合就不啟動瀏覽器，和現在的入參錯誤一樣。
  • 執行 upload：target → locate(…).set_input_files(路徑, timeout)；trigger → expect_file_chooser 裡點擊，再 set_files。都交路徑（3.1 的 6b）。Playwright 的錯誤翻成看得懂的訊息（3.1 的 1c、8）。
  • 原始檔名：網頁看到的檔名就是磁碟上的檔名，所以每個檔案放在 暫存資料夾/inputs/入參名稱/序號/原始檔名。
  • 攔下沒人處理的選擇檔案視窗（D6）：每個分頁（含 popup 開出的）一開始就監聽 filechooser。有頭模式不會再跳出系統視窗、卡在 Worker 的畫面上（3.1 的 7）。不是 upload 開出的視窗：這一步照樣通過，但步驟紀錄、automation.log 與調試畫面多一條提醒「這一步開出了選擇檔案的視窗，沒有指定檔案；如果這裡要上傳，把這一步改成 upload，用 trigger 指定這個元素」。這也補上 3.2 的 C。
  • 紀錄與報告：input.json、steps.json、報告只寫名稱、大小、sha256，不寫本機路徑；報告列出這次上傳了哪些檔案，在 Portal 上可以下載伺服器那份。上傳的檔案不複製進執行目錄（不重複上傳回伺服器、不佔 512 MB 的產物上限）。
  • Python 腳本場景：第一期的 file 入參只給 DSL 步驟；腳本場景用到時校驗擋下並說明，等 Python 腳本場景設計 的 D9 一起做（那邊拿到的是本機路徑）。

4.4 檔案怎麼到執行的那台（D4、D7、D8）

  • 上傳：表單選檔後馬上以串流上傳到 POST /api/files（沿用 Worker API 的 save_upload 做法，不整個放進記憶體），邊寫邊算 sha256，超過上限就拒絕。檔案存成 資料目錄/uploads/前兩碼/sha256，同內容只存一份；資料表 uploaded_files 記 id、sha256、原始檔名、大小、類型、上傳時間。回傳的參照填進入參。
  • 建立執行時：檢查每個參照存在、大小與類型（同 Runner 的規則，早一點擋下），在 run.input 存參照，並記下這個執行用到哪些檔案（用來判斷保留）。重新執行沿用同一份參照。
  • 交給遠端 Worker（D8）：領取任務的 JSON 多一個 inputFiles 清單（入參、序號、id、原始檔名、大小、sha256），不帶內容。Worker 用 GET /worker-api/v1/runs/<執行>/files/<id> 逐一下載（只能下載派給自己、執行中的這個執行用到的檔案），比對 sha256 後放到 jobs/<執行>/inputs/…，再把入參換成本機路徑交給 Runner。下載失敗照 M9a 的規則回報失敗（「準備檔案失敗」），不執行任何步驟。
  • 本機執行：伺服器把檔案硬連結（不行就複製）到這次執行的暫存資料夾，用原始檔名。
  • 錄製端調試：開始調試前選檔（同執行表單）；錄製端用 Client API 的同一種下載放進 .inputs/（不同步回伺服器）。換版本、接著錄製沿用這次調試的檔案。
  • 保留（D7）：被任何執行用到的檔案一直保留（運行紀錄目前也不刪）；上傳後 24 小時沒被用到的刪除。第二期加總量上限與保留天數，規則比照 M12 的錄影。

4.5 管理 Portal 與 API

  • 執行與驗證表單：JSON 文字框上方，每個 file 入參一個選檔區（按鈕或拖曳），顯示上傳進度、檔名與大小；accept 交給 <input accept>。上傳完把參照寫進 JSON，JSON 仍然是送出的內容。沒有選檔就送出時，照現在的入參錯誤提示。
  • 運行頁與報告：入參表格顯示檔名與大小，可以下載；步驟清單裡的 upload 顯示交了哪些檔案；選擇檔案視窗的提醒顯示在那一步。
  • 場景詳情與入參編輯（M4 的表單編輯）：型別多 file，可以編輯 accept、maxSize、multiple；rpa schema --part inputs 輸出 {"type": "object", "format": "x-rpa-file", …}。
  • Portal 內部 API：新增 POST /api/files（multipart，回傳參照）與 GET /api/files/<id>（下載）；建立執行與調試的 API 接受參照。Agent API 在第二期（加 files 權限範圍）。

4.6 相容與安全

  • 舊 App：rpa_core.dsl.features 加上 upload（步驟）與 fileInputs（入參），App 上線時回報。用到的場景不交給沒回報的 Worker／錄製端，直接說明要更新哪個 App（同 M7a）。沒用到的場景照舊。
  • 不能指定任意路徑（D5）：Portal 與 API 的入參只接受伺服器上的檔案參照，不接受路徑；不然能執行場景的人就能把 Worker 或伺服器上的任何檔案上傳到外部網站。本機路徑只有命令列 rpa run（使用者自己的電腦）。
  • 檔名：網頁看到原始檔名，但寫到磁碟前檢查：去掉路徑、控制字元、Windows 保留名稱（CON、NUL、COM1…）與結尾的點或空白，長度不超過 200 位元組，換不掉的字元換成 _。存放一律用 sha256，不用原始檔名；Unicode 檔名先轉成 NFC（macOS 與 Windows 寫法不同）。
  • 大小（D4）：單檔預設 50 MB、一次執行合計 200 MB，伺服器設定可以改；場景的 maxSize 只能更小。
  • 內容：只計 sha256，不解析、不執行、不預覽。
  • 權限：M8 之前沒有使用者權限，檔案和現在的入參一樣，能進 Portal 的人都看得到；M8 再加上「只有能看這個執行的人能下載」。日誌與錯誤訊息不寫本機路徑。
