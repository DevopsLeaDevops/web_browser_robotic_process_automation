進度、決定與下一步

  • 為什麼不能只設 UV_INDEX_URL（查證）：uv.lock 記著每個套件的 registry（https://pypi.org/simple，78 個）與每個檔案的下載網址（files.pythonhosted.org，754 個）。本地用 uv 0.11.32 驗證：原本的鎖檔加上 --default-index 指向鏡像時，uv lock --locked 要重新解析（線上會報鎖檔過期）；把鎖檔裡的這兩種網址換成鏡像、--default-index 用同一個網址（不能多一個結尾斜線）時，--locked 檢查通過，而且 uv sync 從換過的網址下載（指到 127.0.0.1:9 時錯誤訊息顯示的就是那個網址）。其他專案也遇到同樣的問題（例如 bytedance/deer-flow #7003）。
  • 做法（實作選擇）：
    • --mirror auto（預設）：PyPI、清華、中科大、阿里雲、騰訊雲、華為雲同時下載鎖檔裡的一個 500 KB～4 MB 的純 Python wheel（目前是 pygments），sha256 和鎖檔相符的才算，選最快的並列出每個來源的速度；都不行時用 PyPI。最多約 20 秒（連線逾時 5 秒、整體 20 秒）。
    • 可指定 --mirror pypi|tuna|ustc|aliyun|tencent|huawei|<simple 網址> 或 RPA_PYPI_MIRROR；都沒有、但有 UV_DEFAULT_INDEX／UV_INDEX_URL 時用它（不測速）。自訂網址的檔案位置取 simple 的上一層（bandersnatch、Nexus、Artifactory 的慣例）。內建鏡像的檔案路徑沒辦法在這個環境實際確認：路徑不對的鏡像在測速時因為下載失敗或雜湊不符而不會被選上。
    • 用鏡像時只在這次 uv sync 期間把 uv.lock 的索引與檔案網址換成鏡像的（版本、檔案、sha256 不變，uv 照樣驗證雜湊），結束、失敗或中斷（EXIT trap）都還原；鏡像安裝失敗時還原後改用 PyPI 再試一次。uv 的呼叫一律清掉 UV_INDEX_URL 等變數，避免和鎖檔不一致。
    • 文件改寫了 #44 的「由維護者產生並審閱對應鏡像的鎖檔」：現在不用另外的鎖檔，暫時換網址就能用鏡像；也說明公司只允許核准來源時用 --mirror pypi 或公司鏡像，不要用 auto。
  • 已完成：上述實作；測試：測速選最快而且內容正確的（最快但內容不符的不用）、沒有測速檔時用 PyPI、鏡像安裝時鎖檔只在安裝期間換網址而且只換網址、鏡像失敗改用 PyPI（ERR trap 不誤報）、UV_INDEX_URL 當成公司鏡像且不測速、不認得的來源與不安全的網址會停止、中斷時鎖檔還原、--mirror 缺值時停止。
